# df88c1b2 — a precondition on the ACTION instead of a corpus scanner: recommendation

Worker design deliverable, 2026-08-06. **This is a design card. DoD ends at a written argument — no production or test code was written to produce this document.** `filesChanged` for this task is this document only. `packages/daemon/test/fixed-wait-negative-guard.mjs`, `_wait.mjs`, `_timing-guard.mjs`, and every other test file are untouched — `git status` on this branch shows only this new `docs/` file.

Read `docs/investigations/e3faa8ac-fixed-wait-polarity/findings.md` first — this document is the direct successor to it and assumes its measurements (TIER 1: 240 sites/78 files, TIER 2: 90 sites/36 files, the direction-not-polarity finding, the 62%-of-TIER-2 prose-match false-positive mode) without re-deriving them.

## The question

`fixed-wait-negative-guard.mjs` has accumulated five independent scope/correctness defects as a single static-scan instrument: `0f744aa4` (blind to `observeOnce`/`windowMs` idioms), `743be0c9` (scans comment text as code), `4479e6f0` (stale baseline metadata), `e3faa8ac` (blind to the whole positive-polarity class), and `e3faa8ac`'s own investigation independently reproducing `743be0c9`'s failure class inside a from-scratch heuristic. Is a sixth scanner patch — or a corpus-wide scanner widened to cover direction — the right next move, or is there a fundamentally different mechanism that should replace the scan-and-baseline approach for the direction-risk class specifically?

## Recommendation: a diff-scoped presence requirement, extending a mechanism this project has already proven, not inventing a new one

**Reject a sixth scanner patch or a corpus-wide direction-aware scanner.** `e3faa8ac` already measured this path to failure: the naive positive-polarity widening reproduced the exact "flags every `sleep()`" failure mode (23/26 sites in one file), and the tightened, direction-aware version still carries a 62%-of-TIER-2 false-positive rate from prose-matching a variable name inside an assertion's label text — the same failure class as `743be0c9`, independently reproduced. Two rounds of tightening, from scratch, did not close this. A sixth round inherits the same wall: **direction — is this fixed wait racing a real, uncontrolled duration, or proven to exceed a known threshold? — is a semantic fact about what the two numbers mean in the running system, not a syntactic one.** No static text scan decides that without an unacceptable false-positive rate for a hard block, and AST-based analysis does not close this gap either — it only closes `743be0c9`'s specific comment-as-code bug class, at the cost of introducing ESLint infrastructure this repo does not currently have, for a partial fix.

**Reject "rely on documentation + reviewer vigilance."** This is not a hypothetical risk in this repo — it is already falsified, with a dated paper trail. `_wait.mjs`'s own header — written specifically to prevent exactly this mistake, with an explicit "BARRIER vs DEFERRED" explainer distinguishing a controllable `deferred()` promise from a real-timer race — landed in commit `2cb7bbc1` on **2026-07-23**. The `81a6e4e1` incident (`sleep(20)` racing `sleep(80)` in `pending-ops-registry.mjs`, reddening a live merge gate) was fixed **2026-08-06** in commit `003a1080`, which touched only `pending-ops-registry.mjs` and never touched `_wait.mjs`. **The explainer predated the incident it was written to prevent by two weeks, sitting in the same test directory, and did not prevent it.** This is the specific, checkable form of project memory `a-rule-stored-next-to-an-artifact-does-not-check-it` — proximity and prior authorship of the rule did not confer immunity.

**Recommended mechanism: a new diff-scoped static guard, run at merge-gate time, that requires a WITNESS on any newly-added raw-sleep-adjacent-to-check() line — never a verdict on whether that site is safe.**

This is not a new design. `_timing-guard.mjs`'s own header states the precedent directly: `fixed-wait-negative-guard` **already** enforces exactly this shape on the negative-polarity axis today — "a negative assertion paired with a fixed wait either goes through `assertNeverWithControl`'s mandatory `positiveControl` ... or carries an explicit `TIMING-GUARD-SAFE` exemption." `assertNeverWithControl` does not classify whether a test-writer's negative claim is correct; it requires the ARTIFACT of that judgment — a `positiveControl` function that must itself observably pass — enforced at runtime, not by convention or a comment. That is a presence check, not a correctness check, and it is exactly why it can safely block without becoming a false-positive fight. **This recommendation extends that same, already-proven local mechanism to the direction axis** — it is not a novel design being proposed on top of an unproven idea.

Two concrete witness shapes, both already attested in the real corpus (not hypothetical):

- **Exceeds-a-threshold shape** — the safe direction (e.g. `sleep(70)` past `retainMs:50` in `pending-ops-registry.mjs:301`, current tree). Add a small helper alongside `waitUntil`/`deferred` in `_wait.mjs`: `sleepPast(ms, thresholdMs, label)`, which throws at runtime if `ms <= thresholdMs`. This turns a trusted comment ("`// past retainMs`") into an executable assertion, the same move `assertNeverWithControl` already made for the negative axis. `await sleepPast(70, 50, "past retainMs")` replaces `await sleep(70); // past retainMs`.
- **Racing-a-real-op shape** — the risky direction (the `81a6e4e1` specimen: `sleep(20)` racing `slow()`'s internal `sleep(80)`). No new helper is needed — `deferred()` already exists in `_wait.mjs` and is exactly what `003a1080`'s actual fix used: a hand-resolved promise, no timer, no race. `003a1080`'s fix additionally added a companion precondition `check()` — `check("...precondition: both calls degraded to pending...", r1.settled === false && r2.settled === false)` — immediately before the real assertion, proving the raced state was actually achieved rather than assumed. That pattern (a companion precondition check, or the `TIMING-GUARD-SAFE`/`TIMING-GUARD-FALSE-MATCH` comment convention already in production use) is the witness this shape needs.

**Enforcement, concretely (answering DoD-2):** a merge-gate step, run in the same place `fixed-wait-negative-guard.mjs` runs today, diffing `<merge-base>..<branch>` restricted to `packages/daemon/test/*.mjs`. This is not a novel mechanism either — `worktrees.ts`'s `diffBranch` (`git.diff([range])`) already does line-content diffing this way for other purposes. The gate scans only **added** lines (skip `//`-comment lines before idiom-matching, closing `743be0c9`'s bug class by construction in the new mechanism rather than reproducing it) for the fixed-wait idiom shape immediately followed by check()/assert(), covering **both polarities** — direction, not polarity, is the real axis per `e3faa8ac`. A hit fails closed unless it is a `sleepPast(...)` call, a companion precondition `check()` in the same block, or a `TIMING-GUARD-SAFE`/`TIMING-GUARD-FALSE-MATCH` comment.

Diff-scoping is what makes DoD-2's own false-positive warning survivable — a legitimate post-assertion cleanup drain (like `003a1080`'s own `await sleep(10); // let the settle .then() microtask actually run`, which has no check() immediately after it and so does not even match this idiom shape at all) costs at most one honest line to clear, not a fight with a risk verdict. That changes the economics DoD-2 warned about: a **true** one-liner is cheaper to write than to game, unlike a hard classify-and-block.

## Honest limitation — the escape hatch is gameable, and that is an accepted, not a new, cost

The `TIMING-GUARD-SAFE`/`FALSE-MATCH` comment witness can be attached to a genuinely unsafe site by a careless or bad-faith author (`// TIMING-GUARD-SAFE: totally fine` on a site that is not). This is not proof of safety — it is a forced, reviewable artifact placed at the exact point a reviewer is already looking, which is the actual mechanism behind project memory `shipping-a-detector-is-not-someone-reading-it`'s two successful blocking-precondition cases (`tasks_create` refusing a duplicate, `baseVersion` refusing a stale write): those work by making the ACTION itself carry evidence of intent, not by proving that intent is correct. **This gameability is a cost the project has already accepted on the negative-polarity axis** — `fixed-wait-negative-guard.mjs` has run this exact comment-exemption mechanism in production since card `1addef27` — not a new risk this recommendation introduces. `sleepPast` narrows the gap for the majority (exceeds-threshold) shape specifically, because that claim is mechanically checkable and does not need to rely on trust at all.

## DoD-3: the ~240 existing sites — explicit, argued grandfathering by scope

Nothing happens to them, and this is not "add them to a baseline." The new gate only ever evaluates lines a diff newly adds; it never retroactively applies to code that predates it. There is consequently no baseline to construct — unlike a baseline, which exempts existing code from a check that would otherwise apply to it, this mechanism's check never reaches old code in the first place. That is the categorical difference this project's standing rule ("fix the file, never widen a guard's debt baseline") is actually protecting against, and it is why this is the legitimate form of grandfathering DoD-3 permits when argued explicitly.

The 240 sites are a static, fully-enumerated population (`docs/investigations/e3faa8ac-fixed-wait-polarity/scripts/corpus-scan-output.txt`), not a growing one, and this project already has a working reactive safety net for this exact class: `81a6e4e1` was found via a live gate failure, root-caused, and fixed the same day in `003a1080`. The harm this card is actually responding to is unbounded NEW debt accumulating with no gate at all — not the fixed size of an already-enumerated, already-shipped population.

## DoD-4: fixed-wait-negative-guard.mjs and its three open cards

**Keep `fixed-wait-negative-guard.mjs`, unwidened, doing its current narrow job** — the negative-polarity corpus baseline plus regression detection on the 4 retrofitted files. `e3faa8ac`'s own finding forecloses ever widening it to positive polarity; that is the exact experiment that failed twice. It should not be retired either: it still catches real regressions today, and it costs nothing to keep running alongside the new diff-scoped gate — any overlap on new negative-polarity sites between the two is harmless redundancy, not a conflict.

- `0f744aa4` (blind to `observeOnce`/`windowMs` sites), `743be0c9` (comments scanned as code), `4479e6f0` (stale baseline metadata): **none become moot.** All three are real, bounded scope-bugs on the existing corpus scanner, independent of this recommendation, and still worth fixing on their own terms.
- **Hard requirement on any build of the new diff-gate:** it must not blindly reuse `fixed-wait-negative-guard.mjs`'s `IDIOM_A`/`IDIOM_B` regexes as-is, or it inherits `0f744aa4`'s blindness to `observeOnce`/`windowMs` idioms on day one — a new mechanism that silently reproduces an already-known gap in the old one is the same failure this whole redesign exists to move away from.
