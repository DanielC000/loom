**No BLOCKING-GAP found in what could actually be checked from documentation alone.** But this probe is incomplete in a way that matters: the one point most likely to make-or-break a pty-driven worker adapter (#4, scriptable TUI + ready/busy/idle detection) could not be assessed at all — not "assessed as green with caveats," but genuinely unassessed — because doing so requires a real install, which is explicitly out of scope for this worker. **Recommendation, not a decision:** before committing to Phase 1 driver work, someone with authorization to install Codex CLI (a human, or a worker under a kickoff that lifts the no-install boundary) needs to run the same probe-first discipline the claude driver was built with — actually launch `codex` under a pty, observe its raw output for a ready/busy/idle signal, and confirm the `~/.codex` session-log shape on a real, current install — before adapter code is written. That is a different, narrower ask than this card's own hold, and I'm reporting it up rather than acting on it.
