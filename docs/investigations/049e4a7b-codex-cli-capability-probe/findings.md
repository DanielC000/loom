### Point 4 (the make-or-break point): is the TUI pty-drivable, with real ready/busy/idle detection? — **YES, GO-WITH-NAMED-DEGRADATIONS**

Spawned bare `codex -a never -s workspace-write --no-alt-screen` under a real `node-pty` pty (120×40, `xterm-256color`), cwd = a throwaway scratch directory never used by codex before. Five real spawns total, three of which reached a genuine model turn (kept deliberately trivial: `"Reply with exactly the single word: pong. Do not run any commands."`).

**State 1 — boot.** The very first frame renders a boxed header (`OpenAI Codex (vN.N.N)`, `model:`, `directory:`) and an input placeholder line `› Ask Codex to do anything` **before the model/profile has even finished loading** (header shows `model: loading` at this point). This is a real trap for a naive "wait for the ready-looking text, then submit" adapter — see State 2.

**State 2 — first-use-per-directory trust gate (the first real, load-bearing surprise).** On a directory `codex` hasn't seen before, a **second, later frame replaces the boot skeleton** with an interactive confirmation:
```
Do you trust the contents of this directory? Working with untrusted contents comes with higher risk of prompt
injection. Trusting the directory allows project-local config, hooks, and exec policies to load.

› 1. Yes, continue
  2. No, quit

  Press enter to continue
```
This is undocumented in anything fetched for the 09-06 pass and **is not optional** — it renders every time on a directory with no prior trust decision, `-a never` and `-s workspace-write` notwithstanding (those flags govern *command-execution* approval, not this directory-trust gate). **A naive adapter that submits its real kickoff text as soon as it sees the State-1 "Ask Codex to do anything" placeholder will have its kickoff's raw characters land on this menu instead of an input box.** Confirmed by direct reproduction: sending prompt text before explicitly checking for the trust-gate string caused the model's own keystroke handling to consume the text as menu input — in one run this silently selected "2. No, quit" and the whole process exited cleanly (`exitCode 0`) after doing nothing, which is the worst failure shape (looks like a clean, successful no-op from outside). The fix that worked reliably: **poll raw output for the literal substring `"Do you trust the contents of this directory?"` and, only if it appears, answer it explicitly** (`"1"` + `\r`) before ever writing real prompt text; then wait for the *real* ready state (see State 3) before submitting anything.
- A genuine, documented, per-project config field for this exists — read directly (not modified) from the real `~/.codex/config.toml`: `[projects.'<lowercased-path>'] trust_level = "trusted"`. This is the config-side fix path for Loom's own adapter: pre-write this entry into the worker's own `CODEX_HOME` at spawn time, exactly the same shape `pty/host.ts` already uses to pre-write claude's per-session `settings.json` — not a new pattern for Loom, just a new file to write it into.
- ⚠️ **Side effect I caused and then corrected, disclosed in full:** answering this dialog for real (pressing `1` + Enter through the pty, not via a `-c` override) causes `codex` **itself** to persist that trust decision into the real `~/.codex/config.toml` — three `[projects.'<scratch-dir>']` blocks were added across three of my five runs. I did not edit the file myself; this was `codex`'s own first-use-trust bookkeeping, exactly the kind of side effect the card's hard fence #4 was warning about ("if you must test a config shape, use a temp `CODEX_HOME`"). I caught it via an md5 check I'd taken before starting the pty runs, diffed the three added blocks (each a throwaway scratch path under this session's own temp dir, nothing sensitive), and removed exactly those three blocks, restoring the file to its pre-probe project-trust state (verified: only the pre-existing `loom` repo trust entry remains). A residual hash difference remains after that removal, isolated to a `[tui.model_availability_nux]` usage counter (`gpt-6-astra = 4`) that increments on ordinary invocation regardless of any config value set — an unavoidable, content-free side effect of running the real CLI at all (the same category as the sqlite/log growth already disclosed in the 09-06 pass), not a residue of anything I configured. `auth.json` was never opened, copied, or modified by me directly at any point.

**State 3 — real ready state.** Once trust is resolved, a fuller frame renders: the header now shows the actual model (`model: gpt-6-astra medium`, not `loading`), an MCP-server-startup status line (`• Starting MCP servers (N/M): <name> (Ns • esc to interrupt)` — Codex boots its **own** built-in MCP servers, e.g. `cua_repl`, on every session start), the same `› Ask Codex to do anything` placeholder, and — directly relevant to point 6 (context telemetry) — a **live percentage counter in the input footer**: `100% context left`. This is a stronger, more directly observable signal than anything the 09-06 documented pass could confirm; Point 6 is upgraded from MINOR-GAP to GREEN — **on the capability existing and being observable, not on Loom having wired it; see the Point 6 row's own 09-08 correction above before treating this as "context telemetry works today."**

**State 4 — busy.** Submitting text (`term.write(prompt)`, then 300ms later `term.write("\r")`) into the real State-3 ready box works exactly as expected: the prompt is echoed into the transcript and a status line appears: `• Working (Ns • esc to interrupt)`. The terminal **title** (an OSC-0 sequence, `\x1b]0;<title>\x07`) also changes to include a spinning braille glyph while busy (e.g. `⠹ <dirname>`) and reverts to the plain directory name with no glyph once idle — this is a clean, single-line, regex-friendly busy/idle signal independent of scraping the visible screen content at all, and is arguably a *better* automation hook than the `Working`/`esc to interrupt` text (see the negative finding below for why the text hook alone is not reliable).
- **Negative finding, load-bearing:** the input-box placeholder text `› Ask Codex to do anything` is **static UI chrome that is present on screen during State 4 as well as State 3** (it's the empty-input hint, redrawn as part of the same frame that also shows the `Working` status line above it). A naive "wait for `Ask Codex to do anything` to reappear" idle-detector is a **false-positive trap** — it matches while the model is still actively working, because that text never actually leaves the frame. Confirmed directly: my own first idle-detection attempt matched this text ~20ms after the busy marker appeared and concluded (wrongly) that the turn had completed; sending Ctrl+C on the strength of that false "idle" reading, ~2 seconds later, produced Codex's own on-screen confirmation `■ Conversation interrupted - tell the model what to do differently.` — proof the turn was still genuinely running when interrupted. **The reliable idle signal is the disappearance of the `Working (Ns • esc to interrupt)` status line (or the title losing its spinner glyph), not the reappearance of the input placeholder.**

**State 5 — interrupt (a genuine, OBSERVED mid-turn interrupt mechanism).** A single Ctrl+C (`\x03`) sent while State 4 (busy) is active does **not** exit the process — it interrupts the current turn and returns control to the ready box, with an explicit on-screen confirmation (`■ Conversation interrupted - tell the model what to do differently. Something went wrong? Hit /feedback to report the issue.`). This is a real, directly analogous mechanism to Loom's `worker_redirect` (interrupt current turn, deliver something new) for the **interactive TUI** specifically — a materially better story than the 09-06 pass could establish for `codex exec` (which the documented pass correctly noted has no live-interrupt-and-redirect story, only a fresh `codex exec resume` process after the prior one exits). This is worth carrying into Phase 2 design: **the interactive TUI, not `codex exec`, is the shape to adapt if Loom wants a `worker_redirect`-equivalent.**

**State 6 — clean exit.** A second Ctrl+C, sent ~800ms after the first (i.e., once back at the ready box), triggers a graceful shutdown: the screen shows `› Shutting down...`, then prints either `Session ID: <uuid>` or (in the run where a turn had actually been in flight) `To continue this session, run: codex resume <uuid>`, then the process exits with **`exitCode: 0`** within roughly 1.2–2.2 seconds of that second Ctrl+C across all observed runs — no hang, no force-kill ever needed in any of the five runs. This resume hint is a **directly OBSERVED** confirmation of the 09-06 pass's DOCUMENTED-only claim that `codex resume <id>` is the real continuation mechanism (point 2, upgraded from GREEN/DOCUMENTED to GREEN/OBSERVED) — the CLI itself prints the exact command to run, unprompted, on every exit of a session that has state to resume.

### Updated GO/NO-GO verdict

**GO-WITH-NAMED-DEGRADATIONS**, on this evidence:
