# 6e7fc28d — should a worker's engine transcript dir be GC'd once its worktree is removed?

**Decision: no. Do not GC a session's `~/.claude/projects/<encoded-cwd>/<engineSessionId>.jsonl` on worktree removal, and no safe-by-construction predicate for "worktree removed" exists today.** Nothing was deleted, changed, or built by this pass — this is a read-only investigation per the card's own DoD, which explicitly names "do nothing" as a legitimate outcome. Provenance: raised (not decided) by worker `4a8e0f62` on card `f432cbb8`; this card is that trade-off.

## Bottom line, stated plainly

DoD-2 asked for a worked example: can a manager `worker_transcript` a retired worker whose card merged days ago? **Yes — and that single example is enough to kill "worktree removed" as a GC trigger.** `worker_transcript` (`mcp/orchestration.ts:1622-1671`) reads a worker's transcript by calling `readTranscript(w.cwd, w.engineSessionId)` unconditionally, with **no archived-snapshot fallback at all**. The worker's session row is fetched by plain `db.getSession(workerSessionId)` — nothing deletes or expires that row when its worktree is removed at merge, and `workerReadableByManager` stays true for as long as the calling manager's lineage owns it (indefinitely, in practice). So the moment a hypothetical GC deleted that worker's raw transcript dir, every `worker_transcript` call against that worker — from its own manager, from a recycled successor manager, from a code-review sweep days or weeks later — would silently return `[]` (empty turns, not an error). Below, this is reader #1 of at least four with the same shape.

## DoD-1 — reader enumeration (a FLOOR, with what the search could not see)

Six functions in `sessions/transcript.ts` touch a session's *raw, live* engine transcript by (`cwd`, `engineSessionId`): `encodeProjectDir`, `engineTranscriptPath`, `resolveTranscriptFile`, `engineTranscriptExists`, `readTranscript`, and (indirectly, via `resolveTranscriptFile`) `readContextStats` in `sessions/context.ts`. `git grep` for calls to these six across `packages/daemon/src` (excluding `dist/` and `test/`) returns exactly the 14 files below — **positive-controlled**: the pattern is the same one that surfaces the already-known `worker_transcript`/`session_transcript` call sites, so it is not a vacuous zero-finding search. It would **not** catch a hypothetical reader that hand-rolls its own `path.join(os.homedir(), ".claude", "projects", …)` instead of calling these exported helpers — a second, broader grep for `.claude` + `projects` string literals across `src/` was run to check for exactly that shape and found two more hits (`pty/claude-config.ts`, `orchestration/usage-status.ts`), both false positives (`.claude.json` config and `.claude/.credentials.json` — unrelated files, not the transcript dir). No third reader shape was found, but "none found" is a floor, not a proof of absence.

### Readers auto-detecting archival, safe *contingent on snapshot success*

These four all use the same pattern — `s.archivedAt != null ? readArchivedTranscript(...) : readTranscript(s.cwd, ...)` — so once a session's pty has exited, `archiveOnExit` (`service.ts:8704`, called from `index.ts:364` for every non-`run`, non-still-fleeted-manager exit) stamps `archivedAt`, and these readers switch to the snapshot. **They are not immune, only lower-risk**: `snapshotTranscript` (`transcript.ts:567`) is explicitly best-effort and "NEVER throws" on failure — a failed copy leaves `archivedAt` set with no usable snapshot, and these readers do not fall back to the raw path in that case; they'd return `[]`, same silent-empty failure mode as the unprotected readers above, just triggered by snapshot failure instead of GC.

## DoD-2 — the crux, answered directly

**"Worktree removed" is not a safe GC trigger.** At least five production readers (`worker_transcript`, `transcript_read`, `resume()`'s diagnostic path, `forkSession()`, the runs-transcript REST route) and one ops recovery script (`backfill-transcripts.mjs`) can be invoked, by design, for a session whose worktree has already been removed — and depend, to varying degrees, on the raw transcript dir still existing at that point. `worker_transcript` is the sharpest case: it is the single most routine tool a manager or a Code-Reviewer sweep calls to inspect a past worker's work, it has zero fallback, and nothing bounds how long after worktree removal it might be called (a manager auditing "what did that worker actually do" on a three-week-old merged card is a completely ordinary use, not an edge case).

The manager's premise correction (from `f432cbb8`/`b7f758f4`, verified merged and an ancestor of this branch's `HEAD`) holds up on direct read of the current `transcript.ts:35-92` doc comment: `resolvedPathCache` (line 93) bounds only the *repeat-lookup* case; "a cache MISS here always falls through to the full scan below, unchanged" (line 76) is the file's own sentence. **The not-found path's worst-case cost is unbounded by directory count and its real-world frequency is unmeasured** (per project memory `resolve-transcript-file-fallback-scan-cost-measured`, one box, not under load) — this pass adds nothing new to that measurement and does not attempt to re-measure it; it is repeated here only because it bears directly on DoD-4's "leave it" case below (an unmeasured worst case is not the same as a large expected cost, and growing the miss-path's input via more sessions accumulating is exactly what continued non-GC does).

## DoD-3 — a safe-by-construction predicate: none exists today

No predicate keyed on "worktree removed" (or the weaker "session row is archived") is safe, because the archived-snapshot fallback is neither universal (see `worker_transcript`, `transcript_read`, `forkSession`) nor guaranteed even where present (`snapshotTranscript` is best-effort and silently failable). Two structural changes would need to land *first*, as separate build cards, before any GC predicate could be considered safe:

1. **Give every raw-path reader the same auto-detect-and-fallback the other four already have.** `worker_transcript` and `transcript_read` would need the `s.archivedAt != null ? readArchivedTranscript(...) : readTranscript(...)` pattern; `resume()` and `forkSession()` would need to consult the snapshot (or refuse cleanly) once the raw path is gone rather than assuming it never is.
2. **Make the snapshot a *verified* precondition for deletion, not merely an *attempted* one.** `snapshotTranscript`'s return value (or a subsequent `archivedTranscriptExists` check) would need to gate the GC — never delete a raw transcript whose snapshot copy is unconfirmed.

Even with both of those, a GC would only be deleting the *raw, original* JSONL in favor of a *copy* — `readArchivedTranscript`/`archivedTranscriptExists` reuse the exact same `parseTranscriptFile`, so the rendered turns are byte-for-byte equivalent by construction (not verified independently in this pass — this is inference from reading the shared code path, not a run comparison). That is a real, if generally acceptable, trade: the raw file also backs `backfill-transcripts.mjs`'s recovery-of-last-resort for sessions whose snapshot silently failed, and once both the raw file and a failed snapshot coexist, that recovery path is permanently gone for that session. This pass does not attempt to quantify how often `snapshotTranscript` actually fails in production (no logging of failures beyond `console.warn` in the ops script's own dry-run path) — that would need to be measured before treating "verified snapshot" as a cheap precondition.

Candidates considered and not recommended without the above two prerequisites: age-based retention (arbitrary — doesn't address the fallback gap, just delays hitting it), archive-to-compressed-blob (same fallback-gap problem, plus a new format to keep in sync with `parseTranscriptFile`), GC only after the session row itself is purged (session rows are not currently purged on any schedule this pass found, so this reduces to "never" today anyway).

## DoD-4 — decision: do nothing

**Leave the raw transcript dirs alone. No GC on worktree removal, on this card.** Reasoning, plainly:

- The strongest reason *for* GC (bounding `resolveTranscriptFile`'s scan input) is real but its actual production cost is unmeasured — a large *worst case* at an *unknown frequency* is not evidence of a large *expected* cost, and this pass did not attempt to close that gap (out of scope; the manager's own framing already named this).
- The reasons *against* GC are concrete and structural, not speculative: at least one routinely-used reader (`worker_transcript`) has zero fallback today, and the ops recovery script's whole value proposition depends on the raw file outliving the session it belongs to by an unbounded amount. Both were traced to specific lines, not inferred.
- Implementing a safe predicate is a two-step prerequisite (fix every raw-path reader's fallback, then verify-before-delete) that is real work belonging to separate build cards — not something to retrofit into "the GC logic" as an afterthought, per the manager's explicit "propose the predicate, I will card the build separately" instruction.
- If directory-count growth becomes a measured problem later (not established here), the two prerequisites above are the concrete next cards, in that order — fixing the readers first, since a GC predicate built before that fix would be safe on paper and wrong in production the same way the original near-miss (substituting "machine-generated" for "disposable") was.

## What this pass did not do

Nothing was deleted, no code was changed, and no GC was implemented, per the card's hard fence. No attempt was made to measure `resolveTranscriptFile`'s not-found-path hit frequency in production, or to measure how often `snapshotTranscript` silently fails — both are named above as real gaps in the evidence, not resolved by it. The reader enumeration is a floor (see DoD-1's own caveat on search shape); a differently-constructed reader that doesn't go through `sessions/transcript.ts`'s exported functions and doesn't use the `.claude`/`projects` string pattern would not have been found by either search used here.
