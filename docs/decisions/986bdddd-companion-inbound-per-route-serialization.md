# 986bdddd — serialize companion inbound processing per (channel, chatId) route; bound the wait, not the stuck call

## Narrative

`ChatGateway.handleInbound` (`packages/daemon/src/companion/chat-gateway.ts`) had no per-chat serialization. Every caller invoked it independently and concurrently: the Telegram adapter wiring (`companion/factory.ts`) is fire-and-forget per update, and grammY's own `bot.on("message", ...)` handler (`companion/telegram.ts`) does not await it either; the in-app REST/ws paths (`companion/controller.ts`'s `handleInAppInbound`/`handleInAppAudioInbound`) each independently `await` one call per request, with nothing serializing two concurrent requests for the same session.

The method does variable-latency ASYNC work before its one synchronous `submitTurn(...)` call: a plain text message reaches `submitTurn` almost immediately, while an audio message detours through `downloadAttachment` (bounded `DOWNLOAD_TIMEOUT_MS` = 60s, `telegram.ts`) and `transcribe.transcribe` (bounded `STT_SUBPROCESS_TIMEOUT_MS` = 60s, `stt.ts`). Two concurrently-running `handleInbound` calls for the SAME chat — one for an earlier voice note, one for a later text message — could therefore call `submitTurn` (and so `pty.enqueueStdin`) in the OPPOSITE order from real arrival, because `pty/host.ts`'s FIFO/drain only ever sees the order it was CALLED in, with no visibility into real-world arrival order.

Separately, the shared `CompanionTranscriber` (`companion/stt.ts`, one instance injected into every companion's gateway — see `index.ts`/`controller.ts`) spawned a Python subprocess per `transcribe()` call with no concurrency limiter, so N different chats each sending a voice note at once would spawn N concurrent decodes with no cap.

## Fix

1. `ChatGateway` gained a per-ROUTE (`channel\x00chatId`, keyed before a binding is even resolved) promise chain (`inboundChains`). The public `handleInbound` is now a thin, synchronous (no internal `await`) wrapper that reads/extends this chain and delegates to the renamed private `processInboundOnce` (the original logic, unchanged). The method body is deliberately `await`-free: the key read + chain-extension write must happen in one synchronous tick, or a second call for the same route arriving before the first yields would read the same `prior` and race it anyway (the standard promise-mutex construction).
2. The wait on a route's predecessor is BOUNDED by `INBOUND_QUEUE_MAX_WAIT_MS`. Past that bound, the successor proceeds anyway; the predecessor's own work keeps running in the background (nothing cancels it — JS promises aren't cancellable without threading an `AbortController` through every internal await, which is out of scope here). Ordering across that pair becomes best-effort only once the bound is exceeded.
3. The chain entry stored for the NEXT caller is always `.then(noop, noop)`-settled before being stored, never the raw task promise, so a `processInboundOnce` rejection can never poison the chain for whatever is queued behind it (it is documented never-throw today; this is a correctness belt, not a reliance).
4. `companion/stt.ts` added a global (process-wide, since the transcriber instance is shared across every companion) concurrency cap of 1 concurrent `transcribe()` call, with its OWN bounded acquire (`STT_ACQUIRE_MAX_WAIT_MS`). A timed-out acquire resolves `null` — the SAME "no transcript" result a real STT failure already produces, so a long queue degrades through the existing `transcribe-unavailable` ack rather than hanging.

## Round 2 (Code Review `217bbd17` of `bb711e97`, APPROVE WITH CHANGES)

1. **MAJOR — `INBOUND_QUEUE_MAX_WAIT_MS` was undersized.** Round 1 hand-picked a flat `150_000ms`, documented as "comfortably above the ~120s worst legitimate case: 60s download + 60s transcribe" — but that arithmetic silently OMITTED the STT acquire wait (`STT_ACQUIRE_MAX_WAIT_MS`, also 150_000ms at the time) that can sit BETWEEN download and transcribe whenever the global STT slot (`companion/stt.ts`) is held by another chat's in-flight decode. The real worst case for a non-stuck voice note is download + acquire + transcribe ≈ 270s, not ~120s — so under cross-chat voice contention a perfectly legitimate, un-stuck voice note could still lose its place to a later text message: the exact inversion this card exists to prevent, just via a different mechanism than the original stuck-call case. **Fix:** `INBOUND_QUEUE_MAX_WAIT_MS` is now DERIVED — `DOWNLOAD_TIMEOUT_MS` (telegram.ts) + `STT_ACQUIRE_MAX_WAIT_MS` (stt.ts) + `STT_SUBPROCESS_TIMEOUT_MS` (stt.ts) + a flat `INBOUND_QUEUE_MARGIN_MS` (30_000ms) — all now exported from their owning module and imported into chat-gateway.ts, so the bound can never again fall below the sum of the real per-stage bounds it's supposed to cover. Test: `companion-inbound-serialization.mjs` case 6 — a busy global STT slot (held via the real `acquireSttSlot`/`releaseSttSlot`) delays a voice note's own acquire past what the OLD flat bound would have survived, using test-overridden small constants that preserve the SAME derivation formula, and still keeps a later text message behind it.
2. **MINOR — the `Promise.race([prior, delay(ms)])` timer was never cleared.** Every inbound message left a live, un-cleared `INBOUND_QUEUE_MAX_WAIT_MS`-long timer running even on the common path where `prior` resolves almost immediately. Harmless (shutdown is a bare `process.exit`, and the daemon process always holds other live handles open regardless) but untidy. **Fix:** `delay()` was replaced by `raceWithTimeout()`, which wraps the same race in a `.finally(() => clearTimeout(timer))` so the loser's timer is always cleared once the race settles either way.
3. **MINOR TEST GAP — `companion-stt-concurrency.mjs` only drove `acquireSttSlot`/`releaseSttSlot` directly**, so deleting the `acquire`/`finally` pairing inside `createFasterWhisperTranscriber().transcribe()` itself would have stayed green. **Fix:** `stt.ts` gained a `__setTranscribeRunnerForTest` seam (swaps the "run the decode" step called AFTER the slot is acquired), and the test gained cases that go through the real `transcribe()` surface: two concurrent calls serialize on the global slot, and both a throwing run and a null-resolving run (mirroring the real subprocess-timeout-degrades-to-null contract) still release the slot via the existing `finally`.
4. **NITPICK — `handleInbound` is not `async`,** so (unlike an `async` method, which always wraps a synchronous throw into a rejection) a synchronous throw inside its own body would propagate straight to the caller instead of rejecting the returned promise — surprising a fire-and-forget call site that only ever expects to `.catch()` a `Promise`. **Fix:** wrapped the method's existing synchronous body (unchanged — see "Do not" above, it must stay `await`-free) in a `try`/`catch` that converts any synchronous throw into `Promise.reject(...)`.
5. **Scope limits, now stated rather than left implicit:**
   - `warmSttModel` (stt.ts, the boot-time `transcribe.py --warm` pre-fetch) calls `runPythonHelper` directly and runs OUTSIDE `acquireSttSlot`/`releaseSttSlot` — it's a pre-traffic, boot-time call with nothing else contending for the decode slot yet, so it deliberately doesn't take it. If a future caller ever invokes model-warming OUTSIDE boot time (e.g. a manual re-warm endpoint), it would bypass the concurrency cap and must acquire the slot like a real `transcribe()` call.
   - The per-route `inboundChains` ordering guarantee is scoped to ONE live `ChatGateway` instance, not to a (channel, chatId) route for all time. `CompanionController`'s config-driven rebuild path (`controller.ts`'s `reconcileOne`, ~line 647-648, and `startGatewayFor`, ~line 678-681) stops the old gateway and constructs a brand-new one via `createCompanionGateway` — which starts with an empty `inboundChains` map. A predecessor still mid-flight on the OLD instance when a rebuild happens is no longer chained against anything that arrives on the NEW instance; ordering across that boundary is not guaranteed. In practice a rebuild is a human-initiated config change (or a REST re-bind), not something that fires mid-conversation under normal traffic.

## Do not

- Do not widen the `ChatGateway` inbound-serialization key to anything coarser than (channel, chatId) — e.g. per-session. A session can hold more than one binding (multi-channel), and two DIFFERENT routes must always run fully concurrently; serializing a whole session would silently throttle an unrelated channel's traffic.
- Do not raise `STT_MAX_CONCURRENT_TRANSCRIPTIONS` above 1 without first confirming the host can actually run that many faster-whisper decodes concurrently — the cap exists because CPU-bound decodes contend, not because of a correctness requirement.
- Do not read the bounded wait (either `INBOUND_QUEUE_MAX_WAIT_MS` or `STT_ACQUIRE_MAX_WAIT_MS`) as cancelling the stuck predecessor — it only stops the predecessor from blocking the SUCCESSOR. A call that times out while queued keeps running to its own completion in the background.
- Do not let a future change to `processInboundOnce` make it throw without also re-checking the `.then(noop, noop)` settle wrap in `handleInbound` — removing that wrap reopens the chain-poisoning failure mode this fix exists to prevent.
- Do not hand-pick `INBOUND_QUEUE_MAX_WAIT_MS` (or re-inline its old literal) instead of deriving it from `DOWNLOAD_TIMEOUT_MS` + `STT_ACQUIRE_MAX_WAIT_MS` + `STT_SUBPROCESS_TIMEOUT_MS` + margin — that is exactly the round-2 Major incident above, and a hand-picked value can silently fall back out of sync with those three the moment any one of them changes.
- Do not call `warmSttModel` from anywhere other than the boot-time prewarm path without first wrapping that call in `acquireSttSlot`/`releaseSttSlot` like a real `transcribe()` call.
