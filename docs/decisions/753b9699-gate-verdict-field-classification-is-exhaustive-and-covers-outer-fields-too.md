# 753b9699 — cross-project gate-verdict redaction is an exhaustive, compiler-enforced field classification, covering outer fields too

## Narrative

Card 5ef78900 code-review round 2: a scattered per-line `&& !crossProjectRedacted` on each spread has two failure modes, both found by executing a real cross-project read rather than reading the diff. (1) It's an ALLOWLIST-BY-OMISSION — a field spread with no guard silently defaults to VISIBLE, so widening the fix requires remembering to gate every new sensitive spread by hand; `reason`/`commitSubject`/`retriedFile`/`emitCompareTestFiles`/`emitCompareNotHermeticExcluded` were missed exactly this way. (2) It can only gate a field spread VERBATIM from `payload` — it cannot protect a DERIVED field computed from a raw (unredacted) input: `retryWarning` reads the raw payload directly via `formatWeakerPassWarning`, so gating the verbatim spreads does nothing to stop its own text from leaking a one-bit read of foreign content.

FIX, PASS 1: filter the fully-assembled verdict-fields object BY KEY, after every field — verbatim or derived — has already been computed, closing the `retryWarning` bypass.

FIX, PASS 2 (manager review): a plain deny-`Set` is STILL a deny-list — a field added to `PendingGateOpVerdict` tomorrow and not also added to the Set by hand is still visible cross-project, silently, the same failure mode just moved up a level.

REAL FIX: an EXHAUSTIVE, COMPILER-ENFORCED classification, `Record<GateVerdictFieldKey, "sensitive" | "structural">` over `GateVerdictFieldKey = keyof PendingGateOpVerdict | <4 gateStatus-computed fields>`. TypeScript's excess/missing-property checks on an object literal assigned to a `Record` of a union-of-literal-keys type make this a real forcing function: add a field to `PendingGateOpVerdict` without classifying it here and the file fails to COMPILE. `validatedHead`/`headWarning` are classified `"sensitive"`; `retryPassed`/`transientRetried`/`transientRetryWarning` are `"structural"` (no foreign content of their own). RUNTIME is fail-closed too: an unrecognized key reads `undefined !== "structural"` and is DROPPED — a genuine allowlist at runtime, layered under the compile-time exhaustiveness, not a deny-list with a compiler nudge on top.

LIMITATION (worth recording where the scheme itself lives): this classification governs FIELDS — it is structurally blind to a datum RE-EXPRESSED inside another field's own PROSE. Card 67030bb9's `batchBranchCount` is the concrete case: the same integer N it carries is ALSO interpolated, twice, into `retryWarning`'s own generated text for a batch-merge retry. A key-based scheme cannot see that two fields carry the same fact under two different names — it can only classify each field on its own. The fix is not a smarter key scheme; a DERIVED string field must be classified by everything it can ever CONTAIN across its own interpolations, not by what it's named. `retryWarning` is `"sensitive"` as a whole, which happens to already cover N as a side effect — not because N was separately reasoned about when `retryWarning` was first classified. The next derived field needs the same "what can this string ever say" check done deliberately, not assumed from this precedent. `batchBranchCount` itself is classified `"structural"` on its own merits (a bare count, no path/test/error/identifier) — that decision does not silently double as a decision about `retryWarning`'s classification too. APPLIED AT REBASE: before `batchBranchCount` was added to the classification Record, both `tsc` (`error TS2741: Property 'batchBranchCount' is missing in type '{...}' but required in type 'Record<GateVerdictFieldKey, "sensitive" | "structural">'.`) and `gate-verdict-field-classification-exhaustive.mjs` independently refused/flagged the rebased tree — the forcing function fired for real, against a genuinely new field from a sibling branch, not a synthetic mutation.

CARD 753b9699 — THE GAP LEFT OPEN, AND ITS FIX: the classification above governed only the `verdictFields` object. The OUTER return fields (`state`/`gateType`/`elapsedMs`/`idleMs`/`admittedAt`/`ownerSessionAlive`/`outcome`) used to be spread straight into the return literal, entirely OUTSIDE the classification, so a future outer field would default to VISIBLE cross-project by the exact silent-omission shape this whole scheme exists to kill (found by Code Review, card 213fe600, reviewing card d5e67146's addition of `ownerSessionAlive` — the first new outer field since the classification landed). FIX: `GateOuterFieldKey` folds into the SAME `GateVerdictFieldKey` union, so the outer fields are filtered through the SAME `GATE_VERDICT_FIELD_CLASSIFICATION` Record, rather than a second parallel mechanism. Every outer key is classified `"structural"` — this is a PRESERVING change (card 753b9699 DoD-2: adds the forcing function, does not re-open what anything is set to).

MANAGER REVIEW CORRECTION (same card, card 6cf1b174's lesson that a comment asserting a failure direction must match the code): folding `GateOuterFieldKey` into the union does NOT by itself give the outer fields the SAME compile-time guarantee `verdictFields` gets — `GateVerdictFieldKey`'s `keyof PendingGateOpVerdict` half derives from a real interface, so the `Record` demands a matching entry there; `GateOuterFieldKey` is a HAND-WRITTEN literal union of 7 strings with no interface to derive from, so adding an 8th outer field without adding it to the union type-checks FINE. Only the `_outerRawFieldsAreClassified` compile-time assertion (checking `keyof typeof rawOuterFields extends GateVerdictFieldKey`) actually turns that omission into a build error — empirically confirmed to fire for both an unconditionally-added field and one added inside a conditional spread (TS 5.9 widens a conditional object-literal spread to an optional property rather than dropping it from `keyof`). Runtime is, and always was, safe either way: an unclassified key reads `undefined`, fails `=== "structural"`, and is filtered out — REDACTED, never leaked.

## Do not

- Do not gate cross-project redaction with a scattered per-line `&& !crossProjectRedacted` on each spread — it silently defaults new fields to visible and cannot protect a derived field computed from a raw, unredacted input.
- Do not use a plain deny-`Set` for this classification — a field added to `PendingGateOpVerdict` and not added to the Set stays silently visible cross-project.
- Do not classify a derived string field (like `retryWarning`) by its name alone — check everything it can ever CONTAIN across its own interpolations; a bare-fact field like `batchBranchCount` can be `"structural"` on its own merits even while a field re-expressing the same number in prose is `"sensitive"`.
- Do not spread the outer return fields (`state`/`gateType`/`elapsedMs`/etc.) straight into the return literal outside the classification — fold them into the same `GateVerdictFieldKey` union and filter through the same Record.
- Do not assume folding a hand-written literal union into `GateVerdictFieldKey` alone gives compile-time exhaustiveness for it — only a `keyof typeof extends` assertion (like `_outerRawFieldsAreClassified`) actually forces a build error for a missing classification of a non-interface-derived key.
