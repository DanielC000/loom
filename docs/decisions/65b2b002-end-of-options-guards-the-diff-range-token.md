# 65b2b002 — `--end-of-options` guards `changedPathsBetween`'s range token against option-shaped commit content

## Narrative

`verifyPersistedPathSet` (`git/worktrees.ts`) takes a `baseOverride` sourced from a commit's own `Loom-Worker-Base` trailer — commit-content-derived, validated at parse time only by `/^\S+$/` (no whitespace) — and feeds it into `changedPathSetDigest` → `changedPathsBetween`, which builds `args = [...NAME_ONLY_DIFF_FLAGS, `${base}..${ref}`]` and calls `git.raw(args)`. Two readers feed this an attacker-reachable value: `findLandedSquashCommit` (via `trailers.base`, read directly off a candidate commit found by `git log --grep`) and `resolveMergedCommitMapHit` (via `hit.baseSha`, read off `scanMergedCommitMap`'s cached map, reached from `getTaskMergedInfo` — called per task on every polled board read — and from boot-reconcile/batch-lookup). Both gate on a truthy `Loom-Worker-PathSet` trailer (any non-whitespace string, never validated for correctness before this call runs — only compared AFTER). A THIRD consumer of the same `trailers.base` value exists outside this record's scope: `recordedTipContentLanded` (`git/worktrees.ts` ~line 7838) runs `git.raw(["merge-base", recordedTip, recordedBase])`, where `recordedBase` is `candidate.trailers.base` passed straight through from its one caller, `sessions/service.ts`'s review-attribution path (~line 27373). Not fixed here (a different git subcommand, a different argument shape — `recordedBase` lands as its own positional arg, never concatenated into a single range token) — carded into phase 2 under card `b8122303` so the phase-2 consumer list above stays complete.

MEASURED on real git 2.47.0 (temp repos, no claude/daemon — see `test/merge-trailer-argv-injection.mjs`): a forged commit carrying `Loom-Worker-Base: --output=<path>` plus a `Loom-Worker-PathSet` trailer, naming a now-gone branch, makes `changedPathsBetween` spawn `git diff --name-only --no-renames --output=<path>..<sha>`. Git parses the ENTIRE string after `--output=` — including the literal `..<sha>` the template appends — as ONE option value (the output path). The diff then receives ZERO positional range args (defaults to working-tree-vs-index) and `--output` writes a file at `<path>..<sha>` BEFORE the digest comparison that would otherwise reject the forgery ever runs. The eventual `null`/not-merged verdict is unaffected — the write is an independent, unconditional side effect of the spawn itself.

Fix (phase 1; phase 2, a `resolveValidatedObjectId`-shaped helper validating `baseOverride` before it reaches `changedPathsBetween`, is deliberately deferred — see "Do not"): insert `--end-of-options` immediately before the range token at every call site building a `${base}..${ref}` argument — `changedPathsBetween`, its `--name-status` sibling `changedPathStatusesBetween`, and `computeEmitCompareGate`'s own inline `--name-status` invocation (a third, hand-maintained copy of the same flags; not currently trailer-reachable, protected anyway as cheap defense-in-depth). MEASURED that `--end-of-options` makes the same malicious string fail loudly instead (`fatal: option '...' must come before non-option arguments`, exit 128, no write), and is a no-op for a genuine range (byte-identical output either way).

NOT baked into the shared `NAME_ONLY_DIFF_FLAGS` constant: `stagedPathsAgainstHead` also consumes it, appending `--cached HEAD` (option, then literal) AFTER — MEASURED that `--end-of-options` ahead of `--cached` breaks that call (`fatal: option '--cached' must come before non-option arguments`). That consumer has no untrusted content, needs no protection, and must not receive this flag.

## Do not

- Do not bake `--end-of-options` into `NAME_ONLY_DIFF_FLAGS` (or `NAME_STATUS_DIFF_FLAGS`) itself — `stagedPathsAgainstHead` appends a real option (`--cached`) after the shared flags, and `--end-of-options` ahead of an option breaks that call (measured). Insert it at each range-building call site instead, immediately before the `${base}..${ref}` token.
- Do not read this fix as closing the vulnerability — it is defense-in-depth against the CURRENT exploitation shape (an option-prefixed value), not a validation of `baseOverride`'s actual shape. Phase 2 (a shared `resolveValidatedObjectId` helper, validating via `rev-parse --verify --quiet <id>^{object}` and requiring the resolved stdout to equal the candidate exactly) still needs to land at `findLandedSquashCommit`'s and `resolveMergedCommitMapHit`'s call sites, PLUS `recordedTipContentLanded`'s `recordedBase` parameter (card `b8122303`), before `trailers.base`/`baseOverride` is trusted anywhere — deliberately sequenced to wait until cards `c0d0eac9` and `c7dc99bf` (both mid-flight on `git/worktrees.ts` at the time of this record) land, to keep this hunk minimal and cheap to union.
- Do not widen this pass to the many OTHER ad hoc `git diff --name-only`/`--name-status` call sites elsewhere in `git/worktrees.ts` (e.g. lines building a range from a `mergeBase`/`landedSha`/`recordedTip` the gate itself computed) — none of those take a commit-content-derived value as of this record, and auditing/fixing them is a separate, broader question explicitly out of this card's scope.
- Do not treat the `git branch --list ${branch}` / `git branch -D ${branch}` call sites (same argument-injection CLASS, different data: the caller's own known branch name, never trailer-derived) as covered by this fix — carded separately by the manager, out of scope here.

## Consequences

Every current and future caller of `changedPathsBetween`/`changedPathStatusesBetween`/`computeEmitCompareGate`'s diff invocation is protected against an option-shaped range value writing an arbitrary file, at zero behavioral cost to a well-formed sha/ref pair. `baseOverride` itself is still untrusted content until phase 2 lands — a forged commit can still make the lookup spend a (now-failing, not file-writing) git spawn and fall through to `null`/not-merged, which was already the correct, safe outcome.
