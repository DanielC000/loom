# afd51f5d — disk-I/O signal for the gate host-sample row: the gap, the metric choice, and its scope limit

## Narrative

Card `5988a3fc` investigated two full-suite gate reds and reached "unattributed" — correctly, having exhausted the available instruments rather than run out of ideas. CPU was checked and ruled out as a discriminator (a clean contrast case: the very next run, with 0 failures, had *higher* average CPU and a *longer* high-CPU streak than the failing run — a condition present in both a failing and a passing run cannot discriminate). Disk I/O was never checked, because nothing recorded it — and both failing sites were bounded polls waiting on disk-bound work (a detached child process spawn; real git worktree provisioning), making disk the most plausible binding resource with no instrument available to check it. This card adds that instrument to the periodic `kind:"host-sample"` row.

**Metric choice, decided empirically against this Windows host, not assumed:**

- No Linux-`/proc/diskstats`-shaped counter exists on Windows; the real system-wide per-volume queue-depth/await-time metric (`typeperf`/`Get-Counter \PhysicalDisk(_Total)\...`) is reachable only via a subprocess — measured: a single `typeperf` sample costs ~454ms, a single `Get-Counter` sample ~1.35s. Riding that on the same 5s sampling tick would itself perturb the host being measured.
- `process.resourceUsage().fsRead`/`fsWrite` (libuv's Windows mapping of `GetProcessIoCounters`) is cheap and genuinely obtainable — verified moving under real file I/O (0/0 idle → 301/300 after 300 read+300 write ops) — but it counts this process's own I/O *operations*, not latency: the count doesn't rise when the same operations take longer under contention, so it can't discriminate, and was rejected.
- **Chosen:** the wall-clock latency of a small, fixed-size, forced-to-physical-media write (open + write + fsync + close) against a dedicated probe file (`DISK_PROBE_FILE`, 64KB buffer, overwritten in place every tick — never appended to, never grown, and never the NDJSON file itself). A contended physical disk queues this write behind other pending I/O, so its latency rises with contention — a directly-measured proxy for queue depth/await-time. Verified on this host (2026-08-06): idle mean ~2.2ms (range 1.6-2.6ms) vs. ~5.8ms mean (peak 31.7ms) while 4 concurrent processes hammered the same disk with 4MB fsync'd writes, relaxing back to ~2.2ms once contention stopped.

**Cost bound:** synchronous, in-process, no added subprocess; one open+write+fsync+close per 5s tick, measured ~2ms idle (<0.1% duty cycle at 5000ms) and ~32ms observed peak under real induced contention. `writeFn` is injectable for tests. Returns `null` (never throws) on any probe failure — same posture as every other reader feeding `onHostSample`.

**Scope limit — read before treating a flat reading as "disk wasn't the bottleneck":** this probe is a *bulk sequential-write* canary. `git worktree` creation — the actual workload behind this card's two motivating specimens — is metadata-heavy small-file I/O (`git worktree add`'s checkout, then `provisionWorktreeDeps`'s `pnpm install`/`npm install` populating `node_modules`), a structurally different I/O shape that can queue and stall independently of bulk-write latency on the same disk. A flat `diskProbeMs` is evidence this specific bulk-write pattern wasn't queued, **not** evidence disk wasn't the bottleneck for worktree/install-shaped metadata I/O; widening the probe to a metadata-heavy pattern is deliberately left to a separate card.

Measured on this host under two concurrent gates (the `maxConcurrentGates=2` condition, an 18-file worktree/merge-test selection): host CPU pinned 80-99% in *every* condition including the "quiet" single-gate baseline, while this probe stayed flat (quiet mean 2.73ms vs. contended 2.87-2.99ms — no clean separation). Because CPU was pinned high throughout and the "quiet" baseline was never checked against ambient third-party load on this shared self-hosting box (a prior investigation, `docs/investigations/e4a2e789-host-load-sampler`, found this host's ambient CPU floor already sits at 40-56% from non-gate fleet load with nothing under study running), the pinning cannot be cleanly attributed to the test population alone. Read the flat result only as "CPU was pinned and this probe was flat here; the cause of the pinning is unresolved" — not as "this workload is CPU-, not disk-, bound." See project memory `disk-io-signal-windows-canary-write-not-op-counts` for the controlled experiment proving this same probe clearly separates idle vs. induced bulk disk contention (the flatness above is a property of that workload/host, not of the instrument).

## Do not

- Do not read a flat `diskProbeMs` during high CPU as proof disk is never the bottleneck — check it only alongside `cpuBusyPct`, and remember the probe is bulk-sequential-write-shaped, not metadata-write-shaped.
- Do not grow `DISK_PROBE_FILE` or reuse it as an append target — it is fixed-size and overwritten in place every tick, by design.
- Do not swap in a subprocess-based OS counter (`typeperf`/`Get-Counter`) for this sampling tick — both measured too expensive to ride on a 5s cadence without perturbing the host under measurement.
