# f1969787 — a manager recycle's ownership-transfer steps retry once, then halt instead of retiring the predecessor

## Narrative

Background (from the Code Review of card `2fd55955`, landed as commit `82b68e28` on main): `recycleManager`'s ownership-transfer steps (`reparentLiveWorkers`, `reparentWakes`, `reparentQuestions`, `reparentEventTriggerTargets`, `reparentPollJobTargets`, `reparentWebhookTargets`, `reparentPendingOwnerMessage`, `capQueue.reparent`, plus the pending-queue carry) run AFTER the successor is already live. Before this card, any one of them throwing aborted `recycleManager` entirely — the successor stayed live, the predecessor was never stopped (since `settleRecycleHandoff` is only reached on the success path), and the caller saw a bare thrown error with no structured signal about what transferred and what didn't. Two live managers, no record of which owns what.

This card:

1. Added `attemptManagerOwnershipTransfer` — runs the 8 reparent/cap-queue steps, retries ONLY the ones that failed exactly once (each is a single atomic `better-sqlite3` statement or an idempotent copy-then-clear, so retrying a step that already succeeded is harmless — the retry is scoped to the failed subset for clarity, not safety).
2. Split the pending-queue-carry step's own retry granularity: the durable-queue DB read and `pty.flushPending` are retried independently, and `pty.flushPending` is NEVER re-run once it has already returned successfully (a second flush on an already-drained queue returns empty and would look like a clean carry while actually carrying nothing).
3. If anything is still failing after retry (any reparent step, or any individual durable message's carry — see decision `f1969787` on `carryPendingToSuccessor`, below): do NOT call `settleRecycleHandoff` at all. The predecessor's pty is never stopped and stays genuinely live/functional — `clearRecycleSettlePending` is called directly (normally only cleared inside `settleRecycleHandoff`'s own `finally`) so boot-time `recycle-settle-reconcile.ts` doesn't try to reconcile a settle that will never happen. A new durable event `recycle_ownership_transfer_failed` is filed (under the successor's id, mirroring `recycle_complete`'s own filing identity) naming the failed steps plus the actual stranded worker/question/wake ids (resolved only for the categories that failed). Two `enqueueDurableNudge` calls go out — one to the predecessor stating exactly what it still owns, one to the successor correcting its kickoff's "your predecessor's live workers have been re-parented to you" claim where that's no longer true, and naming exact ids in both.
4. `recycle_complete`'s own `detail` always carries `failedSteps` (present only when non-empty) so `reparentedWorkers: 0` can never again be confused with "the predecessor genuinely had no workers."
5. `carryPendingToSuccessor` (decision `f1969787`, its own doc comment) was restructured: the re-mint onto the successor happens FIRST, and the old record is only marked "superseded" once that mint actually succeeds — never the reverse. A prior version resolved every durable `flushed` entry "superseded" eagerly, in its own earlier pass, before the re-mint loop even started, so a record whose re-mint later failed still had its old copy marked resolved with nothing live behind it: a genuine, silent loss. On a failed mint the old record is left unresolved and re-armed directly on the predecessor's own live pty instead (never the successor) — correct because `recycleManager`'s new failure branch keeps the predecessor alive specifically so a message that didn't survive the carry still has somewhere real to drain. The function now returns `{ failedRefs: string[] }` instead of `void`, and never throws as a whole — every per-record failure is independently try/caught.
6. `redriveQueuedMessage` (`sessions/service.ts`) previously treated ANY `hasSuccessor(recipientId)` as "recipient gone/superseded," unconditionally retiring the queued record — correct for the ORDINARY case (a recycled predecessor's pty was already stopped) but wrong for this card's new halted case, where the predecessor stays genuinely live with a successor that exists. Reordered, SCOPED TO `role:"manager"` ONLY, so a live manager is always redriven directly regardless of `hasSuccessor`; a non-live manager with a successor is still treated as superseded, and every non-manager role (worker/platform) keeps the exact old unconditional-`hasSuccessor` behavior — `recycleWorker` hard-stops its old pty before a successor is ever linked, so a worker never legitimately reaches live+hasSuccessor, and widening the fix to it would have regressed `queued-message-liveflip-redrive.mjs` scenario (3) (a synthetic "what if a superseded worker somehow flips live" defensive case). Without this, a daemon restart (or any other redrive trigger) during the halted manager state would wrongly retire a message this card's own `carryPendingToSuccessor` fix deliberately left live and deliverable on the predecessor.
7. `recycleWorker`'s existing `carryPendingToSuccessor` call site was updated to read the new `{ failedRefs }` return and include it in its existing `[loom:recycle-carry-failed]` nudge, since the function can no longer be relied on to throw as a signal of partial failure.

Verified NOT broken by a permanently-true `hasSuccessor(oldManagerId)` in the halted state: `archived_at` is never set on the predecessor by `recycleManager`; the idle watchdog (`orchestration/idle-watcher.ts`) does not reference `hasSuccessor`/`recycledFrom` at all; `workerReport` routes by `worker.parentSessionId` directly, never through a "find the project's live manager" lookup, so a worker whose reparent genuinely failed still reports correctly to the predecessor; the `peer_message`/Platform-Lead "find the live manager/Lead for project X" lookups (`sessions/service.ts`) deliberately exclude a `hasSuccessor` session by design (card `e79e2956`, itself citing `redriveQueuedMessage`'s own guard as the pattern it mirrors) — that exclusion is about routing a FRESH incoming message to the nominal forward-going owner and stays correct/unaffected by this card; the MCP/gateway surface has no `hasSuccessor` gate at all.

**CORRECTION (Code Review, fix round) — ITSELF LATER REVERSED, see ROUND 3 below:** a fix round once claimed the predecessor was captured and resumed on a clean daemon restart via `resume()`/`deriveCrashOrphanedManagers` carve-outs keyed on the durable `recycle_ownership_transfer_failed` event. That carve-out was REMOVED by ROUND 3 (below) — **do not reintroduce it from this paragraph's history.**

**ROUND 3 (delta review, scope cut) — the carve-out above was REPRODUCIBLY WRONG and has been REMOVED.** The event it keyed on is **PERMANENT** (never cleared), so a predecessor that halted once, was later cleanly reclaimed (its halted successor died, ownership came back to the predecessor), and was then cleanly re-recycled to a BRAND NEW successor would still match `hasWorkerEventKind(id, "recycle_ownership_transfer_failed")` on its *next* restart — `resume()` and `deriveCrashOrphanedManagers` would auto-resume it ALONGSIDE its new, unrelated successor: two live managers on one lineage. **What this card actually guarantees today, matching main's pre-existing behavior exactly:** a halted predecessor is never stopped and keeps running for as long as its own process stays alive (in-process recovery via `watchHaltedRecycleSuccessor` + the boot-time `halted-recycle-reconcile.ts` pair still fully apply — see below) — but if that predecessor itself crashes or the daemon restarts while it's still halted, it is **refused by every automatic resume path** (`resume()`, `resumeFleetOnBoot`, `deriveCrashOrphanedManagers`/`recoverCrashOrphanedWorkers`), identically to an ordinary recycled predecessor — only a manual (human) `allowSuperseded` resume can bring it back. Auto-resuming a halted predecessor safely — through a predicate keyed to whether its CURRENT successor is still the exact one the halt event named, not the event's bare permanent presence — is tracked as follow-up work (card `386e4eb5`), not provided by this card.

**ROUND 3 finding:** when BOTH the predecessor and the halted successor are unresumable at once (the (F) scenario below), the fleet is left permanently split across two dead-or-archived sessions with nothing automatic able to unify it — only a human can sort it out.

**Also fixed (Code Review, fix round):** the halt branch never armed successor-death recovery — if the halted successor died before ever reaching SessionStart, whatever DID transfer to it (e.g. live workers, when only `wakes` failed) stayed parented to a dead session forever, with the live predecessor owning nothing of it. `SessionService.watchHaltedRecycleSuccessor` mirrors `settleRecycleHandoff`'s own e07b1b1a death-watch but DELIBERATELY omits its "reached ready -> stop predecessor" branch (a halted predecessor is never stopped, no matter what the successor does) — on the successor's confirmed death it calls the SAME `recoverFleetAfterFailedRecycleSuccessor` the ordinary path uses, and (ROUND 3) mirrors `settleRecycleHandoff`'s own unresolved-alert leg too: if the successor neither reaches ready nor confirms dead within the same bound, it fires one `recycle_fleet_unresolved` event + nudge, then keeps watching. A daemon restart loses that in-memory watch exactly like `settleRecycleHandoff`'s own 08c81809 gap; `halted-recycle-reconcile.ts`'s `reconcileHaltedRecycleSuccessorsEarly` (folded into the shared `runBootRecoveryPrefix`, under the SAME before-`recoverStaleSessions` ordering constraint as `reconcileStrandedRecycleSettlesEarly`) plus `SessionService.finishReconcilingHaltedRecycleSuccessors` (run at the identical boot point as `finishReconcilingRecycleSettles`, before either resume path computes its candidate set) close that gap for a successor that never becomes durably resumable across a restart. A successor that DOES survive the restart durably is left alone — ownership legitimately stays split; bringing the predecessor itself back after a restart is the manual-resume-only gap ROUND 3 above describes, not something either reconcile phase does automatically. **ROUND 3** also hardened `reconcileHaltedRecycleSuccessorsEarly` itself, mirroring `reconcileStrandedRecycleSettlesEarly`'s own two guards: (1) NEVER RESURRECT — it now checks `isDurablyResumable(predecessor)` too, not just the successor, before reparenting anything back; a predecessor that is ALSO unresumable this boot is left untouched, same as the successor (nothing archived/overwritten/nudged onto a destination that can't come back). (2) STALE SUCCESSOR (id is the real discriminator, gen only a defensive secondary check — a real round-2 lineage can mint a new successor with the SAME gen as the stale one) — since the halt event is permanent, it only acts when the predecessor's CURRENT successor (`db.getSuccessor`) is the EXACT successor the LATEST halt event named (matching both `managerSessionId` and `detail.gen`); a lineage that was reclaimed and then cleanly re-recycled to a different successor is left entirely alone, so this reconcile never double-processes a lineage the ORDINARY `reconcileStrandedRecycleSettlesEarly` (08c81809) is already correctly handling via its own, unrelated settle-pending marker.

**Also fixed (Code Review, fix round) — three smaller gaps:**
1. **Order**: the pending-queue carry now runs AFTER `attemptManagerOwnershipTransfer`, and is SKIPPED ENTIRELY when `workers` is among `failedSteps` — carrying the predecessor's inbound queue (worker reports among it) to a successor that never actually received those workers stranded the reports on the wrong owner. Every other failure shape (e.g. `wakes` alone) still carries normally.
2. **`carryPendingToSuccessor`'s non-durable-entry failure** (the `enqueueStdin` catch with no durable record to fall back on) now RE-ARMS the entry on the predecessor (mirrors the durable re-mint's own re-arm) instead of just logging "this entry is lost" while still counting it in `failedRefs` — the predecessor's "still yours to deliver" nudge is only true once something is actually re-enqueued there.
3. **Best-effort wraps**: the halt branch's own stranded-id reads (`listWorkers`/`listQuestionsForSession`/`listWakesForSession`, pure observability for the event/nudge text) and its two `enqueueDurableNudge` calls are now wrapped (`bestEffortPostSpawnResultSync` / try-catch) so a persisting DB fault there can't throw past the event/nudges and resurrect the pre-card bare-throw defect for an unrelated reason.

**Also fixed:** `recycle_me` (mcp/orchestration.ts) used to return the ordinary success shape (`{newManagerSessionId, gen}`) even when the recycle halted, and its description claimed it unconditionally "closes you." It now checks for the durable `recycle_ownership_transfer_failed` event and returns `{..., halted:true, failedSteps}` when it fired; the description states the halt possibility.

**ROUND 4 (small fix round, test hardening):** Code Review found scenario (G) in `recycle-manager-halted-successor-dies.mjs` VACUOUS for the ROUND 3 stale-successor guard it names — (G) also makes M1 unresumable, so the EARLIER `isDurablyResumable(predecessor)` NEVER RESURRECT gate (08c81809, which runs before the stale-successor guard's own `continue`) already blocks the reparent regardless of what the stale-successor guard decides; a `if (false) continue;` mutation of the guard left (G) fully green. Added scenario (G'): the identical reclaimed-then-re-recycled lineage shape, but with M1 made durably resumable (real engine id + transcript) so the NEVER RESURRECT gate can no longer mask the guard — S2 is driven to a genuine, fully-settled ready state (a real `settleRecycleHandoff` completion, not a simulated crash mid-recycle like (G)) and left unresumable only by never capturing a real engine id, isolating the check to the guard alone. Negative control: mutating the guard to `if (false) continue;` in `dist/sessions/halted-recycle-reconcile.js` turns (G') red (the worker's fleet gets wrongly reparented back onto the stale M1, S2 gets unlinked/archived, a `recycle_fleet_recovered` event is fabricated); restoring the build turns it green again — (G) alone is untouched by the same mutation, confirming it was the vacuous one.

Also corrected a stale inline comment on the `recycle_ownership_transfer_failed` event's own `workerSessionId` field (`recycleManager`'s halt branch): it used to say `resume()` and the crash-recovery candidate derivation read this field — true only of the CORRECTION-paragraph carve-out above, which ROUND 3 removed entirely. The field's real reader is `reconcileHaltedRecycleSuccessorsEarly`: `db.listWorkerSessionIdsWithEventKind` selects it to find candidate predecessor ids fleet-wide, and that function's own `latestHalt` filter re-reads it per-candidate for the stale-successor guard above. `recycle_me`'s immediate result (mcp/orchestration.ts, the "Also fixed" paragraph above) surfaces the same event kind but keyed by the successor's `managerSessionId`, not this field. `resume()`/`deriveCrashOrphanedManagers` deliberately do not read it (ROUND 3, card `386e4eb5`).

## Do not

- Do not retry the WHOLE ownership-transfer pass unconditionally on every call — retry only the steps that actually failed; the 8 reparent/cap-queue steps are idempotent, but re-running a step that already succeeded is unnecessary work, not a safety requirement.
- Do not re-run `pty.flushPending` a second time once it has already returned successfully once — a second call drains an already-empty queue and silently looks like a clean, complete carry.
- Do not call `settleRecycleHandoff` (and so stop the predecessor) when any ownership-transfer step, or any individual durable message's carry, is still failing after the one retry — stopping the predecessor at that point is exactly the stranding this card exists to prevent.
- Do not resolve `carryPendingToSuccessor`'s old durable record "superseded" before its replacement mint onto the successor has actually succeeded — see that method's own `@decision f1969787` doc for the mechanism this produces when violated.
- Do not read `recycle_complete.detail.reparentedWorkers === 0` as "the predecessor had no workers" without also checking `failedSteps` — it is ambiguous with "the reparent step itself failed" unless `failedSteps` is checked alongside it.
- Do not treat `hasSuccessor(recipientId) === true` as sufficient, on its own, to retire a queued durable message in `redriveQueuedMessage` for a MANAGER — check `processState === "live"` first; a live manager with a successor (this card's halted state) must still be redriven directly. Do not widen this reordering to worker/platform roles — they never legitimately reach live+hasSuccessor, and doing so regresses `queued-message-liveflip-redrive.mjs` scenario (3).
- Do not assume `isRetired`/`retiredRecycleSuccessorIds` makes a halted predecessor resumable — it only excludes an already-reclaimed SUCCESSOR, never the predecessor.
- **ROUND 3: do not reintroduce a `resume()`/`deriveCrashOrphanedManagers` carve-out keyed on the bare presence of a `recycle_ownership_transfer_failed` event** — that event is PERMANENT, so the carve-out matches a predecessor that was already cleanly reclaimed and re-recycled to an unrelated new successor, auto-resuming it alongside that successor (two live managers). A halted predecessor that crashes or restarts stays refused by every automatic path, exactly like an ordinary recycled one, until a human forces it with `allowSuperseded` — see the ROUND 3 narrative above. Auto-resuming it safely is card `386e4eb5`'s follow-up work, not this card.
- Do not let `watchHaltedRecycleSuccessor` stop the predecessor on any branch — unlike `settleRecycleHandoff`, it has no "reached ready" stop leg; a halted predecessor is never stopped, period.
- Do not run the pending-queue carry when `workers` is in `failedSteps` — the predecessor still owns those workers, so carrying its inbound queue to the successor strands worker reports on the wrong owner.
- Do not let `carryPendingToSuccessor`'s non-durable-entry failure merely log "this entry is lost" — re-arm it on the predecessor, or the predecessor's own "still yours to deliver" nudge is false.
- **ROUND 3: `reconcileHaltedRecycleSuccessorsEarly` must never reparent the successor's lineage back without first confirming `isDurablyResumable(predecessor)`** — a predecessor that is ALSO unresumable this boot is not a viable destination either; leave both sides untouched (mirrors `reconcileStrandedRecycleSettlesEarly`'s own NEVER RESURRECT gate).
- **ROUND 3: `reconcileHaltedRecycleSuccessorsEarly` must only act when the predecessor's CURRENT successor matches the LATEST halt event's `managerSessionId`/`detail.gen` exactly** — never on the bare presence of a (permanent) halt event for that predecessor id; a cleanly re-recycled lineage must be left entirely to the ORDINARY `reconcileStrandedRecycleSettlesEarly` (08c81809) path.
