# 3407caad — `GATE_PROXIMITY_THRESHOLD=0.85` is a warn-before-breach signal, anchored on Loom's own measurement

## Narrative

Card 3407caad: `GATE_PROXIMITY_THRESHOLD` measures how close a step's `durationMs` came to consuming its own `gateCommandTimeoutMs` budget — a WARN-BEFORE-BREACH signal, distinct from `gateExtended`/`anyExtended` (card 9f6598dd), which only tells you a run ALREADY breached it. This fires earlier: a step can be well on its way to needing an extend, or to a hard timeout on a project with `gateRetry` disabled, while still comfortably PASSING today — the point is a signal visible on a passing run, not just a failing one.

WHICH CEILING THIS IS A FRACTION OF (manager review, card 3407caad): there are TWO different ceilings a step can be measured against, and they differ by ~2x. A FIRST attempt's EFFECTIVE ceiling, once its one-time output-gated auto-extend is counted, is `gateCommandTimeoutMs` PLUS one more full `timeoutMs` window (`GATE_EXTEND_IDLE_MS`'s own doc) — roughly 2x `gateCommandTimeoutMs`, while the step keeps producing output. A RETRY after a timeout runs `allowExtend:false` (card 24642c3d, deliberate — stacking two "one more chance" mechanisms would push the worst case to ~4x) — a HARD `gateCommandTimeoutMs`, no net. `fraction` is ALWAYS `durationMs / gateCommandTimeoutMs` — the RAW configured value, the SMALLER HARD retry ceiling, never the ~2x first-attempt-with-extension allowance — because that's the ceiling that actually bites: a step comfortably inside its first attempt's effective budget (extended once, still passed) can be structurally doomed on a retry, which gets no such net. A `fraction` over `1.0` means this step already needed more than the hard ceiling to finish — worth surfacing even on a pass, since a retry of the SAME step would have no reprieve.

COMPOSES WITH, DOES NOT DUPLICATE, card 73a847f5: that card already skips a doomed retry (a timeout that already consumed its auto-extend "reports budget-exceeded" and never re-runs) but fires AT THE MOMENT OF FAILURE, after the fact. This signal is the pre-emptive counterpart, firing WHILE THE GATE IS STILL GREEN. It is NOT the comparison `formatGateStepsDiagnostic`'s own doc warns never to make (inferring correctness from a step's absolute duration, load-variable noise); this compares against the fixed `gateCommandTimeoutMs` ceiling, an operational capacity question, not a correctness one.

THE THRESHOLD, stamped number/condition/population/instrument/as-of, TWO INDEPENDENT SYSTEMS, deliberately NOT averaged or compared against each other (different suites/budgets, no transfer function — only the SHAPE transfers): Loom's own gate (manager review, card 3407caad, 2026-08-04) — merge op `4e7e4123` (card `23471268`) settled with steps `pnpm build 3s · pnpm --filter @loom/daemon test:daemon 18m14s`; worst step (test) ~1,094s against the per-step 1,800,000ms `gateCommandTimeoutMs` = ~61%. Condition: real merge gate, Windows host, daemon gate cap 2. Population: 650 hermetic daemon test files, runner pool size 2 (grows over time with zero change to the threshold — why it needs headroom). Instrument: the settled `gate_status` record + the `[loom:merge-done]` steps line. As-of 2026-08-04. A peer project's own gate (n=4 healthy runs, same review, 2026-08-04): 60.4%/65.4%/73.1%/76.6% of its configured 700,000ms `gateCommandTimeoutMs`. Both sit in a HIGH band (Loom ~61%, peer up to 76.6%) as NORMAL healthy state — that STRUCTURAL convergence, never either system's magnitude, argues a single GLOBAL constant is the wrong SHAPE. 0.85 is anchored SOLELY on Loom's OWN worst-step reading (~61%, ~24 points headroom) — the peer's numbers support the structural argument only, never 0.85's own value (anchoring on the peer's 76.6% would be the exact cross-system comparison this doc forbids). The true margin is worse than the reading suggests: a sibling project's suite can run real-ingest tests against Loom's own live corpus (eroding margin as this repo grows), and worker doctrine defaults a worker's own DoD self-check to running tests directly rather than through `run_gate`, so semaphore-invisible test lanes can compete with an admitted gate at the same moment.

LIMITATION: one GLOBAL constant, not per-project config — a project with a hotter worst-step ceiling, or a build step heavy enough that whole-gate and worst-step meaningfully diverge, could need an override this card does not build.

SECOND CONSUMER (card fd9edb87): the Gates page's `LONG_RUN_WARN_FRACTION` (`packages/web/src/pages/Gates.tsx`, 0.80) scales its LIVE lane cue off the same band, on a DIFFERENT AXIS — whole-run elapsed since admission, not one step's duration; deliberately not unified/averaged (whole-run elapsed is always >= the worst step, so the live cue fires EARLIER at equal fractions — the safe direction). Retuning either constant touches the other's reasoning.

## Do not

- Do not measure `fraction` against the ~2x first-attempt-with-auto-extend ceiling — it is always `durationMs / gateCommandTimeoutMs`, the smaller HARD retry ceiling, because that's the one that actually bites on a retry.
- Do not anchor this constant's magnitude on the peer project's own reading, or average the two systems' numbers — different budgets/suites/hosts, no transfer function; only the structural convergence (both healthy-high) transfers, never a magnitude.
- Do not unify or average this constant with the Gates page's `LONG_RUN_WARN_FRACTION` — they measure different axes (single step vs. whole-run elapsed) on purpose.
