# 4cbbc343 — the trust class follows the LISTENER; trusted-proxy mode is a third, loopback-only listener

Card `4cbbc343` (owner chose "B — build trustedProxyOrigins", request `9bf644c5`), folding in `d0f3c8ea`. Builds on `23496950` (the remote listener is a separate server; loopback stays plain HTTP on PORT). Design reviewed by a Code Reviewer before any code; finding C1 (below) reshaped it.

## Decision

- ONE predicate, `requestClass` (`gateway/trust-tier.ts`), decides a request's trust class: `loopback`, or `remote` via `peer` (a non-loopback or undeterminable TCP peer), `remote-listener`, `proxy`, or `forwarded`. No other file reads a peer address or compares to a loopback literal (`test/remote-trust-single-predicate-guard.mjs`). Every trust decision reads it: the CSRF/Origin/Host hook, the tier wall, the loopback-secret guard, `/ws/term` read-only + no-host-shell (`710a34fa`), the six `/internal/*` routes, and the rate-limit keys.
- **The class follows the LISTENER, never a Host header (review finding C1).** Classifying by Host fails OPEN: a proxy that rewrites Host to its upstream (nginx's default), or a client-chosen `Host: 127.0.0.1:4317`, would be served as loopback — every ungated loopback GET and `/ws/fleet` without a token, i.e. the rejected "just allowlist the Host" option. So proxy mode is a THIRD listener, `remoteAccess.proxyPort`, bound to `127.0.0.1` only, with NO default (nothing listens until a human sets it). Every request/upgrade on it is marked (WeakSet on the raw request, set before `app.routing` and in the upgrade forwarder) and is remote-class whatever its Host, peer or headers.
- `d0f3c8ea`: every request on the REMOTE listener is likewise marked remote-class, even from a loopback peer (a same-host dial of the internet-facing port no longer borrows loopback trust). Answer: yes.
- On the proxy listener: the Host must equal a `trustedProxyOrigins` entry (canonical host + port, the entry scheme's default port applied; trailing-dot and userinfo refused) and an Origin, if present, must be THAT SAME entry (`null` and empty refused). A `Tailscale-Funnel-Request` header is refused on every route. On the daemon's own PORT the class still follows the PEER: a proxy Host there still 403s, and a loopback peer carrying `X-Forwarded-*`/`Forwarded`/`Via`/`X-Real-IP`/`Tailscale-*` is classed remote (`forwarded`) — a downgrade only, UNCONDITIONALLY since card `a3d48a15` (it used to apply only while proxy mode was configured; see the a3d48a15 bullet). That is NOT a guarantee: a proxy that rewrites Host to `127.0.0.1:<PORT>` and adds none of those headers (nginx's default `proxy_pass`) is indistinguishable from a local client and is served as loopback, so the docs say never to point a proxy at PORT (pinned by `remote-trusted-proxy.mjs` (3) LIMIT).
- One source of truth for "is remote trust live": `resolveRemoteTrust` (wall registration, proxy mode, canonical origins). Fail-closed: a request classed remote while NO wall is registered is refused 403 (a determinable peer only) — the loopback-secret guard's skip for non-loopback callers is safe only because "remote ⇒ the wall is on".
- Config is HUMAN-only (`remoteAccess.proxyPort`, `remoteAccess.trustedProxyOrigins`, in the shared `remoteAccessOverride`, so both the override and patch schemas carry it; the agent project-config shape rejects `remoteAccess`). Entries are exact canonical origins: no wildcard, path, userinfo, trailing dot, loopback or ambiguous host; https unless `.ts.net`; max 16. Proxy mode needs `remoteAccess.enabled` (one master switch), a valid entry and a gateway token; a config change needs a daemon restart. Without a gateway token at boot the daemon STILL BOOTS: the proxy listener is simply not opened and a WARN says why, so minting the first token needs a restart (never described as "refuses to boot").
- Rate limiting for the proxy class is THROTTLE-ONLY and VERIFY-FIRST: every caller shares one local socket address, so a per-ip lockout would let one guesser lock out the owner (and tokens are 256-bit, so a lockout adds nothing). A valid token is gated only by its own per-token cap; presented-but-invalid tokens are throttled (429) on the failure path only; a generous shared pre-auth cap covers unauthenticated requests. The webhook ingress is not reachable through this listener.
- **Card `179b6227` extends the same rule to the DIRECT remote listener** (the old direct path checked a db-backed per-ip lockout BEFORE verifying, so behind NAT/CGNAT or a shared office ip one guesser sending `maxAttempts` wrong tokens locked out every other user of that ip, the owner with a valid token included, and the owner's success cleared the guesser's count). Now both listeners run ONE sequence (`verifyThenThrottle`, `gateway/server.ts`, anchored `@decision 4cbbc343`): verify the token first; a valid one meets only its per-token cap (`allowToken`); everything else meets a pre-auth cap and, if a credential was actually presented, a failed-auth throttle (429, in memory, `authFailLockout.maxAttempts` per `windowMs`); then 401. The direct listener keys the pre-auth cap and the failure counter per ip; the proxy class uses one shared bucket each (`PROXY_FAILED_AUTH_PER_MIN`). A success NEVER resets a failure count (on a shared ip it would wipe another party's). `authFailLockout.lockoutMs` is ignored and the `gateway_auth_attempts` table is legacy and never read, so a row persisted before the upgrade is inert (no migration). Card `cf9ebab9` bounds the counters behind it: keys are the peer address with IPv6 folded to its /64 (IPv4-mapped to IPv4), each counter has a hard key cap that evicts the least-recently-touched key (an evicted key just gets a fresh window, i.e. fails open PER KEY — the throttle is a nuisance-limiter, and refusing new keys when full would let a spray lock legitimate callers out), and the stale-key sweep runs at most once per second. The failed-auth 429 carries the same `code:"gateway-token-required"` as the 401 (reached only after the token failed verification), and the web client treats that coded 429 like the coded 401.
- The SPA shell is public to the proxy class ONLY (owner flag F1, recommended by the design review): a browser must load the app before it can present a token. It is keyed on the MATCHED route pattern — `GET|HEAD /*`, the one route `@fastify/static` registers, which matches only what no daemon route matched — never on the request path text (`isStaticShellRoute`). Every non-shell route still needs the token; the remote listener stays API-only; it is deliberately NOT rate-limited (security review 3d70a0a9): it is public static bytes, and every proxied request arrives from 127.0.0.1, so any shared bucket would let one tailnet peer 429 the owner's own app load — the API throttles are unchanged. The static registration sets `dotfiles: "ignore"` so a dotfile in the web dist can never be fetched through it. The web side keeps the GATEWAY token in its own storage key (`loom.gatewayToken`, captured from `?gwtoken=`), sends it on every request and in the ws double-subprotocol, and shows its own banner keyed on `code:"gateway-token-required"`. A `?gwtoken=` link is VERIFIED against `/api/version` before it is stored (a refused link never overwrites a working token and is surfaced instead) — the loopback credential banner (`093981dd`) is untouched.
- Tier-1 only, like any remote caller: a Serve cockpit is reads + answer/steer + view-only terminals; every Tier-0 page (config, writers) 403s.
- **Card `a3d48a15` makes the main-port downgrade UNCONDITIONAL** (security review `3d70a0a9` of this card's own design flagged that it applied only while proxy mode was configured, so a user who never configured it and pointed a proxy at the daemon port got loopback trust for every proxied request). Decision: yes, unconditional — presence of one of the proxy-shaped headers on a loopback peer only ever LOWERS trust, and with no wall registered the fail-closed 403 already applies. Legitimate local clients checked (repo grep for `x-forwarded`/`xfwd`/`x-real-ip`/`via`/`forwarded`/`tailscale-`, excluding tests, `node_modules`, `dist`; positive control: the same pattern hits `trust-tier.ts`): the pnpm web dev proxy (vite's bundled http-proxy adds `x-forwarded-*` only under `xfwd`, which `vite.config.ts` does not set — pinned by `dev-proxy-loopback-nonregression.mjs` with an `xfwd:true` control), `bin/loom.mjs`, the hook-relay, the codescape supervisor (dials its own port) and the in-app companion chat all send none. The residual is a LOCAL debugging/corporate HTTP proxy (Fiddler, Charles, mitmproxy, a corporate agent) configured through `HTTP_PROXY`/`HTTPS_PROXY` that relays a client's calls to `127.0.0.1` and adds `Via`/`X-Forwarded-For`: every such request is now 403 — the correct trust outcome but a confusing failure, so the refusal is diagnosable on every door that REFUSES (REST, `/mcp/:sessionId`, WS routes and the webhook ingress with no wall, and any Tier-0/Tier-2 route with the wall on): the 403 keeps `error:"forbidden"` and adds `code:"proxy-shaped-header"`, the header NAME and a hint naming `proxyPort` and `NO_PROXY`, and the daemon logs one header-name-only line per header family per minute — the ONE diagnostic that is uniform across every case. With a wall registered, a forwarded-class request on a Tier-1 route is simply a remote caller (401 `gateway-token-required` without the gateway token, served with one — pinned by `remote-trusted-proxy-real.mjs`), so no 403 body is involved there. NOT verified: what the claude CLI does with `HTTP_PROXY` for an HTTP MCP server URL on `127.0.0.1` (Claude Code's network docs say it honours `NO_PROXY` and never proxies its own WebSocket connections to loopback, and are silent on MCP servers); no real `claude` was spawned to test it. The nginx-default case (Host rewritten, no forwarding header) still evades this and stays covered by the docs warning only.

## Do not

- Do not classify a request by its Host, Origin, `X-Forwarded-*` or any header a proxy may rewrite or a client may choose; the class is the listener (or the socket peer).
- Do not read a peer address or compare to a loopback literal outside `requestClass`; do not re-derive "is remote trust on" outside `resolveRemoteTrust`.
- Do not add a wildcard/suffix to `trustedProxyOrigins`, accept a loopback entry, bind the proxy listener to anything but 127.0.0.1, give `proxyPort` a default, or make either key agent-writable.
- Do not add a hard lockout (or a per-ip key) to the proxy class, or verify a token AFTER a throttle.
- Do not restore a per-ip hard lockout, or a check-the-ip-before-verifying-the-token order, on the DIRECT listener either (`179b6227`), and do not reset a failure counter on a success: that is the shared-ip lockout of the owner it removed. Keep the two listeners on the ONE `verifyThenThrottle` sequence; do not fork a second copy. Do not key the direct-listener counters on a raw IPv6 address (one /64 = unlimited keys), and do not let the key maps grow without a hard cap or walk the whole map on every request.
- Do not widen the shell exemption past `GET|HEAD /*` or to any class but the proxy listener, and do not decide it from the path text.
- Do not store a `?gwtoken=` link's token without verifying it, and do not add a shared unauthenticated cap on the shell.
- Do not treat a `Tailscale-*`/forwarded header as a credential or as proof of identity — it can only LOWER trust.
- Do not gate the `forwarded` downgrade on proxy mode (`a3d48a15`): the user who never configured proxy mode and points a proxy at the daemon port is exactly the one with no other protection. `requestClass` takes no config; do not add a `proxyMode` argument back.
- Do not put a proxy-shaped header VALUE in the daemon log, and do not log per request: header NAMES only, once per header family per minute (the log is shared across tenants, and a hostile client can rotate names).
