# cc9bce38 — a solo finalize deletes the branch only at the tip that landed, and a retained branch is held only while it differs from that tip

The worker is still alive between `mergeBranch` releasing its lock and `finalizeMerge`'s hard stop, so a commit it made in that window was destroyed by `finalizeMerge`'s plain `git branch -D` (and the worktree force-removal) under `merged:true`. The batch path closed exactly this in 42daa283 (tip check at finalize plus a compare-and-swap ref delete); the solo path passed no `expectedBranchTip` at all.

## What lands, and where the tip comes from

- A solo squash now stamps a `Loom-Landed-Tip: <sha>` trailer (the branch tip it ran on, `resolvedBranchHead`, 7efc2bff) next to `Loom-Worker-Branch`, so the tip that landed is recoverable from main itself with no fresh read.
- The solo Green finish passes `finalizeMerge` the landing pin (35cfcbe0) when there is one, else `landedTip` (`mergeBranch`'s return): a Green squash just created the commit, so the tip it ran on IS the tip that landed.
- EVERY finish of an already-found squash goes through ONE resolver, `pinnedTipForLandedSquash`: the four callers are the early idempotency finish, catch-recovery in `confirmWorkerMergeTracked`, boot-reconcile Pass A (all via `tipAcrossLandedCheck`) and the IN-CONFIRM ALREADY_MERGED finish. It pins to the found squash's TRAILER tip, never to a fresh read and never to a content check — and for the in-confirm finish that includes `merge.landedTip`, which is only the tip `mergeBranch` froze and found EMPTY (a late whole-file or partial revert squashes empty too, so pinning to it deletes the revert). The trailer is read only from the FINAL trailer block (after the last `Loom-Worker-Branch:` line), so a batch-landed worker body that merely quotes the text is not a trailer. Why not a content check: `findLandedSquashCommit`'s content check counts a late whole-file revert as "landed", so any tip derived from it would bless the late commit. RESIDUAL: a squash with NO trailer (anything landed before this card) falls back to the resolver's legacy tip (the branch tip read before AND after the lookup, trusted only when stable; for the in-confirm finish, the tip `mergeBranch` froze), which still cannot see a late commit made before that read. The trailer closes this for every squash from now on.
- A branch already gone has nothing to protect; an unreadable tip fails CLOSED via a sentinel that never equals a real ref, so finalize retains.
- The ONLY tip comparison is `finalizeMerge`'s existing check and `deleteBranch`'s `expectedTip` CAS, skipped only while git still lists the branch as checked out.

On a mismatch the branch, worktree and task stay (phase `at-finalize`, or `ref-kept-after-finalize` when only the ref delete was refused), the result stays `merged:true` with `warning` and the dedicated `branchRetainedWarning` (echoed on the `[loom:merge-done]` / `[loom:already-merged]` nudge; the latter is sent AFTER finalize so it never says "finishing the cleanup" over a retention), and a durable `merge_branch_retained` event (`source:"solo"`, `landedTip`, `liveTip`, `phase`) is filed.

## The hold

A retained branch is HELD through the ONE `isBranchHeld`, which reads both `batch_merge_branch_retained` and `merge_branch_retained` (`listRetainedBranches` too). A first version only warned; Code Review reproduced the loss (a late commit that is a partial REVERT stages nothing in the 3-way squash, so a re-confirm reads ALREADY_MERGED and the CAS deleted it). A second review found the hold could be PERMANENT when nothing was left to land (a transient unreadable tip, the fail-closed sentinel, a ref kept at the landed tip), since every re-confirm squashes empty and is refused. So the release is STATE-based, one rule for both kinds: the hold lasts only while the branch's current tip differs from the tip the retaining merge landed (`landedTip` for solo, `assembledTip` for batch; a retention that recorded none resolves it from the landed squash's trailer). An unreadable OR MISSING current tip stays held (fail closed): 42daa283 deliberately does not release on a missing branch (a ref probe reads a transiently locked ref as missing) and `batch-merge-retain-hold-release` pins that. RESIDUAL: a retention that recorded no tip (the fail-closed sentinel) on a squash with no trailer has nothing to compare, so it stays held until a real merge_done or a later Loom-Worker-Branch squash; the existing releases (a newer real merge_done, a later Loom-Worker-Branch squash) are unchanged. A re-confirm with a non-empty squash goes Green through the held path; an empty one is refused with cherry-pick guidance and stays held until the tip returns to the landed tip or a real landing happens.

## Do not

- Do not call `finalizeMerge` / `finishAlreadyMerged` from a solo confirm or its recovery/reconcile siblings without an `expectedBranchTip` (except for a branch confirmed gone): no unconditional `branch -D` on a finalize that has a tip to protect.
- Do not add a second "is the branch still at X" implementation, or a second definition of "held": the solo path reuses `finalizeMerge`'s check, `deleteBranch`'s CAS and `isBranchHeld`.
- Do not fold the solo event kind into `batch_merge_branch_retained`: the kind stays distinct (`source:"solo"`); only the hold READS both.
- Do not derive the pinned tip from a fresh read after the squash or lookup, from `findLandedSquashCommit`'s content check, or from `merge.landedTip` on the ALREADY_MERGED finish: all bless a late commit. Use the pin (Green), or `pinnedTipForLandedSquash` (any found squash) — and do not compute a tip at a new caller: route it through that resolver.
- Do not read the trailer from anywhere but the final trailer block.
- Do not make the hold event-only: a hold that does not compare the current tip to the landed tip is permanent when nothing is left to land.
- Do not skip the CAS delete merely because the worktree was not removed, and do not run it while the branch is checked out: `finalizeMerge` runs `listCheckedOutBranches` whenever a tip is set and skips the delete only while git still lists the branch (fail closed on an unreadable list), because `update-ref -d` would drop a checked-out branch. A worktree git already de-registered still gets its branch deleted, as `branch -D` did.
- Do not move the `[loom:already-merged]` announcement back before finalize, and do not word the ref-kept guidance as "land it with worker_merge_confirm": the worktree is gone (the confirm fails) and an empty squash refuses, so it can loop. It says cherry-pick onto a follow-up card's worker, like merge_batch's text for the same event.

## Not covered

- Pass A and the catch-recovery site share `tipAcrossLandedCheck` (and so the resolver) with the early-finish path but only the early-finish path (case L) and the in-confirm finish (case N/N2) have a hermetic test here; the other two are covered by the shared helper, not by their own scenario.
- The `listCheckedOutBranches`-throws-so-skip branch is a plain `catch` with no seam to test it; the still-checked-out branch is covered (case I).
- A batch landing carries no `Loom-Landed-Tip` trailer (its retention records `assembledTip` instead).
- Card bbccf470 (a review-side refusal of commits added after the last `worker_merge`) is a separate, pending guard and is NOT relied on here.
