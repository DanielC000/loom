# 79b8d8a9 — `removeWorktree` uses `-f -f`; the filesystem backstop already exercises everything the second force adds

## Narrative

`removeWorktree` handles a Windows handle-release race: when a worker is hard-stopped just before its worktree is removed (the merge path — `confirmWorkerMerge`), node-pty's exit event fires when the process SIGNALS exit, but the OS releases the worktree's directory handle a beat later. `git worktree remove` then fails ("failed to delete '…': Permission denied") and is NOT idempotent — it can drop the worktree's admin record while leaving the dir on disk, so retrying the same command fails with "is not a working tree". So: attempt the clean git removal once (best-effort), then back it up with the killable filesystem removal (`killableRemoveDir`, card `bd9fc808`), then prune any stale admin record. When nothing holds the dir (merge-gate's no-pty rows) the git removal succeeds and the backstop is a no-op.

Both git ops are BOUNDED (priority reliability fix): a busy/locked worktree dir makes `git worktree remove` HANG INDEFINITELY rather than throw, and boot-reconcile's Pass B calls this DURING daemon boot — so one stuck removal blocked the whole daemon from booting for hours (2026-06-03). They now run through a `block`-timeout simpleGit AND a `withTimeout` race, so the worst case is a BOUNDED failure within ~`GIT_OP_TIMEOUT_MS` — the dir is left on disk for a later GC pass, NEVER an infinite hang. Each `killableRemoveDir` attempt is additionally wrapped in `withTimeout` so an injected test seam that never resolves is still bounded, failing SAFE by treating a never-settling seam as WEDGED (`killed:true`), never as a clean reject — a hang must never be looped, injected or real. Two distinct failure shapes follow: a CLEAN reject (settled, `killed:false` — a transient EBUSY/EPERM handle-lag) gets up to `REMOVE_DIR_CLEAN_RETRY_ATTEMPTS` short, bounded retries in-session (it SETTLES, so it never risks hanging a thread); a KILLED timeout (`killed:true`, genuinely wedged) is NEVER retried in this one call (a fast in-process loop on a hang would be the same bd9fc808 defect again) — the caller (`SessionService`) instead tracks it and retries on a SLOW cadence (once per boot plus a low-frequency background sweep, tens of minutes apart), since most wedges are eventually resolvable.

Card `79b8d8a9`: the git removal uses `-f -f` (not a single `--force`), git's own documented override for a LOCKED admin record (e.g. the `.git/worktrees/<name>/locked` residue a killed `worktree add` can leave — card `1a858805`). Against a locked record, single `--force` refuses outright ("cannot remove a locked working tree"); the filesystem backstop still deletes the directory anyway, but the trailing `prune` SKIPS locked records BY DESIGN, so the admin record survived forever and the next `worktree add` at that path failed with "is a missing but locked worktree" — a real, verified bug `-f -f` closes. This is judged SAFE, not merely convenient, because the second `-f` adds NO destructive capability beyond what the filesystem backstop already exercises today: git's SINGLE `--force` already deletes tracked-dirty and untracked files on an ordinary (non-locked) worktree (the second force bit only ever gates the LOCKED/corrupted-HEAD check), and even when the git removal fails for ANY reason, the filesystem backstop runs UNCONDITIONALLY and deletes the directory's contents regardless of dirty/uncommitted state — so a locked-and-dirty worktree already loses its uncommitted files today, via the backstop, before this change. `-f -f` does not create a new way to lose work; it only makes git's own admin bookkeeping match what the backstop already does to the filesystem, closing the ghost-record gap.

## Do not

- Do not retry a KILLED (wedged) removal in a fast in-process loop — that is the bd9fc808 defect again; hand it to the caller's slow-cadence retry instead.
- Do not treat `-f -f` as adding new destructive capability — the filesystem backstop already deletes dirty/untracked content unconditionally; `-f -f` only brings git's own admin bookkeeping in line with what already happens on disk.
- Do not skip the `killableRemoveDir` backstop after a failed git removal — the git removal is not idempotent and can leave the admin record dropped while the dir remains on disk.
