# 4fa36502 — alert when the mainline moves without a Loom landing (a tripwire, not a sandbox)

## Do not

- Do not turn this alert into a refusal, a merge block or a retry. It is DETECTION only: the merge always proceeds exactly as it would without the check.
- Do not let an error, timeout or cap in the check reach the merge. It is FAIL-OPEN: any failure logs `[mainline-watch] check skipped (fail-open)`, files nothing, and leaves the watermark alone.
- Do not advance the watermark after a landing whose own check did not complete. The check returns `false` on failure and the hook then skips the advance, so an unverified move stays visible to the next landing's check.
- Do not read this as protection against an adversarial worker. See "What it cannot detect".
- Do not scan unbounded. The `W..tip` walk, the reflog read and the `refs/heads/loom/` scan are capped (`MAINLINE_RANGE_CAP`, `MAINLINE_LOOM_REF_CAP`); past a cap the outcome is ONE low-severity "unverifiable" event and the watermark advances. THE STORE/RETAIN RULE (card `05e7f246`): a verdict that cannot be re-derived more cheaply next time (a range/reflog over the cap) STORES W; a verdict a retry might resolve (a deadline, a read error) leaves W untouched.
- Do not add a git call to `git/mainline-watch.ts` that bypasses `canonicalGit` (the module is in `canonical-git-helper-guard.mjs`'s STRICT list).
- Do not alert on first sight of a (project, repoKey, branch): the first check initialises the watermark silently.
- Do not store the watermark in a new table or column; it is an `app_meta` key, `mainline-watermark:<projectId>:<repoKey>` (JSON `{branch, sha}`), purged by `deleteProject`.
- Do not treat a `loom/*` tip reachable from the mainline as a bypass unless the BRANCH'S OWN reflog shows it CREATED that commit object (`isAuthoredBranchReflog`): `commit`, `cherry-pick`, `am`, a non-fast-forward `merge`, or a `rebase (finish)` whose tip differs from its `onto` sha. A fast-forward (`merge <x>: Fast-forward`, also what Loom's own `mergeMainIntoWorktree` does) and a no-op rebase (`tip == onto`) only MOVE the ref onto a commit the mainline already had, and a worker spawned with no commits has a tip that IS a mainline commit (`createWorktree` cuts off the current HEAD). The test is "a new object was made", not "the ref moved". A missing branch reflog reads as "cannot tell", not a hit.
- Do not let a cap on the loom-tip signal (`MAINLINE_LOOM_REF_CAP`, the rev-list range, `MAINLINE_LOOM_TIP_CHECK_CAP` applied AFTER trailered tips are dropped) turn the whole move "unverifiable": it skips ONLY that signal (`loomTipsSkipped`), and the reflog-raw-write classification still runs.
- Do not apply the reflog cap to the whole reflog. It bounds the window after W; only a window that fills up WITHOUT reaching W is "unverifiable" (the real repo's main reflog has thousands of entries).
- Do not advance the watermark after a landing unless the landed commit's first parent is the tip the check verified; a move in the window stays catchable.
- Do not spawn one git process per candidate tip: all in-range tip messages are read in one `git log --no-walk` call, and the authored-tip reflog check is capped (`MAINLINE_LOOM_TIP_CHECK_CAP`).
- Do not advance the watermark after a BATCH landing by the first-parent rule (a batch ff lands several commits): advance only when the ff result is known ok with something landed, the checked tip equals `baseMainSha` (the sha the batch was cut from, which `fastForwardCanonicalMain` requires HEAD to still be), AND the checked tip is an ancestor of the landed tip (fail-open ⇒ no advance); set W to the landed tip. A move between the check and the ff forfeits the batch and is never absorbed. (card `59d2577a`)
- Do not let the BOOT path absorb an alert: an alerting boot verdict files the durable event (`source:"boot"`, empty manager id) but does NOT store W, so the next landing's check re-detects the same move WITH a manager to nudge (one event at boot + one at that landing is accepted). A clean or unverifiable boot verdict stores W. The boot pass takes no repo guard (its store is a compare-and-set) and is a fire-and-forget kick after `app.listen()`. (card `59d2577a`) It is filed ONCE per move and READ by a manager, see the next three bullets (card `05e7f246`).
- Do not run a check without an AGGREGATE deadline (`mainlineDeadlineMs`, 4 × the per-call git timeout, max 30s, on the monotonic `performance.now()` clock; card `0eb7ff27`): each call is bounded by min(per-call timeout, time left), and when the time left is what bounds it the TIMER ITSELF rejects with `MainlineDeadlineError` (never infer the cause from the clock afterwards). Past the deadline: a deadline before the reflog/range reads finish, or a hung head/facts reader (raced in the service), is a fail-open skip — W untouched, so the move stays catchable — never an "unverifiable" store. A deadline DURING the loom-tip signal skips only that signal (`loomTipsSkipped` + `loomTipsDeadline`) and a raw-write alert still files; but any verdict short of an alert then also fails open (W untouched), because the loom-tip signal is the only one that catches a bypass whose reflog message looks porcelain (`merge loom/x: Fast-forward`, a forged `update-ref -m`). A deadline error must never be swallowed as `watermarkMissing` or a rewind.
- Do not read the watermark-resolves and W-is-an-ancestor-of-tip checks from an EXIT STATUS (`rev-parse --verify --quiet`, `merge-base --is-ancestor`): simple-git's `raw()` resolves a non-zero exit with empty stderr as success (bc2240d7), so a real rewind read `forward=true` and a dangling W read "present" — `rewind-raw-write` and `watermarkMissing` were unreachable. `readMainlineFacts` reads the rev-parse OUTPUT sha (empty ⇒ missing) and routes ancestry through `isAncestorCommit` (merge-base OUTPUT; ONE helper, the runner is a parameter so the deadline-bounded `run` is used). (card `864bdd63`)
- Do not let any derived fact short-circuit the range read or the loom-tip scan: only the explicit cap and deadline paths may skip them. An early `if (!facts.forward) return` (once `forward` became real) made a divergent bypass with a porcelain-looking message (`update-ref -m "merge loom/x: Fast-forward"` onto a worker tip cut before main advanced) read "explained" and store W with no event; `W..tip` is well-defined for a divergence, so the scan runs and the classifier decides (an owner `reset --hard` backward has an empty `W..tip`, an amend has a porcelain message and no loom tip: both stay silent). A `rewind-raw-write` alert names the tip as its suspect. (card `864bdd63`)
- Do not classify an ERROR from those two reads (per-call timeout, spawn failure, deadline, an externally killed child that simple-git reports as empty success) as missing, rewound, unverifiable or "explained": every error propagates out of `readMainlineFacts`, `checkMainlineMove` returns null and W is untouched. Storing W there absorbs the move (a timed-out rev-parse used to store as "unverifiable"; a timed-out merge-base used to set `forward=false`, skip the loom-tip check and store as "explained"). (card `864bdd63`)
- Do not read the authored-tip reflogs one `reflog show` per tip: ONE `git log -g` over all candidate refs (per-branch by the `%gD` selector, matched to the candidate ref by EXACT equality), falling back to the exact per-branch reads only when that shared read fills its own cap (`mainline-watch-spawns.mjs` counts spawns).
- Do not use `git reflog show` as evidence of WHICH WORKTREE moved the ref. It records none (measured, below).
- Do not file a boot alert twice for the same move: the `app_meta` marker `mainline-boot-alerted:<projectId>:<repoKey>` (JSON `{branch, from, to, evidence, suspectShas, nudgedAt}`) holds the move's `(from, to)`; a boot pass that finds the same pair files nothing, a new `to` files again. The marker is dropped ONLY when it is DELIVERED (`nudgedAt` set) and W is stored, when a landing's own nudge told the manager, when main is back on W with a different tip than the alerted `to` (the move was UNDONE), and by `deleteProject`. An UNDELIVERED marker is NEVER dropped by a later `store()` of W (a non-alert landing verdict would otherwise absorb an alert nobody has read). Three boot passes over one unhandled move ⇒ ONE event. (card `05e7f246`)
- Do not leave a boot alert as an event nobody reads. THE READER is the project's live MANAGER(S), told as an ADDRESSED DIRECTIVE (full from/to shas, the exact `git log --oneline <from>..<to>` and `git reflog show <branch>`, and "ask the owner whether it was theirs"), via ONE helper, `SessionService.deliverPendingBootAlerts(projectId)`, with exactly TWO callers: the boot check right after it files (managers already up), and the ONE chokepoint every manager spawn path crosses, `onOrchestrationMcpFirstSeen` (the gateway calls it on a session's FIRST `/mcp-orch/` contact, `PtyHost.markMcpSeen` newly true): fresh, resume, fork, profile-derived `startNew` and a recycle successor all mount that surface, so none has its own call. Deliberately excluded: a manager whose orchestration MCP never connects (it never reads anything anyway). The text is `mainlineMovedNudgeText` (also used by the landing nudge): never a second copy, never per-site logic. GAP, named on purpose: a project that never has a live manager stays event-only until its next landing. (card `05e7f246`)
- Do not claim the delivery by read-then-write, and do not let the claim outlive its durable record. `db.compareAndSetMeta` (one `UPDATE … WHERE value = <expected>`) sets `nudgedAt`; delivery is `enqueueDurableMessage` (its `session_message_queued` row is written in the SAME synchronous step), NEVER `enqueueDurableNudge` (it defers up to 9s on an MCP wait, and a daemon death in that window would leave a claimed alert with no record). A throw while enqueueing hands the claim back (compare-and-set to unclaimed), so a claimed marker never has no record (at-least-once: a manager enqueued before the throw may be told again). ONE predicate (`dropBootAlert`) governs EVERY marker delete: a marker goes only once DELIVERED, or when the check's baseline IS the marker's own `from` (tip==W with `from == tip` is a true undo; a landing alert about the SAME window re-reported it); `store()` alone never drops an undelivered one, and a marker whose `to` W absorbed unread stays. Only the caller that wins delivers, to EVERY live manager of the project, so two paths racing on one marker (resume vs the boot check, or a run interleaved inside another's read→claim window) deliver exactly once. The helper never throws into a spawn/resume/boot path. (card `05e7f246`)
- Do not classify a watermark that git POSITIVELY reports missing as "unverifiable" and store it. "Positively" is `cat-file -t <W>` REJECTING with git's own not-found message after an empty `rev-parse`, run with `LC_ALL=C`/`LANGUAGE=C` pinned (a localized or reworded message would otherwise fail open FOREVER: W stays missing, every check rethrows, nothing is filed; only the probe is pinned, canonicalGit's other calls stay env-less; the pinned env is built by `localReadGitEnv` (bounded.ts), which also STRIPS the transport family `GIT_ASKPASS`/`SSH_ASKPASS`/`GIT_SSH(_COMMAND)`/`GIT_PROXY_COMMAND`/`GIT_TEMPLATE_DIR`/`GIT_CONFIG_COUNT`, because an EXPLICIT env makes simple-git's unsafe guard throw on those (VS Code's terminal sets `GIT_ASKPASS`), which would make the probe a read error on every call and blind the repo forever; a local `cat-file` never authenticates, so they cannot matter to it); empty output alone is NOT proof (simple-git resolves an externally killed child, e.g. the OOM killer, as success with empty stdout), and an empty `cat-file` or a `commit` answer is a read error: a mainline commit never becomes unresolvable in normal operation, so it is ALERT-class (severity high, evidence `watermark-missing`, reason "watermark commit no longer resolvable (possible reflog expire/prune or force-rewrite)"). At BOOT it follows the boot-alert rules (marker-deduped, W untouched, delivered by the helper); at LANDING it files, nudges, then STORES W so the next landing has a fresh baseline (retaining a missing W on the landing path would blind the tripwire for good). A rev-parse/cat-file that did NOT positively answer (timeout, spawn error, an externally killed child) is a read error ⇒ fail open. The nudge for this evidence gives `git reflog show <branch>` and `git log --oneline -20 <to>` (the baseline `<from>` cannot be logged). A `repoPath` rebind used to leave the old W, which read as a (loud, false) missing alert: see the rebind-reset bullet below. (card `05e7f246`)
- Do not leave the watermark or boot-alert marker behind when a repo is rebound or repathed, and do not reset them on anything but a REAL repo change. ONE helper, `Db.resetMainlineBaselinesForRepoChange`, runs from `Db.updateProject` — the single writer of `repoPath` and of the `repos` registry, so it covers platform `project_update`, REST `PATCH /api/projects/:id` (repoPath and registry edits) and any future caller with no per-site call. Per repoKey (`primary` = `repoPath`, else the registry entry's `path`) it compares the old and new path (resolved, trailing separator stripped, lower-cased on win32): an unchanged path keeps W (a no-op rebind must not launder a raw move), a changed or REMOVED key deletes both keys. A reset that dropped a real baseline ALWAYS files one `mainline_moved_outside_loom` event (`source:"rebind"`, `reset:true`, `fromPath`/`toPath`, no nudge), so a wiped baseline is auditable rather than silent: LOW normally, but HIGH when the marker it deletes is UNDELIVERED (`nudgedAt` unset; the boot-alert never-drop rule above): that event carries the marker's `branch`/`from`/`to`/`evidence`/`suspectShas` as `discardedAlert` and a reason saying an unread mainline alert for the old repo was discarded by the rebind. A delivered marker or none stays low. Readers of the kind (checked): only the two writers, the durable-kind set/type map, and a human-configured event trigger on that kind; nothing counts, nudges or classifies it by `source`, so a rebind row is never a landing-path alert. Reachable only from the human REST PATCH and the LOOM_DEV Platform Lead's `project_update` (elevated); the loom-setup and loom-orchestration surfaces have no `repoPath`/`repos` writer, and `db.ts`'s trust-boundary note forbids adding one. Residuals by design (both need a human or elevated surface; no per-path watermark storage): a path-only comparison cannot see that a different path is the same repo, so an elevated caller could repoint to an alias and reset W; and a rebind A→B then B→A resets the baseline twice and re-seeds W at A's current tip, so a raw move made before the round trip is absorbed with only rebind events in the trail. (card `84ea9f67`)
- Do not absorb a loom-tip CAP skip silently: when `loomTipsSkipped && !loomTipsDeadline` and the verdict is not an alert, W is still stored (a busy repo must not become permanently unverifiable) but ONE low `unverifiable` event names it ("loom-tip signal skipped (cap)"). The residual (a forged porcelain reflog on a cap-tripping repo) stays by design. (card `05e7f246`)

## The threat, and what Loom already had

A worker's worktree shares the canonical `.git` (see `356538ef-canonical-git-isolation.md`), so it can `git update-ref refs/heads/<main> <sha>` and bypass the merge gate. Loom persisted no "last Loom-landed main sha": `project_merge_gate_state.last_pass_sha` is written only by a PASSING gate (ungated landings record a count only), `tasks.merged_sha` is per task and abbreviated, and the `merge_done` event carries no sha. The Loom trailers on every landing (`Loom-Worker-Branch`, `Loom-Landed-Tip`) make git history a complete ledger of landings, but the latest trailer commit alone hides a bypass under a later legitimate landing, so a high-water mark is needed.

## Design

- **Watermark W** per (project, repoKey): the canonical branch tip Loom last saw or produced. Advanced after a SUCCESSFUL solo landing (`advanceMainlineWatermark`, right after `mergeBranch`, inside the repo guard), after a SUCCESSFUL batch landing (`advanceMainlineWatermarkForBatch`, see the Do-nots) and after every completed non-boot check (`store()` is a compare-and-set: it never overwrites a value another writer changed since the read).
- **Check** (`checkMainlineMove`) runs inside the repo guard just before the solo squash trusts main's tip, and (card `59d2577a`) at the end of the batch's passing `runGate` closure — still inside the guard, immediately before `runBatchedMerge`'s fast-forward. `checkMainlineMovesOnBoot` runs it once per (project, repoKey) at daemon boot (async, after listen, no guard, `source:"boot"`), catching a move made while the daemon was down.
- **Strong signals only** (any one alerts):
  1. `reflog-raw-write`: a reflog entry newer than W has an empty or non-porcelain message AND the first-parent range `W..tip` holds a trailer-less commit. A bare `git update-ref` writes an empty message.
  2. `loom-branch-reachable`: a trailer-less `refs/heads/loom/*` tip is reachable from tip but not from W. Squash and cherry-pick landings never put a worker tip into main's history; a bypass that moves main onto the worker's tip does.
  3. `rewind-raw-write`: W is not an ancestor of tip and a raw reflog entry exists.
- **Silent** (explained): a human commit / merge / pull / reset / rebase / fetch (porcelain messages, measured: `commit: …`, `commit (amend): …`, `pull …: Fast-forward`, `merge <x>: Fast-forward`, `reset: moving to …`), Loom's own landings (trailers), and Loom's human-REST `GitWriter.commit` (a plain `git commit`).
- **Alert** = one durable `mainline_moved_outside_loom` event (in `DURABLE_AUDIT_EVENT_KINDS`, `detail.projectId` stamped) + one `[loom:mainline-moved]` warning nudge to the confirming manager. The watermark advances after the alert, which is the dedupe.
- **Unverifiable**: the same event kind with `severity:"low"`, `unverifiable:true`, and no nudge: a range/reflog over the cap, or a loom-tip cap skip. (A positively missing watermark is an ALERT, see the Do-nots.)

## What was measured (git 2.47.0.windows.2, real repos)

- The shared `logs/refs/heads/<main>` records old/new sha, committer and a free-text message, and NO worktree identity. The moving worktree's own `logs/HEAD` records nothing about an `update-ref`.
- A bare `update-ref` writes an EMPTY message; `update-ref -m "commit: x"` is fully spoofable; `git -C <canon> commit` from a worker is byte-identical to a human commit.
- `git branch -f <main>` and `git push . HEAD:<main>` are refused by git while main is checked out in the canonical worktree.
- The reflog is worker-writable: `git reflog delete <ref>@{n}` removes an entry silently.
- After a worker `update-ref`, the canonical index/working tree is stale (staged reverse changes); a human can produce that too.

## What it cannot detect

A worker that forges the reflog message AND removes its `loom/*` branch before the check (pinned in the test as the documented limit, `(S5)`); a worker that edits or deletes the reflog AND has no branch reachability; a worker committing through `git -C <canon> commit`; a bare canonical repo (no reflog by default); a human's own raw `update-ref` (a documented false positive of signal 1). It is a tripwire.
