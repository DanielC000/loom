# 44d45f81 — raised `DEFAULT_PORT_REPORT_TIMEOUT_MS` after a live production regression

## Narrative

`DEFAULT_PORT_REPORT_TIMEOUT_MS` bounds how long the supervisor waits for either the reported bound-port stdout line (see `parsePortReportLine`) or the child's own exit, on the self-reporting `--port 0` capability probe embedded in the FIRST spawn attempt of an instance's life (card `4e0df6ce`) and any later attempt after `port` goes back to `null` (a `stop()`/restart give-up).

Card `44d45f81` RAISED this from the original 5,000ms: card `4e0df6ce`'s original reasoning ("a capable `serve` reports essentially at bind time") was measured FALSE under real host contention and caused a live production regression — two live, functioning `serve` attempts abandoned on the FIRST boot after deploying that constant.

Measured directly against the REAL installed binary (never the fixture, which reports instantly and so cannot exercise this bound at all — same family as this project's standing real-spawn rule): quiet host, n=8, 765-836ms; under SYNTHETIC CPU load oversubscribing 16 logical cores 18x, n=6, 2442-3557ms; oversubscribing ~2.5x (40 workers), n=9 across two batches, 975-7942ms — several runs already past the OLD 5,000ms bound. This synthetic load is CPU starvation, a stand-in that reproduces the SAME CLASS of failure on demand — it is NOT a measurement of the actual production condition (a fleet-wide restart doing ingest + project registration, which is I/O- and child-process-contention-heavy, different IN KIND, not just degree). Do not read the percentiles above as the production distribution; treat them as a documented floor on how bad this gets, with real reason to expect I/O contention could push higher.

A byte-level trace under that same synthetic load showed essentially ALL of the elapsed time lands BEFORE the child writes its first byte (module load + graph-store open); the gap from first byte to the report line itself was consistently under 100ms — codescape is SILENT from spawn until it reports, never chatty-but-stalled. That is the deciding fact for shape: an idle-reset bound (reset on any child output) is indistinguishable from an absolute bound for a silent child — it buys nothing — while an idle-reset bound WOULD be actively wrong if codescape ever became chatty-but-never-reporting (steady startup logging, bind never completing), since idle-reset alone never fires against a live stream of unrelated output. Given the measured data says the child is silent, the simpler absolute bound is the correct choice, not a cheaper stand-in for the more elaborate one.

Sized generously (30,000ms) rather than tightly against the measured synthetic ceiling (~7.9s), given the CPU-vs-I/O gap above: the cost of an over-long bound is a slower give-up on a genuinely dead child (already handled by the restart ladder), while the cost of a too-short one is the exact regression this card fixes. Deliberately NOT mirroring the short already-alive-server probe bounds elsewhere in this file (`DEFAULT_VERSION_PROBE_TIMEOUT_MS` et al.) — those probe a server that's already up and answering fast; this one waits out a COLD START, a fundamentally different cost that scales with host contention far more steeply.

Card `44d45f81` DoD-3: repeated `spawnServeSelfReporting` timeouts DO feed the give-up arithmetic (each abandoned attempt calls `scheduleRestart(false)`, never "healthy") — a slow-but-genuinely-broken host CAN still reach the give-up path, this raised timeout does not make that structurally impossible, only much harder to reach. With this bound at 30,000ms and the default `DEFAULT_RESTART_BACKOFF_MS` (6 entries), give-up via backoff exhaustion now needs 7 consecutive attempts that EACH individually exceed 30s — worst case ~7*30s + the backoff sum (1+2+5+10+30+60=108s) ≈ 318s (~5.3 min) of sustained badness, versus ~143s (~2.4 min) at the old 5s bound. That is the DELIBERATE tradeoff: a transient slow start now succeeds on the FIRST attempt instead of ever entering this path at all (closing the production regression); a process that is genuinely, permanently unable to report still reaches the same loud "needs a human" diagnostic, just after a longer, bounded wait — never silently stuck (this only changes HOW LONG until give-up, never WHETHER it fires). Unmeasured against a real production host under real sustained badness (only synthetic CPU-contention data exists) — do not assume this arithmetic transfers 1:1 to a real crash loop.

## Do not

- Do not read the synthetic-load percentiles (765ms-7942ms) as the real production distribution — they are a documented floor, not a ceiling; real I/O contention could push higher.
- Do not lower this bound back toward 5,000ms without re-measuring against the real installed binary under real contention — the original 5s bound caused two live, functioning `serve` attempts to be abandoned on first boot.
- Do not switch to an idle-reset bound — codescape is measured silent from spawn until its report line, so an idle-reset bound would buy nothing over the current absolute bound.
