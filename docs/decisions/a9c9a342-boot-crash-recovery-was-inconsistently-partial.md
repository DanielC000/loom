# a9c9a342 — boot crash-recovery was inconsistently partial: a sticky dead-stamp excluded healthy workers, and a solo manager never got a resume attempt

## Narrative

Commit `a9c9a342c0` ("fix(daemon): boot crash-recovery is inconsistently partial — a 2nd crash marked one project's live sessions "dead" and skipped them while another project's lane auto-resumed") fixed two related gaps in `deriveCrashOrphanedWorkers`/`deriveCrashOrphanedManagers` (`orchestration/crash-orphaned-workers.ts`), found from board evidence: `"[watch] marked N session(s) dead"` then an Orchestrator + its Web-Designer worker sat exited-and-unresumed while a sibling project's identical shape came back clean.

**Gap 1 — a sticky `resumability:'dead'` stamp was trusted outright.** `deriveCrashOrphanedWorkers` used to gate recovery on the cached `resumability` column instead of a live check. `resumability:'dead'` is written by two places — this module's own transcript-missing branch, and `sessions/liveness.ts`'s `sweepDeadSessions` (the boot sweep AND the continuous `watchClaudeProjects` chokidar watcher, debounced 1500ms off ANY `.jsonl` unlink anywhere under `~/.claude/projects`) — and it is STICKY: nothing ever clears it back once set except a brand-new `setEngineSessionId` capture. The debounced watcher re-sweeps EVERY resume candidate on an unrelated file event, so a transient TOCTOU miss (Claude's own atomic rewrite of a DIFFERENT session's transcript, an AV/indexer lock, a concurrent `--resume` spawn touching the same directory tree) can permanently stamp a perfectly-healthy worker `dead` at some point during normal operation — long before any crash. On the NEXT crash, the function used to trust that stale stamp and silently exclude the worker with no logged reason. Because `CrashOrphanedWorker`s are grouped BY MANAGER downstream (`SessionService.recoverCrashOrphanedWorkers`), a manager whose ONLY worker got excluded this way never even got a resume ATTEMPT — not because the manager itself was unresumable, but because it had no surviving worker to ride along on. `resume()` (`sessions/service.ts`) never trusted the cached column to begin with — it always re-verifies live — so the fix makes `deriveCrashOrphanedWorkers` use that SAME real-time source of truth instead of a second, staler one: a cached `dead` stamp is now RE-VERIFIED (via `engineTranscriptExists`) rather than trusted, self-healing (`db.setResumability(w.id, "resumable")`) when the transcript actually exists.

**Gap 2 — a manager crash-orphaned in its own right, with no surviving worker to ride along on, never got a resume attempt at all.** Because `recoverCrashOrphanedWorkers` groups its resume targets BY MANAGER (keyed off `orphanedWorkers`), a manager whose entire worker set was legitimately excluded (all landed, all recycled, all archived pre-crash) never got a resume attempt — even though it was just as much a live/starting victim of the SAME crash as any manager that happened to still have a worker. The fix adds `deriveCrashOrphanedManagers`: every manager/platform row in `recovered` not already covered by `orphanedWorkers` gets ONE independent attempt, via `SessionService.recoverCrashOrphanedWorkers`'s `soloManagerIds` option.

## Do not

- Do not trust a cached `resumability:'dead'` stamp outright when deriving crash-orphaned workers — it is sticky and can go stale from an unrelated watcher race; re-verify live (`engineTranscriptExists`) and self-heal when the transcript is actually present.
- Do not gate a crash-orphaned MANAGER's resume attempt solely on it having a surviving crash-orphaned worker — a manager whose whole worker set is legitimately excluded is still itself a crash victim and needs its own independent resume attempt (`soloManagerIds`).
