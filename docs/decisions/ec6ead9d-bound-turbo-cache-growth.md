# ec6ead9d — bound the main checkout's turbo cache growth (native eviction + a non-writing deploy force)

## Narrative

The owner reported their GitHub checkout had grown a lot. Measured: `.turbo/cache` at the main checkout was ~19.8GB (28,775 files), never evicted, growing ~6-13GB/month and accelerating (by file mtime: 2026-06 0.23GB, 07 2.98GB, 08 2.83GB, 09 7.53GB, 10 6.21GB in half a month). `.git/objects` for comparison was 0.70GB.

Investigation found two independent, additive causes:

1. **Turbo 2.x shares ONE local cache directory across every git worktree of the repo.** Confirmed live via `turbo build -vv`, which printed `Using shared worktree cache at: <main checkout>\.turbo\cache`, `is_shared_worktree=true`. So every build anywhere in the fleet — the deploy rebuild, the lead's own `pnpm build`s on main, every worker's own gate self-check / dev build in its own isolated worktree — writes into this one directory. This is the dominant source: it accumulates regardless of which producer writes.
2. **The installed turbo (2.9.14) has zero cache eviction unless explicitly configured.** Confirmed by reading the real cache contents read-only: the oldest file dated back to 2026-06-03, the day it seems the cache first existed in its current form — every entry ever written was still there.
3. **Secondary, avoidable waste:** the deploy build's own "build" step (`restart.ts` › `deployBuildSteps`, STEP 2) passed `--force` directly to turbo. Per `turbo run --help`, `--force` is equivalent to `--cache=local:w,remote:w` — it disables the cache READ (the load-bearing invariant: a deploy must always do a real compile, never replay a stale cache hit) but leaves the WRITE on. Every deploy therefore wrote a fresh cache entry *the deploy itself* never benefits from (it always forces past its own future reads) — but it is NOT true that nothing ever reads it back: per `24f53a72`'s own record, a LATER, non-forced build elsewhere (a plain `pnpm build`, a worktree's own provisioning build) CAN cache-hit a forced deploy's entry, since `--force` only ever bypassed this ONE invocation's read, never the entry's eligibility for anyone else's. A SAME-hash deploy (no source change since the last one) overwrites that one entry in place rather than growing the count — the growth driver is a source change between deploys, same as any other producer — but either way the entry, once written, never got evicted.

## The fix

**Primary — turbo's own native local-cache eviction**, not a hand-rolled prune script: root `turbo.json` now declares `cacheMaxAge: "14d"` and `cacheMaxSize: "5GB"`. Per turbo's own documentation, both run automatically, in a background thread (non-blocking — doesn't slow the task graph), at the start of every `turbo run`; when both are set, age-eviction runs first, then size-eviction on what remains. This bounds growth regardless of which producer wrote the entry (source 1 above), and needs no custom `fs.rm` retry logic at all — it is turbo's own internal mechanism, so decision `bd9fc808` (killable removal, never an in-process retry loop on a wedged `rm`) never comes into play; there is no hand-rolled removal to guard.

Values: `cacheMaxAge: "14d"` — most of a cache's hit value is recent; two weeks keeps the fast path warm for active work without keeping months of dead entries from abandoned worktrees. `cacheMaxSize: "5GB"` — a hard backstop on disk use regardless of age, since the owner's concern was disk, not staleness per se. Both were the owner/manager's explicit call (card `ec6ead9d`), not derived from any formula — revisit them if either turns out too tight (frequent evictions of still-useful entries) or too loose (growth resumes).

**Secondary — the deploy build's own wasted write.** `deployBuildSteps`'s "build" step now passes `--cache=local:,remote:` instead of `--force`. Per turbo's `--cache` syntax, an empty mode (`local:` with nothing after the colon) turns that cache source off entirely — neither read nor write. This was verified empirically, not assumed, in an isolated fixture monorepo (own temp dir, own `--cache-dir`, never the real shared cache): (1) a first build populates the cache (cache miss, executes); (2) a second ordinary build confirms a cache HIT (`cache hit, replaying logs`, `>>> FULL TURBO`, the build script's own real side effect — an incrementing exec-count file — did NOT advance); (3) a third build with `--cache=local:,remote:` genuinely RE-EXECUTES (`cache bypass, force executing`, no `FULL TURBO` banner, the exec-count file DID advance) — proving it still defeats the read exactly like `--force` did; (4) the cache directory's file count and every existing file's mtime were unchanged after that third build — proving it writes nothing, unlike `--force`.

## Do not

- Do not assume `cacheMaxAge`/`cacheMaxSize` block or slow a build waiting on disk I/O — turbo documents eviction as running in a background thread, not inline with the task graph.
- Do not revert the deploy "build" step's flag back to `--force` without re-running the SAME empirical proof this card ran (populate → confirm ordinary hit → confirm the candidate flag genuinely re-executes with no `FULL TURBO`/`cache hit, replaying` banner → confirm it writes no new cache file) in an isolated fixture. The two flags are not obviously equivalent from `--help` text alone, and nothing else in this codebase checks this at build time.
- Do not read `cacheMaxAge`/`cacheMaxSize` as scoped to this repo's deploy path alone — they bound the ONE shared `.turbo/cache` directory at the main checkout that every worktree on the whole daemon reads and writes. A value tuned for "the deploy build specifically" without accounting for gate/worker/dev traffic will mis-size.
- Do not delete the pre-existing ~19.8GB cache directly as part of landing this fix. Turbo's own eviction fires at the start of ANY `turbo run` in ANY checkout that carries this config — not just "after this merges to main." A pre-merge WORKER WORKTREE on this very branch triggers it too: the daemon's own worktree-provisioning build (`createWorktree`, best-effort install+build) runs `turbo build` against the branch's checked-out turbo.json, which already carries `cacheMaxAge`/`cacheMaxSize`, against the SAME shared `.turbo/cache` every worktree of this repo reads and writes — confirmed live (card ec6ead9d, follow-up incident): the cache dropped from ~19.8GB to ~5.1GB from exactly this path, before the card ever merged. **Holding the merge does NOT hold this — the config change is live, host-wide, the moment ANY provisioned worktree on a branch carrying it runs a build, which can happen before a human ever approves anything.** An owner-gated change to SHARED HOST STATE (not just this repo's own checked-in tree) cannot be gated by the merge gate at all; it needs its own precondition — e.g. not committing the values until the owner has answered, or landing the mechanism without the specific values first — not "hold the merge and assume nothing moves until then."
- Do not test either change against the real main-checkout `.turbo/cache` (it is `is_shared_worktree`-linked from any worktree of this repo, including a worker's own). Every test for this card runs against an isolated fixture with its own `--cache-dir`/own repo root.
