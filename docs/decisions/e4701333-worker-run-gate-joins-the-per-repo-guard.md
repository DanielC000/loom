# e4701333 — a worker `run_gate` self-check now serializes against a same-repo merge gate too

## Narrative

Found live by a Loom lead: the daemon structurally prevents two `merge`-kind gates on one repo (card `92e960d1`'s per-repo admission guard), but nothing prevented a `merge` gate and a `worker`-kind `run_gate` self-check on the SAME repo from being admitted and running CONCURRENTLY. On this project both routes through the `--codex-real-spawn` test family, which serializes on a cross-process file lock (`packages/daemon/test/_codex-real-spawn-lock.mjs`) whose wait budget was explicitly sized on the premise that it never has to cover another holder finishing first — true only WITHIN one gate process (which schedules that family sequentially at pool 1), false across two concurrent gate processes. A lock-wait timeout under that condition would present as a random red on an innocent branch.

THE FIX IS ASYMMETRIC, NOT A SHARED MUTEX: a `merge`-kind entry is blocked by ANY active holder of its `repoPath` — another `merge` (`GateSemaphore.activeMergeRepos`, unchanged from card `92e960d1`) OR a `worker` (`GateSemaphore.activeWorkerRepos`, new) — but a `worker`-kind entry is blocked ONLY by an active `merge` holder, never by another worker. Two workers on the same repo (e.g. two different workers each running their own `run_gate`) stay fully concurrent. `deploy` remains excluded from both maps — a deploy gate runs in the project's canonical repo directly, was not implicated in the motivating incident, and widening further was judged out of scope for this card.

**⚠️ THE FIRST DRAFT OF THIS FIX WAS SYMMETRIC AND WAS A REAL REGRESSION, CAUGHT BY `run_gate` BEFORE MERGE.** It widened `mergeRepoFree` to `gateType !== "merge" && gateType !== "worker"` sharing the SAME single-holder `activeMergeRepos` map for both kinds — which made two `worker`-kind gates on the same repo mutually exclusive too, breaking `gate-history.mjs`'s `(e2e, REAL WRITE PATH, card 3a6f04cc)` fixture, whose own precondition comment states plainly: *"worker1 (the ARM-2 holder) and worker3 (the ARM-3 running-cancel target) both need to be ADMITTED concurrently... cap:2... mirrors every other daemon test that needs cap>1."* Under the symmetric draft, worker3's own `run_gate` op never admitted and its `waitUntil(... "op3 to admit (running)")` timed out at 10s — a genuine `run_gate` FAIL against the worker's own committed diff (`685fedfd`), not a flake. Diagnosed by reading the fixture's own precondition, fixed by splitting the single map into `activeMergeRepos` (merge-only, unchanged) + `activeWorkerRepos` (a `Map<repoPath, Set<holderId>>`, since multiple workers can concurrently hold the same repoPath), and `mergeRepoFree` branches on the entry's OWN gateType rather than checking one shared map both ways. Regression coverage added: `gate-semaphore-concurrency.mjs`'s `(repo-mutex, c2)`, proven RED against the symmetric draft (temporarily reverted via `git checkout HEAD --`, rebuilt, re-run) before the asymmetric fix was restored.

`runWorkerGate` (`sessions/service.ts`) now sets `repoPath` on its `GateDescriptor` (previously omitted — a worker gate never participated in this guard, so it had never needed the field), resolved via the same `resolveRepoByKey(project, worker.repoKey).path` a merge gate already uses, so a merge and a worker serialize on the identical canonical path a multi-repo project's registry resolves either way.

The squash-hold extension (`holdRepoGuardOnExit`/`beginSquash`/`endSquash`) stays merge-only — a worker's `run_gate` never calls it, so its hold on the guard always releases at its own gate settle, exactly like before this card for a merge without a squash extension declared.

## A second, broader mechanism observed live (not this card's scope to fix)

While this fix's own `run_gate` was queued behind two concurrent, unrelated gates (a real merge + a real worker `run_gate`, both on this same project — cap fully saturated at 2/2), one of those two gates (the merge, card `e61deaab`) came back a weaker pass: its FIRST attempt failed on `gate-history.mjs`'s `merge-batch-verification-stamp` scenario, which itself spawns a real merge-batch op needing a `GateSemaphore` admission — with `cap` fully saturated by the two outer gates, that inner op had no slot and the test's own sync-wait budget expired; an isolated retry then passed once the outer contention cleared. This means the hazard is broader than "two gates contend on the codex lock": **any test that itself needs a `GateSemaphore` slot can be starved when concurrent gates saturate the cap** — a strong, well-supported hypothesis (confirmed `concurrentGatesMax=2`; the in-test op admitted late then completing fast; the isolated retry passing), not yet fully confirmed (the sync-wait budget's exact value and proof the delay was spent waiting on admission specifically were not captured). Specimen banked at `~/.loom/workspaces/e4701333-concurrent-gate-starvation/specimen-1-op-5ee5682d-2026-09-22.log`. Same family as card `827f342f` ("gate-history's cancel-settle wait flakes under concurrent gates and rejected a docs-only merge") — this is the SECOND recorded instance, not the first. Separately, the gate's own retry warning ("an order-dependent/cross-test-pollution bug can pass alone and fail in the full suite") misattributes this shape — it sends a reader hunting for test pollution, which is not what happened; worth fixing in the warning's own wording, not in this card's scope. This card's own fix (queueing a worker `run_gate` behind a same-repo merge) is exactly what would have prevented the two-lane saturation observed here — the incident is evidence FOR this fix, not a reason to expand it.

## Amendment (card `eb491463`): a QUEUED merge now also blocks new same-repo workers

The asymmetry above left a worker unblocked by a merge that was merely WAITING, so back-to-back worker self-checks starved a queued merge for 87+ min. `mergeRepoFree` now also blocks a `worker` while a same-repo `merge` is queued. Worker-vs-worker with no merge waiting is unchanged. Full record: `eb491463-queued-merge-blocks-new-same-repo-worker-admissions.md`.

## Do not

- Do not read this as a single shared mutex — it is ASYMMETRIC: `merge` excludes/is excluded by anything; `worker` excludes/is excluded ONLY by `merge`. A "worker takes the same guard as merge" mental model is exactly what produced the regression above.
- Do not merge `activeMergeRepos` and `activeWorkerRepos` back into one map "for simplicity" — the single-holder shape of `activeMergeRepos` cannot represent multiple concurrent worker holders of the same repoPath, which is a real, tested requirement (`gate-history.mjs`'s worker1+worker3 fixture).
- Do not extend this to `deploy` without a fresh card — it was deliberately left out of scope here.
- Do not "fix" `gate_queue`'s `repoContended` field to add a separate worker-specific cause — its existing recompute-from-`mergeRepoFree` logic already reports the correct asymmetric answer for both a queued merge and a queued worker with zero extra code; it was verified correct as-is (card `92e960d1`'s own `@decision` on that field) before this card started.
- Do not treat the broader gate-cap-starvation mechanism above as fixed by this card — it is a separate, still-open hazard (see card `827f342f`'s family); this card's fix reduces its likelihood (fewer concurrent same-repo gates) but does not close it.
