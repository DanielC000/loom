# b472645a — The dev End-user preview is READ-ONLY for everything PlatformView owns

## Narrative

On a `LOOM_DEV=1` install the Platform page offers a "View as: Developer | End-user" toggle that previews the shipping end-user surface. Before this card only the OPERATOR spawn ("Start Platform") was held by `previewOnly`. Measured on the e2e `loomDaemon` fixture — the preview reached by fulfilling `GET /api/platform/home` 200 (the one signal `Platform.tsx` reads) plus `localStorage["loom.platformViewAs"]="enduser"`, with every non-GET `/api/` request intercepted and aborted so nothing reached the daemon — **eight** controls were live, identically under the classic layout and the Atlas node: the auditor spawn (`POST /api/agents/:id/sessions`), the `AgentPromptEditor` Save on BOTH cards (`POST /api/agents/:id`) **and that editor's own Ctrl/Cmd+Enter shortcut**, the cadence create (`POST /api/schedules`), all four Stop buttons (`POST /api/sessions/:id/stop`), and the Atlas Findings tab's Adopt/Dismiss. Card `f437d4e9`'s C5 concern was that the preview must never act on the never-upgraded agent; the auditor spawn was the sharpest hole, because `endUserEdition.auditorCreateOnly` makes `auditorSpawnDisabled()` ignore `live` entirely, so that button was enabled unconditionally.

A Code Review then found a **ninth**, and it is the one worth remembering: Run History's **Resume** (`components/RunHistory.tsx`), firing `POST /api/sessions/:id/resume` — which un-archives AND respawns the previewed home's own session. The end-user edition renders its history sections EXPANDED, so it took no disclosure click to reach. It was missed because the first version of the structural sweep read only `PlatformView.tsx` and `AgentPromptEditor.tsx`: a file-local sweep cannot see a control that lives in a leaf the shell renders but does not itself contain. That is why the sweep is now TRANSITIVE over the import graph, and why the lesson here is about the SHAPE of the check rather than about one missed button.

Why this matters more than "a dev clicked their own dev install": on a dev install `platformHome` resolves the reserved **"Loom Platform"** project while `setupHome` resolves **"Platform"** — two different projects. The Developer view never shows the setup home's agents at all, so the preview is the *only* Platform-page route to them, and `migrateSetupHomeToLead` deliberately returns early under `isLoomDev()`, which is precisely what leaves that operator un-upgraded at role `"setup"`.

**The criterion chosen:** gate a control when its effect is scoped to the previewed (setup) home's own agents, schedules or sessions — i.e. wherever the preview grants a reach the Developer view does not have. That criterion, not an inventory of today's buttons, is what a future control should be judged against.

**Relationship to `@decision 8adccd37`.** That record prohibits the `ViewAsToggle` becoming anything but a pure client-side view switch: it must never be read by, passed to, or wired into a spawn/role/stop REST call. Gating is compatible with it and does not erode it. `previewOnly` *prevents* calls rather than parameterising them; the toggle's value never travels into a request; `Platform.tsx` remains the only decider and hands the shell a plain boolean, which the shell and every leaf below it consume without ever reading the toggle, its persisted key, or browser storage.

**What this broadens.** The rule previously existed only in three code comments (`Platform.tsx`'s `previewOnly` call-site note, `platformEdition.ts`'s `endUserEdition.operatorRole` note, and `PlatformView.tsx`'s `AgentControl.previewDisabled` prop doc), and all three stated the narrow form — don't let the *operator spawn* mint a stray `role:"platform"` session. No record stated the broad form. This record is that broadening, decided by the lead on the grounds that the preview is dev-only and reversible.

**Deliberately NOT gated**, so a later reader does not read these as oversights:

- `<Board projectId>` — its four CARD mutations (create / update / delete / drag-move) are reachable from the preview, and **are ungated on the criterion, not on reachability**: card CRUD writes TASKS, and a task is not one of the previewed home's agents, schedules or sessions. That half of this entry is unchanged.

  ⛔ An earlier version of this record justified it as "the same board is reachable at `/board`, so a gate here contains nothing." **That was false**, and false in the direction that matters: a RESERVED home is not selectable in the project picker (`db.ts`'s `listProjects` filters `reserved = 0`; `lib/activeProject.tsx` documents the consequence), so on a dev install this preview is the ONLY UI route to the setup home's board. The decision did not change; its stated ground did. Do not reintroduce the reachability argument for any reserved-home surface.

  ✅ **The Board subtree's REQUEST actions are no longer ungated — card `edfd8295` closed them** (its own section below). It transitively includes `components/requests.tsx`, whose connected-Requests rail carries "Open request ↗" into the app-root request modal: the answer / permission / credential controls, and the provider's own `markQuestionsRead`-on-open. Those act on the previewed home's own SESSION, which is inside the criterion, so they are now held — at the rail's button and, structurally, inside `useOpenRequest` itself.

  Two of the controls this entry used to name are **not reachable from a board at all**, and the gate deliberately does not touch them: `DismissButton` and `NudgeMgrButton`'s `api.sendInput` render only in `RequestRow`, i.e. in `RequestsInbox` / `RequestHistory` on the /requests page, which `Board.tsx` never mounts. Gating them would be dead code no test could exercise — the same ground on which `AuditorCadenceListSection` is exempt below.

  **Why they were unreachable before that card**, kept because it is the history of a claim that was corrected twice. The original reason given was "no role the setup home hosts on a dev install registers `question_ask`", verified by grep with a positive control — the pattern `"question_ask"` DOES hit `mcp/orchestration.ts` and `mcp/platform.ts`, so it is capable of matching, and returns zero in `mcp/setup.ts` and `mcp/user-audit.ts`. But that home hosts THREE roles on a dev install, not two: alongside the operator (`setup`) and the Workspace Auditor (`workspace-auditor`) it also hosts the **Companion** (role `assistant`), served by `mcp/orchestration.ts` — a router that DOES register `question_ask`. So "setup.ts and user-audit.ts are the routers serving that home's roles" was FALSE, and the zero-hit grep alone never carried the conclusion. What carried it was structural: the assistant branch (`if (role === "assistant") { … return server; }`, `orchestration.ts` ~:2153-2184) returns **before** `question_ask` is registered (~:3946).

  Note the precise shape of that reason, because a looser version is wrong: `mcp/platform.ts` **does** register `question_ask`, and on a NON-dev install the setup home's operator IS role `platform`. That did not reach the residual only because a non-dev install has no preview at all (no View-as toggle).

  **What the four residual triggers mean now.** A dev-install setup-home role gaining `question_ask`; that home being migrated onto the Lead (`migrateSetupHomeToLead` returns early under `isLoomDev()` today); the assistant surface gaining `question_ask` (losing or moving that early return is enough, with no change to any role list); or a manager or worker session existing on that home at all, since neither role returns at the assistant branch. None of them opens a hole any more — the gate holds whether or not a request can exist. They now only decide whether it is **load-bearing or precautionary**, which is why the e2e legs SEED a request rather than wait for one of them: the coverage does not depend on that reachability, in either direction.
- `PlatformFindings` → the shared `SuggestionRow` — the preset-suggestion store is daemon-GLOBAL, not home-scoped, so Adopt/Dismiss from the preview is identical to doing it from any composer popover. Not "acting on the never-upgraded agent".
- `GuidedSetupLauncher` / `SetupWizard` — edition-agnostic, rendered identically in the Developer view, and it creates a NEW project rather than touching this home.
- `AuditorCadenceListSection` / `AuditorScheduleList` — the dev LIST variant. `previewOnly` is passed on the end-user mount only (pinned by `test/platform-edition.mjs`), and that edition's `auditorScheduleVariant` is `"single-form"`, so this leaf is unreachable in a preview; a gate would be dead code no test could exercise.

**How it is held.** Every gate named in the list above is a `previewOnly` boolean threaded down from `Platform.tsx`, hop by hop. One gate is NOT, and the exception is structural rather than stylistic: the Board rail's request actions are held by a React CONTEXT (`lib/previewOnly.tsx`, card `edfd8295`), because the writes they reach are rendered by the APP-ROOT `RequestModalProvider`, outside any Platform subtree, where no prop can arrive however many hops it takes. The DECISION still lives in exactly one place — `Platform.tsx` mounts the provider beside the same `previewOnly` prop — so what moved is the read, not the decider. `PlatformSessionTile` gates through `readOnly` + `lifecycle="none"` + withheld `subPanels` — props `TerminalCard` already has — so the shared card is untouched and `/terminals`, Overview, `SessionView` and Companion are byte-identical. `AgentPromptEditor` takes a `readOnly` that holds the TEXTAREA, not just Save, because the textarea's own Ctrl/Cmd+Enter handler is an independent save trigger. `RunHistory` threads `previewOnly` to each `RunRow`, whose Resume button ORs it in. The cadence form gates the COMPONENT: a `<fieldset disabled={held}>` wraps its controls, so a **form control** added there later is inert even if its author never reads the flag. That is the exact claim — a disabled fieldset disables the form controls it contains, and nothing more; a non-form-control write added there (a plain `<div onClick>`, an anchor, a drag handler) still has to read `held` itself. The per-control `disabled={held || …}` flags stay on top of it, because they are what the structural pin can read and they keep each control's own reason visible at the call site. The component-level gate matters because four of the form's five mutations only render once a schedule exists — exactly the ones a button-by-button gate misses on a home that has none.

**What the structural pin actually covers** (`packages/web/test/platform-edition.mjs`), stated precisely because an overstated coverage claim here is what let Resume through once:

- The gate THREAD, per mount rather than per file: for each of eleven components the flag passes through, every mount must carry it. Per-mount, not a whole-file occurrence count — several components now share the spelling `previewOnly={previewOnly}`, so a count can be satisfied by the wrong mounts entirely.
- Each leaf's own gate expression: the Stop button, the textarea's `readOnly` and the `dirty` fold that gates Ctrl/Cmd+Enter, the Resume button, the tile's three `TerminalCard` props, the `held` flag, and the disabled fieldset.
- A TRANSITIVE WRITE SWEEP over every local module reachable from `PlatformView.tsx`, stopping at declared subtree boundaries. In each swept module it finds: `useMutation(` in every shape (named, destructured, generic); a custom hook wrapping one (`use*Session` / `use*Mutation`, which is how the tile's stop is spelled and which no `useMutation` pattern matches); a raw `api.<write>(` call; a request that bypasses the client entirely (`fetch(`, `navigator.sendBeacon(`); and a module boundary the walk cannot follow statically (`lazy(`, dynamic `import(`). Every site must carry a reasoned entry; a new write goes red, and so does a stale entry.

  The api WRITE members are **derived by a TypeScript AST walk over the `api` object, fail-closed on BOTH sides of the verdict** (card `66b9e590` made the second side fail-closed too — see its own section below): a member is a READ only when it makes a BARE call to one of `api.ts`'s three read helpers (`get` / `getOrNull` / `getErr`) AND every OTHER call it makes is either a BARE call to a global named in a small, reasoned allowlist (`encodeURIComponent`, `String`) or to a declared api.ts function the SAME fixpoint proves request-free; everything else — an unrecognised bare call, a method call named `fetch`, a `new WebSocket`/`new EventSource` — is a write. "Request-free"/"request-shaped" is itself derived as a fixpoint over api.ts's own declared functions (does it reach `fetch`/`guardedFetch`, or a method call named `sendBeacon`?), so a member delegating to `updateTaskReq` or `provisionCompanionReq` is caught without either being named here, while a pure formatter like `errorMessageFrom` is correctly ignored.

  **Both of those properties are corrections of a measured defect, and the figures below are one coherent set, all against the same `api.ts`:**

  | classifier | writes found | missed (vs AST) |
  | --- | --- | --- |
  | open-polarity, windowed regex (round 1) | 67 | 54 — 45% |
  | fail-closed regex (round 3) | 118 | 3 |
  | **AST, fail-closed (current)** | **121** (93 reads, 214 members) | — |

  The open form asked "does it call a known WRITE helper?" and so missed every helper that list never named (`delErr`, `putErr`, `patch`) plus every member delegating to a bespoke per-route function; a planted `api.updateTask(` stayed green. Inverting it fixed 51 of those but left 3, because a REGEX cannot tell a helper call from a method call: `\b(get|getOrNull|getErr)\s*[<(]` also matches `r.headers.get("content-type")`, which is how `vaultRawBlob`, `vaultRawHead` and `questionAttachmentBlob` — each calling `guardedFetch` and NO read helper — classified as reads and sat outside the sweep. The AST distinguishes `get(…)` from `x.get(…)` structurally, and has no slicing window and no comment bleed, so three earlier patches (window removal, comment stripping, a `deepestReadHit` assertion) became unnecessary. The last of those was worse than unnecessary: its own specimen was `vaultRawBlob`, so it had been *encoding* the defect rather than guarding it.

  Four shapes that were GREEN under the round-3 regex and are RED now, each planted as a control: `guardedFetch(url,{method:"POST"})` beside a `r.headers.get(`; `get(…).then(() => post(…))`; a write with a trailing SAME-LINE comment mentioning `get()` (whole-line comment stripping never saw it); and a SHORTHAND member (`updateTaskReq,`), which the line-based parse could not see at all while the member total stayed put — so `reads + writes === total`, which is true by construction, had looked like evidence of exhaustiveness and was not. The real exhaustiveness check is an INDEPENDENT count: the AST's property count against a line scan, which must agree.

  **Shapes this sweep does NOT catch**, stated rather than implied, because an overstated coverage claim here is what let Resume through once: a write reached through an ALIASED binding (`const a = api; a.updateTask(…)`), a DESTRUCTURED client (`const { updateTask } = api`), an optional or bracket call (`api?.updateTask(…)`, `api["updateTask"](…)`), a write performed by a CONTEXT PROVIDER the swept module merely consumes, a write passed IN as a callback prop from a parent outside the swept graph, and a write exported from `api.ts` BESIDE the `api` object rather than in it (see the Do-not on `restartCompanionSession`). The api classifier is AST-based; the per-module write scan is still source-text, and neither is type-aware. It raises the floor on what can be added silently; it is not a proof of absence.

  **Shapes the READ/WRITE classifier (`classifyApiMembers`) does NOT catch**, stated for the same reason, as of card `66b9e590`'s follow-up (its own section below, which closed the one residual this record previously named here — a declared helper's request issued through a method call on the bare identifier `api`, e.g. `restartCompanionSession` calling `api.stopSession(…)`, used to be invisible to `requestShapedHelpers`): a write reached through a method call whose receiver is anything OTHER than the bare identifier `api` — an aliased binding (`const a = api; a.updateTask(…)`), a destructured client, or a receiver that is itself the result of another call — still passes the fixpoint unseen. Narrower than it reads: the classifier only needs ONE true thing about this codebase to hold (every `api.<x>(…)` issues a request, so the receiver name alone is sufficient), and nothing here claims to resolve an arbitrary receiver expression to the `api` object the way a type-aware tool would.
- The boundaries are themselves checked: a boundary naming a path the walk never reaches fails, and removing one makes the walk descend and report that subtree's writes as undecided. `pages/Schedules.tsx` is the one boundary that is a FACT rather than a decision — it is reached only because the shell imports the pure helper `looksLikeCron` from it — so the pin asserts that import list is exactly that one symbol. Import reachability is not render reachability, and that is the form the distinction takes as a check instead of as prose.

- Section 8 (card `edfd8295`) covers the Board rail's request gate, which the sweep structurally cannot: `pages/Board.tsx` is a boundary, so the walk never descends to find those controls. It pins that the provider is mounted in exactly one file and wraps exactly the preview mount; that `useOpenRequest` both reads the context AND returns an inert opener; that the rail's button carries the gate and says why; that `RequestModalContext` has exactly one consumer and never leaves its module (which is what makes gating the funnel sufficient); and that `Board.tsx`'s imports from `components/requests` are exactly the two presentation tags plus that funnel.

`packages/web/e2e/atlas-platform.spec.ts` pins the behaviour per shell with an aborting mutation counter asserting zero requests — including the Ctrl/Cmd+Enter path, a force-click past each disabled attribute (so a control that is merely styled disabled is caught), a seeded exited run for Resume and a seeded schedule for the cadence form's other three controls — against a contrast test on the real end-user edition proving the same write paths DO fire.

## Do not

- Do not re-narrow `previewOnly` / `previewDisabled` to the operator spawn alone. It now holds every write that `PlatformView.tsx` and its own leaves render.
- Do not gate a control by reading the `ViewAsToggle`, its persisted `loom.platformViewAs` key, or browser storage anywhere in `platformEdition.ts`, `PlatformView.tsx` or a layout. `Platform.tsx` decides; everything below receives a boolean (`@decision 8adccd37`).
- Do not gate the session tiles by changing `TerminalCard`. Use its existing `readOnly` / `lifecycle` / `subPanels` props, so `/terminals`, Overview, `SessionView` and Companion stay unaffected.
- Do not gate `AgentPromptEditor` on its Save button alone — the textarea's Ctrl/Cmd+Enter handler still fires the save.
- Do not gate the cadence form button-by-button, and do not remove the disabled `<fieldset>`. Save / Enable / Disable / Remove render only when a schedule already exists, so a home without one hides exactly the mutations a per-button gate would leave open; the fieldset is what makes "a control added here inherits the gate" true rather than merely claimed.
- Do not narrow the write sweep in `packages/web/test/platform-edition.mjs` back to the shell's own file(s). It must stay TRANSITIVE over the import graph: the Resume gap existed because a file-local sweep cannot see a control in a leaf the shell renders.
- Do not replace the api classifier's AST walk with a pattern match, however carefully written. Two regex versions preceded it and both were wrong: the question "does this member issue a read?" is about CALL STRUCTURE, and a pattern cannot tell `get(…)` from `r.headers.get(…)`. Do not invert its polarity back to "does it call a known WRITE helper?" either, and do not hand-list the write members or the request-shaped helpers — derive them.
- Do not treat `reads + writes === total` as evidence the parse saw every member. It is true by construction. The exhaustiveness check is the INDEPENDENT count (AST properties vs a line scan); keep both.
- Do not reintroduce a fixed character window into the import-specifier parsing. A window there silently drops a whole subtree, and nothing else in the suite would notice; the reference-scan differential is what guards it.
- Do not assume the sweep sees every write api.ts can expose. A write exported BESIDE the `api` object (`restartCompanionSession`, api.ts ~:1396) belongs to no object the classifier walks and no `api.<write>(` call matches it. What makes that safe is a separate assertion that every swept module's VALUE imports from `lib/api` are exactly `{ api }` — keep it, and give any new value import from there its own decision.
- Do not add a write anywhere in that transitive graph without either threading the gate and recording a reasoned entry, or declaring its whole subtree a boundary with its reason. Adding it to a list alone defeats the point.
- Do not import a COMPONENT from `pages/Schedules.tsx` into this shell. That module sits in the graph only as the source of a pure helper, and its boundary entry claims it is never rendered; rendering it would make the Schedules page's own schedule CRUD genuinely reachable from the preview.
- Do not re-open the "other calls" side of `classifyApiMembers`'s read verdict to open polarity (card `66b9e590`). A member's other calls must each be a bare read helper, a global named in `PURE_GLOBALS`, or a declared api.ts function the fixpoint proves request-free — never "anything not on a known-write list." That is exactly the shape that let an imported request helper, method-form `fetch`, and `new WebSocket`/`new EventSource` pass silently as reads.
- Do not grow `PURE_GLOBALS` casually. It is reasoned from what today's real read members actually bare-call (`encodeURIComponent`, `String`), not a general allowlist of "obviously pure" globals — adding to it widens what a future member's other calls can get away with without the fixpoint ever proving it request-free.
- Do not mount `PreviewOnlyProvider` outside `Platform.tsx`, nor around the Developer or shipping `<PlatformView>` mount (card `edfd8295`): a second provider is a second decider, and one on the shipping mount holds the REAL end-user surface.
- Do not drop `useOpenRequest`'s inert-opener return, add a second consumer of `RequestModalContext`, or export that context. That hook is the ONE funnel every in-app open-request affordance uses, which is the whole reason gating it is sufficient; the call site's `disabled` is only the visible half.
- Do not thread the Board rail's gate as a prop, and do not gate `DismissButton`/`NudgeMgrButton`. A prop cannot reach the app-root modal's own controls at any number of hops; those two render only in `RequestRow`, which no board mounts, so a gate there is dead code. If either changes, gate it and say so here.
- Do not narrow `requestShapedHelpers`'s `api`-receiver check back to a fixed method-name list. It intentionally does not ask WHICH `api.<x>(…)` a helper calls — every member of `api` issues a request by construction, so the receiver identifier alone is enough, and naming individual methods is exactly the hand-authored-list shape this whole classifier exists to avoid.

## card 66b9e590 — the "other calls" side was itself fail-open; now fail-closed too

The read verdict in `classifyApiMembers` (`packages/web/test/platform-edition.mjs`) already derived the WRITE members fail-closed (see the table above), but the *second* condition it ANDs against — "and makes no other request-shaped call" — was computed fail-OPEN: it only recognised a bare call to a declared-and-shaped helper, or a bare `fetch`. Three shapes slipped through silently as "no other call": a request helper IMPORTED into `api.ts` from another module (not in `declared` at all, so `shaped.has(b)` is false and the bare call is simply dropped); method-form `window.fetch(`/`globalThis.fetch(` (a `PropertyAccessExpression`, and the method check only ever looked for `sendBeacon`); and `new WebSocket`/`new EventSource` (a `NewExpression`, which `callsIn` didn't track at all before this card).

Inverted the same way as the read-helper side: a member's other calls must now each be a bare call to `PURE_GLOBALS` or to a declared, fixpoint-proven-request-free helper — anything else, including a method named `fetch` or either streaming constructor, is a write. `callsIn` now also returns `news` (every `new X(…)` with an identifier callee), and `classifyApiMembers` derives `pureHelpers = declared \ shaped` (disjoint from `shaped` by construction) instead of re-deriving a narrower "is it shaped" test per call.

**Measured against the SAME `api.ts` this record's table is built from: counts are unchanged — 93 reads / 121 writes / 214 members**, because no current read member actually makes one of the three previously-invisible calls; all of today's genuine non-read-helper bare calls in read members are exactly `encodeURIComponent` and `String`, which is where `PURE_GLOBALS` came from. Pinned exactly (not just by the `>=` thresholds already in the file), so a future change that newly crosses one of those shapes shows up as a count change here instead of being silently absorbed.

Four planted, self-contained fixtures (their own `get`/`getOrNull`/`getErr`/`guardedFetch` declarations, so they drive the same fixpoint the real file does) prove the fix, each measured RED under the pre-fix logic and GREEN under the fix before being written as assertions: (a) `get(...)` + an imported helper, (b) `get(...)` + `window.fetch(...)`, (c) `get(...)` + `new EventSource(...)`, (d) `get(...)` + an arbitrary unlisted bare function — (d) is the general fail-closed proof, not just a fourth named shape.

**Follow-up, same card: the fixpoint itself (`requestShapedHelpers`) had a matching residual.** `pureHelpers` is only as trustworthy as the fixpoint that proves a declared helper "request-free," and that fixpoint's own method-call detection only ever looked for a method named `sendBeacon` — so a declared helper that performs its request as a METHOD call on the bare identifier `api` (exactly how `restartCompanionSession` calls `api.stopSession(…)`, and, found by re-measuring once the fix was in, exactly how `workerDiffQuery` calls `api.workerDiff(…)` in its `queryFn`) landed in `pureHelpers` rather than `shaped`. Fixed the same way: `callsIn`'s `methods` entries now carry `{ receiver, name }` instead of a bare name, and `requestShapedHelpers` treats ANY method call whose receiver is the identifier `api` as request-shaped — no need to know which member it names, since every `api.<x>(…)` issues a request by construction. `workerDiffQuery` and `restartCompanionSession` both move from `pureHelpers` into `shaped` as a result; **counts are still unchanged (93/121/214)** because no current api MEMBER bare-calls either of them (checked by grep, not assumed). A fifth planted control, (e), proves this half: a declared helper calling `api.updateTask(...)`, called in turn by a `planted` member that also calls `get(...)` — RED (misclassified read) before this follow-up, GREEN after.

## card edfd8295 — the Board rail's request actions, and why this one gate is a context

The named residual above, closed. The reachable surface was narrower than the residual's own list, and wider than a per-button gate could reach, in opposite directions — both worth stating, because each was a correction.

**NARROWER:** `DismissButton` and `NudgeMgrButton`'s `api.sendInput` are rendered only by `RequestRow`, i.e. by `RequestsInbox` / `RequestHistory`, which live on the /requests page. `Board.tsx` imports `useOpenRequest`, `RequestTypeTag` and `RequestProvenance` and nothing else, so neither control is render-reachable from any board. The residual named them from the MODULE's contents; render reachability is the question that decides a gate, and the two differ here.

**WIDER:** everything the rail does reach is rendered OUTSIDE the Platform subtree. "Open request ↗" calls the app-root `RequestModalProvider`, which marks the row read (`api.markQuestionsRead`) and renders `RequestModal` → `RequestDetail` → the answer / permission / credential control. No prop from `Platform.tsx` can arrive there, at any number of hops — the provider is a sibling of the router in `App.tsx`. So the choice was never "prop versus context, which is tidier": a prop can gate the BUTTON and nothing behind it.

**The gate is therefore two layers, and each holds something the other does not.**

1. The rail's button carries `disabled={previewOnly}` plus a title saying why (`PREVIEW_REQUEST_HELD_TITLE`), read from the context directly in `ConnectedRequestRow` — three hops below `Board`, with no thread in between. This is the layer a user actually reads.
2. `useOpenRequest` returns an inert opener under the same context. This is what holds a control added inside the preview later whose author never reads the flag — the same structural property the cadence form's disabled `<fieldset>` buys, and the reason losing layer 1 in a refactor re-opens nothing. It is sufficient BECAUSE that hook is the one funnel every in-app open-request affordance goes through; `RequestModalContext` having exactly one consumer and never leaving its module is asserted rather than assumed.

Blocking the OPEN, rather than the answer controls, is also what holds `markQuestionsRead` — a write that fires on open with no control of its own, which no per-button gate would ever have covered. The e2e contrast leg records it as a distinct path for exactly that reason.

**Coverage, and what it rests on.** `test/platform-edition.mjs` section 8 holds the structure (above). `e2e/atlas-platform.spec.ts` holds the behaviour: both shells in the preview, plus one real-edition contrast leg. The contrast runs ONCE where test 9's runs twice, deliberately — test 9's pair exists because `previewOnly` is threaded once per LAYOUT, so an over-gate there is per-layout too; this gate is a single provider ABOVE both layouts, so a layout cannot differ from the other on it, and a second leg would re-measure the same boolean.

Each preview leg ends by filing a board card and requiring that write to land. That is DoD-2 (card CRUD stays ungated) and the INSTRUMENT CONTROL in one: a counter that records nothing produces the same empty array as a perfect gate. Measured both ways before being written as assertions — with the context forced to `false`, both preview legs go red on a recorded `POST /api/questions/mark-read`; with it forced to `true`, the contrast leg goes red on the shipping rail's opener being disabled, while the preview legs still pass.

⚠️ The silence is asserted only after waiting for the board's own next poll to land. `toHaveCount(0)` on the modal passes instantly — before a broken gate could even have rendered it — and a fixed sleep would be a guess; the writes a broken gate issues go out synchronously inside the click handler, strictly before that later GET, and `page.route` records in issue order. Without that wait the leg is a tautology, not a control.

## The repaint frame — verified, not a residual

Attaching to a live session in this preview sends a `{"type":"repaint"}` WebSocket frame. This is **allowed by design and carries no input**: `@decision 710a34fa` establishes that the remote `/ws/term` takes no input for an agent session *bar a repaint*, which is a Ctrl-L redraw request and nothing else. So a watch-only tile in the preview sending it is correct behaviour, not a hole in this gate. (Earlier drafts of this record listed it as unverified; it has since been checked against that record and the frame's own handling.)
