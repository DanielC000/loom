# fdfe8a56 — Skip the locked-record cleanup when the failed add's child isn't confirmed dead

## Narrative

Card `fdfe8a56`: `boundedLockedRaw`'s production path (`withTimeoutKillingChild`) only guarantees the child is confirmed dead on its PATH-1 settlement (the "(git child killed)" rejection). Its `giveUpTimer` fallback (PATH 2, "...giving up (hung git child?)") rejects on a bare timer with NO such confirmation — see card `963f69ab` for the discriminator regex. On a PATH-2 `addErr` the add's child may STILL BE ALIVE, so running the destructive `remove -f -f` recovery (see the `1a858805` record) there would race a possibly-still-writing child: clear the dir, then have the still-live add re-create part of it with no admin record — a shape Code Review flagged as newly reachable BY THIS CLEANUP (not pre-existing), probability unquantified. The fix SKIPS the cleanup on PATH 2 rather than risk that race.

A follow-up review of this exact paragraph re-priced the trade against the ACTUAL residue mechanics: an earlier draft claimed `worktreePath` is "per-spawn unique, never reused" — FALSE. `worktreePath` is a pure deterministic function of `taskId` (`taskKey(taskId)`), so a respawn/retry/recycle on the SAME task lands on the IDENTICAL path, straight into the `fs.existsSync(worktreePath)` reuse branch — the residue absolutely CAN be reused into. Traced empirically (real git, not a mock) for both shapes: SKIP leaves the admin record INTACT whenever the child dies without cleanup racing it — a locked-but-otherwise-valid worktree. A later respawn's reuse path works completely normally against it (`locked` only ever blocks `worktree remove`/`prune`, never ordinary git ops run inside the worktree — verified: `reset --hard`/`status` both succeed against a still-locked worktree), and it's not a permanent leak either: `removeWorktree()` clears an intact locked residue on its own, confirmed by direct call. NOT skipping risks the other shape: the cleanup's own `remove -f -f` racing the still-alive add, wiping the admin record while the child keeps writing, leaving `worktreePath` populated but with NO `.git` link at all — confirmed by direct call, a later respawn's reuse branch then throws "fatal: not a git repository" (loud, not silent — the canonical repo's own HEAD stays untouched), but `createWorktree` has no fallback to recover from THIS shape, so that task's respawns stay broken until a human deletes the stray directory by hand.

So SKIP trades a residue that self-heals through `removeWorktree()`'s ordinary lifecycle for one that — only if the race actually manifests — needs a human to notice and clear it, and skipping is what makes that second, worse shape structurally UNREACHABLE via Loom's own code (it can only occur through Loom's own destructive call racing the child; leaving the child alone never produces it). PATH 2 has never been observed firing in this fixture (0/45, 0/65 local trials — an upper bound on those approaches, not a rate, not proof it's unreachable), so this trade is made on the mechanism argument, priced against the TRUE reuse-path behavior rather than an assumed one.

## Do not

- Do not run the locked-record `remove -f -f` cleanup on a PATH-2 (`giving up (hung git child?)`) failure — the add's child may still be alive, and racing it can leave `worktreePath` populated with no `.git` link, which `createWorktree` cannot recover from on its own.
- Do not assume `worktreePath` is per-spawn unique when reasoning about this trade — it is deterministic per `taskId`, so a residue left behind absolutely can be reused into by a later respawn.
