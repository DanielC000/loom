# 24c22912 — `gateBaseBranchHead`'s stability proof is narrower than "matched at capture": three sequential awaits, never one atomic read

## Narrative

A correction to how far `gateBaseBranchHead`'s own stability proof (card `b0ab78d6`, see [[eda70da6-gate-base-re-verification-and-the-toctou-closed-squash-target]]) actually reaches. `preLanded` proves — via `branchContentLandedInCommit` — that the branch's content matched what's landed AS OF `findLandedSquashCommit`'s OWN read, BEFORE `gateBaseBranchHead` is captured, not AT the capture itself: three sequential `await`s run across this window, never one atomic read — `findLandedSquashCommit`'s own read, then `resolveGitRef(repoPath, "HEAD", ...)` for the companion `gateBaseMainHead`, then `resolveGitRef(repoPath, branch, ...)` for `gateBaseBranchHead` itself.

What this capture actually proves is narrower and forward-only: an UNCHANGED branch tip FROM THE CAPTURE ON shows the match still holds, regardless of anything main did meanwhile. A commit landing in the window BETWEEN `findLandedSquashCommit` returning and this capture resolving would be captured here as the new "stable" tip, with `preLanded` never having proved anything about that particular commit's content. This residual gap is closed structurally, not by widening the proof: given the above, the eventual squash can only land as a true no-op (safe) or hit a genuine line-level conflict on the branch's own already-landed paths (handled elsewhere, fails loud, zero side effects) — it can never silently land unverified new content. Only when the branch itself has moved since capture (new commits landed during the gate) does the stability signal no longer apply, and `mergeBranch` falls through to the ordinary `requireCanonicalHead` check — protecting exactly the content this mechanism exists to protect.

## Do not

- Do not describe `gateBaseBranchHead`'s proof as "the branch matched main's landed content at the moment of capture" — it proves the match held as of an EARLIER read (`findLandedSquashCommit`'s own), with two more awaited git calls still to run before capture.
- Do not treat the residual gap (a commit landing between that earlier read and this capture) as unsafe — it is closed structurally: the eventual squash can only no-op or hit a genuine, loud conflict, never silently land unverified content.
- Do not re-derive the EXPECT-ALREADY-LANDED invariant below (fix, card `afa80698`) from `branchStableSinceGateBase`/`gateBaseBranchHead` being set — thread `expectAlreadyLanded` EXPLICITLY from the preLanded producer. A revert landing BEFORE the re-confirm ever captures `gateBaseMainHead` leaves `branchStableSinceGateBase` true and `requireCanonicalHead` trivially satisfied (current HEAD already equals what was captured) — neither gives any signal that content diverged; only checking what the squash actually STAGES catches it.

## Consequences

A reader of `gateBaseBranchHead`'s own doc gets the precise window the stability proof covers, rather than a claim broad enough to imply an atomic check that was never actually made.

## Known gap, FIXED (card `7e6461e5` found it; `afa80698` closed it)

The Do-Not line above — "the eventual squash can only no-op or hit a genuine, loud conflict, never silently land unverified content" — was FALSE on the dirty-preLanded path when main REVERTS the already-landed squash, whether that revert lands DURING the gate or had already landed BEFORE the re-confirm ever ran. Sequence (pre-fix): `preLanded` set on a dirty worktree (service.ts) skips the clean ALREADY_MERGED shortcut; `gateBaseMainHead`/`gateBaseBranchHead` captured once, pre-gate; the preLanded producer is never re-verified before squash; a human/Platform-Lead reverts the landed commit on main; inside the lock the branch tip is unchanged so `branchStableSinceGateBase` is true and `requireCanonicalHead` is SKIPPED (or, on the revert-before-re-confirm variant, trivially satisfied — `requireCanonicalHead` was captured POST-revert, so it already equals current HEAD); `git merge --squash` against the now-reverted HEAD is a clean three-way merge (merge-base unaffected, main's tree now matches it) that reproduces the reverted content exactly — landing as a brand-new commit, never a no-op, never a conflict. **A branch-tip-stability or main-tip-equality check cannot catch this in either timing variant — git revert never removes the reverted commit from history, so the landed sha stays a trailer-matched, content-verified "already landed" sha regardless.**

### The fix — EXPECT-ALREADY-LANDED invariant

The preLanded producer's own premise — this branch's content is ALREADY on main, proven once by `findLandedSquashCommit` — means the eventual squash MUST stage nothing. That is a claim about what the squash *produces*, not about any tip matching, so it is checked at the one place that can actually see it: the staged-diff classification in `mergeBranchLocked`, right after `git merge --squash` runs. An explicit `expectAlreadyLanded: boolean` (never inferred from `gateBaseBranchHead` being set — see the Do-Not above) threads from the preLanded producer in `service.ts` through `mergeBranch`/`mergeBranchLocked`. When it's `true` and the squash stages non-empty content, `mergeBranchLocked` resets the staged squash (reusing the same `resetOrSkip` cleanup every other post-squash refusal in that function uses), lands no commit, and refuses with a distinct `landedContentDiverged: true` flag — worded for a human: the content is no longer on main, Loom will not silently re-land it, and a human must decide (abandon the worker/card, or re-cut the branch if re-landing is actually intended). `landedContentDiverged` is a real, resolved verdict about canonical main, so it is in `NEVER_CACHED_OUTCOMES` (`landed-content-diverged`) exactly like `gateBaseInvalidated`'s `stale-base` — a re-confirm must always re-derive `preLanded` fresh, and refusing again while main stays diverged is correct, not a bug.

**NOT defensively reset on the reuse producer** (`service.ts`, right where `gateBaseBranchHead` resets to `undefined` for that producer) — DELIBERATELY, found wrong at Code Review (round 2, item 4). The `gateBaseBranchHead` reset beside it is safe because it SWAPS one real check (the branch-stability exemption) for another (ordinary `requireCanonicalHead` enforcement) — no protection is lost either way. Resetting `expectAlreadyLanded` to `false` there would instead have DISABLED the only check that can catch a staged squash, with nothing replacing it — strictly LOOSENING the guard in exactly the "the stated mutual-exclusivity invariant was violated" case defense-in-depth exists for. Costs nothing when that invariant genuinely holds (the check only ever refuses a non-empty stage, never produces a false positive); if it's ever violated, leaving it armed is the only thing standing between a reused-gate confirm and silently re-landing reverted content.

**Closes the no-gateCommand asymmetry too** (round 2, item 3): the capture above lives entirely inside `if (gate)`, so a GATELESS project's confirm never computed `expectAlreadyLanded` at all before this — the exact silent-revert-undo window stayed wide open for any project with no `gateCommand` configured, where it needs no "gate in flight" window at all, just a re-confirm landing after a revert. Closed with a second, independent derivation right at the `mergeBranch` call site: when nothing already has (`!gate`, so the `if (gate)` block never ran) and the branch isn't owed/held (mirrors the identical `owedBase ? null :` gate the `if (gate)` block's own preLanded producer uses), a fresh `findLandedSquashCommit` call sets `expectAlreadyLanded` the same way. Fail-safe like every other producer here: a failed read leaves it at its `false` default, never "assume landed".

**The refusal's own wording is conditional on whether the reset actually ran** (round 2, item 1, BLOCKING — found at Code Review: reproduced as `A feature.txt` staged next to ` M other.txt` unstaged, with the refusal still claiming "canonical repo untouched"). `resetOrSkip` does NOT always reset: when the canonical repo already carried unrelated unstaged dirt before this attempt (`hadUnstagedDirtAtEntry`), it SKIPS the reset rather than risk discarding that dirt — exactly like every other post-squash refusal in this function — leaving the reverted content staged right alongside it. `mergeBranchLocked` now sets `residuePossible: true` for EVERY unsuccessful cleanup outcome, not just the pre-existing `transient` case; `service.ts`'s `landedContentDiverged` handling (moved to run AFTER the `quarantined`/`transient` checks, so either of those wins first with its own already-correct wording) branches its `detailText` on that flag — "canonical repo restored to its pre-merge state" ONLY when the reset genuinely succeeded, else a wording naming the residue and the `git diff --cached` remedy, mirroring `merge.transient`'s own pre-existing residuePossible-conditional wording one branch up.

Verified NOT to false-positive on a legitimate unrelated edit: a later main commit touching the SAME file as the branch, on a non-overlapping hunk, still merges cleanly and stages nothing (`git merge --squash`'s own 3-way merge recognizes the branch's hunk is already present) — pinned by `merge-prelanded-content-diverged.mjs` scenarios (3)/(4). Confirm-level wiring (a real `SessionService.confirmWorkerMerge`/`confirmWorkerMergeTracked` call, not just the `mergeBranch` primitive directly) is pinned by `merge-prelanded-content-diverged-wiring.mjs` — scenario (A) the refusal itself, (B) that it is never served from the until-superseded verdict cache (`r.cacheHit` stays unset across a second tracked confirm), (C) that the no-gateCommand derivation above actually reaches a real confirm. Proven RED-before/GREEN-after via `pnpm --filter @loom/daemon negative-control` (the whole-diff proof) plus three targeted single-line source mutations verified by hand (documented at each mutation's own former call site in the round-2 commit).

### Do not (fix-scoped)

- Do not infer `expectAlreadyLanded` from `branchStableSinceGateBase`/`gateBaseBranchHead` — thread it explicitly; see the Do-Not above for why those signals alone miss the revert-before-re-confirm timing.
- Do not check this invariant by comparing `requireCanonicalHead`/`gateBaseMainHead` against current HEAD — a revert is a NEW commit, so an ancestry or tip-equality check cannot distinguish "main still contains it" from "main reverted it". Only the squash's own staged-diff emptiness proves it.
- Do not land a commit, even an empty/reconstructed one, when `expectAlreadyLanded` and the stage is non-empty — reset and refuse unconditionally; there is no safe partial landing here.
- Do not cache or replay a `landed-content-diverged` refusal — it is a verdict about canonical main's current content, not the branch, exactly like `stale-base`.
- Do not reset `expectAlreadyLanded` to `false` on the reuse producer's own defensive-reset site, even though `gateBaseBranchHead` resets right beside it — that reset swaps one check for another; this one would only disable a check with nothing to replace it.
- Do not claim "canonical repo untouched" in the refusal's wording without checking `residuePossible` first — `resetOrSkip` can SKIP the reset (pre-existing unrelated dirt), leaving the reverted content staged.
- Do not scope `expectAlreadyLanded`'s derivation to `if (gate)` only — a gateless project needs its own derivation at the `mergeBranch` call site, or it stays unprotected.
