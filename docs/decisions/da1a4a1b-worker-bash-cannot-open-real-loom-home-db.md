# da1a4a1b — Loom-driven agent sessions must not open the real LOOM_HOME database through Bash

## Do not

- Do not treat the shipped PreToolUse(Bash) guard as the boundary. It is string matching over the command text; it stops accidents and the casual path, not a deliberate or merely indirect read.
- Do not widen it to deny all of LOOM_HOME. Workers legitimately write their own `$LOOM_SCRATCH_DIR` under it, and the Platform/Setup homes run with cwd == LOOM_HOME. It keys only on the DB files, `backups`, and `secret.key`.
- Do not key it on the bare word `loom.db`. Hermetic tests use a temp LOOM_HOME with their own `loom.db`; the guard keys on the REAL resolved path.
- Do not wire it for manager/platform/operator/plain sessions without an owner decision (see Role scope).
- Do not add the guard to the attribution PreToolUse group; that group is observational and must never block.

## Incident

A Research Analyst worker copied the real `~/.loom/loom.db` (370 MB) with a `better-sqlite3` script launched from Bash and queried it. The copy was deleted; the saved queries were aggregates only. Root cause: every existing worker deny is TOOL-scoped (`Read`/`Glob`/`Edit` permission rules, `37310431`), so an interpreter launched from Bash reads freely. The DB also carries AES-GCM credential blobs whose key is `secret.key`, which is just as reachable.

## How worker sessions get their deny today (read before building)

- `pty/claude-settings.ts#writeSessionSettings` writes the per-session `--settings` file: `permissions.{allow,deny}` (Read/Glob deny-globs, the `Edit(//<abs>/**)` LOOM_HOME write registry from `37310431`) plus `hooks`.
- Existing hooks: `SessionStart/UserPromptSubmit/Stop/StopFailure/SubagentStart/SubagentStop/InstructionsLoaded` go through `hook-relay.mjs`; `PreToolUse` is ONE group, matcher = `PRE_TOOL_USE_ATTRIBUTION_MATCHER` (watched MCP tools only), observational, never blocks; `PostToolUse` carries the Read/Write|Edit lint hooks (advisory).
- So before this card no hook inspected a `Bash` command at all, and no permission rule constrained a process spawned by Bash. (Claude Code applies `Edit()` deny to recognised Bash write idioms, per `37310431`, but that is write-side and path-shape-limited; it does not stop an interpreter READING a file.)

## Options

| | Option | Effort | Strength | Concrete bypass |
|---|---|---|---|---|
| (a) | PreToolUse(Bash) hook refusing commands that name the real DB/backups/secret.key | S (shipped here) | Weak: stops accidents and the naive "open it from node" path | `node -e "require('fs').copyFileSync(require('path').join(require('os').homedir(),'.loom','loom.db'),'x')"` (path assembled at runtime); a script FILE the worker writes that reads the path from `process.env`/`os.homedir()` (the command text never names it); a symlink/junction to the file created in an earlier call; `cd` into a parent then a glob (`cp ../../.l*/loom.d? x`); `LOOM_HOME` of the daemon itself is not even needed since `~` is predictable |
| (b) | Don't hand workers LOOM_HOME / move per-session work dirs outside it | S-M | Accident reduction only | The path is `~/.loom` by default and trivially guessable; `os.homedir()` works in any script. Scratch dirs live under LOOM_HOME today by design (`$LOOM_SCRATCH_DIR`) so moving them is a behavioural change with its own blast radius |
| (c) | OS-level containment: Claude Code's own sandbox (filesystem deny), or an ACL/separate OS user for agent processes | M (sandbox) / L (separate user) | Strong when it works (kernel-enforced, covers every child process) | Sandbox: none by design if enabled, but see feasibility. Separate user: a same-user daemon cannot be both the owner of the DB and unreadable by a worker without running the engine as a different account, which breaks subscription auth (the `claude` login lives in the user profile) and every shared path (worktrees, vault) |
| (d) | Encrypt the DB at rest (SQLCipher) with a key only the daemon holds | L | Strong against copying, ONLY if the key is not worker-readable | Key must live somewhere the daemon reads at boot; today `secret.key` is a plain file in the same dir the workers can read, so (d) without (c) just moves the target to the key. Also a native-dependency swap (better-sqlite3 -> SQLCipher build) on Windows + npm release |

### (c) feasibility on Windows with subscription auth — what was and was not verified

- Verified (installed CLI `2.1.322`, strings of `C:\Users\danie\.local\bin\claude`, 2026-11-12): the binary contains `Error: Sandboxing is currently only supported on macOS, Linux, and WSL2.` and `Error: Sandboxing requires WSL2. WSL1 is not supported.`, and also `Windows sandbox is not active on this session (feature gate off)`. So native-Windows sandboxing exists in the binary behind a feature gate that is OFF for this install.
- Not verified: that the gate can be turned on by a user setting, that its filesystem deny covers a child `node.exe` reading a path outside the cwd, and that it works with subscription (OAuth) auth. I did not enable or run it. No public documentation was fetched for this record; treat "supported on macOS/Linux/WSL2 only" as the CLI's own message, not as a statement about the docs.
- Consequence: on the owner's native Windows host (c) is NOT available today. On macOS/Linux/WSL2 it is the right primitive, and Loom would need a per-session `sandbox` settings block plus a restricted-network decision (sandbox network defaults interact with MCP loopback to the daemon).

## Recommendation (one strong layer)

Pursue (c) via Claude Code's sandbox with a filesystem read-deny on the real LOOM_HOME DB/backups/`secret.key` (and the worker still allowed its scratch dir), because it is the only option that binds the process, not the text of a command, and it protects the key file too, which is what makes (d) unnecessary. It is blocked on Windows by the feature gate; the follow-up card must start by verifying, on a real spawn, that the gate can be enabled and that a child `node` read is actually denied (with a no-deny control). Until then (a) is the only layer and its residual is the whole bypass column above. (d) alone is not recommended: it relocates the secret rather than protecting it.

## What shipped (layer a)

- `assets/bash-loom-home-guard.mjs`: standalone hook script (`node <script> <realLoomHome>`), reads the PreToolUse JSON on stdin, exits 2 with a refusal on stderr (blocks the call and feeds the message to the model) or 0. Unparseable payload fails open.
- Wired in `writeSessionSettings` as a SECOND PreToolUse group (matcher `Bash`) when the new `guardLoomHomeFromBash` param is true; `host.ts` passes `isLoomDrivenRole(opts.role)`, the same predicate as `disableSkillShellExecution`.
- Normalisation: slashes in both directions and doubled slashes collapsed; case-fold on win32 only (POSIX is case-sensitive, so a differently-cased path is a different file and is not refused); Git-Bash `/c/...` drive form; `~`, `$HOME`, `${HOME}`, `%USERPROFILE%`, `$USERPROFILE`, `$env:USERPROFILE`/`HOME`, `$LOOM_HOME`, `%LOOM_HOME%`, `$env:LOOM_HOME` expanded before matching. Names matched (secret-bearing files/dirs resolved under LOOM_HOME in `paths.ts`): `loom.db`, `loom.db-wal`, `loom.db-shm`, `secret.key`, `gateway-loopback.key` (human-REST bearer), `.env`, `backups`, `tmp/settings` (per-session settings and mcp-config files carrying hook tokens and MCP capability secrets). Also: the real home dir named together with a bare `loom.db`/`secret.key`/`gateway-loopback.key`/`.env` token (`cd ~/.loom && cat .env`). Deliberately LEFT OUT (content or operational state, not credentials; naming them would only add false positives): `archives`, `attachments`, `companion-memory`, `gate-output`, `logs`, `codescape`, `skills`, `daemon.pid`, `update-config.json`, `restart-intent.json`.
- There is NO `LOOM_HOME=` exemption (round 2 of review removed one): bash expands `$LOOM_HOME` before a prefix assignment applies, so `LOOM_HOME=/tmp/x cp $LOOM_HOME/loom.db y` reads the real DB. The hermetic shape `LOOM_HOME=<tmp> node test.mjs` never names `$LOOM_HOME/<sensitive>` and passes untouched; a test command that does reference `$LOOM_HOME/loom.db` is refused (a false positive: spell the temp path out literally).
- The home-dir-plus-bare-token rule anchors to the home directory ITSELF (end, whitespace, quote, `;&|)`, one optional trailing `/`), never a path that descends further: the worker's own `$LOOM_SCRATCH_DIR` (`<home>/tmp/scratch/<sid>`) and `<home>/logs/...` are not the home dir, so `sqlite3 <home>/tmp/scratch/s/h/loom.db` is allowed.
- The hook command passes the home as `b64:<base64url(path.resolve(LOOM_HOME))>`, so no path character (trailing backslash, `$`, `%`, quote) can break the shell quoting into a silent fail-open.
- `/./` and `seg/../` are collapsed lexically (to a fixpoint) before matching, so `~/.loom/tmp/../loom.db` and `~/.loom/./secret.key` name what they resolve to. A `..` that climbs out of a RELATIVE start cannot be collapsed (`cd <home>/tmp && cat ../loom.db`), so a second rule refuses a sensitive bare token reached through `../` whenever the command names a descendant of the home. The scratch usage never needs `../<sensitive>`, so it stays allowed. This is lexical only: it does not resolve symlinks or a shell `cd` chain across separate calls.
- Normalisation is STRUCTURAL and runs once before any rule: (a) strip every `"` and `'` (approximates bash quote removal, so `cat ../"loom.db"`, `cat ..'/.env'` read as bash executes them), (b) slash/case/variable expansion, (c) a single-pass segment-stack collapse per path token (linear; the earlier regex fixpoint loop was quadratic: a 310 KB nested `/a…/..…` input took ~31.9 s, a 60 KB one ~1.1 s; after, 4 ms and 0 ms). A `..` immediately after a root (`/`, `x:`) is dropped, so `C:/../Users/Tester/.loom/loom.db` and `C:/Users/../../Users/Tester/.loom/secret.key` resolve and are refused. Every rule then runs on the normalised text; the per-rule quote tolerances left in the character classes are harmless redundancy, not load-bearing.
- A command over 65536 characters fails CLOSED ("command too long for the Loom Bash guard", exit 2): a worker's legitimate very large heredoc is refused too and must go through a file.
- Known false positive: after a scratch redirect, a repo-relative `cat ../.env` (or `../loom.db`) in a command that also names a home descendant is refused by the `../<sensitive>` rule, since it cannot tell a repo-relative path from one under the home. Spell it from the repo root.
- `<` and `>` are separators everywhere (dir lookahead, bare-token prefix/suffix, tilde prefix), so `cd ~/.loom>/dev/null && cat .env`, `cat .env>/tmp/x`, `cat<.env` and `cat <~/.loom/.env` are refused.
- A malformed or missing home ARGUMENT fails CLOSED and visibly (exit 2, "Loom Bash guard misconfigured: …, report this to your manager"): the b64 value must be canonical base64url (re-encoding the decoded value gives the input) and the result an absolute path. An unparseable stdin PAYLOAD still fails open. Residual: a truncation that lands on a valid base64url length decodes to a different, shorter absolute path and is not detectable without a checksum (the daemon builds this argument programmatically, so it is not an expected failure).
- Suffix behaviour: a FILE entry is refused on any suffix (`.env.local`, `loom.db.bak`); a DIR entry (`backups`, `tmp/settings`) is refused unless the next char continues a longer name (`backups-old`).
- Role scope: `LOOM_DRIVEN_ROLES` (worker, setup, auditor, workspace-auditor, run, assistant) — the roles whose stdin/ownership is Loom's and which have no reason to read the DB. Manager/platform/operator/plain are excluded: they are human-supervised, and the Platform Lead runs with cwd == LOOM_HOME and has documented DB-recovery recipes. This is a judgement; if the owner wants managers covered it is a one-line change, and `setup` runs in the LOOM_HOME home, so it is the role most likely to hit a false positive (its legitimate work does not touch the DB).
- Test: `test/bash-loom-home-guard.mjs` (matcher on win32 + POSIX flavours, real hook process exit codes, settings wiring). A mutant making the matcher always allow fails 24 assertions.

## Residual (honest)

- Path assembled at runtime (`os.homedir()`, `path.join`, string concat, env var other than the ones listed, `$(...)`), a script file reading the path from env or computing it, a symlink/junction created earlier, a relative path after `cd` to a parent, a glob that resolves to the file, hex/base64-encoded path.
- Codex-harness workers get NO guard at all: `createCodexPty` writes no claude settings, so there is no PreToolUse hook to wire (the claude-only deny levers do not exist there). A codex worker can read the real DB freely; closing that needs the process-level layer (c), not this hook.
- Only `Bash`. `PowerShell`/other shells, if a role has them, are not matched (matcher is `Bash`); MCP tools and an interpreter launched by a different tool are untouched.
- Content stores left out (see the list above), notably `archives` (session transcripts), remain readable by a worker.
- Fail-open on unparseable hook input and on a hook crash (Claude Code treats a non-2 exit as non-blocking).
- Observed once (n=1, CLI 2.1.322, Windows, worker role, `test/bash-loom-home-guard-real-spawn.mjs`, manual-only): a real claude process refused `cp <temp LOOM_HOME>/loom.db …` (output file absent) with the transcript tool_result reading `PreToolUse:Bash hook error: [command hook 2]: Refused: this command names the real Loom data directory's…`, while the control `echo > file` in the same turn ran. No no-hook control spawn was run, so attribution rests on that message text. Not observed: a refusal for each added name (those are matcher-tested only).
