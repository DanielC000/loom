# 6f13746c — the merge-gate INTERVAL: run the real gate every N ungated landings while the gate is off

## Narrative

Card 6f13746c extends the human-only per-project `orchestration.mergeGate` switch (card e8df2659). With the gate "off", a human may now set `orchestration.mergeGateInterval` = N (integer 1..1000): N branches may land ungated, then the landing that would exceed N runs the REAL `gateCommand` — a genuine, fail-closed gate. The cadence is derived in one place (`resolveMergeGateCadence`, `packages/shared/src/config.ts`): `every` = gate on, `interval` = off + N, `never` = off + no N.

The rule lives in one pure function (`decideMergeGate`, `packages/daemon/src/orchestration/merge-gate-interval.ts`), evaluated ONCE per landing (solo: `confirmWorkerMergeTracked`; batch: `mergeBatchTracked` with K = the chosen candidate count) and threaded down as a `MergeGateDecision`. Gate this landing iff cadence=every, OR gateOwed, OR (cadence=interval AND ungatedSinceLastPass + K > N).

Durable state is keyed **(project, repo)** (`project_merge_gate_state`, one lazily-created row per repo; the primary repo is `"primary"`), so a pass in repo B never resets repo A's count and `fromSha`/`toSha` always come from one repo. It holds: the ungated counter, `gateOwed`, `lastPassAt`/`lastPassSha` and a ring of the last 6 periodic/owed gate outcomes (newest kept, one row per gate opId). One recorder (`SessionService.recordMergeGateOutcome`, called from `finalizeMerge` once per landed candidate) applies: an ungated landing adds the LANDED count; ANY passing gate resets the counter, clears owed and `lastFailure`, and stamps `lastPass*`. A failing gate (`recordMergeGateFailure`) is recorded under every cadence but sets `gateOwed` only when it was periodic/owed (cadence ≠ every) — under `every` every later merge is gated anyway, and a later off-switch must not find the project retroactively "owed". The failure's range `fromSha = lastPassSha` (null = never passed) `.. toSha = main HEAD` names the unverified suspects already on main; `branchTip` is the rejected solo branch, a rejected batch carries `candidates: K` instead.

Decisions taken (owner accepted the four behaviour calls; the manager ruled the rest):
- **Unit is branches landed.** A batch of K adds the number that ACTUALLY landed (a partially-landed fallback adds that number, not K).
- **A red does not reset.** A failing periodic/owed gate owes the NEXT landing a gate until one passes.
- **Turning the gate on↔off does not reset the counter**; cadence `never` keeps counting (it is the "unverified on main" figure). Changing N mid-cycle needs no special case — the `> N` rule clamps.
- **Not counted (counter untouched):** a landing in a repo with NO `gateCommand` (already labelled "unverified" by its own warning), an inert docs-only skip, and the 479f449f evicted-predecessor rescue landing (`finishAlreadyMerged` from the thrown-error path carries no gate info). A finalize replay never double-counts: the recorder is skipped when the worker already has a `merge_done` event.
- **The batch fallback honours the batch's decision.** When a batch is "not this landing's turn" (or has no gateCommand) each candidate takes the per-branch solo fallback with the batch's `MergeGateDecision` threaded in (`opts.mergeGateDecision`), so K is counted once and no candidate re-decides with K=1. Overflow/stranded members decide for themselves. The verdict-cache identity folds the decision (`|mergeGate:on` for a gated decision, `off` for an ungated one) so a cached red is never replayed onto an ungated landing or vice versa.
- **The skip landing is PINNED.** An ungated landing (`gate-interval`, and — the same seam — `gate-disabled`) is a `gateRan:false` landing like a reuse, so it is pinned to the branch tip stamped once the repo guard is held (`skipExpectedTip`, passed to `mergeBranch` as `expectedBranchTip` exactly like 01777ceb's reuse pin): a worker commit landing after that but before the lock is refused in-lock (`gateTipMoved`, nothing squashed, never cached) and does not advance the counter. Without the pin the late commit was squashed in unseen. The refusal text still says "this PASS …" (shared wording with the gated refusals).
- **Reservations (no overshoot).** The decision is taken at confirm-attach but the count is recorded at finalize, so an in-process per-(project, repo) RESERVATION bridges the gap: `decideMergeGateFor` counts pending reservations as already landed, a skip decision reserves its landing in the same synchronous step (`reserveMergeGate`), and the reservation is released when the confirm settles (`runWithMergeGateRelease`; landed ⇒ the recorded count takes over, rejected/cancelled/failed ⇒ just released; a dedupe/cache hit that never runs the factory releases at once). A batch's not-due decision reserves one unit per chosen candidate, each carried by that candidate's solo fallback and released when it settles. A restart drops reservations — nothing was recorded, so nothing is lost. The batch's **overflow/stranded** members are NOT handed the batch decision: it covers K=chosen only, and reusing it would let them land ungated past N; they decide for themselves (K=1, with the reservations counted), so N=5 with 4 chosen + 2 overflow lands 5 ungated and gates the 6th.
- **A HUMAN cadence change clears `gateOwed`.** A REST config PATCH that changes the resolved `mergeGate` or `mergeGateInterval` (a no-op PATCH does not) clears `gateOwed` on every repo of the project and appends a `recent` entry `{result:"cleared", reason:"cadence-changed"}` (only where something was owed). The ungated counter is NOT reset (the "unverified on main" figure stays honest). That is the owner's escape when the gate itself is broken, via the controls they already have; `gate-next` is unchanged.
- **A passing batch gate records ONCE**, with the batch's final landed tip, so `recent[].toSha == lastPassSha` (ungated landings still record per landed candidate).
- **Identity-void reds still owe.** 01777ceb's identity-void FAIL (a red whose final link left the gated commit / unreadable reflog) still counts as a failing periodic gate and owes the next landing a gate — deliberately conservative; the failure is recorded before that classification and is not re-litigated here.
- **The counter's order is MAIN's order — landings record at the squash, INSIDE the repo guard.** A solo landing records right after `mergeBranch` succeeds (before the `finally` that releases the guard: `endSquash` / `releaseInertRepoGuard`), and a passing batch records right after `runBatchedMerge` returns (before `endSquash`), ONCE with the final landed tip. Recording later (in `finalizeMerge`, after the guard) let an ungated landing that squashed AFTER a pass be recorded BEFORE that pass's reset, which then erased a landing the gate never tested (reproduced: counter 4, N=5, a gated batch holding the guard, an overlapping skip-decided solo; ends 0 instead of 1). Because recording no longer happens in `finalizeMerge`, a boot/replay re-finalize cannot double-record (the old `merge_done` replay guard is gone with it); the price is one more under-count window (below).
- **A skip decision does not outlive a newly OWED gate.** Just before the squash, inside the guard, an ungated (`gate-interval`/`gate-disabled`) landing whose project became `gateOwed` after its decision (a red recorded while it waited for the guard, or a human gate-next) is refused in-lock — reason "a gate is now owed…", nothing squashed, reservation released, classified `stale-base` (never cached). The re-call decides gated. Applies to a batch's fallback candidates carrying the batch decision too (same code path). Reds are recorded after the gate's own exclusive section, so this is best-effort ordering for reds and exact for anything recorded inside the guard.
- **Reservations cannot leak:** the attach call releases in a `.finally` (a reject before `run()` or a dedupe hit), and `runFallback` releases every unit not handed to a started confirm in a `finally`. A batch's K is `liveChosen.length` (branches actually batched; held candidates count for nothing).
- **The cadence-change clear compares the EFFECTIVE cadence** (`{cadence, interval}`): editing N while the gate is on changes nothing, so a gate-next-owed flag survives. A failure entry's `branchTip` is the gate's PINNED tip (falling back to the live tip only when no pin exists).
- **Known UNDER-COUNT paths (a landing that reaches main without being recorded, i.e. slightly fewer gates than intended):** (1) `finishAlreadyMerged` from the thrown-error rescue (479f449f) and any retained landing (42daa283: a branch that advanced during the gate is retained, no `merge_done`) carry no gate info; (2) the squash→record window (the squash committed and the daemon died before the recorder ran, a few synchronous statements later; boot Pass A re-finalizes with no gate info). Both bias toward under-counting, never over-gating.
- **`skipReason`:** `gate-disabled` (cadence never) vs NEW `gate-interval` (interval, not this landing's turn); neither is ever recorded as a pass. The merge result carries `mergeGateNote` ("ungated 3/5 since the last passing gate" / "this was the periodic gated landing …") and `[loom:merge-done]` echoes it.
- **Trust posture = `mergeGate`'s.** HUMAN-only: the agent config validator rejects the key, and it is in `HUMAN_ONLY_NESTED_PROJECT_CONFIG_KEYS` so the Lead's elevated `project_configure` can neither set nor clear it. REST (`GET /api/projects/:id/merge-gate/status?repoKey=`, `POST .../gate-next?repoKey=`, default primary, unknown repo ⇒ 404) is human loopback only; agents get a READ-only `{repoKey, cadence, interval, ungatedSinceLastPass, nextLandingGated, gateOwed}` (the repo being merged on `worker_merge`, primary on `my_context`) on `my_context` and `worker_merge`'s review — never the ring or shas. There is no project-scoped ws event channel, so the UI polls the GET. Both routes stay on the default (non-Tier-1) trust tier.

## Do not

- Do not decide without counting the in-process reservations, and do not reserve anywhere but in the same synchronous step as the decision — overlapping confirms would overshoot N. Do not share one state across repos.
- Do not evaluate the decision more than once per landing, and do not let a batch fallback re-decide with K=1 — that is how a batch would silently gate mid-fallback or count K twice. `merge-gate-interval.mjs` counts calls.
- Do not record an ungated landing anywhere but once per landed candidate (`finalizeMerge`, guarded by the absence of a prior `merge_done`), and do not count a landing that had no `gateCommand`.
- Do not make `mergeGateInterval` agent-settable or agent-clearable on any path (agent validator, setup router, the Lead's elevated `project_configure`), and do not expose the ring/shas on an agent surface.
- Do not treat `skipReason:"gate-interval"` (or `gate-disabled`) as a pass, and do not let a failing gate under cadence `every` set `gateOwed`.
