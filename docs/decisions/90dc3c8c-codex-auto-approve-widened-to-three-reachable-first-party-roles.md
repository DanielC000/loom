# 90dc3c8c — `CODEX_AUTO_APPROVE_MCP_SERVER_IDS` widened, in two stages, to every first-party server id

## The gap this closes

Card `702f2197` granted `default_tools_approval_mode=approve` to `loom-tasks` + `loom-orchestration` only — the two servers a WORKER mounts, which is all that card needed. But `harness` is profile-pinned and resolved on every role's spawn path, so a codex `setup`/`operator`/`platform`/`auditor`/`workspace-auditor`/`run` session was equally spawnable, and every tool call on that session's OWN first-party role surface was (and, for three of the six, still is) denied by `-a never` — the exact defect `702f2197` fixed, unfixed for the other six.

## Per-role analysis (the DoD this card required — reachability first, then claude parity)

**Reachability was established by code-reading `sessions/service.ts`'s six `start*` methods plus an empirical `validateProfile()` probe (not assumed):**

| role | mounts | reachable today? | why |
|---|---|---|---|
| setup | loom-setup | yes | ungated CORE profile ("Setup Assistant"/"Platform" operator), `role:"setup"` is a valid `profileSchema` enum member, `startSetup` threads `harness` through to `pty.spawn` |
| operator | loom-operator | yes | ungated CORE profile ("Elevated Operator"), flag-gated at spawn time (`platform.operatorEnabled`) not seed time, `role:"operator"` is a valid enum member, `startOperator` threads `harness` through |
| platform | loom-platform | yes (under `LOOM_DEV`) | "Platform-lead" bundled profile seeds only under `LOOM_DEV`, but when it does, `role:"platform"` is a valid enum member and `startPlatformLead` threads `harness` through |
| auditor | loom-audit | **no** | `profileSchema`'s `role` enum deliberately EXCLUDES `"auditor"`/`"workspace-auditor"` (profiles/validate.ts, by design — a profile must never confer either, only `startAuditor`'s explicit caller role can). The bundled "Platform-audit" profile carries `role:"auditor"` anyway (seeded outside that validator). `PUT /api/profiles/:id` merges `{...existing, ...patch}` then re-validates the WHOLE merged object — so ANY patch to this profile (including a harness-only one) re-validates `role:"auditor"` against the enum and 400s. Verified empirically: `validateProfile({..., role:"auditor", harness:"codex"})` → `{ok:false, error:"role: Invalid option..."}`, against a control (`role:"setup"`, same patch) → `{ok:true}`. `harness` can never be set on this profile via any live human action — only by editing the `BUNDLED_PROFILES` literal in `profiles/seed.ts` and redeploying. |
| workspace-auditor | loom-user-audit | **no** | same mechanism as auditor — "Workspace Auditor" is a CORE ungated profile, but `role:"workspace-auditor"` is equally excluded from the enum, so the same PUT-revalidation blocker applies. |
| run | loom-run | **no** | `sessions/service.ts#startRun` calls `resolveAgentSpawn(agent, config, "run")` but destructures only `{ model, skills }` from the result — `harness` is silently dropped and never reaches its `pty.spawn(...)` call. A "run" session boots as claude regardless of what an agent's profile pins `harness` to. (`createCodexPty` itself works fine for `role:"run"` when invoked directly — this is a gap in the SERVICE layer's wiring, not the PTY layer.) |

**Claude parity:** under claude, every role already boots unattended with `--permission-mode`+allowlist covering its own curated MCP surface — so claude already runs setup/operator/platform (and, if it were reachable, auditor/workspace-auditor/run) fully autonomously with no human approving individual tool calls. Codex has no per-tool mechanism, only this per-server lever (per `702f2197`'s own finding) — so for a REACHABLE role, "proportionate" reduces to a binary: either the whole already-curated, already-role-gated surface is usable under codex (matching claude), or the role is completely non-functional under codex. There is no narrower, safer middle ground available.

## The decision

Widened `CODEX_AUTO_APPROVE_MCP_SERVER_IDS` to `loom-tasks`, `loom-orchestration`, `loom-setup`, `loom-operator`, `loom-platform` — the five of eight first-party ids whose role is reachable today. `loom-platform` (Platform Lead) is the most privileged of the three added: CLAUDE.md already documents that this role is trusted, human-driven-but-unattended, to `git_checkout`/`git_commit`/`git_push`/`vault_write` as agent tools under claude — this grant does not create a new trust boundary, it extends an already-made one to a second harness.

**Deliberately NOT widened to `loom-audit`/`loom-user-audit`/`loom-run`** — not a proportionality judgement (parking that question), but because granting an unreachable role's auto-approve is dead code with zero present benefit, and the card's own instruction is "do NOT just add all six" without a concrete need. Revisit each once its OWN independent blocker is fixed (a future card):
- auditor / workspace-auditor: the `PUT /api/profiles/:id` merge-then-revalidate blocker above.
- run: thread `harness` through `startRun`'s `pty.spawn()` call.

## Do not

- `loom-audit`/`loom-user-audit`/`loom-run` are now IN this set (added by `cea3cec6`, 2026-09-22 — see that section below) — the reachability blockers this table originally found are fixed, and the per-role proportionality question for `auditor`/`workspace-auditor` is answered there, on its own argument. Do not read this record as still withholding any of the three.
- Do not restate the `.size ===` guard count or the role table here if either changes — re-derive from `codex-host-decisions.mjs` / `sessions/service.ts` directly; this record is a snapshot of its own analysis date, never a live source of truth for either.
- Do not add a NINTH first-party id to `CODEX_AUTO_APPROVE_MCP_SERVER_IDS` without its own reachability + proportionality re-derivation — see the `cea3cec6` section's own Do-not for the same rule stated there.
- Do not treat a NEW TOOL added to one of the eight already-granted routers (`mcp/audit.ts`, `mcp/operator.ts`, `mcp/orchestration.ts`, `mcp/platform.ts`, `mcp/run.ts`, `mcp/server.ts` [loom-tasks], `mcp/setup.ts`, `mcp/user-audit.ts`) as a smaller decision than adding a ninth server id — registering it auto-approves it under codex the instant it merges, with no separate review step of its own. The two bullets above only ever covered a ninth SERVER; this is the orthogonal "new tool on an already-approved server" gap (card `93a15059`, filed from `b1960b04`'s merge-gate finding on `cea3cec6`). Each registration site carries its own inline `@decision 90dc3c8c` guard stating this; the surface-pin tests (`audit-surface.mjs` etc.) catch the ADDITION but say nothing about the auto-approval CONSEQUENCE — read the inline guard, not just the test failure, before adding a tool there.

## cea3cec6 (2026-09-22) — the remaining three widened; `CODEX_AUTO_APPROVE_MCP_SERVER_IDS` now covers every first-party id

Both of the above blockers were fixed and merged onto this project's mainline before this section was written: `71bcb207` (sha `9d87582`) made `auditor`/`workspace-auditor` carry-forward-only in `profiles/validate.ts`'s role enum, so an existing bundled profile of either role can now be PATCHed (e.g. a harness-only edit) without 400ing on its own pre-existing role; `56e6c046` (sha `4def7e7`) threads `resolveAgentSpawn`'s resolved `harness` through `startRun`'s session row and `pty.spawn()` call, which previously silently dropped it (a `run` always booted claude regardless of its profile pin).

**Reachability re-verified empirically, not inferred from the two cards merging** (per this card's own DoD-1): `packages/daemon/test/profiles-rest.mjs` exercises the real REST `PUT /api/profiles/:id` path against the bundled "Workspace Auditor" profile (role `workspace-auditor`) and confirms an unrelated-field patch now returns 200 with the role carried forward unchanged (previously 400). `packages/daemon/test/agent-runs-harness-thread.mjs` drives a real `SessionService.startRun()` against a codex-pinned profile and confirms the opts object actually reaching `pty.spawn()` — not just the DB row — carries `harness:"codex"`. Both ran green on this branch. `startAuditor`/`startWorkspaceAuditor` (`sessions/service.ts`) already destructured and threaded `harness` from `resolveAgentSpawn` before either fix — the blocker for those two roles was purely the profile-validation 400, never a service-layer wiring gap like `run` had. `buildMcpServers`/`createCodexPty` are role-generic (no harness-specific branch), so once a role's session can be configured+spawned at all, its own MCP server mounts identically under codex as under claude.

**Claude parity, per role — no departure from it for any of the three:**

- **`run`**: claude's `--allowedTools` grant for a `run` session is the whole-server wildcard `mcp__loom-run` (`pty/host.ts`'s `roleAllow`), and `loom-run`'s entire tool surface is the single, self-terminating `submit_result` (`mcp/run.ts`) — the narrowest surface of any role discussed in this record. Granting codex the same whole-server auto-approve is exact parity with claude, not a widening.
- **`auditor` / `workspace-auditor`**: this card's own DoD explicitly forbids appealing to the `platform` precedent above for these two — they ingest UNTRUSTED session-transcript content (a prompt-injection surface), unlike `platform`/`setup`/`operator`, which act on trusted human/operator input. Their own argument: (1) claude's `--allowedTools` grant for these roles is ALSO the whole-server wildcard (`mcp__loom-audit` / `mcp__loom-user-audit`, same `roleAllow` table) — so codex's per-server approve-mode is granularity-identical to claude's own mechanism for these two roles specifically, not a wider grant; (2) both routers' own trust-boundary doc comments (`mcp/audit.ts`, `mcp/user-audit.ts`) already assume fully-unattended, no-per-call-human-approval tool calls against adversarial transcript input UNDER CLAUDE TODAY. The FULL surface each grants (the exhaustive pins in `test/audit-surface.mjs`/`test/user-audit-surface.mjs`, not a hand recount — an earlier miscount on this card undercounted both): `auditor` gets 9 tools — `list_sessions`/`transcript_read` (cross-project transcript reads, the audit input) + `repo_read_file`/`repo_grep`/`repo_glob` (read-only Loom-source reads) + `requests_list` (cross-project Requests reads) + the three writes (`audit_file_finding`, `preset_suggestion_suggest`, `end_me`); `workspace-auditor` gets 12 — the same read+write shape plus `agent_prompt_read`/`skill_list`/`skill_read` (own-project prompt/skill reads) and `audit_handoff` (a confined nudge to exactly the home operator, no free-form target) in place of `requests_list`. Every WRITE has a server-resolved TARGET but caller-supplied, free-form CONTENT — `audit_file_finding`'s `title`/`detail` and `preset_suggestion_suggest`'s `label`/`prompt`/`rationale` are plain `z.string()` fields, not constrained — so an injected transcript could in principle get its own text quoted verbatim into a board-card `detail`, including a secret or another session's transcript content read via `repo_read_file`/`transcript_read`. The ceiling that makes this proportionate anyway: every write still lands on an inert, dedupe-guarded, daemon-local row (a board card / a suggestion) with no outward channel and no reach to git/vault/config/spawn/host/escalation/archive, `end_me` is self-scoped, and the read tools are independently hardened (`repo-read.ts`: root-confined, symlink-escape refused, no child process, ReDoS-bounded). A hostile transcript routed through either role can at worst file a spurious, human-reviewable board card (possibly containing content it shouldn't) or end its own scan — the same ceiling under codex as under claude, since claude already runs these roles fully unattended against this exact surface. Widening to codex therefore extends an already-accepted risk shape to a second harness, exactly as `platform`'s git/vault-write trust boundary did — but proved on these two roles' OWN containment argument, not borrowed from `platform`'s. (The "any new tool silently inheriting an already-granted server's auto-approve" gap, and the `end_me`-reachable-by-injected-transcript question, are both pre-existing — equally true under claude today and for the five ids `90dc3c8c` already granted — and are tracked separately, not by this card.)

`CODEX_AUTO_APPROVE_MCP_SERVER_IDS` now equals `LOOM_FIRST_PARTY_SERVER_IDS` in full (all 8 first-party ids) — there is no longer a "withheld" subset. The `.size ===` pin in `codex-host-decisions.mjs` and the real-spawn argv pins in `codex-update-check-spawn-argv.mjs` were both updated in the same commit as the `pty/host.ts` change (see their own headers for what changed).

### Do not (this section)

- Do not read "now equals `LOOM_FIRST_PARTY_SERVER_IDS`" as "just widen to that constant going forward" — a NINTH first-party id, if one is ever added, needs its own reachability + proportionality pass before joining this set; the equality today is a consequence of the per-role analysis above, not a shortcut for future ones.
- Do not cite `platform`'s trust boundary as the reason `auditor`/`workspace-auditor` were granted — they were granted on their OWN routers' documented containment (see above), which this card's DoD required precisely because the platform precedent does not transfer to a role that ingests untrusted input.
