# fcf8a0f8 — a fleet reclaim onto a predecessor whose kill is in flight: RECLAIM, don't refuse

## Narrative

Raised by card `b59d11f6`'s own "Residual" section (unverified at the time): `recoverFleetAfterFailedRecycleSuccessor` (`sessions/service.ts`) gated "is the predecessor still viable" on `pty.isAlive(oldId)` alone. `PtyHost.stop()` sets `live.stopping = true` at the top of the call (both graceful and hard modes) and, for a hard stop, `live.killed = true` SYNCHRONOUSLY at `pty.kill()` — but `live.alive` does not flip to `false` until the async `'exit'` event actually lands, non-instant on Windows conpty's tree-walk kill path. A reclaim decision whose death observation lands in that window reads the predecessor as alive and reparents the fleet onto it while its own kill is still in flight.

**First cut (reverted): refuse the reclaim in that window.** Code Review `7c51b622` showed this makes the OUTCOME WORSE, not safer — the two end states were never compared before shipping it:

- **Reclaim (what actually happens today, deliberately):** the fleet moves onto M1. If M1's kill then genuinely lands, `archiveOnExit`'s `manager_exited_with_live_workers` branch (`@decision 6cd3ce9e`) sees the live workers it just reclaimed and refuses to archive — M1 stays on the live rail, visible, resumable, carrying the `[loom:orphaned-fleet]` banner, and the durable "your fleet is back" nudge (`enqueueDurableNudge`, filed unconditionally by the reclaim itself) survives as a queued message a human or a later resume can act on.
- **Refuse (the reverted fix):** the fleet stays on M2 — a confirmed-dead recycle successor with no engine id, structurally unresumable. M1, now with zero live workers at exit time, gets `archiveOnExit`'d outright (the `liveWorkers.length > 0` branch never fires). The settle path's own `finally` (`settleRecycleHandoff`/the watch loop) clears the durable settle-pending marker regardless of outcome, so no boot-time reconcile ever revisits this lineage either. The fleet is now stranded with no automatic owner and no durable trace pointing anyone at it.

A stranded fleet (refuse) is a strictly worse outcome than a reclaim onto a predecessor whose own death — if it actually lands — is already handled safely by existing, independent machinery. **Decision: reclaim, never refuse.** The `isStopping` read survives only as a diagnostic annotation (`predecessorStopping` on the `recycle_fleet_recovered` event) — never as a gate, anywhere.

Investigated at source (not assumed): there is exactly ONE function that gates a fleet reclaim on a predecessor's viability — `recoverFleetAfterFailedRecycleSuccessor` — reached by exactly 3 call sites (`settleRecycleHandoff`, `watchHaltedRecycleSuccessor`, `reattemptManagerOwnershipTransfer`, all `sessions/service.ts`), all of which delegate the decision to it. Every boot-time reconcile path (`finishReconcilingRecycleSettles`, `finishReconcilingHaltedRecycleSuccessors`, and their "early" halves) gates on `isDurablyResumable`/`resume()`, never a bare `isAlive`/`isStopping` read, and so was never exposed to this question at all.

A second, narrower site shares the predicate (not the window-vs-refuse question): `recordUnresolvedRecycleOutcome` reads `pty.isAlive(oldId)` to decide whether to call `db.restoreLiveAfterConfirmedAlive(oldId)` (platform role only). **A round-2 ruling briefly gated this one too, additionally on `!isStopping` — ALSO wrong, corrected in round 3.** `onPtyExit` (`pty/host.ts` ~7173) unconditionally sets `processState:"exited"` the instant the real `'exit'` event lands, independent of anything this restore wrote beforehand — so a premature "live" restore during the stopping window is never a lasting lie; the moment the stop genuinely lands, `onPtyExit` overwrites it, same as it always does. The reclaim path's own identical restore (`recoverFleetAfterFailedRecycleSuccessor`, line ~13846) has ALWAYS been ungated — gating only this sibling site was an asymmetry with no correctness benefit, and in the specific case where `live.stopping`'s own monotonic latch misreads the session as still-stopping when it is not, the gate makes things WORSE: it wrongly withholds the restore from a predecessor that is genuinely fine, leaving the DB stuck asserting `processState:"exited"` for a session that never actually died. Dropped; both restore sites are now symmetric, ungated.

## Mechanism

**`PtyHost.isStopping(sessionId)`** (`pty/host.ts`, beside `isAlive`/`isBusy`): reads `live.stopping` — true for the WHOLE duration a `stop()` (either mode) is in flight on this session, not merely the narrower kill()->'exit' sub-window the first cut used (`live.killed`). Uses the same `findAnyLive` lookup `isAlive` already uses, covering both the claude `Live` map and `CodexLive` uniformly.

**`recoverFleetAfterFailedRecycleSuccessor`**: reclaims unconditionally once the predecessor is confirmed alive (the pre-existing `!isAlive` dead-branch is unchanged) — `isStopping` is read ONCE, before the reclaim work, purely to annotate the outcome: `detail.predecessorStopping` on the `recycle_fleet_recovered` event. Nothing branches on it.

**`recordUnresolvedRecycleOutcome`**: the platform-only `restoreLiveAfterConfirmedAlive(oldId)` call is gated on `oldStillLive` alone, exactly as it was before this card touched it — `isStopping` is read nowhere in this function. `onPtyExit` owns convergence to `"exited"` when the real exit lands; no gate is needed here.

**`companion/attention-push.ts`**: unchanged from before this card — no new `reason` value is ever produced now, so no new clause was needed (the first cut's `"predecessor-stopping"` clause was added and then removed in the same card).

**Correction to this record's own earlier claim**: an earlier version of this record asserted `attention-push.ts`'s `alertLine` was the ONLY reader anywhere that branches on `recycle_fleet_unresolved`'s `reason` field. That was FALSE — `orchestration/crash-orphaned-workers.ts`'s `latestMatchingUnresolvedSettleEvent` (line ~158) also checks `detail?.reason !== "timeout"` to decide whether an unresolved event is the specific "settle timed out" shape. It was never updated because it was never found by a text search for the specific reason strings this card touched — the grep that produced the false claim searched for known reason VALUES, not for every place that reads the `reason` FIELD at all. Harmless in practice here (it already excludes anything that isn't `"timeout"`, and this card never introduces a surviving `reason` value other than the two that already existed), but the claim itself was wrong and is corrected here rather than left standing.

## Do not

- Do not refuse a reclaim onto a stopping predecessor — `archiveOnExit` already handles its exit safely (stays visible, resumable, bannered, with a durable nudge) if the stop actually lands; refusing instead strands the fleet on a confirmed-dead, unresumable successor with no durable trace once the settle path's own `finally` clears the pending marker. This was tried (Code Review `7c51b622`) and reverted.
- Do not gate `recordUnresolvedRecycleOutcome`'s `restoreLiveAfterConfirmedAlive` flip on `isStopping` (tried in round 2, reverted in round 3) — `onPtyExit` unconditionally overwrites `processState` to `"exited"` the moment the real exit lands, so a premature restore is never a lasting lie, and gating it is a pure asymmetry with the reclaim path's own identical, always-ungated restore. Worse, a `live.stopping` latch misread leaves a genuinely healthy predecessor's processState stuck wrong with nothing to correct it.
- Do not duplicate the `isStopping` read inline at each of `recoverFleetAfterFailedRecycleSuccessor`'s 3 call sites — keep it in the one chokepoint.
- Do not widen `isStopping` back to `killed`-only (the first cut's definition) — `live.stopping` is the correct, broader signal for "a stop is in flight." (It is no longer used as a gate anywhere, only as the `predecessorStopping` diagnostic, but keep the broader definition regardless — a future legitimate use of this read should not have to rediscover why `killed`-only was too narrow.)
- Do not treat `recycleWorker` as sharing this question — it hard-kills its own predecessor and WAITS for the real `'exit'` before proceeding, and a worker owns no sub-fleet to reclaim; there is no analogous decision there.
- Do not assume a grep for specific reason VALUES finds every reader of the `reason` FIELD — see the correction above; a future audit of this family should grep for `detail.reason`/`detail?.reason`, not for the string literals this card happened to touch.
