# 816f0056 — `VAULT_FLUSH_WORKING_TREE_TIMEOUT_MS` sizing (`VaultVersioner.flushSync()`)

## Narrative

`VAULT_FLUSH_WORKING_TREE_TIMEOUT_MS` (5 minutes) is the ceiling for `VaultVersioner.flushSync()`'s two WORKING-TREE-SCALE `execSync` calls (`git add -A`, which hashes every new/changed blob across the whole vault, and `git commit`, which runs the user's own hooks — the actual named hang vector in this card — plus writes tree objects). Deliberately much larger than `VAULT_GIT_OP_TIMEOUT_MS`: the goal on this path is "no INFINITE hang", not "fail fast" — `flushSync`'s timeout throwing lands in its own best-effort `catch` and SILENTLY DROPS the commit (now at least logged — see `flushSync`'s own doc), so a bound tight enough to fail a real, still-progressing flush on a large or network-backed vault would trade a rare hang risk for a routine, guaranteed data-loss failure. See `flushSync`'s own doc for why the THIRD call (`git status --porcelain`, a cheap stat-based comparison) is bound by `VAULT_GIT_OP_TIMEOUT_MS` instead.

**Sizing (review round 2 — corrects an earlier, wrong appeal to convention): this is NOT sized to match `git checkout`.** This repo's own `GIT_LOCAL_TIMEOUT_MS` (`git/writer.ts`) bounds `checkout` at the SAME 15s as `VAULT_GIT_OP_TIMEOUT_MS` — citing it as precedent for "5 min is generous" was backwards. The real basis: a cold `git add -A` over a 20k-file vault measured ~11.6s on local NVMe ALONE — comfortably eating a 15s bound with zero margin left for a slower disk or a bigger vault — so this needs to be in the same league as this codebase's OTHER genuinely-large working-tree op, `git/worktrees.ts`'s `PROVISION_TIMEOUT_MS` (3 min, for a full dependency install into a fresh worktree). 5 minutes sits comfortably above both.

## A timeout ABANDONS the child, it does not always STOP it (review round 2 finding 4; differs by call, round 3)

`git add -A`/`git status --porcelain` run via shell-string `execSync` (`cmd.exe` on Windows, spawned as the immediate child); a timeout kills only THAT shell — no job object, no tree kill — so the real `git.exe` it launched (a grandchild) survives and keeps running in the background. Measured: a `git commit` blocked in a `sleep` hook, timed out at 500ms via a shell-wrapped call, still landed its commit ~8 seconds later. `git commit` itself is different: it runs via `execFileSync` (no shell — see "Identity fallback" below), so `git.exe` IS the immediate child Node kills directly on timeout — but a hook grandchild it already spawned can still survive and run to completion harmlessly.

Whether the commit OBJECT itself lands is a RACE, not a fixed outcome (`test/vault-flush-sync-hang-bound.mjs`) — it depends on how far `git.exe` had progressed (had it already written the commit object and updated the ref?) before the kill signal reached it. Observed both ways on this exact test: in an ordinary worktree run the commit did not land; under merge-gate conditions (different host/scheduling timing) it did. Neither outcome is assertable, and the code does not claim either — "bounds a true hang" means bounds how long `flushSync` waits, not a guarantee about what the underlying git process does afterward, so its warn says a commit "may have been dropped," never a certainty.

`execSync`'s own native `timeout` option is the bound (can't use the async `withTimeout` race — `flushSync` is synchronous by necessity), plus `GIT_TERMINAL_PROMPT=0` so a credential prompt can't hang either. `execSync` THROWS on timeout expiry like any other failure, landing in the same best-effort `catch` a missing identity or plain git error would — the intended trade: a dropped shutdown auto-commit beats a wedged `gracefulShutdown` (which would otherwise hang `loom stop` and, worse, `daemon_restart`'s exit `75`, stalling the whole fleet).

## Identity fallback (review round 2 finding 2; round 3 correction)

Mirrors `commitVault`'s fallback via `hasConfiguredGitIdentitySync` — `flushSync` never had one at all, so a host with no configured git identity silently failed EVERY shutdown flush, forever, while the async `commit()` path succeeded. **Genuinely ARGS, not a shell string (round 3 correction):** the first cut of this fix interpolated the fallback identity into a shell-string `execSync` call — safe only BY COINCIDENCE, because `FALLBACK_GIT_IDENTITY` happens to contain no spaces today. `execFileSync("git", [...])` passes each piece as a real argument instead, so a future edit to that constant (e.g. adding a space) can never re-open the exact silent-drop failure this card closed.

## Do not

- Do not tighten this ceiling by appeal to `git checkout`'s 15s bound — that comparison was already tried and is wrong; the real basis is the measured `git add -A` cost on a large vault, not `checkout`'s cost.
- Do not make this ceiling as tight as `VAULT_GIT_OP_TIMEOUT_MS` — the goal here is "never hang forever," and a tight bound on this path converts a slow-but-working flush into a guaranteed, silent commit-drop.
- Do not assert whether a timed-out `git commit`'s object lands or not — it's a genuine race, observed both ways; only claim the flush *waits* bounded, never what the git process does afterward.
- Do not interpolate `FALLBACK_GIT_IDENTITY` into a shell-string `execSync`/`exec` call — use `execFileSync` with a real argument array, or a future edit adding a space to that constant silently reopens the identity-fallback failure this card closed.
