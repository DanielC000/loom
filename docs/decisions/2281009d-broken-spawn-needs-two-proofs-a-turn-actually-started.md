# 2281009d — `broken-spawn`: a non-null `engineSessionId` alone is not proof a turn ran

## Narrative

`broken-spawn` — `busy` fell to false WITHOUT the worker ever running a turn (the fresh-spawn kickoff race — host.ts's scheduleKickoffGuarantee / the short pre-first-turn healIfStuck window). Two independent proofs feed this, checked in order: `engineSessionId` is captured ONLY on the engine's own SessionStart hook, so `null` is definitive proof not even the kickoff ever started. But `engineSessionId` being SET is NOT proof a turn ran (card 2281009d) — SessionStart can fire while the kickoff sits unsent in the composer forever (card f91c8634's parked-Enter signature), so this ALSO checks the same "did a turn actually start" fact `handleKickoffGiveUpExhausted` uses (`hasFirstTurnStarted` OR a non-empty transcript) before falling through past this branch — keeping both nudge paths agreeing on one fact instead of one keying off session-id presence and the other off turn/transcript state. Either way: a DISTINCT failure, not a "did not report" stall.

A second, more detailed site of the same decision (the actual `if` guard in `classifyIdleWorker`'s body, not the summary JSDoc above it) extends the two-proof check to THREE signals, OR'd together: `hasFirstTurnStarted` (free, in-memory), a real `worker_report` event for this worker (`listEventsForWorker`), and a non-empty transcript. The `worker_report` addition matters because it's STRICTLY STRONGER evidence than the other two — an MCP tool call can only be made from within a live engine turn, so a worker that already reported and is legitimately parked (awaiting an ack, a wake, or a background task) is never wrongly reclassified as `broken-spawn` for the sole reason that its transcript read raced or its `hasFirstTurnStarted` flag hadn't yet been set. The three checks are deliberately ORDERED cheapest-and-most-decisive first — reordering the `&&` chain can never change the *result* (all three are side-effect-free reads), only its *cost*: (1) `hasFirstTurnStarted` is a free in-memory Map read; (2) `listEventsForWorker` is a local sqlite query, sub-ms; (3) `readTranscript` is SYNCHRONOUS filesystem I/O — for the exact case this branch targets (a transcript that genuinely doesn't exist yet), `resolveTranscriptFile`'s fast `existsSync` path always misses by construction, so this hits its full recursive fallback scan every time, measured at ~169-239ms worst case on a real `~/.claude/projects` tree of 5,778 dirs (that repo's own historical measurement, not remeasured here). Do not "tidy" the three checks back into declaration order — that silently reintroduces a synchronous FS scan on a path a cheap sqlite check would already have skipped.

## Do not

- Do not treat a non-null `engineSessionId` as proof a turn ran (card 2281009d) — SessionStart can fire while the kickoff sits unsent in the composer forever (card `f91c8634`'s parked-Enter signature).
- Do not let this classifier and `handleKickoffGiveUpExhausted` key off two different facts (one off session-id presence, the other off turn/transcript state) — both must check the SAME `hasFirstTurnStarted` OR non-empty-transcript fact.
- Do not reorder the `hasFirstTurnStarted` / `listEventsForWorker` / `readTranscript` checks back into declaration order — the ordering is deliberately cheapest-and-most-decisive first (free map read, then sub-ms sqlite query, then a synchronous FS scan measured at ~169-239ms worst case) to avoid a needless disk scan when a cheaper check already resolves the branch.
- Do not drop the `worker_report` OR-arm from the three-signal check — it's strictly stronger evidence than the other two (an MCP tool call can only fire from a live engine turn), and without it a worker that already reported and is legitimately parked gets wrongly reclassified as `broken-spawn`.
