# b1ea823d — the test-only reap guard survives gate load instead of crashing the test process

Card `b1ea823d` (from the `24608d33` classification): under gate load, `assertReapTargetIsOwnLiveDescendantUnderTest`'s own `powershell.exe Get-CimInstance Win32_Process` enumeration (pty/host.ts) was tighter-bounded than production's equivalent call, routinely ETIMEDOUT, and — because `refuseReapTarget` throws whenever the calling test process has a test-spawn registry — crashed the whole test process from inside a bare `pty.onExit` callback with nothing above it to catch the throw. A second, narrower race ("not a live descendant") hit the same call site when a just-exited root's own pid number was already reused by an unrelated process before the guard's enumeration ran.

Four independent fixes, all scoped to `assertReapTargetIsOwnLiveDescendantUnderTest` and its three real callers (`reapOrphanedDescendants`'s guard call, `killProcessById`, `killSingleProcessById`), plus `PtyHost.reapExitedDescendants`'s onExit chokepoint (the caller of `reapOrphanedDescendants` via `sweepOrphanedDescendants` that this whole card is really about):

## 1. The enumeration timeout floor

`TEST_GUARD_ENUMERATION_TIMEOUT_MS` was a hardcoded `5_000`, tighter than production's own `REAP_ENUMERATION_TIMEOUT_MS` (`10_000`) for the identical `powershell.exe`/`ps` call — backwards, since a test run under real gate concurrency (see `run_gate`'s own pinned `LOOM_GATE_TEST_CONCURRENCY` value, `CLAUDE.md`) contends with sibling test files for the same powershell/WMI resources production never has to share.

## 1b. The env seam rejects Infinity/fractional/non-positive values

Code Review `79a80cd5` (round 2): `resolveTestGuardEnumerationTimeoutMs(rawEnvValue, floorMs)` parses the raw env string with `Number(...)`, then requires `Number.isFinite` AND `Number.isInteger` AND `> 0` before accepting it. The original shape (`Number(v) || 0`) let `"Infinity"` and a fractional string straight through to `execFileSync`'s own `timeout` option, which THROWS `ERR_OUT_OF_RANGE` on every single enumeration call — the opposite of this card's goal (a bad env value would break every test, not just skip the override). An invalid value falls back to `floorMs`; a valid value below `floorMs` is clamped up, never accepted as a lower bound. Negative-controlled: reverting to the old `Number(v) || 0` shape reproduces exactly two red unit checks (Infinity, fractional) in `pty-root-reap-test-tripwire.mjs`'s own `(unit, timeout-clamp)` scenarios — the other edge cases (NaN, zero, negative) happen to still pass under the old shape by incidental JS truthiness, which is why only those two are the real hole.

## 2. Crash containment at the one onExit chokepoint

`PtyHost.reapExitedDescendants` (the single method both the claude and codex `pty.onExit` handlers call) now wraps its `this.sweepOrphanedDescendants(...)` call in a try/catch. The catch discriminates structurally, via a `code` property stamped on the thrown Error by `refuseReapTarget` (never by parsing `message`): `REAP_TEST_GUARD_ENUMERATION_FAILURE_CODE` is set ONLY on the could-not-enumerate refusal path. That one refusal is swallowed and logged (`[pty-reap] ... onExit sweep's enumeration-failure refusal caught at the exit chokepoint, not crashing`) because it proves nothing either way and nothing was killed either way — crashing the whole process to report "I couldn't check" serves no purpose. Every other refusal (the ancestry/lineage refusal above all) still rethrows unconditionally and crashes the process exactly as before this card — that is a genuine "would reap a pid we don't own" finding and must stay loud.

## 3. The just-exited pid-reuse race ("not a live descendant")

⛔ **CORRECTED by Code Review `79a80cd5` (round 2) — the original fix here was itself a kill-widening bug.** The original reasoning argued: "the guard returns `true`, execution reaches `computeOrphanSweepPlan`, which independently re-derives the identical tolerance comparison and aborts." That is false, because **the guard's own enumeration and `computeOrphanSweepPlan`'s enumeration are two SEPARATE, independently-timed OS reads** — `reapOrphanedDescendants`'s own enumeration is reached only after `rootReapEnumerationSemaphore.acquire(ROOT_REAP_ENUMERATION_QUEUE_TIMEOUT_MS)` (decision `6d484a46`, a 30s queue-wait bound), so the two snapshots can be taken up to ~30s apart under load. Concretely:

1. Our real root R (pid P, creation C0) exits.
2. An unrelated process F reuses pid P (creation C1 ≠ C0) and spawns a real child K (ppid P, creation C2 > C0).
3. The guard's enumeration sees P live with creation C1, mismatched against our known C0 → (ORIGINAL BUG) returns `true`, proceeds.
4. F exits before the SECOND (downstream) enumeration ever runs.
5. That second read finds NO live row at P at all (F already gone), so `computeOrphanSweepPlan`'s `liveRootRow` check never fires — there is nothing live to compare, so the live-root abort never triggers either. The walk proceeds to `byParent[P] = [K]`; K's own creation C2 is LATER than C0 (our real root's time — the only `rootCreationTime` `computeOrphanSweepPlan` was ever given), so the stale-ppid filter does **not** exclude it.
6. K — a real, unrelated process's child — is added to `toKill` and SIGKILLed.

The pre-card code (an unconditional throw) never reached this far: it refused and killed nothing. The original (now reverted) fix introduced the kill-widening bug by turning that refusal into a `true`/proceed.

### The fix (corrected)

The same proven-mismatch detection stands, but its action is inverted: **return `false` (a silent skip), never `true`, and never throw.** `reapOrphanedDescendants`'s own call site already reads the guard's boolean return and bails (`if (!assertReapTargetIsOwnLiveDescendantUnderTest(...)) return;`) — this is the SAME contract decision `dbbb52db` already established for every other refusal, so returning `false` here costs nothing new: no enumeration ever starts, no `deps.enumerate`/real OS spawn is ever reached, no kill is ever attempted. Logged once (`[pty-reap-test-guard] SKIPPED ...`), clearly distinguished from a REFUSED/error log line since this is not a bug finding — it is a correctly-recognized, already-understood race, the exact thing this card exists to stop treating as fatal.

**Win32-only in practice.** `enumerateLivePidPpidRowsForTestGuard`'s POSIX branch (`ps -eo pid,ppid`) carries no creationTime column at all, so `liveRow?.creationTime` is always `null` for a POSIX-enumerated row — the `expectedCreationTime != null` mismatch check above can only ever fire against a win32 CIM-enumerated row. This section's whole fix is structurally inert on POSIX; the pid-reuse race it guards against falls through to the unchanged, fail-closed ancestry walk there, same as before this card.

Traced across every caller that reads this boolean:
- **`reapOrphanedDescendants`** (the only caller that can ever reach this branch — the only one that passes `expectedCreationTime`): `return;` immediately. No enumeration, no kill. This covers `verifyRootDeadOrForceKill`'s own post-kill sweep too (`this.sweepOrphanedDescendants(rootPid, check.creationTime)`) since that call routes through the SAME `reapOrphanedDescendants` function.
- **`killProcessById`** / **`killSingleProcessById`**: neither ever passes a 3rd argument, so `expectedCreationTime` is always `null` for them and this branch can never fire. Their existing `if (!assert...) return;` contract is unchanged and was never the risk.

### Why this cannot widen what gets killed (now genuinely true)

The new path is a pure early-return with **zero** side effects — it is reached strictly BEFORE the sanity checks, the semaphore acquire, and the enumeration that the (unmodified) kill logic depends on. There is no second read for a bug to hide behind: nothing downstream ever runs for this call. When either creation time is unknown, or the two agree, this branch never fires and the ancestry walk runs exactly as before this card. Negative-controlled: reverting this one `return false` back to `return true` reproduces a genuine kill of a real spawned grandchild process in `pty-root-reap-test-tripwire.mjs`'s own scenario (H).

## 4. The still-unresolved creation-time capture at `reapExitedDescendants` (card `0201b378`)

Residual left open by section 3 above: `PtyHost.reapExitedDescendants` read `liveRef.creationTime` SYNCHRONOUSLY, at the exact instant `onExit` fired — before `armRootCreationTime`'s own async OS capture (`captureRootCreationRow(...).then(...)`, measured idle max 677ms / loaded max 1144ms, decision `87691385`) had any chance to settle. A fast-exiting session (the pty exits before that capture resolves) therefore ALWAYS reached the guard with `expectedCreationTime == null`, skipping section 3's mismatch check entirely and falling through to the unconditional, throwing ancestry walk — the mcp-config-secret-lifecycle incident's exact shape. `verifyRootDeadOrForceKill` already awaited this same in-flight promise (bounded by `ROOT_CREATION_CAPTURE_AWAIT_MS`, exported, default 3000ms) before its own guard-2 cross-check; `reapExitedDescendants` never did, for the EARLIER guard call.

### The fix

`reapExitedDescendants` is now `async`. Before calling `sweepOrphanedDescendants`, it awaits `Promise.race([liveRef.creationTimeReady, boundedTimer(ROOT_CREATION_CAPTURE_AWAIT_MS)])`, gated on `resolveRootReapPlatform() !== "linux"` — the exact same precondition `verifyRootDeadOrForceKill`'s own guard-2 wait already uses, and for the same reason: `armRootCreationTime` returns early on Linux and never arms `creationTimeReady` at all, so an unconditional await would hang this call forever there. This never widens what gets killed on a VERIFIED capture — it only gives section 3's existing "proven-reuse → silent skip" logic a real chance to fire, with real data, instead of falling through to the throwing ancestry walk for lack of a timely capture. On a capture that stays null (CR `018fba2a`: see the three residual shapes below), the sweep is merely DELAYED by at most the capture latency (≤3s, `ROOT_CREATION_CAPTURE_AWAIT_MS`'s own bound) — within an already-existing window (the ~0.6s capture itself, decision `87691385`, plus `reapOrphanedDescendants`'s own semaphore-queue wait, decision `6d484a46`) the ancestry walk already tolerated before this card.

Converting the method to `async` changes a genuine lineage refusal from a same-tick synchronous throw into an async rejection. Both real `onExit` call sites (`host.ts`, the claude and codex exit handlers) deliberately keep calling `this.reapExitedDescendants(...)` with NO `.catch()` — exactly as before this card — so a genuine refusal still surfaces as a loud, unhandled rejection rather than being silently absorbed; nothing downstream in either handler depends on this call's completion (both already treated it as fire-and-forget before this fix).

In production, nothing that previously completed synchronously now rejects: `assertReapTargetIsOwnLiveDescendantUnderTest` returns `true` immediately outside test mode (never reaching the enumeration/throw logic at all), and every other path inside `reapOrphanedDescendants`/`sweepOrphanedDescendants` was already async and documented "never throws past this handler" (decision `6d484a46`). The only new behavior is a bounded wait — up to `ROOT_CREATION_CAPTURE_AWAIT_MS` — before work that was already fire-and-forget at both call sites; nothing synchronously depends on this call's completion, in production or in the test suite.

**Does not close the residual completely — CORRECTED by Code Review `018fba2a`: three distinct shapes still leave `expectedCreationTime` null after the await, not one "enumeration failure."** (The enumeration-failure shape — the guard's OWN OS enumeration throwing — is a DIFFERENT, already-code-swallowed case; see section 2's catch, keyed on `REAP_TEST_GUARD_ENUMERATION_FAILURE_CODE`, not this residual.) The three:

(i) **A genuine verification failure.** The capture settles, but `resolveVerifiedRootCreationTime` rejects the row (no row found, a ppid mismatch, or a creation time later than `startedAt` + slack — see `armRootCreationTime`'s own `[pty-reap-capture]` log) — `liveRef.creationTime` stays `null` even though the await ran to completion.

(ii) **Linux.** `armRootCreationTime` returns early there and never arms `creationTimeReady` at all, and this fix's own await is deliberately gated OFF on Linux (see "The fix" above) — so on Linux the mcp-config-secret-lifecycle incident shape stays FULLY OPEN, not merely narrowed; this fix is win32/POSIX-non-Linux only, same scope as section 3's own mismatch check.

(iii) **The capture is genuinely slower than `ROOT_CREATION_CAPTURE_AWAIT_MS`.** The await's own bound (default 3000ms) is generous relative to the capture's measured ~0.6-1.1s typical latency, but a sufficiently loaded host could still exceed it.

In all three cases the unconditional ancestry-walk throw still fires, exactly as before this fix. What this fix actually closes is narrower: the "fast exit before an otherwise-successful, otherwise-timely capture gets a chance to even START settling" window — the dominant, and previously undocumented, cause of the mcp-config-secret-lifecycle shape on non-Linux.

## Do not

- Do not make the test-only enumeration bound tighter than `REAP_ENUMERATION_TIMEOUT_MS` again — define `REAP_ENUMERATION_TIMEOUT_MS` first in source order and derive the test bound via `resolveTestGuardEnumerationTimeoutMs(rawEnvValue, REAP_ENUMERATION_TIMEOUT_MS)`.
- Do not let `LOOM_TEST_GUARD_ENUMERATION_TIMEOUT_MS` lower the bound below the production floor — it is a ceiling-raising override only, never a replacement value.
- Do not widen the catch in `reapExitedDescendants` to swallow every throw — only the one `code` this file mints. A bare catch-and-log here would silently defeat the tripwire's whole reason to exist for every other refusal shape.
- Do not discriminate by matching `err.message` substrings — match `err.code === REAP_TEST_GUARD_ENUMERATION_FAILURE_CODE` only. Message text is for humans reading the log line, not for a catch site's control flow.
- Do not add this try/catch anywhere else (e.g. around a direct call to the free `reapOrphanedDescendants` function) — the two unit tests that assert a synchronous throw from a direct call (pty-root-reap-test-tripwire.mjs scenario A) call the free function directly, never through `reapExitedDescendants`, and must keep seeing the unmodified throw.
- Do not ever make section 3's mismatch branch return `true` — that is the exact regression `79a80cd5` found. A proven mismatch is reason to do NOTHING for this `rootPid`, never reason to proceed.
- Do not apply section 3's mismatch branch to `killProcessById`/`killSingleProcessById` (the guard's other two callers) — neither ever supplies `expectedCreationTime`, so the branch is structurally unreachable for them; don't add a 3rd argument to either call site to "complete the coverage" without a real need, since there is no comparable expected-creation-time source for a worktree-rooted kill target.
- Do not duplicate `computeOrphanSweepPlan`'s own tolerance comparison anywhere else, or diverge the two constants — both must keep reading `ROOT_CREATION_MATCH_TOLERANCE_MS`.
- Do not let section 3's mismatch branch fire when `expectedCreationTime` is `null` or the live row's own `creationTime` is `null` — an unprovable case must keep falling through to the unchanged ancestry walk (fail-closed, same posture as `computeOrphanSweepPlan`'s own "abort unless positively proven" default, decision `87691385`).
- Do not call `sweepOrphanedDescendants` before awaiting the bounded `creationTimeReady` race in section 4's fix — a fast-exiting root's still-unresolved capture must get a real chance to land first, or the guard reads a permanently-null creationTime it could have had.
- Do not await `creationTimeReady` unconditionally — gate it on `resolveRootReapPlatform() !== "linux"` exactly like `verifyRootDeadOrForceKill`'s own guard-2 wait; Linux never arms it, so an unconditional await hangs the call forever there.
- Do not add a `.catch()` at `reapExitedDescendants`'s two real onExit call sites — a genuine lineage refusal must still surface as a loud, unhandled rejection (the async equivalent of the old synchronous throw), never be silently absorbed.
- Do not assume section 4's fix closes every historical "not a live descendant" crash through this chokepoint, or every cause of a missing creation time — it closes only the fast-exit-before-capture timing window. Three distinct shapes still leave `expectedCreationTime` null and the ancestry-walk throw still firing (CR `018fba2a`): (i) a genuine verification failure (the capture settles but is rejected), (ii) Linux (the await is deliberately gated off, so the incident shape stays fully open there), (iii) a capture genuinely slower than `ROOT_CREATION_CAPTURE_AWAIT_MS`. None of these is the code-swallowed enumeration-failure case from section 2 — that is a different mechanism entirely (the guard's own OS enumeration throwing), not a missing creation time.
