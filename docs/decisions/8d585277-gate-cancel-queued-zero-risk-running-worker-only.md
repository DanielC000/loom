# 8d585277 — `gate_cancel`: QUEUED is zero-risk for any gate type, RUNNING stays worker-only

## Narrative

Card 8d585277: `cancelGateOp` is the manual cancel/supersede escalation for a case auto-supersede-on-merge does NOT cover — no merge decision exists yet (a known-failing base, a stale/unverified self-check, a force-push, a worker recycled mid-run). Manager-facing, PROJECT-SCOPED (`outcome:"refused"` for an op outside the caller's own project, checked before any mutation), resolved by the same `opId` a `run_gate`/`worker_merge_confirm` pending response or `gate_queue` entry already names (full id or an unambiguous prefix, via the same `GateSemaphore.findByOpId` resolution `gate_status` uses).

**QUEUED → zero process risk** (see `GateSemaphore.cancelQueued`'s own doc: `fn` was never invoked, nothing to kill) — cancels immediately. Supported for `gateType:"worker"` AND, since card 361520a0 (Half Two — see that card's own record), `gateType:"merge"`: a queued merge gate is just as zero-risk as a queued self-check, since nothing has been admitted or touched the canonical repo/worktree yet. `confirmWorkerMerge` now carries the same `GateCancelledError` catch `runWorkerGate` already had, which is what makes a withdrawn QUEUED merge settle as a clean `cancelled` `ConfirmMergeResult` instead of the crash-shaped `[loom:merge-failed] … errored: gate cancelled` it used to produce. `gateType:"deploy"` stays refused in BOTH phases — `deployOwnProject` has no such catch, so cancelling one would still crash-shape-throw; nothing establishes it's safe to add, and the card never asked.

**RUNNING → scoped to `gateType:"worker"` ONLY**, deliberately not treated the same as QUEUED: interrupting a RUNNING merge risks leaving staged residue in the canonical checkout mid-squash, which fails closed and needs a human to clear it by hand before any further merge on that repo succeeds (memory `concurrent-squash-merges-lose-work`, trigger 2; a fail-closed guard the source cites as `62fb673` refuses rather than absorbing it — that token is 7 hex characters, not a resolvable 8-hex card id, so it is preserved here uninterpreted rather than guessed) — a risk that simply does not exist for a gate that was never admitted. `run_gate`'s self-check remains the only gateType whose `fn` actually reads/forwards `cancelSignal` into `runGateStep`, so a RUNNING merge or deploy gate is refused in either case: refused honestly rather than silently issuing a cancel a caller might mistake for a supported one. A later reader must not "simplify" queued and running merge cancellation into one rule — they differ on purpose.

RUNNING, once past that gate (worker self-checks only): asks it to stop (`cancelRunning`), then waits up to `DEFAULT_GATE_CANCEL_VERIFY_MS` (the ADMISSION clock the op's own settle races against, never a bare wall-clock guess). Landing in time means the kill was VERIFIED, reported `cancelled`. Not landing in time reports NOT cancelled — the process tree's death is unverified, so the slot stays held rather than freed on an assumption; the run continues under its pre-existing `gateTimeoutMs` bound exactly as if no cancel had been attempted. A cancel that can't be verified is never worse than no cancel at all.

**Race with natural completion:** `cancelRunning` no-ops (`false`) if the op already left "running" by the time this call reaches the semaphore — reported as `not_cancelled` with the real reason, never a fabricated cancelled/failed outcome over a result that already landed for real.

**Ambiguity is project-scoped too** (Code Review finding B2-3): the first resolution is intentionally UNSCOPED so a clean, unambiguous global match belonging to another project still yields the informative `refused` outcome (the caller already typed that one id; confirming it exists elsewhere and isn't theirs is not a new disclosure). If that comes back `ambiguous` instead, its `ids` could include other projects' live opIds — so this RE-RESOLVES scoped to the caller's own project before returning anything: a clean hit within their own project proceeds normally, a still-ambiguous result only ever names their own project's ids, and no match within their own project reports `not_found` — never `ambiguous` — since none of the globally-ambiguous candidates was a valid target for this caller.

`params.intent`/`params.reason` (DoD-4 of this same card): folded into the same `detail` string threaded into `cancelQueued`/`cancelRunning`/`cancelRepoGuardOnlyWait` — already what a QUEUED cancel's `GateCancelledError.detail` (and a RUNNING cancel's captured abort reason) surfaces back out as the settled op's own `reason`, and from there into the `[loom:gate-cancelled]`/`[loom:merge-cancelled]` nudge text — so `cancelGateOp` is the ONE place that needs to compose it; nothing downstream needs its own intent/reason plumbing.

## Do not

- Do not treat QUEUED and RUNNING merge-gate cancellation as the same rule — QUEUED is zero-risk for any gate type (nothing admitted yet); RUNNING stays refused for `merge`/`deploy` because interrupting mid-squash leaves staged residue that fails closed and needs a human to clear.
- Do not report a RUNNING cancel as `cancelled` unless the kill was actually VERIFIED within `DEFAULT_GATE_CANCEL_VERIFY_MS` — an unverified death leaves the slot held, not freed on an assumption.
- Do not skip the caller-project re-resolution on an ambiguous global `opId` match — a still-ambiguous result must only ever name the caller's own project's ids, and a global-only match must report `not_found`, never `ambiguous`, once rescoped.
- Do not add intent/reason plumbing downstream of `cancelGateOp` — it is composed once, here, into the same `detail` string every settle/nudge path already reads.
