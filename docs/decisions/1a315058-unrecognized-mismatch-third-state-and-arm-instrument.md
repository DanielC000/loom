# 1a315058 — an unrecognized prompt-mismatch divergence gets a THIRD state, and every detection is now instrumented by arm

## Narrative

Card `1a315058` (a direct owner report: too many false `[loom:prompt-mismatch]` notices, too much churn) traced the architecture, not another implementation bug: `mismatchText` (`pty/host.ts`) was a chain of five recognized confirmed/benign shapes (`confirmedFusion` / `confirmedDivergedPrior` / `confirmedWrapperDeficit` / `confirmedAnsiStripDeficit` / `confirmedWrapperAwareFusion`), then a single shared "fallback" template — effectively an allowlist of known-benign shapes with "possible LOSS" as the default for everything else. Nine prior cards had each correctly fixed one benign shape; the false-positive rate survived all nine because the DEFAULT never changed.

Re-tracing the fallback found it is actually FOUR sub-populations sharing one template, not one: (i) a recognized-but-unconfirmed replay (`isRecognizedReplayAwaitingResolution`, `replayedEntry !== undefined`) — correctly worded per `b7158b99`, arms the resolve-timer (`f9b1ea00`), UNCHANGED by this card; (ii)/(iii) the two already-benign offset shapes (`00b5066e`, "NOT A LOSS" wording), UNCHANGED; and (iv) genuinely unrecognized — no exact match, no offset reconciliation, at most a partial substring recognized (`unmatchedRecognized`, `d005f55b`) — which is the ONLY population that said "may not have reached you at all — a possible LOSS... not established" while offering nothing actionable to check.

`b7158b99`'s own record (line 15) states the genuinely-unmatched branch's "possible LOSS" framing "stays correct as-is" — that claim is now SUPERSEDED for this specific sub-population by this card: the wording still correctly declines to assert an ESTABLISHED benign explanation, but no longer asserts loss either. New const `isTrulyUnrecognizedDivergence = isUnmatchableMismatch && !(isOffsetInsertion && !unmatchedRecognized) && !(isOffsetOmission && !unmatchedRecognized)` isolates exactly population (iv), disjoint from `isRecognizedReplayAwaitingResolution` by construction (the two partition `!confirmedFusion && ... && !confirmedWrapperAwareFusion` on `replayedEntry` definedness) — so this new branch structurally can never arm the resolve-timer; nothing needed suppressing.

New wording for population (iv): `UNRECOGNIZED, NOT AN ESTABLISHED LOSS — Loom could not classify this divergence as any of its known-benign shapes ..., and it also could not confirm the content was lost; this is a THIRD state, distinct from both.` — followed by the existing `replayNote` (unchanged; still names any partial substring recognized, or that no prior write exists), and a closing that does NOT ask the recipient to audit its own artifacts for a duplicate (there is nothing recognized to have duplicated).

A DoD-3 sub-question — should the fallback notify the session at all, or route to the manager only — was resolved by checking `sessions/service.ts`'s `handlePromptMismatchUnmatched`: `if (!s?.parentSessionId) return;` means a session with no parent (a top-level manager — the exact shape of this card's own live specimen) gets ONLY the session-facing notice. Removing it would silently drop the one channel a parentless session has for a genuine, unrecognized divergence — exactly what DoD-2 forbids. The session-facing notice for this arm stays, reworded rather than removed.

While verifying that manager-push path, found a second, more actionable defect in the SAME population: `handlePromptMismatchUnmatched`'s `senderMsg` (`sessions/service.ts`) unconditionally said "a possible LOSS of N char(s)" for the WHOLE `isUnmatchableMismatch` population it's called on — including the two already-benign offset shapes, which the SAME event's session-facing notice tells the recipient is "NOT A LOSS". One event, two recipients, two contradictory verdicts. Fixed by threading the already-computed arm classification (`mismatchArm`) across the `onPromptMismatchUnmatched` event boundary as a new `arm: string` field, and branching `senderMsg` on it: the two benign-offset arms get a "NOT A LOSS" senderMsg mirroring the session-facing wording; only the truly-unrecognized arm keeps the "possible LOSS" wording (correctly, for the manager/sender, who — unlike the recipient — is positioned to actually resend).

DoD-1's instrument extends the EXISTING `[prompt-echo]`/`[prompt-mismatch]` log pair (already a usable denominator/numerator, per this card's own measured 0.96%-of-5290 baseline) rather than building a new counter: a `mismatchArm` local, computed to mirror `mismatchText`'s own real branch precedence exactly, feeds one new `[prompt-mismatch-arm]` log line — logged UNCONDITIONALLY (before the exact-repeat-suppression branch) so a suppressed repeat is still counted, carrying `delivered=<!isExactRepeatNotice>`, both hashes, and both lengths. A second new line, `[prompt-mismatch-unmatched-pushed]`, marks the sender-push half. The pre-existing `[prompt-mismatch-unresolved]` line (`checkPromptMismatchUnresolved`) already carries gen+hashes for the "unresolved" arm and needed no change.

## Do not

- Do not fold `isTrulyUnrecognizedDivergence` back into `isRecognizedReplayAwaitingResolution`'s own population, or vice versa — they partition disjointly on `replayedEntry` definedness; conflating them would either re-arm the resolve-timer for an unrecognized-but-not-replayed shape, or silence it for a shape that legitimately needs it.
- Do not restore a "possible LOSS" senderMsg for the two already-benign offset arms in `handlePromptMismatchUnmatched` — that reproduces the exact one-event-two-contradictory-verdicts defect this card fixed.
- Do not log `[prompt-mismatch-arm]` only on the delivered branch — a suppressed exact-repeat is still a real detection and must still be counted, or the arm-by-arm rate becomes an undercount relative to the `[prompt-echo]` denominator.
