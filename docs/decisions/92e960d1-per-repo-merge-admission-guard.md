# 92e960d1 — A per-repo merge-admission guard serializes same-repo merges independently of the worktree guard

## Narrative

Card 92e960d1: `GateDescriptor.repoPath` is the CANONICAL repo path a MERGE gate targets — set ONLY at the merge-gate call site (`confirmWorkerMerge`, resolved via `resolveRepoByKey(project, worker.repoKey).path`, never a bare `projectId`, so two DIFFERENT repos on the same multi-repo project are never cross-serialized). Never set on a `worker`- or `deploy`-kind descriptor. THE HAZARD THIS CLOSES: two `merge`-kind gates admitted concurrently for the SAME repo race to squash — at most one lands (canonical main is a single shared resource), and the other burns a full gate run before `mergeBranchLocked`'s `requireCanonicalHead` re-check fails closed and aborts it; this field lets the semaphore refuse to ADMIT the second one at all, queueing it instead.

AT THE TIME THIS FIELD WAS ADDED it was NOT yet a fix for the second merge's own odds of landing: its captured `gateBaseMainHead` was fixed before it ever reached this semaphore, so a same-repo merge landing while the second was queued still left the second stale on admission — still ran its own gate, still self-aborted. Card `b798e706` (fast-follow) re-derives `gateBaseMainHead` at the instant of admission (`confirmWorkerMerge`'s `reunionAtAdmission`), but by itself left the HEADLINE scenario open: this guard's own `release()` used to free the moment a running merge's GATE settled, strictly before that merge's own squash. CLOSED FOR REAL by card `c24dd48a`: `runExclusive`'s `fn` can call the `holdRepoGuardOnExit` callback it's handed to keep the guard held past the gate's own settle, and `confirmWorkerMerge` extends that hold across its own squash via `beginSquash`/`endSquash` — so a queued same-repo sibling is not admitted until the holder's squash has actually landed (or failed). A residual TOCTOU window remains BY DESIGN (a landing at the exact admission instant), caught fail-closed by `requireCanonicalHead`'s own in-lock re-check at squash time — this guard only ever narrows the admission window, never replaces that check.

`GateSnapshotEntry.repoContended` names the ONE cause this field's own contention is: while `phase:"queued"`, whether THIS entry's per-repo guard is currently the reason (or one of the reasons) it isn't admitted — another `merge`-kind gate for the same repo is already RUNNING. Always `false` while running, and for a non-merge or repoPath-less descriptor. A live, point-in-time read, recomputed fresh on every `snapshot()` call, never cached at enqueue time — it can flip between two reads of the same still-queued entry as sibling ops settle. Before this field, "queued" only ever meant cap contention or the pre-existing per-worktree guard (card `8d585277`, which this field does NOT cover) — without it, an operator reading `gate_queue` with a free cap slot and a queued merge would see something that looks like a bug instead of the deliberate repo-exclusivity wait.

## Do not

- Do not assume `release()` freeing the per-repo guard the moment a merge's GATE settles is sufficient — a queued same-repo sibling must wait for the holder's own SQUASH to land too (`holdRepoGuardOnExit`/`beginSquash`/`endSquash`, card `c24dd48a`), or two same-repo merges can still race at squash time.
- Do not read a queued merge with a free cap slot as a bug — check `repoContended` first; it names the deliberate per-repo exclusivity wait this guard adds, distinct from cap contention or the per-worktree guard (card `8d585277`).
