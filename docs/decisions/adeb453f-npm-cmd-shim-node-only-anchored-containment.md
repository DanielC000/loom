# adeb453f — the npm cmd-shim parser matches one anchored node-only block, with containment, and refuses pnpm-global/npm≤6 shims rather than also parsing them

Card `adeb453f`, non-blocking findings from the delta Code Review (`dfbb791e`) of card `7b2670d8` /
commit `a92c4490` (`pty/resolve-bin.ts`'s `parseNpmCmdShim`/`winCmdShimSpawnTarget` — see also
`docs/decisions/8ddd12c6-win-cmd-shim-safe-quoting-not-shell-true.md` for why this module exists at all:
a resolved `.cmd`/`.bat` is parsed and spawned as node + its real entry script, never routed through
`cmd.exe`).

## What changed and why

1. **Interpreter was never checked.** `cmd-shim` derives its shim's `_prog` from the target script's OWN
   shebang interpreter — any word (`node`, `deno`, `bun`, `python3`, ...), not always `node` — so a
   cmd-shim for a deno/bun-shebanged package with a `.js` entry is a perfectly real, legitimately-shaped
   shim that sets `_prog` to that other interpreter. The old parser extracted the entry path and always
   launched it under node regardless of what `_prog` actually named, silently misinterpreting it. Fixed
   by requiring both `_prog` markers to literally name `node`/`node.exe`.

2. **The entry-extraction regex wasn't anchored.** It matched the first occurrence of an
   invocation-shaped substring ANYWHERE in the file, so a `REM "%_prog%" "%dp0%\..\decoy.js" %*` line
   placed before the real invocation would win. Fixed by matching the ENTIRE node-interpreter dispatch
   block (the `IF EXIST`/`ELSE` `_prog` assignment through the `endLocal & goto ... "%_prog%" ...
   "%dp0%\<entry>" %*` invocation) as one contiguous pattern, and additionally requiring it to match
   EXACTLY ONCE in the whole file — a decoy occurring anywhere else (behind a `REM`, or duplicated)
   either fails to match at all (lacking the real preceding `_prog` block) or, if a full decoy block were
   somehow duplicated, trips the "found N, expected 1" refusal instead of silently picking the first.

   The combined regex also naturally enforces that nothing but whitespace sits between `"%_prog%"` and
   the entry's opening quote — a real cmd-shim whose shebang carries extra interpreter args (e.g.
   `#!/usr/bin/env node --harmony`) inserts that text in exactly this gap, so such a shim is refused
   rather than silently dropping the flags or misparsing them as part of the path.

3. **Containment.** The captured relative entry is normalized (`\` → `/`, so `..` segments are
   recognised the same way on every host OS, not just win32) and resolved; if the result doesn't stay
   inside the shim's own directory tree, `parseNpmCmdShim` refuses. Low severity on its own (whoever
   writes the `.cmd` already controls what gets executed), implemented anyway because it was cheap and
   now has a real test.

4. **Doc wording.** The old doc comment implied "arbitrary shell logic is refused." The real guarantee
   is narrower and stated positively now: a file is accepted iff it carries the dp0 lookup AND the
   node-interpreter dispatch block matches exactly once with an in-tree entry; content OUTSIDE that
   matched block is never inspected and never matters, because Loom never executes the `.cmd` file
   itself — it spawns the resolved node binary directly against the resolved entry path, so any other
   line in the file (real or decoy) is dead text from this module's point of view.

## pnpm-global and npm≤6 shims: refused, not supported

The npm ≥7 shape (`%APPDATA%\npm\codex.cmd`/`corepack.cmd`/`pnpm.cmd` on this host, all genuine
`npm install -g` outputs) is the one quoted in `resolve-bin.ts`'s own doc comment above
`NPM_CMD_SHIM_NODE_BLOCK_RE` — not repeated here.

**pnpm-global (`pnpm add -g <pkg>`)** — generated by actually running `pnpm add -g semver` in an isolated
throwaway `PNPM_HOME` (never the real one), the resulting `semver.CMD` (captured 2026-10-04):
```
@SETLOCAL
@IF NOT DEFINED NODE_PATH ( @SET "NODE_PATH=...;..." ) ELSE ( @SET "NODE_PATH=...;...;%NODE_PATH%" )
@IF EXIST "%~dp0\node.exe" (
  "%~dp0\node.exe"  "%~dp0\global\5\.pnpm\semver@7.8.5\node_modules\semver\bin\semver.js" %*
) ELSE (
  @SET PATHEXT=%PATHEXT:;.JS;=;%
  node  "%~dp0\global\5\.pnpm\semver@7.8.5\node_modules\semver\bin\semver.js" %*
)
```

**npm ≤6** (`cmd-shim@2.x`, confirmed from its published source) is the SAME family — no `dp0`/`_prog`
indirection, `%~dp0` used directly, and the real invocation written out TWICE (once per `IF EXIST`/`ELSE`
branch, which would need cross-validating against each other to trust), vs. npm ≥7's single `_prog`-
indirected invocation line. The pnpm shape additionally embeds a mutable global-store generation index
(`global\5\...`) in the entry path. Materially different and less deterministic than the modern-npm block
this parser anchors to — not a shape worth special-casing.

## Do not

- Do not loosen `NPM_CMD_SHIM_NODE_BLOCK_RE` to lenient-match a shim missing the literal node `_prog`
  markers, and do not drop the "matches exactly once" requirement in `parseNpmCmdShim` — either reopens
  the wrong-interpreter and decoy-line defects this card exists to close.
- Do not special-case the pnpm-global or npm≤6 template to also parse it. If real demand shows up, it
  needs its own anchored, cross-validated parser (matching both branches and asserting they agree) — not
  a loosened version of the modern-npm regex above, and not a shared code path with it.
- Do not remove the containment check as "low value" now that it exists and has a test — the entry is
  attacker-shaped input from whoever wrote the `.cmd`, however low the realistic severity.
- Do not reintroduce `cmd.exe`/`shell:true` for a pnpm-global or npm≤6 shim "just to support it" — see
  `docs/decisions/8ddd12c6` for why that's refused categorically, not just for the modern-npm shape.
