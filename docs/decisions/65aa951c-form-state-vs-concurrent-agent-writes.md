# 65aa951c — a settings form diffs against the seed it last synced from, never against the live row

The follow-up half of [654869e2](./654869e2-config-deltas-not-echoes.md). That record covers forms that echoed a whole CACHED SERVER OBJECT back; this one covers three that echoed their own MOUNT-TIME FORM STATE. Same loss, different route: `Settings.tsx`'s `ConfigEditor`, `Profiles.tsx`'s `ProfileEditor` and `Projects.tsx`'s `AgentEditor` each seeded `useState` once at mount and then re-sent every modelled field on Save, reverting any write an agent had made to that record since — a manager's `project_update`, a Platform Lead's `agent_update`, the Setup operator's profile tools.

One shared primitive: `packages/web/src/lib/formSync.ts` (pure algebra) plus `useFormSync.ts` (the React bookkeeping each form was doing by hand). The split keeps the pure half importable by `packages/web/test/form-sync.mjs` under bare `node --experimental-strip-types`.

## Do not

- **Do not decide "the human changed this" by comparing local state to the record's CURRENT value.** Compare to the SEED the form last synced from. Only a seed that lags the live row can express "stale, and the human never chose it" — against the live row, a field an agent rewrote reads as a pending human edit, which is exactly how `AgentEditor` armed its own Save button with text nobody typed.
- **Do not rely on the re-sync alone.** It fires only when the query actually refetches, and nothing guarantees one: react-query refetches on invalidation or `visibilitychange`, so a human can sit on Settings for an hour with no refetch at all. The DELTA is the load-bearing half — an untouched field is never on the wire, so the server's own value survives with no refetch required. The re-sync is the honesty half: it keeps the form showing the truth and stops a stale field reading as dirty.
- **Do not hold the seed in a `useRef`.** `dirty` is derived from it, so advancing it must re-render; with a ref, the one path that adopts nothing — the record refetching after this form's OWN save, where local already equals the row — advances the seed silently and leaves the editor reading "unsaved changes" forever. Measured, not reasoned: the first implementation did this and only `profile-harness-codex-save.spec.ts`'s `expect(getByText("saved")).toBeVisible()` caught it. Full account: project memory `seed-backed-dirty-must-be-state-never-a-ref`.
- **Do not re-seed the whole form from a save's response.** Only the Save BUTTON is disabled during a save; the inputs stay live, so a field typed into while the PATCH was open holds a draft the response knows nothing about, and adopting the persisted record across every field destroys that keystroke silently — the owner watches their own typing vanish while the save reports success. `onSaved(persisted, sent)` adopts a persisted value ONLY into a field whose local value still equals what was SENT. That snapshot therefore has to ride as a mutation VARIABLE: react-query re-reads the options object every render, so `values` read from an `onSuccess` closure is whatever has been typed *since* — which is the state to compare against, never the stand-in for what was sent.
- **Do not retire a conflict by clearing the whole list.** Retire a field when it stops DIVERGING from the row (`retainConflicts`): one field settling must not erase a live conflict on another the human has not dealt with yet. Convergence is what clears the notice after the form's own save, since local then equals the stored row and there is nothing left to overwrite. The render-time "is this field still changed" filter HIDES a never-cleared flag at rest, which is why only a RE-EDIT exposes one — `ProfileEditor` and `AgentEditor` both shipped with that bug while Settings cleared its list, and three hand-rolled copies drifting is the whole argument for there being one.
- **Do not report a conflict when the record moved TO the value the human is holding.** That is the ordinary post-save refetch, and flagging it makes every successful save accuse itself. A conflict is: the human touched the field, AND the record moved, AND the record's new value still differs from theirs.
- **Do not leave a field whose SERVER value can invalidate the save to the delta.** A delta knows what the human changed, not what the store holds. `clearCodexRejectedFields` makes a payload storable on codex, but the delta then drops a cleared field that already equals the seed — and an agent writing `browserTesting: true` after mount leaves the store holding a value `validateProfile` REFUSES while the patch carries only `harness`. The server merges the two and 400s, with no control to fix it (disabled on codex) and no warning either (that copy is computed from local state, which is already clear). So a switch ONTO codex sends the whole `CODEX_REJECTED_FIELDS` set explicitly. Only that direction: nothing is refused on claude.
- **Do not start `ConfigEditor`'s `buildOverride` from `structuredClone(ov)`.** The clone re-asserted every unmodelled stored key on every save — including one the REST validator REJECTS (654869e2's instance 4) — and it put `kanbanColumns` into the dirty comparison, so saving the column layout in the panel above made this form read "unsaved changes" with an armed Save the owner never touched. The PATCH deep-merges, so the clone preserved nothing.
- **Do not split an atomic stored object across a field-level delta.** `orchestration.alertWebhook` is ONE stored object built from two form fields; sending `{url}` without `events` 400s on the server's "both required", so either half changing sends both. The delta is per FORM FIELD with explicit `include(...)` guards, never a generic path-diff over the built override — a path-diff cannot know which subtrees are atomic.

## The shape

`changedFields(seed, local, comparers)` drives BOTH the save payload and `dirty`, so Save can never offer a save that would send nothing nor hide one that would send something. `reconcileSeed(seed, local, next, comparers)` returns `{values, adopted, conflicts}`; the caller applies `values` and advances the seed to `next` WHOLESALE — including for a conflicting field, so a held edit is measured against the record as it is now rather than re-reported forever. `retainConflicts` advances the accumulated conflict list across one reconcile.

`useFormSync(row, project, local, apply, comparers)` holds all of it. `row` (the raw server value) and `project` are separate arguments on purpose: the reconcile must fire exactly when the row moves, and a projection rebuilt every render is a fresh object each time, so passing one as the effect's dependency would reconcile on every keystroke instead.

Each form supplies a field record, a projection of its server row, and per-field comparers mirroring the normalization its own save applies. A comparer wrong in the lax direction loses an edit; wrong in the strict direction sticks the form dirty against a value the server normalized — which is why `ConfigEditor` re-seeds from the save RESPONSE, not from what it believes it sent. `sessionEnv` is outside all of this: it keeps its own stricter delta protocol (card `32b23f0f`), so `ConfigEditor` ORs `sessionEnvDirty` on separately.

## Why a unit test was not enough

The defect is a `useState` initializer sampling the record once at mount, and a pure test cannot see WHEN its caller samples state — the same limit 654869e2 recorded for its own planner. `test/form-sync.mjs` covers the algebra; `e2e/concurrent-agent-write.spec.ts` covers the wiring, and its fixture ORDER is the whole test (that spec's own header states the rule). Everything here was proved RED against the pre-fix sources.

⚠️ Two round-2 specs first went red at the WRONG assertion: they drove the refetch with a `focus` event, which react-query v5 ignores, so they failed for the instrument rather than the bug. A test asserting a notice APPEARS has to be shown to reach that state before its absence proves anything.
