# e312b207 — LIVE-COMMITMENTS floor unioned with the rules file, order-independent of the migration

## Narrative

Owner-approved option (a): move §LIVE COMMITMENTS out of the rotating active resume doc into the non-rotating `Orchestrator Rules.md`, and move its count guard with it. Before this card, `countNumberedSection` was called against `input.activeText` alone, while the marker check already unioned against `rules` — so moving the section into the rules file, on its own, would have made every future rotation's floor check refuse a perfectly correct doc (the section it's looking for would no longer be where it's looking). `countNumberedSectionUnion` closes that gap the same way the marker union already works: `activeText` is tried FIRST (byte-identical behavior while the section stays in the active doc), `rulesText` is consulted ONLY when `activeText` carries no such heading at all. This makes the two landings — this guard shipping the union, and the lead separately moving the section into the rules file — order-independent: neither ordering of "guard ships" vs. "vault moves" ever produces a seat where a section that genuinely still exists somewhere durable reads as missing. This mirrors `rotation-gate.mjs`'s own extension of the exact same shape (the script this module ports). FAIL-CLOSED throughout: `count: null, source: null` when the heading is in NEITHER text is the catastrophic "the block was lost outright" case, and callers must treat a null count as a hard failure, never a vacuous "0 items, nothing to check, ok:true" — the union only widens WHERE a hit can come from, never what happens when there is no hit at all.

AMBIGUITY (code review): `findHeadingLine` matches ANY heading containing the configured token, so a post-move breadcrumb left in the active doc — e.g. "## §LIVE COMMITMENTS — moved to Orchestrator Rules.md" — still counts as "found in active" and SHADOWS the now-authoritative rules-file section (active wins by precedence; the rules file is never even read for the count in that case). A doc in that shape can green at exit 0 while the real, current block goes unmeasured. `countNumberedSectionUnion` does not change WHICH count wins when this happens — hard-failing "found in both" would reopen a red window during the migration itself, and is a deliberate non-goal — it only makes the shape VISIBLE via `ambiguous`/`otherCount`/`otherDiagnostic` so `checkRotation` can surface a loud, non-gating warning instead of a silent green.

CORRECTION (code review, on `RotationCheckResult.rulesCheck`'s own doc): an earlier version of that field's doc stated `rulesCheck.ok:false` is "unaffected" by / has no bearing on the overall `ok`, full stop. That was overstated. `rulesCheck.ok:false` never DIRECTLY flips `ok` (it is not a term in the `ok` formula), but it can still flip `ok` INDIRECTLY, through `liveCommitments.ok`/`missingMarkers` themselves: once the rules-file union is the ONLY remaining place a marker or the LIVE COMMITMENTS heading survives (e.g. after it moves out of the active doc into the rules file), an unreadable `rulesPath` removes that sole remaining source, and the corresponding check genuinely fails — dragging `ok` down with it, same as if the content were simply absent. This is correct behavior, not a bug: "the rules file couldn't be read" and "nothing durable protects this any more" are the same practical situation from the caller's side. The one thing that truly never happens is `rulesCheck.ok:false` flipping `ok` while everything it could have supplemented is ALREADY satisfied by the active doc alone.

## Do not

- Do not read a green `ok` as proof the active doc alone protects this seat — check `rulesCheck`/`liveCommitments.source` too; the union may be doing load-bearing work.
- Do not "fix" the ambiguity case to hard-fail on "found in both" — that reopens a red window during a doc's migration from the active doc into the rules file, which is a deliberate non-goal.
- Do not restate "`rulesCheck` is not folded into `ok`" as "`rulesCheck.ok:false` can never affect `ok`" — the indirect path through `liveCommitments`/`missingMarkers` is real.
