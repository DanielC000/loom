# 95940402 — verify each batch-landed commit's parent and tree before pinning it

## The hole

Card `043d83d2` pinned the batch merge's assembled tip from `assembleBatchBranches`'s own landing results instead of a late, independently-readable `rev-parse HEAD` — but its third Code Review named an OPEN RESIDUAL it did not close: `landBranchCommitsIndividually`'s own `newHead`/`landedSha` bookkeeping is itself captured via a late `git rev-parse HEAD` immediately after each candidate's own `commit`/`commit --amend` (two separate spawned processes, however immediately sequential). A racer who swaps the batch worktree's ref to a forged SAME-TREE commit X (same tree, different parent/author/trailers) in that narrow window gets X read back as `newHead`/`landedSha` — X becomes `assembledTipSha`, the pin every downstream check (the pre-gate stamp, the post-gate stamp, the fast-forward target, the ledger/trust stamp) treats as legitimate, because none of those checks re-verify the COMMIT's own identity, only that the WORKTREE REF didn't move again afterward. X can carry whatever `Loom-Worker-Branch:` trailer the forger planted, read by hold-release/`findLandedSquashCommit`'s own ALREADY_MERGED detection as if it were a genuine, already-landed commit for whichever branch the forged trailer names.

This is the batch twin of the solo squash path's own `2a6a292a` round-21 `verifyLandedAsOwnCommit` fix — the batch path had no equivalent at all.

## Reproduced

`packages/daemon/test/batch-merge-head-moved.mjs`, scenario (K): a real `runBatchedMerge` call with a `gitFactory` seam hooking the plain `git commit --author ...` call (never the pathset `--amend`) — after letting the real commit land, it reads that commit's own tree, creates a forged sibling commit sharing the SAME tree but parented on an unrelated commit (`git commit-tree <tree> -p <decoy>`), and swaps the batch worktree's HEAD to it via `git update-ref`. RED before this card's fix (confirmed via a temporary revert of `batch-merge.ts` alone, rebuild, re-run, re-apply, rebuild): the forged commit was silently adopted as the candidate's own landed sha, the gate ran, and canonical main was fast-forwarded onto the forged content. GREEN after the fix: refused `batchHeadMoved`, the gate was never invoked, canonical main stayed untouched.

## The fix

1. **Extract the solo path's own parent+tree(+single-parent) identity check into a shared, exported function** (`verifyCommitParentAndTree`, `git/worktrees.ts`) — the SAME mechanism `2a6a292a` round 21-23 built (parent equality, exactly one parent via `cat-file -p` header parsing — immune to `info/grafts`/replace-refs, tree equality), now callable from both `mergeBranchLocked`'s own `verifyLandedAsOwnCommit` closure (which delegates to it, unchanged behavior) and the batch path. Reused, never duplicated, per this card's own instruction.

2. **`landBranchCommitsIndividually` captures the staged tree right before EACH candidate's own `git commit`** (`git write-tree`, in the same adjacency window `c862f14c` already established for the solo path — no git call between the capture and the commit), pins the expected parent as the pre-commit `currentHead`, and verifies the post-commit `rev-parse HEAD` read against both before trusting it — replacing the old bare `newHead !== currentHead` check (which only proved SOMETHING moved HEAD, not that it moved to OUR commit). A mismatch refuses `batchHeadMoved`, mirroring every other worker-writable-ref check in this function: no rollback attempted (the outcome discards the whole batch worktree regardless, and a worktree whose ref a racer is actively contesting isn't safe to reset either), no per-candidate fallback.

3. **The final post-loop `landedSha` read — the exact late re-read the card names — is verified the same way**, against the LAST commit's own (parent, tree) pair (tracked across iterations in `lastExpectedParent`/`lastExpectedTree`, always describing the most recent commit once the loop ends). This single check covers the window after the per-commit check too, INCLUDING the pathset `--amend` step: an ordinary `git commit --amend -m <msg>` with nothing re-staged in between changes neither the parent nor the tree, so verifying against the pre-amend commit's own (parent, tree) is correct whether the amend landed, failed, or was itself raced — a racer who swaps HEAD before the amend produces a result whose parent is the FORGED commit's own parent, not ours, so this same check still catches it.

## Round 2 (Code Review 4933cb39) — the content-identical-racer residual, closed for the Loom trailer specifically

Round 1's own "Named residual" section claimed parent+tree alone was the whole fix and left message/trailer forgery as an inherited, unclosed gap — that claim is SUPERSEDED by this round and no longer appears in this record. Code Review 4933cb39 reproduced that exact gap LIVE against commit `2b5a9ebf`: a `commit-tree -p <the REAL parent>` substitute, sharing the REAL tree too, differing only in a forged `Loom-Worker-Branch: some-other-branch` message — landed on canonical main with `ok:true`, at both the plain-commit hook (a single-commit branch's tip) and the pathset `--amend` hook. The RULING: fix the trailer forgery in THIS card via a message check, not via `commit-tree`+CAS (the owner declined silently dropping commit hooks on Loom squash commits — record `356538ef`, request `b0fb1e26` — and `commit-tree` bypasses them).

**The fix:**

4. **`verifyCommitParentAndTree` also returns the raw commit body** (`cat-file -p` already reads it) — `{ok, body}` instead of a bare boolean. `body` is present whenever the read itself succeeded, even on an `ok:false` parent/tree mismatch, so a caller inspecting trailers never needs a second read of the same object. The solo path's own `verifyLandedAsOwnCommit` closure (`mergeBranchLocked`) is updated to match this return shape but its OWN behavior is unchanged — it still only checks `.ok` and ignores `.body` entirely (a message/trailer check for the SOLO path is carded separately, not part of this round).

5. **The batch path additionally checks trailers, both per-commit and at the final read.** Right after each plain commit: a NON-TIP commit must carry NO `Loom-Worker-*` trailer at all; the TIP's own plain commit (before the pathset amend) must carry ONLY its own branch trailer (no Base/PathSet yet). At the final post-loop read (which also now supplies `landedSubject` — see S1 below): the trailer must name THIS branch, and its Base/PathSet must equal `batchHeadBefore`/the digest THIS process actually computed (tracked in a new `computedPathSetDigest`) when `pathSetStamped` is true, or be absent entirely when it's false (the real-hook-failure degrade path, unchanged) — never merely "a trailer is present", which a forger controls as freely as parent+tree alone. A mismatch at either point refuses `batchHeadMoved`, same as the parent/tree check.

6. **S1 — `landedSubject` is derived from the SAME verified `body`**, never a second, independently-steerable bare `git log -1 --format=%s` (implicit `HEAD`) call issued after `landedSha`'s own read — that second call was its own, smaller TOCTOU window (subject and sha could legitimately describe two different commits if the ref moved between the two reads).

7. **S2 — `merge-base`/the noop leg's `findLandedSquashCommit` now resolve `batchHeadBefore`, never the literal `"HEAD"`.** Reproduced (scenario L): a HEAD swap scoped to ONLY the `merge-base` call's own execution window (restored immediately after, leaving no trace for the pre-/post-gate stamp checks to catch) to a decoy commit whose own parent is the real candidate's tip — pre-fix, resolving "HEAD" misclassifies the genuinely-new candidate as an already-landed noop, and its real commit is silently never landed at all (not even a refusal — the worst outcome measured in this card, worse than the `batchHeadMoved` refusal every other leg produces). Post-fix, the pinned `batchHeadBefore` is immune to the swap and the candidate lands normally.

Round 2's own "Named residual" claimed only subject/author remained unverified — that claim is SUPERSEDED below; it understated the gap.

## Round 3 (Code Review 820ce6e3, second review) — exhaustive over the Loom namespace, not the keys round 2 happened to check

Round 2 checked `parseLoomTrailerBlock`'s own three RESOLVED fields (branch/base/pathSet) for exact values, but never audited the Loom namespace EXHAUSTIVELY. Code Review 820ce6e3 reproduced the gap LIVE against commit `1d5cb0de` (probe modes `landedtip`/`dup`/`lower`/`hidden`/`nontip-base`/`nontip-landedtip`): a same-parent, same-tree substitute carrying a forged `Loom-Landed-Tip:` (which a batch tip must never carry — it is read by `pinnedTipForLandedSquash`/finalize's own CAS pin, `sessions/service.ts`), a DUPLICATE `Loom-Worker-Branch:` (the LAST match wins in `parseLoomTrailerBlock`'s own loop, so the real branch still reads back correctly and round 2's check never notices the extra line), a lowercase case variant, or a forged line HIDDEN in an earlier paragraph (`parseLoomTrailerBlock` only ever reads the final paragraph) — all landed with `ok:true`, round 2's check none the wiser.

**The fix:**

8. **Two new shared functions, next to `parseLoomTrailerBlock`** (`git/worktrees.ts`, never changing that function's own reader semantics, so the solo card `f224632d` can reuse either without being coupled to this card's batch-specific wiring): `scanLoomNamespaceLines(message)` finds every `loom-*:`-shaped line ANYWHERE in the message (any paragraph, case-insensitive), tagging each with its exact-case key, value, and whether its own paragraph is the message's LAST one. `verifyLoomNamespaceExact(message, expected)` uses that scan to assert the namespace is EXACTLY `expected` — every key once, correct value, canonical case, all in the final paragraph, nothing else in the namespace anywhere (so `Loom-Landed-Tip` on a batch tip, a duplicate, a case variant, and a hidden-paragraph line all fail it, not just a wrong value). Foreign (non-`loom-`) trailers are untouched by the scan, so a real commit-msg hook adding `Signed-off-by`/`Change-Id` never breaks a landing (verified: `extra-foreign` still lands with `ok:true`).

9. **Both batch-side checks now call `verifyLoomNamespaceExact`** instead of reading `parseLoomTrailerBlock`'s resolved fields: the per-commit check (defense-in-depth for the tip, pre-amend; the only check that runs at all for a non-tip commit, which must carry zero Loom-namespace lines) and the final post-loop check (authoritative — the amend rewrites the tip's message, so this is the one that actually sees what lands).

10. **A commit-msg hook that appends a NON-trailer paragraph AFTER Loom's own, otherwise-intact trailer paragraph gets its OWN honest refusal reason**, distinct from the generic "tampered" wording: a third function, `loomTrailerBlockDisplaced(message, expected)`, detects the specific shape where the exact right namespace set exists, nothing else, just not all in the final paragraph — Loom's trailers are unmolested, they are just no longer the message's last paragraph, so `parseLoomTrailerBlock` (and `verifyLoomNamespaceExact`) can no longer see them as such. This is checked whenever the exact-set check fails, and takes priority over the generic tamper wording when it matches.

11. **S1 and S2 (round 2's own fixes) each got a dedicated regression test** (they had none before this round): (L2) a HEAD swap scoped to ONLY `findLandedSquashCommit`'s own `git log --grep=...` call (the noop leg's OTHER TOCTOU window, distinct from `merge-base`'s own, which scenario (L) already covers) — pre-round-2 (reverted to the literal `"HEAD"`), the swap misclassifies which sha is "already landed"; pinned to `batchHeadBefore`, it has no effect. (S1) a structural guard asserting the exact bare call shape `["log", "-1", "--format=%s"]` (no ref argument) is NEVER made during a landing — it fired unconditionally pre-round-2.

12. **The empty-stage probe (`git diff --cached --name-only`) now compares against the PINNED expected parent explicitly**, never an implicit `HEAD` — the same worker-writable-ref discipline every other check in this function already follows.

**Named residual, honestly narrowed again (not closed):** a commit with the CORRECT parent, tree, AND an EXACT Loom namespace — differing only in its SUBJECT LINE or its AUTHOR IDENTITY, or carrying an extra FOREIGN (non-`loom-`) trailer — is still unverified; the probe's own `subject` mode (`ok:true`, forged subject lands) and `extra-foreign` mode (`ok:true`, by design) both confirm this stays true after this round. The SOLO path's own identical residual (`2a6a292a` round 22/23) is unaffected by this round and is being carded separately — do not fold a solo-side fix into this card; this round only changed the solo closure's call site to match `verifyCommitParentAndTree`'s round-2 return shape, not its own trailer-checking surface (it still has none).

## Round 4 (Code Review a399cb11, third review) — the namespace-exact audit vs the READER's own notion of "readable", and a worker-authored reserved line

Code Review a399cb11 reproduced TWO further gaps live against commit `beb12b93`, named below as R1/R2 (Critical/Major); R3-R5 are regression-coverage and wording fixes, not new vulnerabilities; A1-A3 are the owner's own amendments to the R1/R2 ruling.

**R1 (Critical) — the exact-set audit and the READER can disagree.** `verifyLoomNamespaceExact` audits `scanLoomNamespaceLines`'s own, narrower match — but round 3 never checked that the SAME message still round-trips through `parseLoomTrailerBlock`, the reader every mainline consumer (`findLandedSquashCommit`, the merged-commit map, `readLandedTipTrailer`, mainline-watch) actually uses. A line that corrupts the final paragraph WITHOUT being reserved-key-shaped itself — a prose line folded into the same paragraph with no blank-line separator (`echo "[skip ci]" >> "$1"`, no blank line), an indented continuation, or a zero-width-character-prefixed `Loom-Landed-Tip:` — is invisible to `scanLoomNamespaceLines`'s narrower scan (so the exact-set audit reports "exact") while breaking `parseLoomTrailerBlock`'s per-line `key: value` requirement for the WHOLE final paragraph (so the reader returns `null`). The forged commit lands with Loom's own trailer unreadable to every reader that matters.

**The fix:** a new shared helper, `verifyLoomTrailersExactAndReadable` (`git/worktrees.ts`), composes the exact-set audit with a REAL round-trip through `parseLoomTrailerBlock`: when `expected` names a branch, the reader must return non-null with `.branch` matching, `.landedTip` exactly `null`, and `.base`/`.pathSet` matching `expected`'s own entries (or both `null` when `expected` carries neither). A namespace-exact-but-unreadable result gets its OWN honest reason — "a commit-msg hook altered Loom's trailer paragraph — Loom's merge trailers would be unreadable" — distinct from both the generic tamper wording and the `loomTrailerBlockDisplaced` wording; it is a REAL, honest third outcome (`kind: "unreadable"`), never silently treated as a pass. Both batch-side call sites (the per-commit check and the final post-loop check) now call this ONE function instead of `verifyLoomNamespaceExact` + `loomTrailerBlockDisplaced` directly.

**R2 (Major) — strip a worker's OWN reserved-namespace lines BEFORE committing, never refuse the whole batch for them.** Two real batch tips already on mainline (`5e323196`, `6cc1333f`) carry a worker commit body quoting an EARLIER `Loom-Worker-Branch:` paragraph verbatim — round 3's exact-set audit refuses that shape deterministically as "tampered" and drops the WHOLE candidate (or, pre-A2, could have aborted the whole batch) for a line Loom itself is about to overwrite anyway.

**The fix:** `landBranchCommitsIndividually` now strips every line in Loom's RESERVED trailer namespace from the worker's own commit body, chained right after the existing `stripClaudeSessionTrailer` call and before `finalMessage` is built — `stripReservedLoomTrailerLines` (`git/worktrees.ts`), returning `{message, strippedCount}` exactly like its sibling. Per-commit strip counts accumulate into `strippedReservedLineCount`, threaded through `BatchLandedBranch`/`LandResult` and `sessions/service.ts`'s `landed` array the same way `strippedTrailerCount` already flows, and logged via a parallel `console.warn` when non-zero.

**A1 (owner amendment) — ONE shared definition of "reserved", used by BOTH the strip and the scanner.** The owner's ruling on R1/R2 required narrowing `scanLoomNamespaceLines` itself from "any `loom-*:` line" to the RESERVED set (`Loom-Worker-*`/`Loom-Landed-*`, case-insensitive) — otherwise a worker's own non-tip body or subject line reading e.g. "loom-bridge: fix crash" still trips the exact-set audit and refuses the whole candidate, which is exactly the Major R2 fixes. `RESERVED_LOOM_TRAILER_KEY` + the shared `matchReservedLoomTrailerLine(line)` predicate (`git/worktrees.ts`) is the ONE definition `scanLoomNamespaceLines`, `stripReservedLoomTrailerLines`, and `batch-merge.ts`'s own A2 subject check all share — never a second, independently-drifting regex. It keeps matching every shape the exact-set audit already refused for a genuinely RESERVED key (case-insensitive, leading whitespace/tabs, space-or-tab before the colon — round 3's own space-colon/tab-colon/lead-ws probe modes stay refused), while a non-reserved `loom-*` line (an end-user project's own subject/prose) is no longer even scanned.

**A2 (owner amendment) — a reserved key as a worker commit's own SUBJECT is a distinct hazard, handled BEFORE committing.** `stripReservedLoomTrailerLines` deliberately never touches line 0 (the strip's own contract) — so a worker commit whose SUBJECT alone is a reserved line (e.g. `"Loom-Worker-Branch: other-branch"`) survives the strip unchanged. Once the TIP's real trailer paragraph is appended after it, that subject becomes a non-final-paragraph reserved line, which `verifyLoomTrailersExactAndReadable` (correctly) refuses as `kind: "forged"` — mapped to `batchHeadMoved`, which `assembleBatchBranches` propagates as a FULL-BATCH ABORT with no per-candidate fallback (card `043d83d2`'s own mechanism, never bisected). That is the right remedy for a racer's tamper and the WRONG remedy for a worker-authored content defect in one candidate's own commit.

**The fix:** `landBranchCommitsIndividually` checks every commit's own subject line against `matchReservedLoomTrailerLine` right after reading it (before any strip, before any commit), and on a match rolls back whatever this candidate has already contributed and drops ONLY this candidate with its own honest reason ("commit ...'s own subject line is a reserved Loom trailer line ... it will be retried via the ordinary solo merge path") — never a `headMoved` outcome, so the rest of the batch lands normally and this candidate falls back to the ordinary solo path, where card `f224632d`'s own check applies.

**A3 (owner amendment) — the strip operates per LINE on the raw message, never a paragraph rejoin.** `stripReservedLoomTrailerLines` filters the message's own line array directly (never splits/rejoins by paragraph), so a reserved line sitting in the MIDDLE of a multi-line paragraph is removed without concatenating the lines around it onto one line, and every other line survives byte-for-byte; a run of 3+ newlines left behind by removing a line that sat ALONE in its own paragraph still collapses to exactly 2 (mirroring `stripClaudeSessionTrailer`'s own collapse rule).

**R3 (Minor) — a dedicated regression test for the empty-stage probe's pinned expected parent.** The probe (`git diff --cached --name-only <expectedParentForThisCommit>`, ~`batch-merge.ts:645`) had no test proving the PIN itself is load-bearing; reverting it to an implicit `HEAD` (mutation M6) survived every pre-round-4 test. Scenario (M) in `batch-merge-head-moved.mjs` swaps the batch worktree's HEAD to the candidate's own tip (whose tree, once cherry-picked, matches what gets staged) for ONLY this one call's window, proving the pin — not an implicit `HEAD` — is what keeps a genuinely new, non-redundant commit from being misclassified as already-landed and dropped in error.

**R4 (Minor) — S1's own regression test replaced, structural → behavioural.** The old guard asserted a specific bare `git log -1 --format=%s` call shape never fires — satisfiable by accident while still reading the wrong ref some OTHER way. Scenario (S1) now swaps the batch worktree's HEAD to a decoy commit (same parent, different subject) immediately AFTER the `rev-parse HEAD` call that captures `landedSha`, leaves it swapped, and asserts `assembleBatchBranches`'s own `landed[].sha`/`.subject` still describe the REAL landed commit — called directly (not through `runBatchedMerge`) so the result is isolated from card `043d83d2`'s own, separate pre-/post-gate stamp check.

**R5 (Nit) — wording.** Every "must match EXACTLY" claim in this file's own doc comments now says "exact up to surrounding whitespace" where the compared value has already been trimmed by `scanLoomNamespaceLines`'s own regex.

**Named residual, honestly rewritten (not closed):** round 4 closes the "exact-set audit says yes, the reader says no/different" gap (R1) and the "worker's own reserved line forces a refusal instead of a strip/drop" gap (R2/A2) — but a commit with the CORRECT parent, tree, an EXACT reserved namespace, AND a reader that round-trips it correctly — differing only in its SUBJECT LINE, its AUTHOR IDENTITY, or carrying an extra FOREIGN (non-`loom-`) trailer — is STILL unverified; round 3's own `subject`/`extra-foreign` probe modes are unaffected by round 4 and confirm this stays true. The SOLO path's own identical residual (`2a6a292a` round 22/23) is unaffected by this round and remains carded separately (`f224632d`).

**Correction (4th Code Review, `89193398`):** `landBranchCommitsIndividually` has FIVE bare `["rev-parse","HEAD"]` call SITES total — `:371` (`batchHeadBefore`), `:553` (the rollback cleanliness probe), `:752` (the per-commit post-commit verify), `:844` (the post-amend-failure recovery probe), `:877` (the final `landedSha` read) — not four. "How many sites exist" and "how many fire in a given scenario" are different questions: the round-4 `(S1)` test's own comment stated 4 without that qualification, true only because its specific happy-path setup never triggers the rollback probe or the post-amend-failure read. See that test's own comment for the corrected, scenario-scoped count.

## Round 5 (4th Code Review `89193398`) — a split-vs-scanner CRLF mismatch, a hardcoded `landedTip`, and a non-tip strip gap

All three findings are non-blocking (each fails CLOSED — the batch refuses or strips correctly in the failure direction, never silently lands a forgery) but worth fixing for correctness and for `f224632d`'s own reuse.

**F1 — the strip and the scanner split lines differently.** `stripReservedLoomTrailerLines` split on a bare `\n` with no CRLF normalization, while `scanLoomNamespaceLines` normalized `\r\n` to `\n` FIRST. A mid-message `Loom-Worker-Branch: x\r\n` line (authored via `commit-tree`/`--cleanup=verbatim`, which skips the normalization an ordinary `git commit -m` applies) kept its trailing `\r` through the strip's own split — and `matchReservedLoomTrailerLine`'s `[ \t]*$` anchor (JS `.`/`[ \t]*` both exclude `\r`, and `$` without the `m` flag anchors at true end-of-string) then silently REJECTED that line, evading the strip. The scanner, having already normalized the `\r` away, still saw a plain `Loom-Worker-Branch: x` line in a non-final paragraph and correctly flagged it as a forgery — aborting the whole batch for a line the strip was supposed to have removed.

**The fix:** `normalizeMessageNewlines(message)` (`git/worktrees.ts`) — the ONE shared first step, applied before EITHER function's own split (paragraph-split for the scanner, flat line-split for the strip), so the two can never disagree on where a line ends again. `stripReservedLoomTrailerLines` still returns the ORIGINAL `message` byte-for-byte when nothing is stripped (preserving any CRLF the worker's message legitimately used); only when something IS stripped does the rebuilt message's lines join on a bare `\n` (matching the scanner's own LF-normalized world from that point on).

RED/GREEN: `packages/daemon/test/worktrees.mjs` (srl-8)/(srl-9) — a mid-message CRLF reserved line. RED before this fix (confirmed via a temporary revert of the strip's own split back to a bare `message.split("\n")`, rebuild, re-run, re-apply, rebuild): `strippedCount` stayed `0` and the reserved line text survived in the output. GREEN after: stripped, `strippedCount === 1`.

**F3 — `verifyLoomTrailersExactAndReadable` hardcoded `parsed.landedTip !== null ⇒ unreadable`.** Correct for the BATCH path (a batch tip never carries `Loom-Landed-Tip`, so `expected` never names it, so `landedTip` must indeed be `null`) but wrong as a REUSABLE primitive: the SOLO squash path (`mergeBranchLocked`) DOES write `Loom-Landed-Tip` (card `cc9bce38`), and card `f224632d`'s own planned reuse of this function for the solo path would have hit a false "unreadable" on every genuinely correct solo commit.

**The fix:** compare against `expected["Loom-Landed-Tip"] ?? null` instead, mirroring the existing `base`/`pathSet` comparisons exactly. Batch behavior is UNCHANGED (a batch's own `expected` never carries a `"Loom-Landed-Tip"` entry, so the comparison is still against a bare `null` there — the SAME outcome as before, just reached by a general rule instead of a special case) — `packages/daemon/test/worktrees.mjs` (vlt-1)/(vlt-2) (the existing batch-shaped happy paths, neither of which ever carries a `Loom-Landed-Tip` line) still pass unchanged after this fix, confirming it. New unit case (vlt-11): an `expected` that DOES name `"Loom-Landed-Tip"`, with a message whose reader round-trips it correctly, now reads `ok:true` — unreachable before this fix for any caller that legitimately needs it. No RED/GREEN requested for this one (no existing behavior to regress against; the new case simply didn't pass before the fix existed).

**F4 — the R2 integration test only covered a TIP commit.** A regression that strips reserved lines only from the LAST (tip) commit — plausible, since the Loom-Worker-Base/PathSet TRAILER-stamping logic itself genuinely IS tip-only — would have passed round 4's own `(R2)` scenario undetected, since its one candidate commit was always the tip.

**The fix:** `(R2)` now lands a TWO-commit branch: the quoted stale `Loom-Worker-Branch:` paragraph sits in the NON-TIP commit specifically, with an ordinary, unrelated TIP commit after it. RED/GREEN: confirmed via a temporary edit making the strip call conditional on `isLast` (simulating the exact regression named above), rebuild, re-run — RED: the non-tip commit's own quoted line survived, `verifyLoomTrailersExactAndReadable({})` on that non-tip commit correctly flagged it as a non-final-paragraph forgery, and the WHOLE batch aborted (`batchHeadMoved`), never landing either commit. Restored, rebuilt, re-run — GREEN: both commits land, neither carries the stale line.

**Named residual (deliberately NOT fixed this round — carded separately, per the owner's own ruling):** an empty, or blank-first-line, TIP message makes Loom's OWN appended `Loom-Worker-Branch:` trailer the message's effective SUBJECT (line 0) rather than a real trailer paragraph — `parseLoomTrailerBlock` then can't read it back as a trailer at all (`unreadable`), aborting the WHOLE batch rather than dropping just that one candidate. The general fix (verify the CLEANED, about-to-be-committed message BEFORE the commit actually lands, and drop only that candidate on failure — the same posture A2 already established for a reserved-shaped subject) is being carded separately; this round does not attempt it.
