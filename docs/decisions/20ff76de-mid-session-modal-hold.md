# 20ff76de — mid-session consent-modal hold (detect + hold + notify, never answer)

## Context
Claude Code 2.1.322 shows a modal CONSENT prompt, "Teach auto mode about your environment?" (first screen: `1. Yes / 2. Not now / 3. Don't show again`, footer "Enter to confirm · Esc to cancel"; Yes leads to a wizard screen with footer "Enter to continue"). It appeared in several live sessions around 2026-11-11 18:10-18:30Z. It swallows composer input, so deliveries parked (`[loom:redelivery-parked]`, up to ~16 Enters), and worse, every retry Enter could answer it: Enter = Yes = `/auto-mode-setup`, which reads the project and recent sessions (optionally shell history and other repos) and on accept WRITES the user's `~/.claude/settings.json`. Real raw bytes and the owner-supplied second screen are fixtures: `test/_fixture-teach-auto-mode-modal.mjs`.

The pre-existing detector (`detectBlockingDialogSignature`, card 01160ae3) only watches BEFORE SessionStart. Nothing watched a session past boot. Both detectors are detect-and-hold: neither ever answers a prompt.

## What was built
- `detectMidSessionModal(rawTail, {echoText})` (`pty/host.ts`) — pure. Input: a bounded raw tail (`MODAL_TAIL_MAX_CHARS`), cut at the last full-screen ERASE (`ESC[2J`/`ESC[3J`; cursor-home alone is not an erase). The session's echoed `lastPrompt` is removed first. A known dialog is named by its own signature; otherwise the generic footer ("Esc to cancel" + "Enter to confirm/select/continue/accept/choose") must be present. A footer followed by a REDRAWN composer box (a long border run directly followed by the ❯ prompt) is a dismissed or merely quoted footer and does not match. There is deliberately NO "trailing text" length cap: measured on the real bytes, the TUI keeps repainting a cursor-addressed status line (~170 bytes/s) over a sitting modal, so any length/sliding-window rule decays within seconds.
- The FROZEN CANDIDATE (`Live.modalCandidate`): a chunk that leaves the word "cancel" in the tail END (the last `chunk length + 6` chars, so a split "can|cel" is caught) triggers a pure, bounded check of the tail; on a match the tail is snapshotted with the signature. Engage/release/refusals read the candidate, never the sliding tail. A candidate BLOCKS every Loom write; it becomes an EPISODE only at ENGAGEMENT (see "The episode"). What drops it: ONLY (1) a `UserPromptSubmit` hook (the engine accepted a prompt, so no modal has focus), (2) the explicit human release, or (3) — for a candidate with NO engaged hold (a quoted footer in an agent reply, or a just-dismissed dialog) — composer-box evidence (`modalDismissedBy`: a long border run then ❯ positioned after the last footer) that stood `MODAL_DISMISS_SETTLE_MS` (1500ms, env `LOOM_MODAL_DISMISS_SETTLE_MS`) with no footer re-appearing. Nothing else: not time, not status repaints, not a full-screen erase (the TUI erases and redraws a still-up modal; an erase only restarts the post-snapshot evidence), not cursor-home, not a composer entry, not human raw bytes, not Stop/PreToolUse/PostToolUse/Notification (the offer fires at the END of a turn, so a mid-turn hook proves nothing).
- THE EPISODE and its ONE predicate. For a past-boot `BOOT_DIALOG_DETECTOR_ROLES` session (`isPastBoot` — the boot detector keeps sole ownership pre-SessionStart) a candidate BLOCKS writes, and an EPISODE starts only when the hold ENGAGES. `modalWriteBlocked` (hold OR candidate) is the single predicate behind EVERY surface, and `modalBlockedEngaging` is its entry point: it engages the hold on the first blocked attempt of a candidate-only session, EXCEPT while the candidate's dismissal is SETTLING (`dismissSince` set: composer box redrawn after the footer). That exemption lives in `engageMidSessionModalHold` itself so every engagement path inherits it (blocked write, candidate creation, the Enter-verify chain). A settling candidate still refuses every write but is not an episode: an engaged hold is released only by a hook or the human, and the refused write is what would produce that hook, so engaging a just-dismissed dialog deadlocks it. The settle timer drops the candidate and drains; if the footer re-appears first, `dismissSince` resets and `trackModalCandidate` engages at that moment when something is pending or unconfirmed. ENGAGEMENT (`engageMidSessionModalHold`) parks the unconfirmed submit generation (if any), emits the existing `onClaudeBootDialogStuck` event with `phase:"mid-session"` (signature NAME only), arms the ONE owner escalation timer and sets `midSessionModalSince`. The candidate engages at creation when anything is pending or a turn is unconfirmed; otherwise at the first of: a refused write, an enqueue, a composer entry, `modalHoldRefusal`, an interrupt/flush. Once a body paste is refused (`modalBodyRefusedGen`), EVERY later write of that generation (chunk, bracket-end, enter, reassert-paste) is refused at the chokepoint too, so a settle firing mid-sequence can never produce a torn body, a stray Enter or a duplicate; the marker clears when a new generation starts. The refused body's Enter-verify chain stops and requeues the content (a direct submit with no drained origin is re-enqueued from `lastPrompt`), and `resumeAfterRateLimit` queues instead of submitting while blocked. Surfaces on that predicate: the `ptyWrite` chokepoint, `isBlockedOnUnresolvedBootDialog` (drain/kickoff gates), `enqueueStdin` (a HUMAN composer entry is refused with `reason:"modal-held"` + the readable `MODAL_HOLD_REFUSAL`; the composer route answers 409 before recording a pending owner message, so the draft stays with the human), `modalHoldRefusal` (gateway + `SessionService.deliverRedirect`), `interruptForRedirect` and `flushComposer`. `healIfStuck` is skipped while held.
- THE INVARIANT, enforced at the ONE write chokepoint: `ptyWrite` REFUSES every Loom-originated write while the predicate holds. Exempt: human raw bytes (`writeStdin` passes `human`; they pass through and NEVER release), stop's Ctrl-C and the viewer's Ctrl-L repaint. A refused body paste marks the generation `modalBodyRefusedGen` (nothing of it reached the pty), so its release requeues it as a no-write generation with no dirty mark. A generation parked by a hold has its Enter chain killed for good (`modalParkedChainGen`; pending timers bail), so no release resumes it. No path — drain, requeue, heal, reconcile, kickoff, the retry ladder, any future writer — can type into a detected modal.
- RELEASE: evidence only, exactly two kinds, neither writes an Enter. (a) `UserPromptSubmit` ("hook"): it releases ONLY when the current frame is modal-free. A release never wipes a frame already received (hook latency: the wizard can be painted BEFORE the hook lands): `modalFrameStillShown` reads TRACKED STATE, never a re-scan: the candidate carries `shown`, a latch set when a footer is sighted (a small rolling raw window, `recent`, so a footer split across chunks is still sighted) and cleared only by a frame reset (full-screen erase) or positive dismissal evidence (a composer box after the last footer). Status repaints change neither, so ~23+ of them can never evict the footer (a re-scan over the sliding 3000-char window did exactly that and let both a UPS and an un-forced Resume release while the modal was still up). `shown` makes the UPS a no-op, so the following Stop drains nothing. A dismissal with NO erase and NO box (a cursor-addressed clear) stays "shown": Resume is soft-refused until forced (bounded, visible). Consequence: the normal Yes-then-wizard order (UPS lands while the first screen is still the current frame) also stays held until the wizard resolves and a later UPS arrives on a modal-free frame, or the human resumes. When released the hold clears; and a UPS-driven drop never discards frame bytes: `dropModalCandidate(live, true)` carries the last 400 chars of the frame (`MODAL_CARRY_CHARS`; only text since the last reset/dismissal) into the fresh tail, so a footer split across the hook ("...Esc to can" | hook | "cel") still completes and re-snapshots (a settle drop and a non-force human release carry only the bytes AFTER the last sighted footer/dismissal, which hold no complete stale footer but can complete a NEW half-painted one; only a FORCE release WIPES the tail, so a force-released stale footer cannot resurrect a false hold; chosen over deferring the release by a tick: a tick does not bound how far apart the two chunks can land); a parked body that was never written is requeued as a no-write generation (so a parked kickoff is re-guaranteed, not lost). (b) the explicit HUMAN release ("human"): `releaseModalHoldByHuman`, reached ONLY through the loopback REST route `POST /api/sessions/:id/modal-hold/release` (never an agent MCP tool, deliberately not in the remote Tier-1 list; 404 unknown session, 409 when nothing is held) and the "Resume deliveries" button on the existing PROMPT HELD attention row. It is SOFT-refused with 409 `{stillOnScreen:true}` while the current frame still shows a modal footer (same `modalFrameStillShown` check) unless the body carries `force:true`; the web button keys on the structured `stillOnScreen:true` (an `ApiError` carrying the 409 body, never a regex over prose), turns into "Prompt still on screen — resume anyway?" for ~10s and a second click sends force (after the expiry a click re-checks) (overridable because the dismissal evidence is synthetic). A release drops the candidate, clears the hold, requeues the parked still-unconfirmed generation through the normal give-up path and drains. (c) the session ending ends the episode with it. NO screen-settle release and NO other hook release.
- WORDING: ONE shared phrase, `MODAL_RESOLVE_STEPS` (`pty/modal-hold-text.ts`): "resolve the prompt in the terminal, then press Resume deliveries" — used by the composer 409 (`MODAL_HOLD_REFUSAL`), the Lead card, the companion attention push and the parent nudge (which tells the manager the OWNER resumes, and that worker_stop + respawn is the fallback). Do not reintroduce "any human input releases the hold".
- LIVENESS: the hold never times out into the Enter ladder. After `MODAL_HOLD_ESCALATE_MS` (3 min) held, ONE owner escalation per episode is requested (`escalation:true`); `handleClaudeBootDialogStuck` files a `parentNudged:false` mid-session event unless the episode's latest event already is owner-visible. Nobody is nudged by it. The incident shape (every session held at once, the manager included) is why a parent-only nudge cannot be the only signal.
- Refusal visibility on the web: the Composer shows the 409's message (the draft is kept); the Review panel's request-changes and the requests "Nudge mgr" button show their own failure instead of staying silent ("held" only for the on-screen-prompt refusal).
- Exposed: `midSessionModalSince` (epoch ms; null = not held) on `worker_list` and `worker_status` real rows.
- Roles: `BOOT_DIALOG_DETECTOR_ROLES` (workers, setup/auditor/assistant/run, AND manager/platform — the manager exclusion lives in `LOOM_DRIVEN_ROLES`, not here). Excluded: role-less/plain and operator sessions (owner-interactive terminals).
- Owner alert + parent/Lead notice ride the existing `claude_boot_dialog_stuck`/`_resolved` pair (`detail.phase`). Wording switches on `phase` in `SessionService.handleClaudeBootDialogStuck`, `notifyLeadOfStuckManager`, the companion `alertLine` and the web `attention.ts` ("PROMPT HELD"). The Lead board card is reused only within the same phase, so an open BOOT card is never silently absorbed.

## Suppression of the offer (DoD 2)
Suppression of the offer (`skillOverrides` `auto-mode-setup: "off"` in every per-session `--settings` file) is its own change, recorded in `docs/decisions/462c4ae8-auto-mode-setup-off-in-per-session-settings.md`; this record covers the detector and the hold only.

## Do not
- Do not auto-answer, Esc, or Enter a modal to "clear" it: this one is a consent prompt (scan + write to the user's settings). Includes the retry Enter ladder: never time the hold out into it.
- Do not write `~/.claude/settings.json` or `~/.claude.json` to suppress the offer (a cross-tool, user-level write; `autoModeEnvSetup` is undocumented). Do not touch `permissions.disableAutoMode`/`disableBundledSkills` (the former removes auto mode, the latter does not apply to this built-in command).
- Do not release an episode on a heuristic: not on a screen settle once the hold is ENGAGED (a settle only drops a candidate with no engaged hold), not on human raw bytes (arrows, focus reports, mouse), not on Stop/PreToolUse/PostToolUse/Notification, not on a composer entry. Only a `UserPromptSubmit`, the explicit human release, or the session ending.
- Do not resume the parked generation's Enter chain on any release, and do not treat a full-screen erase or cursor-home as dismissal.
- Do not engage the hold for a candidate whose dismissal is settling (`dismissSince` set), and do not move that exemption out of `engageMidSessionModalHold` into a caller: it deadlocks a just-dismissed boot dialog (only a hook/human releases an engaged hold). Do not let a refused body's Enter-verify chain retry an Enter into the composer.
- Do not add a per-caller write check for a new Loom write, and do not add a second predicate for a new surface: `modalWriteBlocked`/`modalBlockedEngaging` are the one answer; a new `ptyWrite` exemption needs a human or stop-class reason.
- Do not re-introduce a sliding-window or trailing-length rule for "is the modal still up": real status repaints defeat it. Do not read the cumulative boot scans (`dialogStuckScan`, `bootScan`, `resumeGateScan`). Do not match text Loom itself typed (`lastPrompt`).
- Do not engage before SessionStart; the boot detector owns that window. Do not expose the release route as an agent MCP tool or a Tier-1 route.

## Known residuals
- THE GUARANTEE: while a candidate or hold exists, no Loom write reaches the session; release only on a `UserPromptSubmit` or a human. THE RESIDUALS of it: (1) the first Enter of a delivery that arrives BEFORE any modal was detected is unavoidable (no candidate exists to refuse on), so one Enter may already have reached a modal that had not yet painted its footer; (2) a FALSE-POSITIVE candidate (a footer quoted in an agent reply that the settle does not clear because the hold ENGAGED meanwhile, i.e. the footer re-appeared or a write was refused before any dismissal evidence) costs a human click, bounded by the 3-min owner escalation.
- "Never a false Enter" holds only when the dismissal evidence is MISSING (the candidate lingers). If the evidence is a FALSE POSITIVE (it reports a dismissal while the modal is still up), the settle drops the candidate after `MODAL_DISMISS_SETTLE_MS` and later writes can reach a real modal. This is the deliberate trade for removing the boot-dialog deadlock; no extra mechanism guards it.
- The composer-box dismissal evidence is SYNTHETIC: no real capture of the modal being dismissed exists yet. It now only matters for a candidate with no engaged hold; if it is wrong the safe direction holds (a candidate that lingers until a UserPromptSubmit or the human release), never a false Enter.
- A modal dismissed by the human in the terminal (raw bytes only) keeps the hold until the human presses "Resume deliveries" (or a UserPromptSubmit arrives): this is the price of "human bytes are not evidence". If the release is pressed while the modal is still up, the candidate is dropped and the modal is only re-detected on its next footer-completing repaint.
- UNVERIFIED: whether the CLI honors `skillOverrides` supplied via `--settings` (the suppression of the offer moved to its own card; its code is unchanged on this branch). The mid-session hold is the backstop if it does not take. The owner's manual fallback is selecting "Don't show again" in a live dialog.
- PRODUCT CALLS (no change): "Resume deliveries" for a PARENTED worker appears only after the 3-minute owner escalation (the owner sees the prompt in the terminal; the manager has no tool for it, by design); remote (gateway-token) owners get the escalation only, since the release route is loopback-only.
- The footer is sighted over (rolling window + the WHOLE post-erase chunk) BEFORE trimming (`MODAL_FOOTER_WINDOW_CHARS`, 1200), so a footer followed by >200 bytes in one chunk is still seen; a footer only before an erase in the same chunk does not count, one after it does. KNOWN GAPS (none a regression; all fail on the safe side or are bounded): (a) ANY visible character, or a DEC save/restore (ESC 7 / ESC 8, which is not CSI), between "can" and "cel" defeats the split sighting at any size; the 1200 window only helps a pure-CSI interleave. The hold still stays (the candidate is not dropped), so `shown` merely under-reports and a Resume is not soft-refused. (b) The erase-to-redraw window: an erase clears `shown` at once and the redraw can land ~300ms later, so a Resume click inside that gap is not soft-refused, and a Stop-before-redraw (M3: a release, then a queued write, before the redraw) can write before the redraw re-holds. (c) A split erase sequence across chunks (SE/SE2) is not recognized as an erase; it fails on the safe side (an over-hold that a force click clears).
- Two real-capture follow-ups: (1) the real timing of the Yes answer's `UserPromptSubmit` relative to the wizard's first paint, and (2) the real bytes of a dismissal (what a dismissed modal paints). Both are inferred today from the owner-supplied text and synthetic frames.
- Detection of the "Teach auto mode" modal is proven against REAL captured bytes of its first screen (and the owner's text for the second); other, unseen modals rely on the generic footer ("Esc to cancel" + "Enter to ...").
- `midSessionModalSince` is on real rows only; the placeholder rows (starting / cap-queued / dangling) do not carry the key.
- The web `attention.ts` wording and the "Resume deliveries" button have no unit test; they are covered by the build (including the inlineError/errorText source scans) only; no browser check was run.
- Observed benign 1318-vs-97 `prompt-mismatch` on manager a3d0467e (18:25:52Z) was the owner's own typed 97-char message (engine transcript), not a modal symptom.
