# 84c1046f — reconcileMarkedBasenameBeforeWrite's reingest branch dropped four runtime-folded fields

From an investigate-first card off CR2 of `6de79dc0` (session `82283d65`): `reconcileMarkedBasenameBeforeWrite`'s reingest branch (merge-quarantine.ts, inside the `isUnreadablePlaceholderEntry(entry)` arm) rebuilds an entry from disk via `{...reingested, ...}` (`reingested = latchEntryFromParsedRecord(parsed)`), explicitly overriding only `tokens`/`resolvedKey`/`resolvedKeys`/`armedKeys`/`provenanceUnknown`/`genuineContributorKeys`. Every OTHER field of `MergeQuarantineEntry` rides through on whatever `reingested` (DISK-ONLY) carries.

## Confirmed reachable, confirmed harmful — the hermetic repro

A runtime fold of a genuine contributor onto a still-unreadable placeholder entry IS reachable: `enterMergeQuarantine`'s own `existing` branch folds a second raiser's identity into `contributorRepoPaths` via a plain `{...existing, contributorRepoPaths, ...}` spread (never `unionQuarantineEntries`), so placeholder-ness survives the fold. The moment the underlying latch file becomes readable again and a further write reaches the chokepoint, the reingest branch above discards that in-memory fold, keeping only whatever `contributorRepoPaths` disk happens to carry (usually nothing, since the contributor's own fold never made it to disk while the file was unreadable).

CONSEQUENCE, reproduced directly: with the fold intact, `clearMergeQuarantineLatchFile` (the identity-blind clear-by-id route) fails closed, naming both identities — see `merge-quarantine-lazy-graduation-contributor-attribution-b5c94cbe.mjs`'s own SCENARIO 2/4. With the fold dropped (pre-fix), the SAME call instead returns `{ok:true, liftedRepoPaths:[...]}` and silently lifts the contributor's own quarantine too, even though the contributor was never addressed by that clear — the contributor has no key of its own; its only protection was the dropped field.

## provenanceTracked — fixed, in BOTH reingest twins (corrected: an earlier draft of this record wrongly left this unfixed)

`provenanceTracked` has the identical structural omission as the three fields above, in BOTH places that rebuild an entry from disk: `reconcileMarkedBasenameBeforeWrite`'s reingest branch AND `reconcileClearedEntryIfPlaceholder` (the human-clear twin, which already carried `orphanLatchFiles`/`contributorRepoPaths`/`reducedContributorRepoPaths` forward via `656fdf39` but had this same gap). An earlier draft of this record argued the drop was masked (`writeMergeQuarantineLatch` unconditionally re-stamps `provenanceTracked:true` on the SERIALIZED bytes of every successful write) and that fixing it here would violate `db0a9db0`'s own "only `writeMergeQuarantineLatch` is the chokepoint" rule — a misreading, caught by Code Review.

`db0a9db0`'s own record states, in the SAME section as that chokepoint rule: "`provenanceTracked` is carried forward at every copy/rebuild site exactly like `provenanceUnknown`" — `unionQuarantineEntries` ORs it, `consumeMatchedPendingsIntoArmedEntry`/`divertRaiseEntry` OR it across every matched entry, and `500e307a` stamps a FRESH `true` only at genuine raise/arm sites (never at a rebuild site). The chokepoint rule forbids ORIGINATING a fresh `true` from nothing at a site with no prior `true` on any side — it says nothing against carrying forward a value ALREADY `true` on one side, which is exactly what an OR-union does, and exactly what `provenanceUnknown` already does two lines above this field in both reingest branches. Masking by `writeMergeQuarantineLatch`'s own disk stamp is real, but only covers the DURABLE bytes — it does nothing for the in-memory object `activeMergeQuarantineFor` hands back to a caller in THIS process, which stayed wrong until the entry was next rebuilt or the daemon rebooted. Fixed: `entry.provenanceTracked || reingested.provenanceTracked ? true : undefined` in both reingest branches, the same OR-carry shape `provenanceUnknown` already uses right beside it.

## Absence semantics

- **contributorRepoPaths**: absent means "no contributors" — the PERMISSIVE side for clear-by-id (bare id addressing is allowed). A union must never let absence win when either side carries entries, and must never coerce an empty union into `[]` instead of `undefined` (every sibling call site in this module keeps this exact convention).
- **reducedContributorRepoPaths**: absent means "nothing has ever been reduced out of this union." Per its own doc, dropping a genuine entry here is ALSO fail-open in the same direction as contributorRepoPaths (a second `/clear` against an already-reduced identity would route through the full ancestor-collapse lift instead of the idempotent no-op reduce arm) — same polarity, same `undefined`-never-`[]` convention.
- **orphanLatchFiles**: absent means "nothing extra needs sweeping for this entry." Dropping a genuine entry here is a disk-hygiene leak (an untracked, never-swept residue file), not a trust-boundary issue — lower severity, opposite-direction concern from the two fields above, but the same carry-forward fix shape.
- **provenanceTracked**: absent means "cannot be sure this entry was ever durably stamped as current-format" — the discriminator input to `detectUnknownProvenance`'s precision guard. Dropping a genuine `true` here is FAIL-CLOSED (a false `provenanceUnknown` on a later boot re-parse), the opposite polarity from the three fields above, but the SAME carry-forward obligation applies — a `true` already established on either side must never be lost. Fixed via OR-union, same as `provenanceUnknown`.

## Do not

- Do not drop a carried-forward field (`provenanceTracked` included) at a rebuild/copy site on the theory that some OTHER write chokepoint masks it — `db0a9db0`'s "only `writeMergeQuarantineLatch` is the chokepoint" rule is about never ORIGINATING a fresh `true` from nothing; it does not forbid OR-carrying one already `true` on either side, which is the SAME obligation every other persisted field in this module already honors. An earlier draft of this record got this backwards and was corrected by Code Review — see the provenanceTracked section above.
- Do not coerce an empty union of `contributorRepoPaths`/`reducedContributorRepoPaths`/`orphanLatchFiles` into `[]` — keep `undefined` when both sides are empty, matching every other union site in this module.
- Do not assume this closes every consumer of `contributorRepoPaths` — `clearMergeQuarantineLatchFile` (clear-by-id) was directly re-exploited and re-verified; the remediation-text helpers (`remediationTextFor` et al.) and the various `ambiguousIdentities`/`canonicalSiblingsFor` call sites were located by reading but not independently re-exploited for this card.
