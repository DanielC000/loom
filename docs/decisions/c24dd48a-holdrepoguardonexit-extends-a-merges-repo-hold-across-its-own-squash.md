# c24dd48a — `holdRepoGuardOnExit`/`beginSquash`/`endSquash` extend an admitted merge's per-repo hold across its own squash, atomically

## Narrative

Card c24dd48a: before this card, `GateSemaphore.release()` freed a merge's per-repo guard (`activeMergeRepos`, card `92e960d1`) the moment its GATE settled — strictly BEFORE that merge's own squash (`mergeBranch`, called outside `runExclusive` entirely) actually landed. That left a window where a queued same-repo sibling could be admitted the INSTANT the gate settled but before the squash landed, closing only part of the class `92e960d1` set out to close.

`runExclusive`'s `fn` now receives a fifth param, `holdRepoGuardOnExit`: a callback `fn` can call — synchronously, any time before it returns — to declare that this run's repo hold should survive PAST this call's own settle instead of releasing automatically in the `finally` block. This exists for EXACTLY ONE caller shape: `confirmWorkerMerge`'s gate callback, which calls it iff the gate it just ran PASSED — a passing gate is about to hand off to that caller's own squash phase. Calling it makes the transition ATOMIC: the flag is read by the SAME `finally` block, in the SAME synchronous turn `fn` set it in, so there is no `await`-shaped window between "gate settled" and "guard still held" for a queued waiter's own `grantNext` to slip through.

The caller is then on the hook to release the guard explicitly, later, once its own squash phase has itself settled — via `beginSquash`/`endSquash` (aliases of the same underlying `releaseMergeRepoGuard`, kept as a distinctly-named pair purely for readability at the call site, begin/end bracketing one squash call). A hold with no matching release is a PERMANENT block on that repo, so every call site that invokes `holdRepoGuardOnExit` must have a `finally` that unconditionally reaches the release, no matter which of throw/cancel/timeout/pass/fail the squash itself hits. A caller whose `fn` never calls it (every pre-c24dd48a call site, and any FAILING merge gate) is byte-identical to before this parameter existed — `holdRepoGuard` defaults to `false` and `release()` frees the guard exactly as it always has.

**`confirmWorkerMerge` calls `beginSquash`/`endSquash` ONLY when `gateRan` is true** — i.e. ONLY for an op that actually went through `this.gateSemaphore.runExclusive(...)` this invocation (`gateRan = !reuseResult`, a provable proxy). The REUSE path (card `e50600d2`) and a GATELESS project/repo DELIBERATELY NEVER call this; those two paths get NO admission-level protection from this mechanism — `requireCanonicalHead` (inside `mergeBranch`'s own lock) protects them instead, exactly as it always has (see card `0196ba78` for the full scoping of that boundary).

**Corrected by Code Review, card b9e07a4a:** `beginSquash` used to `.add()` into `activeMergeRepos` unconditionally, which under the then-unidentified identity gap could silently overwrite a correctly-stored `entry.id` fallback identity with this call's own `opId`, corrupting the ACTUAL holder's stored identity for a caller that never supplied a matching `opId` at admission. The hold's continuity is already fully guaranteed by `admit()` + the release-skip above — there was nothing left for `beginSquash` to acquire. It is now a VALIDATED marker only: logs the expected reaffirmation on a match, and a distinct `beginSquash-identity-mismatch` line (never a throw — this guards a `finally`-adjacent call site) on a mismatch, which should never happen in correct usage. `endSquash`/`releaseMergeRepoGuard` are likewise routed through `freeRepoPath` and IDENTITY-CHECKED against `opId`: an absent key OR a key held by a different identity is a safe no-op (never a throw) — this closes the reviewer's reproduced cascade (see card `b9e07a4a`'s own record for the Set-vs-Map cascade this class of fix belongs to). `opId` is REQUIRED on both `beginSquash` and `endSquash` as of this Code Review — it is the identity these calls validate against, not merely forensics.

## Do not

- Do not free a merge's per-repo guard at `release()` alone — a passing gate must call `holdRepoGuardOnExit` and extend the hold through its own squash via `beginSquash`/`endSquash`, or a queued same-repo sibling can be admitted in the window between gate-settle and squash-landing.
- Do not call `beginSquash`/`endSquash` for a reuse-path or gateless merge — `gateRan` gates both calls; those two paths get no admission-level protection from this mechanism by design (see card `0196ba78`).
- Do not let `beginSquash` mutate `activeMergeRepos` — it is a VALIDATED marker only; the hold's continuity is already guaranteed by `admit()` + the release-skip.
- Do not call `holdRepoGuardOnExit` without an unconditional `finally` that reaches `endSquash`/`releaseMergeRepoGuard` on every exit path — a hold with no matching release permanently blocks that repo.
