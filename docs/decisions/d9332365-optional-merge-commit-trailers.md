# d9332365 — what `orchestration.commitTrailers:"off"` actually suppresses, and the gaps it leaves open

Epic `d9332365` (owner-approved, request `4ccc019c`), shipped by children `9a5d040c` (solo squash), `5933734e` (batch landing) and `bd828fb3` (Settings UI). This record is the standing answer to "what does turning trailers off cost me" — written against the landed code, not the planning analysis, because three of the planning analysis's own predictions turned out to be wrong at the scope it stated them (see "Where the planning analysis was wrong" below).

## Scope — the key, and the three things it is NOT

`orchestration.commitTrailers: "on" | "off"` is a per-project, HUMAN-only config key, default `"on"` (`packages/shared/src/config.ts:460`, default at `:1715`, resolution at `:2278`). It resolves per project with no per-repo-entry override — every entry in a multi-repo registry reads the same project-level value (`packages/daemon/src/projects/resolve-repo.ts:85-108`). It sits in `HUMAN_ONLY_NESTED_PROJECT_CONFIG_KEYS` (`packages/daemon/src/mcp/platform.ts:390`), same trust tier as `mergeGate`/`mergeGateInterval`: the agent-facing validator rejects it and even the elevated Platform Lead's `project_configure` rejects it, because the party it governs must never be able to disable its own paper trail.

`"off"` suppresses exactly the four reserved Loom lines, and nothing else: `Loom-Worker-Branch`, `Loom-Landed-Tip`, `Loom-Worker-Base`, `Loom-Worker-PathSet`. Solo: `packages/daemon/src/git/worktrees.ts:11298` (Branch/Landed-Tip), `:11330` (Base/PathSet text), `:11367` (`expectedTrailers` stays `{}`). Batch: `packages/daemon/src/git/batch-merge.ts:812` (Branch), `:971` (the whole Base/PathSet amend is skipped), `:674` (`pathSetStamp` reads `"disabled"`).

It is NOT the `commitLogBody` key. The worker-commit-log body (card `8b7b81e0`) is a separate, independently-resolved sibling (`config.ts:468`) read at its own site, `worktrees.ts:11285`, explicitly never gated on `commitTrailers`. A user who wants a clean machine-free tail and a readable body sets one, not both.

It is NOT the `Claude-Session:` strip. `stripClaudeSessionTrailer` (`packages/daemon/src/git/writer.ts:204`) runs unconditionally on every landing path — `writer.ts:679` (human REST git write), `batch-merge.ts:801` (every batch candidate commit) — with no `commitTrailers` read anywhere near it. Same for the reserved-line strip applied to a worker's own commit text (`batch-merge.ts:808`, `worktrees.ts:4891`): a worker that quotes a reserved line into its own body is still cleaned, trailers on or off. Both are correctness fixes (cards `b7f965d2`, `95940402`, `112b8d5d`), never a user preference.

It does NOT weaken the landing's identity proof. `verifyCommitParentAndTree` (`worktrees.ts:10685`) is 100% git-structural — parent sha + tree sha of the commit just made against what was staged before it — and reads no commit text at all. `verifyLoomTrailersExactAndReadable` (`worktrees.ts:4987`) returns `{ok:true}` trivially when no `Loom-Worker-Branch` is expected (`:4994`), which is exactly the shape a trailers-off landing passes it, so it degrades to a no-op rather than a skipped check. The anti-forgery chain that feeds `mainline_landed_commits` and the per-branch trust record (decision `2a6a292a` rounds 19-23) never read a trailer; no trailer is load-bearing for mainline trust, and turning them off opens no forgery hole.

It has NO interaction with `mergeGateInterval` or the ungated-landing checks. `decideMergeGateFor` (`packages/daemon/src/sessions/service.ts:24661`) reads only `{mergeGate, mergeGateInterval}`. `ungatedLandingCheckCommand` is a shell string. `packages/daemon/src/orchestration/dist-importer-check.ts` contains zero occurrences of "trailer" in any case and no config read: its landed sha arrives in-process from the merge result (`service.ts:22073`, `kickDistImporterCheck(..., merge.sha)`) and its test selection comes from a git diff of changed `.ts` paths. Nothing in the ungated-landing safety net ever depended on a trailer, so nothing in it degrades.

## The gaps `"off"` actually opens

**1. The crash window is genuinely unrecoverable, and card `e8d4fdc3`'s ledger fallback does not close it.** The solo landing's order is: `mergeBranch` — the real `git commit` — at `service.ts:22043`; then the worker-tip ledger write (`recordMainlineLedgerEntryIfRepoUnchanged`) at `:22052`; then `finalizeMerge` at `:22395`, whose ship-state `updateTask` lands at `:28197`. A crash anywhere between the commit and `:22052` leaves BOTH the ledger row and the task's `merged_sha` unwritten. With trailers on, boot-reconcile rediscovers the landing from the commit's own trailer. With trailers off there is nothing in git to find and no ledger row to fall back to — the landing is undiscoverable by any cheap mechanism. It still fails to a safe "unknown" (never a false "done", never a double-land), but a human has to notice a card that reads open and actually shipped.

**2. Every agent-facing `merged` field reads `null` on a trailers-off project — in steady state, not just after a crash.** This is the gap the planning analysis most understated. `tasks_get` (`packages/daemon/src/mcp/tasks.ts:971`) and `tasks_list` (`:688`) both compute `merged` solely from `resolveMergedInfo` (`:93`) → `getTaskMergedInfo` (`worktrees.ts:9448`) → `scanMergedCommitMap` (`:9110`), whose map is keyed purely off `trailers.branch`. There is NO fallback to the task row's own `merged_sha`, and `getTaskMergedInfo` has no worker-tip-ledger fallback of the kind `findLandedSquashCommit` was given. So the live-landing DB write keeps working perfectly and the read path never consults it: every landed card on a trailers-off project reports `merged: null` forever. The row's `mergedSha`/`mergedDate` are still correct and still returned on a `tasks_get` — read those, never `merged`, on such a project.

**3. `deferredUntilTaskId` auto-clear never fires on a trailers-off project, and every dependent card reports `deferredStuck:true`.** `resolveDeferredEffective` (`mcp/tasks.ts:186`) resolves each named blocker's state through the same `resolveMergedInfo` as above. With `merged` permanently `null`, `allMerged` is never true, so the deferral never auto-releases; and once the blocker reaches the terminal column, `blocker.columnKey === terminalKey` sets `anyStuck`, so `deferredStuck` flips true on a blocker that genuinely did merge. A fail-toward-visible signal firing on a healthy dependency is still a false alarm, and on this project class it is the guaranteed outcome of every `deferredUntilTaskId` deferral. Use a manual `deferred` + `deferredReason` deferral there, or release by hand.

**4. The cross-project escalation link can never read "resolved".** `deriveEscalationStatus` (`service.ts:14461`) decides `"resolved"` vs `"triaged"` purely from `getTaskMergedInfo` against the DESTINATION project's repo. If the destination project has trailers off, a genuinely fixed escalation reads `"triaged"` forever on the Platform board. Of the four `getTaskMergedInfo` call sites (`mcp/tasks.ts:115`, `service.ts:6966`, `:7342`, `:14461`) this is the one a human is least likely to notice, because the staleness is in another project's board.

**5. `findLaterBranchSquash`'s branch-release confirmation is lost — but the ordinary release paths are not.** `findLaterBranchSquash` (`worktrees.ts:603`) is a pure `--grep=Loom-Worker-Branch:` walk with no ledger fallback, so with trailers off it returns `"none"` for every real later landing. Its one caller is `isBranchHeld` (`service.ts:22564`), and it is the LAST of three release routes, not the only one: a `merge_done` event after the retain releases the hold (`:22572`), and the state-based rule releases when the branch's live tip still equals the tip the retaining merge landed (`:22584`) — where that recorded tip comes from the retain event's own in-process `landedTip`/`assembledTip` or from `Db.getVerifiedLandedTip` (`db.ts:4265`, a DB column) before ever falling back to `readLandedTipTrailer` (`service.ts:22597`-`:22614`). So the common cases still release trailer-independently. What is lost is the narrow case the fallback exists for: a branch that advanced past its landed tip and whose owed range later landed by some route that filed no `merge_done` for it. Those branches and worktrees stay retained indefinitely — an operational leak on disk and branch-list hygiene, never a wrong deletion.

**6. `mergedVerificationAtMerge` and `merged` disagree by design on a trailers-off solo landing.** The solo path stamps `mergedVerification: "content"` unconditionally at landing time (`service.ts:22395`), because the parent+tree proof that justifies that tier is trailer-independent. The batch path maps `pathSetStamp === "disabled"` to `null` (`service.ts:24207-24208`, per decision `5933734e`). So `merged: null` beside `mergedVerificationAtMerge: "content"` is the expected, correct shape for a trailers-off solo landing, not an inconsistency to chase.

## Where the planning analysis was wrong

The epic's planning analysis (`analyses/d9332365-commit-trailers.md` under the project work dir, not in this repo — §3/§5) is superseded on three points, each checked against the landed code:

- It called the `worker_merge_confirm` ALREADY_MERGED short-circuit a live loss. Card `e8d4fdc3` closed it at the hot path: `findLandedSquashCommit` now falls back to a branch-keyed worker-tip ledger (`worktrees.ts:8139`, called at `:8210`/`:8271`, plus `findLandedSquashCommitViaMap` at `:9398`), and the confirm's own `preLanded` lookup threads it (`service.ts:20257`, `:20262`), as do the solo finalize tip guard (`:22717`) and boot-reconcile Pass A (`:29041`, `:29046`). What remains is narrower and still real — see the first "Do not" item below.
- It framed the steady-state read path as already DB-sourced, so that only the crash window would lose visibility. That is true of the WRITE and false of the READ — gap 2 above.
- It predicted a per-(project, repo) resolution mirroring `gateCommand`. The key shipped project-level only (`resolve-repo.ts:85-108`); a project cannot turn trailers off for one registered repo and keep them for another.

## Do not

- Do not assume card `e8d4fdc3`'s worker-tip-ledger fallback covers every already-landed lookup. Five `findLandedSquashCommit` call sites still pass only `goneBranchLedger` and so still degrade with trailers off: `service.ts:19176` (notice suppression), `:19690` and `:22027` (the reviewed-tip-moved refusal's escape hatch — these over-REFUSE when the lookup misses), `:19817` (the `priorLanding` gate on the title-entity guard), and `:22034` (`expectAlreadyLanded` for a gateless project). Thread `workerTipLedger` at a site before claiming it is covered; do not generalize the `preLanded` fix to the rest.
- Do not read `merged: null` on a trailers-off project as "not shipped", and do not add a `task.mergedSha` fallback inside `getTaskMergedInfo` to paper over gap 2 — that function's contract is "git-derived", and a silent DB fallback there would make `merged.verification` claim a tier nothing in git supports. If the read needs to become ledger-aware, give it the same explicit, branch-keyed fallback `findLandedSquashCommit` got, with its own verification tier.
- Do not treat `deferredStuck:true` on a trailers-off project as evidence a blocker failed to land — gap 3 makes it the guaranteed outcome for a blocker that merged cleanly. And do not "fix" it by widening `resolveDeferredEffective` to accept the terminal column alone as proof of merge: that silently redefines "until it merges" as "until it's closed", which the field's own contract forbids.
- Do not assume the crash window is recoverable because a ledger exists. The ledger write is downstream of the `git commit` in the same window (`service.ts:22043` then `:22052`), so it is unwritten in exactly the case it would be needed. Closing this needs a durable pre-commit intent row reconciled against git by sha, which is a separate, larger card the epic deliberately did not file.
- Do not re-couple the `Claude-Session:` strip, the reserved-line strip of a worker's own commit text, or `commitLogBody` to this toggle. The first two are correctness fixes with no user-preference dimension; the third is a deliberately independent key.
- Do not claim turning trailers off weakens the ungated-landing safety net, the dist-importer check, or the mainline trust chain. None of the three reads a trailer; the first two were verified to contain no trailer reference at all.
- Do not read `merged: null` beside `mergedVerificationAtMerge: "content"` as an anomaly on a trailers-off project — gap 6 says it is the correct shape there.
- Do not restate this record's gap list in `CLAUDE.md`, an agent brief, or a shipped skill. `CLAUDE.md` carries a pointer only; a shipped skill must stay generic (it may teach "check whether your platform writes machine trailers", never Loom's key name or file paths).
