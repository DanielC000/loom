# 38d68b8d — `onPromptMismatchUnmatched` is the PUSH half a pull-only surface structurally cannot cover

## Narrative

Card 38d68b8d — DoD-2 of card `59757189`'s UNMATCHABLE-mismatch population (the structural twin of `onPromptMismatchUnresolved`, fired on the opposite `isUnmatchableMismatch` branch — none of the recognized/confirmed shapes claimed this mismatch). A pull surface (`getLastMismatchUnmatched`, card `59757189` DoD-1/3, shipped) already lets a session that KNOWS to ask retrieve this text; this event is the PUSH half that was deliberately left for a later card once the content-in-durable-records ruling (card `0eb43216`) landed — a recipient can never self-diagnose (card `68459420`, `lastMismatchReplay`'s own record — same reasoning applies here), and a pull surface only ever helps someone who already suspects a mismatch.

Fires once per genuinely-sent notice (gated behind the SAME `isExactRepeatNotice` check the recipient's own `[loom:prompt-mismatch]` notice already goes through — no separate dedup invented). `intendedText` is the FULL captured text (`Live.lastMismatchUnmatched.intendedText` — see card `59757189`'s own record for why it's captured at detection time, not a later lookup), passed RAW and UNCONDITIONALLY — same posture as `onPromptMismatchUnresolved`'s `messageExcerpt`: `PtyHost` stays DB-agnostic (no DB, no manager/sender lookup), and the implementer (`SessionService.handlePromptMismatchUnmatched`, via `index.ts`) decides who the sender is and applies the `LOOM_LOG_MESSAGE_CONTENT` gate at the one place this content can become durable/queryable — not here.

The ONLY recipient the implementer's `handlePromptMismatchUnmatched` has is the SENDER/PARENT (`s.parentSessionId`) — mirroring `handlePromptMismatchUnresolved`/`handlePasteTripwireGiveUp`'s own "if a parent exists, push to it" shape exactly. It deliberately does NOT also resolve `info.gen`'s own `QueuedMessage.senderId` as an alternate target: `parentSessionId` is the SAME established addressee this notification family already uses for every sibling shape, and inventing a second, untested resolution path here would diverge from that convention for no proven benefit. A session with no parent (e.g. a top-level manager/lead) has no sender to push to, so this is a silent no-op for it, same as its siblings.

`handlePromptMismatchUnmatched` deliberately adds NO separate durable audit event, unlike `handlePromptMismatchUnresolved`'s own `db.appendEvent`: card `59757189`'s own reasoning for the unmatched population is that an in-memory capture plus a pull surface "never creates durable content at rest" — a new durable row here would contradict that deliberate design choice for no requirement this card's own DoD states. `enqueueSystemNudge` already durably queues the delivery itself (the existing message-delivery machinery), which is sufficient for the PUSH obligation this card asks for.

The notification itself fires UNCONDITIONALLY — only the CONTENT inside it is gated. This card's own explicit design constraint: gating the whole notification behind the opt-in content flag would silently re-create the exact defect this card exists to close (a sender who does not know to ask, and now also never told). Gated with `isLogMessageContentEnabled()` directly, the SAME flag every other content-bearing diagnostic in this file uses — mirroring `handlePromptMismatchUnresolved`'s own `messageExcerpt` gating: the signature (`intendedLen`, `writtenHash`) is stated plainly and unconditionally in the shared lead-in sentence, so gating only needs to add-or-withhold the raw text itself, not synthesize a replacement for it. `intendedLen` is stated explicitly per this card's own DoD-1 ("alongside `intendedLen`"), regardless of which branch the content clause takes.

## Do not

- Do not treat the `getLastMismatchUnmatched` pull surface as sufficient on its own — it only ever helps a party who already suspects a mismatch; `onPromptMismatchUnmatched` is the push half that reaches everyone else.
- Do not apply the `LOOM_LOG_MESSAGE_CONTENT` gate inside `PtyHost` for this event's `intendedText` — it stays DB-agnostic; the gate applies only at the implementer (`SessionService.handlePromptMismatchUnmatched`).
- Do not gate the whole notification behind the content flag — only the raw text inside it is gated; the notification itself, and `intendedLen`, always fire.
- Do not add a separate durable audit event for this notification — an in-memory capture plus a pull surface deliberately "never creates durable content at rest" (card `59757189`); `enqueueSystemNudge`'s own durable queuing already satisfies the push obligation.
