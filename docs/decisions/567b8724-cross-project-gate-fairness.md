# 567b8724 — Cross-project gate fairness caps one project's held slots while another project queues

## Narrative

Card 567b8724 (reopening card `a6c7ab29`, which closed the fairness scheduler as "not built, reopen if starvation observed again"): the Platform Auditor observed one project holding both global gate slots and starving sibling projects for 8-25 minutes, repeatedly. Root-caused against source, not just the incident report: `release()` synchronously decrements `active` and calls `grantNext()` in the same tick, so a waiter already queued when a slot frees always beats a brand-new `acquire()` call — this is not a timing race. The real hole is that `grantNext()`'s FIFO scan and `acquire()`'s fast path were both entirely project-blind: if a project has several of its own requests already queued ahead of a sibling project's single request (a batch of merges, or repeated worker self-checks), every freed slot goes to that project's next queued entry before the sibling's, for as long as its own backlog outlasts the sibling's. `mergeRepoFree`'s asymmetry (card `e4701333`) was checked and confirmed unrelated to this mechanism.

The fix (`projectSlotFree`) bounds a project to `Math.max(1, Math.ceil(cap / 2))` concurrently-ADMITTED slots, but ONLY while a DIFFERENT project has a queued waiter that is itself ADMISSIBLE right now (`hasAdmissibleForeignWaiter` — not blocked by its own `worktreeFree`/`mergeRepoFree`). The admissibility gate is load-bearing, added at manager review after the first draft (which counted ANY foreign queued waiter, admissible or not) was shown to be non-work-conserving: cap=2, project A holds 1 slot with a second request queued, project B has a queued MERGE whose own `mergeRepoFree` is false (e.g. B's prior merge is mid-squash) — the first draft would skip A's request for "fairness" while B's request is separately skipped by its own repo guard, leaving a free slot idle that neither project could otherwise use. Requiring the foreign waiter to be independently admissible closes this: a foreign waiter that can't actually run doesn't get to reserve a slot for itself.

Wired into BOTH `acquire()`'s fast path and `grantNext()`'s per-tier scan — needed in both, or a fresh request from an at-cap project could win the fast path past an already-queued admissible foreign waiter that `grantNext` would otherwise have protected. This reuses the EXACT precedent `worktreeFree`/`mergeRepoFree` already established (a queued waiter blocked by either is skipped in `grantNext`'s scan rather than deadlocking the queue behind it) — no new mechanism, and it never touches an already-admitted (RUNNING) entry, consistent with card `24642c3d`'s standing "never preempt a running gate" rule.

The rule is keyed purely on `projectId`, not `gateType`: a batch of merges is exactly as capable of starving a sibling project as a stream of worker self-checks, so both `merge`/`worker`/`deploy` gate types are bound identically. This is deliberately CROSS-TIER: because the check is project-keyed rather than tier-keyed, a foreign project's LOW-tier (worker self-check) waiter can be granted ahead of an over-quota project's own HIGH-tier (merge/deploy) waiter while contested. Tier priority is still fully preserved WITHIN one project (`grantNext` still exhausts all of `highWaiters` across every project before ever looking at `lowWaiters`, so a project's own high-tier waiter is still found before its own low-tier one).

Known, accepted limitation: `ceil(cap/2)` is not a max-min-fair split across 3+ simultaneously-contending projects — it guarantees no single project can take more than half of `cap` while contested, but does not guarantee an even split among many sibling projects. Not fixed here; flagged as a follow-up if 3+-project starvation is ever observed in practice, mirroring how this very card is the reopen-on-evidence follow-up to `a6c7ab29`.

## Do not

- Do not count a foreign queued waiter toward the fairness restriction unless it is itself admissible right now (`worktreeFree`/`mergeRepoFree`) — an inadmissible foreign waiter can never use a slot reserved for it, and reserving one anyway leaves it idle instead of work-conserving.
- Do not add this check to only one of `acquire()`/`grantNext()` — both are needed, or the unchecked path lets an at-cap project's fresh request win a free slot past an already-queued admissible foreign waiter.
- Do not key this on `gateType`/`priority` — cross-project fairness is the point; a foreign low-tier waiter legitimately jumping an over-quota project's own high-tier waiter is intended behavior, not a tier-priority regression.
- Do not read this as preempting a running gate — it only ever gates admission of a QUEUED or brand-new entry, never touches an already-admitted one (card `24642c3d`).
