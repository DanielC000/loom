# 356538ef — the canonical merge path does not trust worker-writable shared `.git` state

## Do not

- Do not construct git for the canonical merge path (`git/worktrees.ts`, `git/batch-merge.ts`) with a bare `boundedSimpleGit(`/`simpleGit(` or a raw `spawn("git", …)` — use `canonicalGit` (or `...CANONICAL_GIT_CONFIG_ARGS` for a raw spawn). `test/canonical-git-helper-guard.mjs` fails on a bypass.
- Do not re-add a per-call `--no-replace-objects` at a call site: `canonicalGit` applies `core.useReplaceRefs=false` to every command, and a per-site copy is exactly how the sibling paths were left unprotected.
- Do not "fix" the driver isolation with `--attr-source` or `core.attributesFile` — verified NOT to stop a worker-set driver (see below).
- Do not read this as a sandbox. Loom does not protect itself from a deliberately adversarial worker (see "Threat model").
- Do not check or strip `GIT_CONFIG` (or any `scrubGitEnv` key) with a case-sensitive key lookup on win32 — use `envKeysNamed`/`deleteEnvKeys` (card e93703d9).
- Do not neutralize `info/grafts`/`.git/shallow` with the literal `"NUL"` — measured that git invoked through an MSYS/bash wrapper resolves a bare `"NUL"` as an ordinary cwd-relative FILE, not the real Windows null device, so a worker who pre-plants a real file named `NUL` can poison it right back in (the daemon's own direct `child_process.spawn` resolves it safely, but nothing here should depend on exactly how git is invoked). Do not use a FIXED literal sentinel path either — this repo is public, so a worker reading `git/bounded.ts` could pre-plant a fixed path before a later call reuses it. Use `freshGitSentinelPath` (a fresh, nonexistent, absolute path per call, never created) via `GIT_GRAFT_FILE`/`GIT_SHALLOW_FILE`.
- Do not shrink `prepareCanonicalEnv`'s materialized env to a bare `{GIT_GRAFT_FILE, GIT_SHALLOW_FILE}` object — simple-git's own `.env(obj)` REPLACES the spawned child's entire environment wholesale (never merges with `process.env`), so a small object would silently strip PATH/HOME/everything else for every canonical call. Always spread onto the full base env first (card 7ebb4acf).
- Do not narrow `-c core.commitGraph=false` (`CANONICAL_GIT_CONFIG`) to the `rev-list --parents` call site, or to any other single subcommand — item 9's re-review (SF1(a)) measured that `merge-base`/`isAncestorCommit` are equally skewed by a forged graph once the forged commit is reached by WALKING PAST it (not named as one of the call's own endpoints); there is no subcommand-level carve-out that stays safe, so the flag is applied unconditionally to every canonical call via `CANONICAL_GIT_CONFIG`, never per-site.
- **(card 3a5c5d4a) Do not "fix" this with a `GIT_COMMON_DIR` (or `GIT_DIR`) environment override** — measured directly: it produces a SPLIT-BRAIN state, not a safe override. `--git-common-dir`/`config` correctly report the trusted repo, but `rev-parse HEAD`/`for-each-ref`/`show-ref`/`log` still resolve the ref VALUE from the planted target and then fail trying to find that object in the (correctly-scoped) object store ("fatal: missing object … for refs/heads/master"). Incoherent and unsafe; see `checkCommondirTrust` instead.
- **(card 3a5c5d4a) Do not "fix" `repo-lock.ts`'s `resolveGitDirsSync` DIRECTORY-branch blindness in isolation.** Its current behavior (a DIRECTORY `.git` is unconditionally its own commonDir, never checking for a `commondir` file inside it) is what keeps its existing NON-security consumers (the cache-key fs reads in `worktrees.ts`'s `readHeadSha`/`readBaseSha`/`computeDiffCacheKey`, `skills/inject.ts`, `pty/codex-doctrine.ts`) accidentally safe today — they never follow a planted DIRECTORY-shape commondir. Making it "agree with git" there without also adding a trust check would hand those consumers the same hijack instead of closing anything.
- **(card 3a5c5d4a) Do not default a NEW `canonicalGit`/`killableCanonicalRaw` caller's `trustedMainRoot` to its own `repoPath`** when `repoPath` is a worker's own linked WORKTREE, not the main checkout — that makes `checkCommondirTrust`'s FILE-shape check compare the worktree's commondir against ITSELF, false-refusing every real worktree call. Pass the real main checkout root explicitly (see `canonicalGit`'s own doc; `killableCanonicalRaw` already reuses its existing `quarantineRepoPath` for this, never a second concept).
- **(card 3a5c5d4a) Do not trust a worktree's own pointer files (`.git`/`commondir`) as proof of where they lead.** A worker already has filesystem write access to the whole shared `.git` tree — including a sibling or its own worktree's PRIVATE `.git/worktrees/<name>/commondir` file, which is legitimate and therefore not itself suspicious-looking. Verify the resolved target against a trust anchor the daemon independently knows, never against what the file itself claims.

## Threat model

A worker's worktree shares the canonical repo's common `.git`: `config`, `info/attributes`, `hooks/`, `refs/*` (including `refs/replace/*`). The daemon's own merge path runs git in the canonical checkout and in worker worktrees, so any of that state a worker can write is state the daemon *executes or trusts*. Code Reviewer b924d0a9 reproduced two cheap-to-close cases:

- **S12 (merge driver):** a worker sets `merge.evil.driver` in shared config plus `f.txt merge=evil` in `<common-dir>/info/attributes`; the daemon's `git merge-tree` / `merge --squash` / `cherry-pick` then runs the worker-chosen command (arbitrary command execution by the daemon, and a way to launder content past the structural reviewed-tip walk).
- **S10/S11 (replace refs):** `git replace <reviewed-tip> <evil>` leaves the branch tip unchanged, so every sha-keyed review check passes, while `git merge --squash` stages the replacement's content.
- **(card 7ebb4acf, from Code Review 57d7a27d of aa7677fa round 4) info/grafts and .git/shallow:** `core.useReplaceRefs=false` disables replace refs but does NOT touch `$GIT_COMMON_DIR/info/grafts` (a separate, older legacy mechanism) or `.git/shallow`. A worker-planted `info/grafts` entry can SUBSTITUTE a commit's reported parent list (the card's own example: a real two-parent forgery `F` with parents `[P, EVILROOT]`, grafted to report only `P`) and a worker-planted `.git/shallow` entry can HIDE a commit's parents ENTIRELY (reports zero, stronger than a graft's one-fake-parent lie) — both skew every canonical-path parent/ancestry read built on `rev-parse <sha>^N`/`rev-list --parents`/`merge-base` (`readFirstParent`, `isAncestorCommit`, `verifyReviewedTipChain`, and every other `merge-base` read in `git/worktrees.ts`/`git/batch-merge.ts`), though NOT `cat-file -p` (the raw stored object — why `verifyLandedAsOwnCommit`, round 5 of `aa7677fa`, is already immune).
- **(card 3a5c5d4a) commondir redirect:** a worker plants (or rewrites) a `commondir` file under the shared `.git` tree — either directly inside a plain checkout `.git` DIRECTORY (a shape real git honours but a real main checkout never legitimately has), or by overwriting an existing linked worktree's own private `.git/worktrees/<name>/commondir` pointer. Measured directly (docs/decisions/3a5c5d4a-canonical-git-commondir-trust.md): this redirects objects, refs AND config for every canonical call — reads (`rev-parse`/`log`/`config`/`for-each-ref`) AND writes, including full write-laundering: a normal-looking commit against a believable decoy (any repo holding every blob the victim's current checkout already has) succeeds, with its parent silently substituted to attacker-forged history, landing only in the decoy while the real repo's own on-disk ref never moves.

**Hardened here (both cases, through ONE helper — `canonicalGit`, `git/bounded.ts`):**

1. `-c core.useReplaceRefs=false` on every command, via simple-git's construction-time `config`. This is git's documented equivalent of `--no-replace-objects`. Chosen over the `GIT_NO_REPLACE_OBJECTS` env var because it avoids simple-git's env handling/blocklist and never touches `scrubGitEnv`. The per-call flag in `verifyReviewedTipChain` was removed as redundant. Raw `spawn("git")` sites in `worktrees.ts` (`ls-tree`, `grep`) carry the same setting via `CANONICAL_GIT_CONFIG_ARGS`.
2. Merge-driver blanking. Before every command that is not a known pure read (deny-by-default: an unrecognised subcommand counts as exec-capable), `raw` enumerates `merge.*.driver` with `git config -z --get-regexp` in the SAME cwd as the call it protects, so `include.path`/`includeIf` files and a worktree's `config.worktree` are honoured, and prefixes `-c merge.<name>.driver=` for each. simple-git refuses that `-c` key unless `allowUnsafeMergeDriver` is set; `canonicalGit` sets it, which is safe because it only ever blanks a driver, never defines one.
3. **A driver name that cannot be blanked FAILS CLOSED.** `-c` splits key/value at the FIRST `=`, and gitattributes accept `merge=a=b`, so `-c merge.a=b.driver=` would set key `merge.a` and leave the real `merge.a=b.driver` live (reproduced through the built helper: the driver ran and its output was laundered as a clean merge). So an exec-capable call THROWS, naming the offending config key, when any enumerated name contains `=` or a control character. `--config-env` was rejected as the alternative: it adds an env-var dependency and simple-git's unsafe plugin is unverified for it; the refusal is simpler and leaves no residual. The refusal surfaces in the confirm/batch reasons (`git merge main into worktree failed: canonicalGit: refusing to run …`, `cherry-pick of <sha> failed: canonicalGit: refusing …`).
4. **The enumeration AND the post-check run with the call's OWN global options** (`-C`, `--git-dir`, `--work-tree`, `--namespace`, `-c`, and their `=` forms — `gitGlobalArgs`), so both reads see exactly the config the real call sees: a call re-pointed at another repo is protected against THAT repo's driver config, and the earlier blanket `-C` refusal is gone. `--remerge-diff` on an otherwise pure-read subcommand (`show`/`log`/`diff-tree`) DOES run merge drivers, so any arg matching /remerge/ makes the call exec-capable. Global options that take a separate value (`--git-dir`, `--work-tree`, `--namespace`, `-C`, `-c`, `--config-env`, `--attr-source`) are skipped when finding the subcommand. `-m` and `--diff-merges*` on those reads are exec-capable too (`--diff-merges=r` runs a driver with no config, and a worker-set `log.diffMerges=remerge` turns `-m`/`--diff-merges=on` into remerge).
5. **THE INVARIANT — verify the resulting state, never predict key spelling (owner-facing ruling, after THREE review rounds and THREE driver-name shapes).** `=` (round 1), an EMPTY name (`[merge ""]`, attribute `merge=` — git selects driver `""`, and a `.+` regex never matched `merge..driver`) and a NON-UTF-8 name (a raw 0xE9 byte: simple-git decodes U+FFFD, so `-c merge.<U+FFFD>.driver=` blanks a DIFFERENT key and cannot be carried in argv on any OS) each defeated a different assumption about how a `-c` key is spelled, and each was reproduced through the real service (the driver ran, exit 0, and main's own edit was lost). So after building the `-c` prefix, `canonicalGit` re-reads `git <prefix> config -z --get-regexp '^merge\..*\.driver$'` in the SAME instance/cwd and THROWS (`CanonicalGitRefusal`) unless the EFFECTIVE (last-wins) value of EVERY key is empty (a key with no value counts as live). It lives in the one place `raw` runs, so no exec-capable call can skip it. The enumeration (regex `.*`, refusal on `=`/control chars/U+FFFD) is only the mechanism; this post-check is what closes the whole class, including any future `-c`-vs-canonical-key mismatch. A `CanonicalGitRefusal` is thrown BEFORE any git process runs, so callers (`mergeMainIntoWorktree`, the canonical `merge --squash` path) report it as `refused, nothing changed: …` via the shared `describeGitFailure`, and do NOT run the exec-capable cleanup resets (which would be refused too and dress a clean refusal up as "the canonical repo needs recovery"). **The post-check is self-sufficient, not a second opinion on the enumeration:** it treats ANY key containing U+FFFD or a control character as live regardless of value (decoding collapses the real key and our own blanking `-c` key into one map entry, so a blank would otherwise hide the live driver — reproduced), and a key with no value as live. It is exercised through an exported `canonicalRaw(git, args, repoPath, trustedMainRoot, buildPrefix)` seam (the `repoPath`/`trustedMainRoot` params were added by card 3a5c5d4a, item 14 below — this one's own `buildPrefix` seam is unchanged) that lets a test inject a prefix-builder that misses a driver, so the post-check is provably WIRED and the last line of defence (removing its call turns that test red).
6. **Ambient `GIT_CONFIG` is stripped from the child env** — via a scrubbed COPY, built when `GIT_CONFIG` is present in `env ?? process.env`. **(Rewritten in place, card 7ebb4acf — the two sentences this replaces, "an env-less caller stays env-less, byte-identical to before this card" and "an always-explicit env was tried and reverted", are now FALSE and must not be restated or relied on.)** `prepareCanonicalEnv` now ALWAYS materializes an explicit env (every canonical call needs the `GIT_GRAFT_FILE`/`GIT_SHALLOW_FILE` sentinels — item 8, below), so there is no more "stays env-less" case: `canonicalGit` is now the one that ADDITIONALLY strips `GIT_ENV_TRANSPORT_KEYS`, unconditionally, whenever the CALLER itself passed no `env` (`env === undefined`) — not gated on whether `GIT_CONFIG` happened to be ambient, which was the OLD, narrower trigger. This is the fix `a746a3eb`'s own "Follow-up 23c74c62" section already argued for in principle (see that record, also rewritten by this card) — it is simply unconditional now that materialization itself is unconditional. The original "always-explicit env throws unsafe" finding below is still TRUE and still the reason the strip exists; only the premise that an env-less call could stay implicit is gone. Only the `git config` builtin honours `GIT_CONFIG` (like `--file`), so both driver reads would see just that file while `git merge` reads `.git/config` — reproduced: driver ran. Every other config-affecting variable feeds the ONE config stack that `merge` and `config` both read, so they cannot blind one and not the other: `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `GIT_CONFIG_NOSYSTEM`, `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n`, `GIT_CONFIG_PARAMETERS`, `GIT_DIR`, `GIT_WORK_TREE`, `HOME`/`XDG_CONFIG_HOME` (checked against git's `config` docs, not exhaustively re-run per variable; `GIT_CONFIG` is the one documented builtin-only exception). **Casing (card e93703d9):** on win32 env names are case-insensitive, so `Git_Config` is `GIT_CONFIG` to git-for-windows and to Node's `process.env.GIT_CONFIG` accessor, but a `{...process.env}` copy keeps the key as spelled — a plain `delete cleanEnv.GIT_CONFIG` missed it and the blindness reopened (reproduced: driver ran). The presence check AND the strip now share ONE case-aware helper (`envKeysNamed`/`deleteEnvKeys`, `git/bounded.ts`: upper-cased match on win32, exact match on POSIX where `Git_Config` is a different inert variable); `scrubGitEnv` (`GIT_PAGER`/`PAGER`/`EDITOR`…) had the same class and routes through it too. Tests: the win32-only `(GIT_CONFIG casing …)` block in `canonical-git-isolation.mjs`, with bare-git positive controls.
7. **LOCALE is a third config-read asymmetry, closed by not using a regex at all.** On glibc in a UTF-8 locale git's regex `.` does NOT match an invalid byte, so `git config --get-regexp '^merge\..*\.driver$'` returned NOTHING for a raw-0xE9 driver name: prefix `[]`, post-check "proved" empty, and `git merge` ran the driver (reproduced end to end in WSL Ubuntu-22.04, git 2.34.1, `LANG=C.UTF-8`: "Merge made by the 'ort' strategy" and the marker file created; with `LC_ALL=C` it was refused). A Windows git matches in every locale, so the owner's Windows gate structurally cannot see this. Both reads now run `git config -z --list` (no regex) and filter `merge.<name>.driver` IN JS. Pinning `LC_ALL` was rejected: another assumption for the invariant to lean on. The three asymmetries between the config reads and the real call are therefore: ambient `GIT_CONFIG` (builtin-only), the call's own global options (`-C`/`--git-dir`/…), and locale-dependent matching.
8. **(card 7ebb4acf) `GIT_GRAFT_FILE`/`GIT_SHALLOW_FILE` are pointed at a FRESH, nonexistent, absolute path on every canonical call, unconditionally.** `prepareCanonicalEnv` (`git/bounded.ts`) now layers both onto the full base env (never a bare 2-key object — simple-git's `.env()` replaces the child's entire environment wholesale, so a small object would strip PATH/HOME for every call) before `scrubGitEnv`, shared by BOTH `canonicalGit` (simple-git reads: `readFirstParent`, `isAncestorCommit`, `verifyReviewedTipChain`, every `merge-base` read) and `spawnCanonicalGitTree` (the raw-spawn mutation path), so every affected symbol is covered by this one chokepoint with no per-site change. `freshGitSentinelPath` generates a fresh value per `prepareCanonicalEnv` CALL — i.e. per `canonicalGit` CONSTRUCTION, but per `raw()` CALL for `spawnCanonicalGitTree` (N1, Re-review 11cd4e3e — `prepareCanonicalEnv` runs INSIDE `rawViaDirectSpawn`/`rawViaWinJobLauncher`, `git/bounded.ts` ~664/~752, not at `spawnCanonicalGitTree`'s own construction time, so every mutating call on that path gets its own fresh pair) — never memoized, never created here — under a Loom-controlled dir; a fixed literal would be readable in this public repo's own source and pre-plantable by a worker with shared-`.git` write access; see the "Do not" list above for why the sentinel is never the literal `"NUL"` either, and is `path.resolve`d (never `path.join`ed) against `LOOM_HOME` so a relative `LOOM_HOME` override can't produce a relative, cwd-dependent sentinel. Neither env var is in simple-git's own unsafe-env blocklist (`@simple-git/argv-parser`'s env→category map), so this needed no new `unsafe:` flag.
9. **REWRITTEN (Code Review of card 7ebb4acf, B1 — this item previously said "commit-graph is NOT an independent attack vector"; that was WRONG and is retracted below, not merely amended).** `git commit-graph write --reachable` does silently no-op for the whole repo while `info/grafts`/`.git/shallow` exist (verified, positive-controlled) — but that only stops git's OWN `commit-graph write` from BAKING a lie in. It does NOT stop a worker from writing an arbitrary commit-graph file directly: the reviewer built a real two-parent commit `F=[P,M]`, ran `git commit-graph write --reachable` (grafts/shallow absent, so the write succeeds and bakes the TRUE parents), then binary-edited `F`'s `CDAT` chunk entry — the `parent2` field, 4 bytes at a fixed offset per commit — from M's lookup-table position to `GRAPH_PARENT_NONE` (`0x70000000`, verified empirically against this installed git 2.47.0.windows.2 by comparing a genuine single-parent commit's own `CDAT` entry; NOT `0xffffffff`/`0x7fffffff` as commit-graph format docs from memory might suggest — this is a case where VERIFYING THE REAL BYTES mattered). `git commit-graph verify` reports "incorrect checksum and is likely corrupt" on the tampered file — **but no ordinary read command calls `commit-graph verify` before trusting the file; the checksum is never checked on load.** With the forged graph in place, `git rev-list --parents -n1 F` reports only `P` — the SAME skew class as a graft/shallow lie, now proven reachable through a THIRD mechanism independent of either. `-c core.commitGraph=false` (now added to `CANONICAL_GIT_CONFIG` — item 1 above gets a sibling) makes `rev-list --parents -n1 F` correctly report both `P` and `M` again.

**REWRITTEN TWICE (Re-review 11cd4e3e of card 7ebb4acf, SF1 — the "Measured scope" paragraph and the graft-presence sentence this replaces were BOTH FALSE, not merely narrow; do not restate either).**

**(a) `merge-base`/`isAncestorCommit` ARE skewed by a forged graph — just not when the forged commit is queried directly.** Querying `F` AS ONE OF A CALL'S OWN TWO ENDPOINTS (`git rev-parse --verify --quiet F^1`, what `readFirstParent` calls; `git merge-base <M> F`, what `isAncestorCommit` calls) is immune — repeatedly measured, including a p1-swap variant — because git resolves a commit it was handed directly (or via chained `^N`/`~N` revision syntax resolved against ONE named commit, e.g. `G^1^2`) straight from the object, never through the graph's cached parent array. But the original measurement never tried WALKING PAST the forged commit while resolving something else: build `G`, a plain single-parent child of `F`, and ask about `M0` (`M`'s own parent, one hop further back than `F`'s forged parent) — `git merge-base M0 G` returns the fixture's shared ROOT instead of the true `M0`, `git merge-base --is-ancestor M0 G` exits non-zero (should be 0 — `M0` genuinely IS an ancestor of `G`), and `git rev-list --count G` under-counts (5 instead of the true 7: root, `M0`, `M`, `P0`, `P`, `F`, `G`) — because once the revision walker reaches `F` as an INTERMEDIATE node rather than one of the call's own named endpoints, it DOES consult the graph's forged cached parent array for `F`'s parents. The real rule: a commit resolved AS AN ENDPOINT of the call is immune; one reached by walking past it is not — and every one of `readFirstParent`/`isAncestorCommit`/`verifyReviewedTipChain` can be made to walk past a forged intermediate commit by a sufficiently deep fixture, so there is no safe narrower, subcommand-level carve-out (see the new "Do not" above). `-c core.commitGraph=false` closes the class categorically regardless of this split.

**(b) A grafts file's mere presence DOES disable an on-disk commit-graph outright — for any read, with as little as one entry.** Verified directly against the SAME forged-graph fixture: a one-line `info/grafts` mapping a wholly unrelated, nonexistent fake sha to another fake sha was enough to make the identical `merge-base M0 G` probe from (a) return the TRUE answer again, with no `-c core.commitGraph=false` anywhere in the invocation. Only an EMPTY or comment-only `info/grafts` file leaves the graph in use (also verified: both read back the forged, wrong answer, identically to no grafts file at all). **This is exactly why `GIT_GRAFT_FILE` neutralization (item 8) makes `core.commitGraph=false` MANDATORY alongside it, not belt-and-braces on top of an already-sufficient defense:** before item 8's fix, a worker's own planted `info/grafts` — whatever fake parent it carried — would have ACCIDENTALLY also defeated a forged commit-graph, as a side effect of a grafts file simply existing. Pointing `GIT_GRAFT_FILE` at a fresh, nonexistent sentinel removes that file from git's view entirely, which also removes the accidental graph-distrust it was incidentally providing. So neutralizing grafts, on its own, makes a forged-graph attack MORE viable, not less — `-c core.commitGraph=false` is the thing that actually closes it, and the two fixes are interdependent, not redundant. `--use-bitmap-index`: **grep says no** — `grep -rn "use-bitmap-index\|useBitmapIndex\|bitmap" packages/daemon/src/git/*.ts` returns zero hits; no canonical-path read opts into reachability bitmaps. **Why `-c` on the invocation, never a `.git/config` `include.path`:** an include lives INSIDE the shared, worker-writable `.git/config` — the exact surface this whole threat model distrusts. A worker could append a LATER `core.commitGraph=true` override to that SAME file (git's own config stacking is last-value-wins within one file/include chain), silently defeating an include-based neutralization. A `-c` flag on canonicalGit's own invocation is the HIGHEST-precedence config source there is, supplied by Loom's own code — never reachable from anything a worker can write. Same reasoning `core.useReplaceRefs=false` (item 1) already relies on `-c` for.

10. **(card 7ebb4acf, N3) Ambient `GIT_TEST_COMMIT_GRAPH` overrides `-c core.commitGraph=false` and must be stripped.** Measured against the SAME forged-graph fixture item 9 builds: `GIT_TEST_COMMIT_GRAPH=1 git -c core.commitGraph=false merge-base M0 G` returns the WRONG (forged) answer — the env var defeats the `-c` flag for this git-internal-test knob, resurrecting item 9's skew from outside `CANONICAL_GIT_CONFIG` entirely. `GIT_TEST_COMMIT_GRAPH=0` does NOT reproduce this (measured) — `prepareCanonicalEnv` (`git/bounded.ts`) strips the var unconditionally on presence anyway, via the SAME case-aware check it already runs for `GIT_CONFIG`, never a value-dependent carve-out for a var this codebase has no legitimate reason to set ambiently.

11. **(card 7ebb4acf, item 11 — SF4, Re-review 11cd4e3e) `detectShallowCanonicalRepo` used to fail OPEN when `resolveGitDirsSync(repoPath)` returned `null`.** That fs-only resolver returns `null` for a `repoPath` with no `.git` entry of its own (a project bound to a SUBDIRECTORY of a repo, or a call made with `GIT_DIR` pointed elsewhere) — and the pre-fix code read that `null` as "not shallow," silently skipping the whole check for exactly the repos it cannot resolve fs-only. Now it fails CLOSED instead: on a `null`, it asks the canonical helper itself for `rev-parse --git-common-dir` — repo DISCOVERY, not a content read; it resolves WHICH `.git` governs `repoPath` without walking any commit history, so a graft/shallow/forged-graph lie (all of which skew commit/parent/ancestry reads, never ref/path discovery) cannot skew its answer — and checks `shallow` at THAT resolved path; if even that probe fails, it refuses the merge outright with an honest "could not determine whether the canonical repo is shallow" reason rather than falling through as "not shallow." `detectShallowCanonicalRepo` is therefore now `async` and takes a `timeoutMs`/`gitFactory` pair like every other canonical-path reader; every caller (`mergeBranch`, `runBatchedMerge`, and the two early `confirmWorkerMerge`/`mergeBatchTracked` refusals below) awaits it.

12. **(card 7ebb4acf, SF3, Re-review 11cd4e3e) The shallow check is also hoisted to the TOP of `confirmWorkerMerge` and `mergeBatchTracked` (`sessions/service.ts`), not just `mergeBranch`/`runBatchedMerge`.** This hoist refuses a shallow canonical repo before `checkCutBaseAncestry`, `reviewedTipVerdict`, `findLandedSquashCommit`, the admission-time union-merge into the worktree, or the gate ever run — so a shallow repo never burns a gate lane, let alone reaches a read that could error unpredictably. Both carry the SAME `ConfirmMergeResult.canonicalRepoShallow`/`MergeBatchResult.canonicalRepoShallow` flag, but **"never cached" is true of only ONE of the two, for a structural reason, not a bug (Code Review e9cbcb15, N2):** `confirmWorkerMerge` IS the function `confirmWorkerMergeTracked` wraps in `pendingOps.attach()`, so its `canonicalRepoShallow:true` return flows straight into that wrapper's own `classifyOutcome` and is correctly classified `"canonical-repo-shallow"` (`NEVER_CACHED_OUTCOMES`). `mergeBatchTracked`'s OWN top-of-function hoist is different in KIND, not just degree: it `return`s a already-`settled` `AttachResult` directly, in the SAME shape as the ownership/branch/repo-mismatch checks immediately above it in that function — `pendingOps.attach()` is never even called for this path, so there is no cache layer to exclude it from; `mergeBatchTracked`'s own `classifyOutcome` ternary DOES carry a `canonicalRepoShallow ? "canonical-repo-shallow"` arm, but it is UNREACHABLE from this hoist — it is reachable only via item 13's in-lock backstop below, which (unlike this hoist) genuinely does run inside the tracked closure.

13. **(card 7ebb4acf, SF1/SF2, Re-review 11cd4e3e) The in-lock/mid-flight backstops (`mergeBranch`, `runBatchedMerge` — item 12's "backstop" reference above) now carry the SAME `canonicalRepoShallow` flag, mapped to the SAME classification BEFORE the generic fallthrough.** Before this round, `mergeBranch`'s own shallow refusal (the pre-lock check inside `mergeBranch` itself, which runs at SQUASH time — i.e. AFTER the gate, since `confirmWorkerMerge` calls `mergeBranch` post-gate) returned a bare `{ok:false, reason}` with no flag; `confirmWorkerMerge`'s post-squash handling had no case for it, so it fell into the generic `squashRefusedResult` fallthrough and earned the actively-wrong "squash was attempted but never committed … **Re-task a rebase**" suffix for a repo a rebase cannot fix. Reproduced end to end (not just reasoned about): a REAL repo that is non-shallow when `confirmWorkerMergeTracked` starts (so the TOP check in item 12 passes and the gate genuinely runs), made shallow via a real `.git/shallow` write injected from inside `reviewedTipVerdict` (a real step between the top check and the squash), now returns `canonicalRepoShallow:true` with NO "Re-task a rebase" text; reverting the fix reproduces the exact wrong text. `runBatchedMerge`'s own early check (which, unlike `mergeBranch`'s, fires BEFORE its gate — it is the backstop for the window between `mergeBatchTracked`'s top hoist and `runBatchedMerge`'s own call, not "during the gate" for batch) gets the identical flag; `mergeBatchTracked` now maps it the SAME no-fallback way as `quarantined`/`indexLockPresent` (every candidate reported via `runFallback`'s no-start mode, `started:false`, never actually dispatched) — **and this is what makes item 12's "unreachable" `classifyOutcome` arm reachable after all**: THIS path runs inside the tracked closure, so it IS classified `"canonical-repo-shallow"`/`NEVER_CACHED_OUTCOMES` for both solo and batch, unlike item 12's own batch hoist. Also fixed in the same round: `detectShallowCanonicalRepo`'s `resolveGitDirsSync`-null fallback (item 11) constructed its git factory OUTSIDE the `try` meant to catch its failure — simple-git's own constructor throws SYNCHRONOUSLY (`GitConstructError`, verified directly) for a `repoPath` that does not exist at all, so a stale/removed repoPath threw raw instead of returning the honest "could not determine" refusal; the construction now sits inside the same `try` as the `.raw()` call. And the refusal text (both the top hoist and this backstop) no longer guesses "(e.g. during dependency provisioning)" — it names the real, verified mechanism (an AGENT's own `git fetch --depth=N` inside a worktree writes the shared `.git/shallow` file) and the correct remedy audience (a manager has no canonical-repo write access; escalate to the Platform Lead or ask the owner, never "run this yourself").

14. **(card 3a5c5d4a) `checkCommondirTrust` — an fs-only pre-check, run first, before even the merge-driver enumeration above.** Refuses outright (a distinct `CanonicalGitCommondirRefusal`, never cached, nothing spawned) when: (a) `repoPath`'s `.git` is a DIRECTORY that also carries its own `commondir` file (never legitimate — verified), or (b) `.git` is a linked-worktree FILE whose gitdir pointer resolves outside the trusted main's own `.git/worktrees/`, or whose resolved commondir does not equal the trusted main's own `.git` — `trustedMainRoot` is the caller's OWN already-known canonical root, never derived from the worktree's own files (see the "Do not" list above for exactly where each default comes from and why defaulting to `repoPath` itself would be wrong for a worktree-scoped call). A `GIT_COMMON_DIR` env override was considered and rejected — measured incoherent (see "Do not"). The full measured hijack table, the write-laundering repro, and the alternates/GIT_COMMON_DIR negative results: docs/decisions/3a5c5d4a-canonical-git-commondir-trust.md. A refusal renders DISTINCTLY from the generic "refused, nothing changed" (`canonicalFailureMessage`, `git/bounded.ts`): it names the mechanism and says this needs human escalation (the Platform Lead inspecting the shared `.git`), surfaced through `worker_merge_confirm`'s/`merge_batch`'s own `reason` text.

A batch rollback that itself fails is appended to the drop reason (`ROLLBACK FAILED — the batch worktree may hold residue`), unless probes prove HEAD and the tree are unchanged.

**Verified on git 2.47.0.windows.2** (which levers stop a worker-set driver): baseline — the driver runs; `--attr-source=<tree>` — still runs (`info/attributes` is still read); `-c core.attributesFile=/dev/null` — still runs; `GIT_CONFIG_COUNT/KEY/VALUE` — works but simple-git blocks that env family; `-c merge.<x>.driver=` (empty) — nothing runs, git reports "cannot spawn" and the merge is a conflict. `GIT_CONFIG_NOSYSTEM`/`GIT_CONFIG_GLOBAL` are irrelevant: the attack surface is the repo's own shared config.

## Deliberate consequence: fail closed on custom merge drivers

A legitimate project-defined `merge.<x>.driver` now surfaces on the canonical path as a **visible conflict/refusal** — never silently ignored and never executed. **User-facing symptom:** `worker_merge_confirm` returns `merged:false` with "branch conflicts with current main — rebase/resolve before merge" and `merge_batch` reports `conflict cherry-picking <sha> onto the batch`; the reason text does not name the driver (the real cause, "cannot spawn", is git stderr). This is deliberate. The builtin `merge=union` (used by the daemon's own union-forward) needs no `merge.*.driver` config and is unaffected. A project that genuinely needs a custom driver must resolve that merge by hand.

## Residual and NOT hardened here

- **TOCTOU window is attacker-driven, not incidental:** the drivers are enumerated immediately before each exec-capable call, so a driver written between that enumeration and the git process is not blanked — and the WORKER controls that timing and can rewrite the shared config in a tight loop. This is acceptable ONLY under the stated not-a-sandbox model above (a worker that can loop on config can equally `git update-ref refs/heads/main`); do not cite this hardening as protection against a deliberately adversarial worker. Not locked.
- **A worker can `git update-ref refs/heads/main` outright.** Loom does not sandbox workers from their repo; detecting a mainline write from a worktree is a separate card (needs a persisted last-landed sha and a policy for legitimate human commits).
- **The wider shared-config exec class is NOT neutralised, and is not a cheap item:** `core.hooksPath` / `<common>/hooks/*`, `filter.*` (including git-lfs clean/smudge), `core.fsmonitor`, diff `external`/`textconv`, `gpg.program` + `log.showSignature` (runs an external program on a pure `git log`), `core.sshCommand`. Hooks and LFS filters have legitimate uses in real projects that the daemon cannot tell apart from worker-set config in the shared common dir, so neutralising them is a product decision (what may a project configure?), not hardening. Separate card.
- **Accepted trust assumption (owner decision, request b0fb1e26, 2026-09-26; card 88dedf8c): workers are trusted with the shared `.git`'s command-executing settings, and nothing here protects against a worker that abuses them.** The class in the bullet above (`core.hooksPath` / `<common>/hooks/*`, `filter.<x>.clean/smudge/process`, `core.fsmonitor`, diff `textconv`/`external`, and the other config-driven command execution) is **deliberately NOT hardened**: a worker can make the daemon's own git calls (its squash commit, merges, checkouts) run commands of the worker's choosing, and Loom neither blocks, blanks, snapshots nor alerts on it. Why: husky/commitlint (`core.hooksPath`) and git-lfs (`filter.lfs.*`) are common legitimate uses in real end-user projects, and the daemon cannot tell a worker-set value in the shared common dir from a human-set one, so blanking them would break LFS projects and silently stop a user's own commit hooks running on Loom squash commits. Alternatives the owner considered and declined: (b) snapshot the human-set values at project bind time and refuse/alert when they change, and (c) run workers without a shared common dir (a real sandbox). Either can be reopened as a new card with a new owner decision; until then, treat this as the same not-a-sandbox model as the TOCTOU and `update-ref` residuals above. Code precedent, for orientation only (it is not a protection): `attemptCodexAutoCommit` already passes `{ allowUnsafeHooksPath: true, allowUnsafeFsMonitor: true }` as `extraUnsafe` to `boundedSimpleGit` (`git/bounded.ts`), i.e. simple-git's guard against setting those keys is deliberately relaxed on that one path.
- **Off-path git construction sites** deliberately not routed through the helper (each is listed with its reason in `canonical-git-helper-guard.mjs`'s allowlist): `git/writer.ts` (human-only REST writes), `git/reader.ts` (read-only UI view), `git/unanchored-comment-blocks.ts`, `runs/snapshot.ts`, `sessions/service.ts` (worktree GC status/count probes — `status --porcelain`, and `rev-list --count HEAD..<branch>` at ~service.ts:19886 and ~20020; NOT routed through `canonicalGit`, so a replace ref could skew GC's unlanded-commit counts: self-harm only for the worker that planted it, deliberately left unchanged in this card), `setup/bootstrap.ts` (`git init` of a new dir), `orchestration/restart.ts` (supervisor ancestry), `vault/versioner.ts` (the human's own notes repo, incl. its `execFileSync commit`), `deploy-staleness.ts`, `skills/assets-git-status.ts`, `mcp/decisions.ts` (all `execFileSync` reads).
- Any test's injected `gitFactory` is used as-is by design.
- **(card 3a5c5d4a) SUPERSEDED: `checkCommondirTrust`'s FILE-shape cross-check no longer skips silently when `trustedMainRoot` is omitted — it now FAILS CLOSED by default.** The round-1 shape of this bullet (a caller omitting `trustedMainRoot` was silently unchecked) is fixed. The only surviving exemption is an explicit, reviewed `opts.commondirCheck:"advisory-read"` opt-out, applied PER CALLER (round 3, S2 — NOT a blanket per-helper grant: `git/worktrees.ts`'s shared `boundedGit` helper applies it only to a caller that does NOT supply its own `trustedMainRoot`; a caller that does, like `computeEmitCompareGate`, gets the real verification instead) — never at a site whose output steers a REAL mutating call's own parameters (round 3, B2/B3: an identity-fallback decision is NOT read-only in that sense, even though it only ever runs `git var`). `diffBranch`'s own worktree-scoped read (`workerDiff`'s uncommitted-diff branch) threads a real `trustedMainRoot` unconditionally — it feeds a manager's merge review directly, the one review-evasion vector this card's investigation specifically confirmed exploitable. See `docs/decisions/3a5c5d4a-canonical-git-commondir-trust.md`'s own round-3 section for the full current call-site list and the `CheckCommondirTrustOpts` mechanism — restated here it would only rot the same way this bullet already did once.
