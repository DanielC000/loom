# 3de74275 — `agent_update`/`updateAgentPreset` excludes profile fields: Option B keeps capability-minting human-only

## Narrative

Card `3de74275` ("[CAPABILITY — design-first] Manager/dedicated-role MCP surface to manage agents, projects, schedules, profiles, skills") was the owner-directed design task behind the whole manager self-service management surface (`agent_assign_profile`, `agent_update`, `project_update`, `project_archive`, `schedule_create`/`schedule_update`), landed by commit `14e1c340f0` ("feat(daemon): manager self-service management surface (Option B)").

The design problem: a manager/lead already had partial MCP access to structural entities (create a project, create an agent) but nothing that let it self-provision the things that actually confer capability — assigning a profile to an agent, creating/editing profiles, editing skills, setting `gateCommand`. The card was explicitly flagged design-first because widening this is a TRUST-BOUNDARY change: a profile confers role + allowlist + `browserTesting` (a navigate-anywhere capability) + model/skills, so an agent able to create or freely assign profiles could escalate its own or another agent's capability. `gateCommand` is host-RCE by design.

**Option B** (the chosen answer): profile CREATE/edit, skill CREATE/edit, and `gateCommand` all stay human-only. What a manager DOES get is `agent_assign_profile` — attach an EXISTING, human-authored profile (or clear it) — never mint one. Because every assignable `profileId` was created by a human who already intended it assignable, assignment itself cannot escalate beyond what a human already blessed; no additional `⊆`-capabilities subset check is needed on top.

`updateAgentPreset` (the `agent_update` MCP tool) is the structural half of this split: it edits an agent's `name` and `startupPrompt` only. The profile field is deliberately absent from its patch shape — not an oversight, the load-bearing half of Option B. Routing capability-conferring changes through the separate, human-blessed-profile-only `assignAgentProfile` path (see that method's own doc comment) is what keeps a manager's self-service surface additive and posture-preserving: every existing spawn stays byte-identical, and a manager can restructure its own agents' identity/instructions without ever being able to grant them anything it doesn't already hold.

## Do not

- Do not add `profileId`, `allowlist`, `gateCommand`, or any other capability-conferring field to `updateAgentPreset`'s patch shape — that would let a manager self-escalate capability through the "structural edit" surface instead of the validated `assignAgentProfile` path.
- Do not treat `agent_assign_profile`'s lack of a `⊆`-capabilities check as a gap to close — it's correct under Option B specifically because profile CREATE/edit stays human-only, so every assignable `profileId` is already human-blessed.

## Amendment (card `a06650d2`) — Option B's premise broke; assignment now checks too

Option B's reasoning (above) rested on one premise: "every assignable `profileId` was created by a human who already intended it assignable, [so] assignment itself cannot escalate beyond what a human already blessed." That premise stopped holding for two independent reasons:

1. **A non-human caller can mint a profile.** The ungated Setup Assistant surface can `profile_create`/`profile_update` its own manager/worker-role profiles (see `mcp/setup.ts`) — "every assignable profile is human-authored" is no longer true by construction.
2. **A human-minted profile can independently carry a field that must stay human-only forever.** `connections`/`capabilities`/`vaultWrite` are rejected at CREATE/PATCH time on every agent-facing profile writer (`AGENT_FORBIDDEN_PROFILE_KEYS`, this file) — but nothing ever checked them at ASSIGN time. Because `Profile` has no `projectId` (profiles are global), a human-authored `vaultWrite`/`connections`/`capabilities` rig meant for one project could be bound, via an ordinary manager's `agent_assign_profile`, to an agent in an entirely different project — a credential-laundering move with no audit trail beyond the bare `agent_assign_profile` event. VERIFIED by direct code read (no live repro needed — the function has no role/field check at all): `SessionService.assignAgentProfile` (`sessions/service.ts`, originally lines 13223-13231) does `requireManager` → `resolveManagerAgentRef` → `requireOwnProject` → a bare `db.getProfile(profileId)` existence check → `db.updateAgent`. A manager could bind its own agent to ANY existing profile regardless of role or capability fields — including a `platform`/`auditor`/`workspace-auditor`/`assistant`-role profile.

**New ruling:** every agent-facing profile-BINDING call (`agent_assign_profile`, `profile_assign`, `agent_create`/`agent_update` with a `profileId`, `agent_clone`/`agent_clone_batch`, `template_apply`) must refuse a profile carrying a non-empty `connections`, a non-empty `capabilities`, or `vaultWrite:true` — UNCONDITIONALLY, via ONE shared predicate, `agentAssignableProfileError` (`profiles/validate.ts`). Every surface except the Platform Lead's own `profile_assign`/`agent_update`/`agent_create` (deliberately elevated-admin, below) and clone (handled differently, below) ALSO refuses an elevated/locked role (`LOCKED_PROFILE_ROLES`) through that same predicate's role branch at its strict default.

**The one deliberate exception — `allowElevatedRoles`:** the Platform Lead (`mcp/platform.ts`'s `profile_assign`/`agent_update`/`agent_create`) is the human-driven, `LOOM_DEV`-gated elevated operator; administering elevated rigs (binding `platform`/`auditor`/`workspace-auditor` profiles to its own platform agents) is its legitimate job, and a role gate there would break real Lead workflows. So Platform's three direct-binding tools call the predicate with `{ allowElevatedRoles: true }` — the ROLE half of the check is lifted, but the FIELD half (`connections`/`capabilities`/`vaultWrite`) is NEVER lifted, for any caller: it is still an LLM turn, and laundering a human-made secrets/vault-write rig across projects is exactly the class this closes regardless of who's asking. A human keeps full reach via REST either way.

**`template_apply` always calls the predicate at its true default** (no `allowElevatedRoles`) — applying a template is never a legitimate way to bind an elevated or field-bearing rig, so the full check applies.

**`agent_clone`/`agent_clone_batch` do NOT route their ROLE check through the shared predicate's own locked-role branch at all** — this was tried and reverted after it broke a real, load-bearing path: `clonedProfileRoleError` (`agents/clone-core.ts`) initially called `agentAssignableProfileError(profile)` at its true default, which rejects every role but manager/worker, including `"assistant"` — but `gateway/server.ts`'s companion auto-clone (a 2nd `/api/companion/provision` call) legitimately clones the bundled default's `assistant`-role agent; that is the actual mechanism by which a 2nd companion gets provisioned. Rejecting `"assistant"` there broke it (caught by `companion-provision.mjs`'s `(6a)`/`(6h)` cases failing under `run_gate`, not by any pre-merge unit test targeted at the change). The fix at the time: `clonedProfileRoleError` kept its OWN pre-existing, narrower role check (`operator`'s own-workspace-confinement message, then `platform`/`auditor` via `isPlatformProfile`) UNCHANGED, and called the shared predicate ONLY with `{ allowElevatedRoles: true }` — meaning "skip the predicate's own role branch, already handled above," never "permit an elevated role through." See the fix round below for why that specific mechanism (reusing `allowElevatedRoles` to also run the FIELD branch) was itself a defect, and what replaced it.

## Fix round 1 (card `a06650d2`, SUPERSEDED by the delta review below) — moved the field check out of the cores

A first pass moved `agentAssignableProfileError`'s FIELD branch (`connections`/`capabilities`/`vaultWrite`) OUT of the shared clone/template cores entirely and into new agent-facing-only pre-checks (`cloneSourceFieldError`, `templateAssignableProfileError`), reasoning that the field check is an agent-surface rule that should never reach a human-only REST writer. **A delta security review of that commit found this went too far — see "Fix round 2" below for the corrected, surviving design; this section is kept only as the narrative of what was tried and why it broke.** The field-check relocation DID fix the real bug (a Companion profile granted `capabilities`/`connections`, a supported live-upgrade flow, could no longer provision a 2nd companion over the human-only REST route) — but in the SAME commit, `applyWorkflowTemplate`'s ROLE check was ALSO removed from the core, which was wrong: that role check PREDATES card `a06650d2` entirely (it ran via `setupRoleError` before `agentAssignableProfileError` existed, and was NEVER meant to be REST-exempt — a human REST template-apply applying an elevated-role template was never a sanctioned flow). The review also found that `mcp/setup.ts`'s `template_apply` pre-check had no test proving it does anything — removing its call left every existing test green, because at that point in the fix nothing backstopped it.

## Fix round 2 (delta review on card `a06650d2`) — the FIELD check is fail-closed IN the cores; ROLE never had an opt-out

**Ruling:** invert fix round 1's field-axis design. `agentAssignableProfileError`'s FIELD branch runs INSIDE the shared cores (`createAgentCore`/`cloneAgentCore`, `applyWorkflowTemplate`) by default, on every caller — fail-CLOSED, not fail-open. The ONLY opt-out is `opts.humanAuthorized: true`, and it is set ONLY by the two bearer-guarded, human-only (reachable over loopback, or remotely by a Tier-1 gateway-token holder — still a human, never an agent) REST routes that call those cores directly: `gateway/server.ts`'s `/api/companion/provision` auto-clone, and its `/api/setup/templates/apply` route. Agent-UNREACHABILITY of `humanAuthorized` is a structural property of the MCP input-schema layer, not of either guard below: `strictShape`'s `.strict()` rejects any unknown key on every tool's `inputSchema`, so an agent could never pass `humanAuthorized` through an MCP call even if a handler carelessly forwarded its raw input into these cores' `opts` — no handler does, but that is what actually closes the door. The two guards are tripwires on top of that, each with a stated, narrower job and real blind spots (see each guard's own header for the authoritative list): `human-only-surface-leak-guard.mjs`'s entry is a plain-text scan of `src/mcp/*.ts` ONLY — it says nothing about the rest of the tree, and would miss a dynamically-built string. `human-authorized-call-site-allowlist-guard.mjs` is a per-line LITERAL-regex scan of `src/` — it catches a plain `humanAuthorized: true` and nothing cleverer: not `humanAuthorized: !0`, not a boolean built from an expression (`1===1`, `Boolean(1)`), not a variable (`const h = true; …humanAuthorized: h`), not ES2015 shorthand (`{ humanAuthorized }`), not a quoted key (`"humanAuthorized": true`), not a value split across lines, and not `opts` built from an untrusted request body and merely spread into a call. Neither guard is a type-checker or a dataflow analysis; both are correctly described as a tripwire against the OBVIOUS mistake, not a proof of the invariant. The ROLE branch is UNCONDITIONAL regardless of `humanAuthorized` — it is never REST-exempt, on `applyWorkflowTemplate` (restoring its pre-card behaviour) or on `createAgentCore`/`agentAssignableProfileError` generally; `clonedProfileRoleError` (clone's own narrower role axis) never took an opt-out to begin with and needed no change here.

**Clone:** `clonedProfileRoleError` (`agents/clone-core.ts`) stays a pure role-only check (`operator`/`isPlatformProfile`), unconditional, calling `agentAssignableProfileError` for NOTHING. `cloneAgentCore` takes an `opts: { humanAuthorized? }` param and forwards it straight into its `createAgentCore` call alongside `{ skipRoleCheck: true }` (role was already vetted above; `skipRoleCheck` only stops `createAgentCore`'s OWN generic role branch from re-checking it, it does not touch the field branch). `createAgentCore` then runs `agentAssignableProfileError(profile, opts)` UNCONDITIONALLY — field fail-closed unless `humanAuthorized`. `mcp/platform.ts`'s `agent_clone`/`agent_clone_batch` never pass `humanAuthorized` (so the core's field check fires there too, on top of their own early `cloneSourceFieldError` pre-check — belt and suspenders, no longer the only defense). `gateway/server.ts`'s companion auto-clone passes `{ humanAuthorized: true }` — the one case the opt-out exists for (`companion-provision.mjs`'s `(6i)`).

**Templates:** the exact same shape. `applyWorkflowTemplate` (`setup/templates.ts`) takes `opts: { humanAuthorized? }` and, for every resolved agent, calls `agentAssignableProfileError(profile, { humanAuthorized: opts?.humanAuthorized })` — role unconditional, field skippable only via that flag. `templateAssignableProfileError` survives as an early, agent-facing-only pre-check (strict, no opts) called by BOTH `template_apply` MCP tools (`mcp/setup.ts`, `mcp/platform.ts` — Platform Lead's included, since role eligibility on a template is never Lead-exempt either) before calling `applyWorkflowTemplate`, which now backstops it. `gateway/server.ts`'s REST template-apply route passes `{ humanAuthorized: true }` to `applyWorkflowTemplate` — the field-skip a human template-apply needs, while the role check still applies to it unconditionally.

**A consequence worth stating plainly:** because the cores now backstop the pre-checks, removing `cloneSourceFieldError`'s or `templateAssignableProfileError`'s call from its MCP handler no longer flips any end-to-end test red — the core's own check still rejects, just with a later/less specific error. That is the INTENDED outcome of "no longer the only defense," not a coverage gap; the pre-checks exist for error quality, not as the sole gate. **Each core's own FAIL-CLOSED DEFAULT (no opts at all) is proven directly** — bypassing every MCP-layer pre-check entirely — by `clone-core-field-check.mjs` (round-2 review BLOCKING finding: no prior test called `createAgentCore`/`cloneAgentCore` directly, so a regressed default hid behind the agent-facing pre-check in every existing test) for clone, and by `workflow-templates.mjs` §5 for templates (a bare `applyWorkflowTemplate` call with no opts). The `humanAuthorized: true` OPT-OUT itself — the ONE path that is supposed to skip the field check — is proven separately: `companion-provision.mjs`'s (6i) for clone, and `setup-templates-rest.mjs`'s (6) for templates. Default and opt-out are deliberately two different tests each, because proving one says nothing about the other.

## Amendment (card `1f52bc75`) — field axis widened to documentConversion/harness(non-"claude")/allowDelta; browserTesting deliberately excluded

The `a06650d2` field axis (`connections`/`capabilities`/`vaultWrite`) left a gap of the same shape: `AGENT_FORBIDDEN_PROFILE_KEYS` also marks `harness`, `browserTesting`, `documentConversion`, and `allowDelta` as human-only to CREATE, but nothing checked them at ASSIGN time either — an agent could bind an existing human-made `documentConversion`/`harness`-pinned/`allowDelta`-widened rig to its own agent via `agent_assign_profile` (or any other binding surface), same laundering shape as the original bug.

**Investigated before implementing** (worker report on card `1f52bc75`, confirmed by the lead): for each of the four keys, whether a bundled profile or a documented agent-facing workflow relies on assigning it without human review.

- **`documentConversion`** — zero bundled profiles set it; CLAUDE.md documents it as human-set-only with no "provision a rig" language anywhere. **Added to the field check** (same posture as `connections`/`capabilities`/`vaultWrite`).
- **`harness` other than `"claude"`** — zero bundled profiles pin a non-default harness; selecting the vendor binary is "the same trust class as gateCommand" per the `8c27ae8e` reasoning, and multi-harness precedence (Profile > project > platform > built-in) is meant to be a human/project-level decision, not an agent's per-assignment pick. A profile explicitly storing `harness:"claude"` is the same as the (more common) absent case — see `validateProfile`'s own comment on why absence expresses the default — so an explicit `"claude"` passes. **Added to the field check, fail-closed on any OTHER value** (`profile.harness != null && profile.harness !== "claude"`, not a `=== "codex"` allowlist) — a future third harness value is rejected by default too, with no code change needed here when one ships.
- **`allowDelta` (non-empty)** — zero bundled profiles ship a non-empty entry; an unreviewed entry (e.g. `"Bash(*)"`) widens the spawn allowlist, "the same trust class as gateCommand" per `8c27ae8e`. **Added to the field check.**
- **`browserTesting`** — **deliberately EXCLUDED, unlike the other three.** `agent_assign_profile`'s own MCP tool description (`mcp/orchestration.ts`) states verbatim: *"Use this to provision a rig (e.g. assign the human-authored 'QA Tester' browser profile) without waiting on a human."* The bundled "QA Tester" and "Web Designer" profiles (`profiles/seed.ts`) ship `browserTesting:true` **specifically** so a manager can autonomously provision them — this is the documented, intentional, routine orchestration path (spawning a QA/design worker), not an oversight the way the other three are. It is structurally unlike `connections`/`capabilities`/`vaultWrite`/`documentConversion`/`harness`/`allowDelta`: none of those six have any bundled-profile precedent for agent-driven assignment, while `browserTesting` has two, named in the tool's own docstring. The ROLE check already bounds the blast radius — a manager's `agent_assign_profile` is strict (no `allowElevatedRoles`), so it can only ever bind non-elevated profiles (the check is on the PROFILE's role, via `LOCKED_PROFILE_ROLES`), onto agents in its own project (`assignAgentProfile`'s separate `requireOwnProject` scope check), which is exactly the QA/design delegation the tool documents. Gating `browserTesting` here would silently break a shipped, documented capability for no security gain the role check doesn't already provide.

**Shape:** all three new checks live in the SAME `agentAssignableProfileError` predicate, after the existing `connections`/`capabilities`/`vaultWrite` checks, inside the same `if (opts?.humanAuthorized) return null` early-out — so a human assigning such a profile via the Profiles UI / REST (or either of the two named `humanAuthorized` REST routes) still succeeds; only the agent-facing paths that call this predicate at its strict default (no `humanAuthorized`) refuse. No second predicate was added.

**Lead ruling (code review on this amendment):** unlike `browserTesting`, the `harness` check gets NO role-based carve-out — the Platform Lead's and the Setup Assistant's own `profile_assign` now refuse a human-made `harness:"codex"` (or any other non-`"claude"`) profile too, even though both surfaces otherwise administer elevated rigs. This is INTENDED, not a regression to relax: `harness` is human-only EVERYWHERE in this codebase, not just at profile-assign time — even the Platform Lead's own elevated `project_configure` rejects a `harness` key (`HUMAN_ONLY_PROJECT_CONFIG_KEYS`, `mcp/platform.ts`), and `AGENT_FORBIDDEN_PROFILE_KEYS` rejects it at CREATE on every agent-facing profile writer, Lead included. A human binds a codex-pinned rig via the Profiles/Agents UI — never through any agent-facing profile-binding tool.

## Do not (amendment)

- Do not read `agent_assign_profile`'s historical lack of a `⊆`-capabilities check (the ORIGINAL "Do not" above) as still correct — it described Option B's now-superseded premise. The current rule is: every binding surface calls `agentAssignableProfileError`.
- Do not grant `allowElevatedRoles: true` to widen WHO can bind an elevated role, anywhere outside the Platform Lead's direct `profile_assign`/`agent_update`/`agent_create` — not the manager or setup surfaces, not `template_apply`.
- Do not let `allowElevatedRoles`, in its true sense (Platform Lead widening), lift `agentAssignableProfileError`'s field checks — that flag affects the role check only, on every caller, no exceptions.
- Do not reuse `allowElevatedRoles` to mean "skip the role check because it's handled elsewhere" (clone's own reason) — use the distinct `skipRoleCheck` instead; conflating the two is what let fix round 1's field-check bug go unnoticed in the first place.
- **Do not move the FIELD check back out of the cores** (`createAgentCore`/`cloneAgentCore`, `applyWorkflowTemplate`) — fix round 1 tried exactly that, and a delta security review reverted it (see "Fix round 2" above): a future agent-facing caller that forgets its own early pre-check would otherwise get NO check at all. The field check is fail-closed IN the core, by design; `humanAuthorized: true` is its only opt-out.
- Do not let `humanAuthorized` affect the ROLE branch, on any caller, ever — it is a FIELD-only opt-out. Role eligibility on a template/clone predates this card and was never meant to be REST-exempt.
- Do not add a THIRD call site (or a fourth, …) that passes `humanAuthorized: true` without updating `human-authorized-call-site-allowlist-guard.mjs`'s allowlist AND getting a security review — that guard fails loudly on exactly this, by design.
- **Do not add `browserTesting` to the assign-time reject list without a carve-out for the bundled rigs.** The bundled "QA Tester"/"Web Designer" profiles and `agent_assign_profile`'s own tool description make autonomous browserTesting assignment the documented, intended path (see the `1f52bc75` amendment above) — gating it unconditionally would silently break that shipped capability. If a future card wants it gated anyway, it needs an explicit carve-out (e.g. an allowlist of known-safe bundled profile ids, or a dedicated opt-out mirroring `allowElevatedRoles`), not a bare addition to the field-check list.
- Do not add `documentConversion`/`harness`/`allowDelta` to the list of fields `restrictedTools`/`noCommit` sit in (fields that stay OUT of `AGENT_FORBIDDEN_PROFILE_KEYS` because they only restrict/declare rather than grant) — all three grant or select something, the same trust class as `connections`/`capabilities`/`vaultWrite`, and now have the matching assign-time check to prove it.

## Amendment (card `c8f1d9b7`) — why `agent_clone`/`agent_clone_batch` never got `allowElevatedRoles`, stated explicitly

A later review (card `c8f1d9b7`, full-review finding `486d4238`) found that `clonedProfileRoleError`'s own error text, and `agent_clone`'s/`agent_clone_batch`'s own tool descriptions, claimed the clone role guard "mirrors the least-privilege guard on assigning one directly" — which is FALSE on `mcp/platform.ts`: the Platform Lead's `agent_create`/`agent_update`/`profile_assign` carry no such guard (by this record's own "Fix round 2" ruling above) — they are the one surface where assigning operator/platform/auditor directly is explicitly permitted. This record never stated why clone itself, on the SAME router, was left out of that same `allowElevatedRoles` widening — "Fix round 2" above only explains why clone's role check can't be ROUTED through the shared predicate's own role branch (it would reject the companion auto-clone's legitimate `"assistant"`-role clone), not why the Lead's own clone calls aren't ALSO given the opt-out its three siblings get.

**The actual reason, stated here for the first time:** `clonedProfileRoleError` is NOT exclusively a Platform-Lead-surface function — it is the SAME function the human-only REST companion auto-clone (`gateway/server.ts`'s `/api/companion/provision`) calls via `cloneAgentCore`, with no `allowElevatedRoles` concept available to it at all (that opt-out is wired ONLY into `createAgentCore`'s role branch via `agentAssignableProfileError`, which clone deliberately never calls — see "Fix round 2"). Unlike `createAgentCore` (used by `agent_create`, which never has this problem because it mints a FRESH agent with no "source" to inherit a confinement guarantee from), `cloneAgentCore` has exactly ONE shared role check serving TWO structurally different callers: the Lead's own `agent_clone`/`agent_clone_batch` (elevated, human-driven, LOOM_DEV-only) and the companion auto-clone (ordinary end-user REST route, zero elevation). Threading an `allowElevatedRoles` opt-out through `cloneAgentCore` so the Lead's calls could bypass the operator/platform/auditor check would require either (a) a second code path/flag plumbed through `cloneAgentCore` → `clonedProfileRoleError` solely for the Lead's two callers, or (b) trusting every future caller of the shared core to pass the flag correctly — both are exactly the kind of per-caller special-casing `clonedProfileRoleError`'s own header comment already rejects ("the ONLY role axis for every cloneAgentCore caller, agent-facing or not"). Keeping clone's role check unconditional, with NO opt-out for any caller including the Lead's own, is the simpler and more conservative choice: bulk/templated duplication of an elevated rig (clone's actual job — "provisioning a per-family role... across a roster of sibling projects," `agent_clone`'s own description) is a materially different, higher-blast-radius action than one deliberate `profile_assign` call, and the Lead retains the exact same end capability via `agent_create`/`profile_assign` one call at a time if it genuinely needs to disperse an elevated rig — clone is a convenience primitive, not the only path, so refusing it costs nothing the Lead cannot already do through its other tools.

**Fix applied:** the false "mirrors" claim is removed from `clonedProfileRoleError`'s platform/auditor message (`agents/clone-core.ts`) and from `agent_clone`'s tool description (`mcp/platform.ts`) — both now state plainly that clone is STRICTER than the Lead's own direct-assign tools, not that it mirrors a guard those tools don't have. Both `agent_clone` and `agent_clone_batch` descriptions were also corrected to list `operator` alongside `platform`/`auditor` as refused roles — they previously named only `platform`/`auditor`, undercounting what `clonedProfileRoleError` actually checks.

### Do not (this amendment)

- Do not read this amendment as inviting `cloneAgentCore`/`clonedProfileRoleError` to grow an `allowElevatedRoles` opt-out for the Lead's own callers — the reasoning above is why that was deliberately NOT done; if a future card wants to revisit it, it needs to weigh the shared-core risk above explicitly, not just copy the pattern from `createAgentCore`.
- Do not restate this amendment's reasoning as a reason to also tighten `agent_create`/`agent_update`/`profile_assign` to match clone — those three staying permissive is the untouched, standing ruling from "Fix round 2" above; this amendment only explains clone's own asymmetry, it does not reopen that ruling.
