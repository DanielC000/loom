# Profile widening reach — extending the grant-reach mechanism to role changes and restrictedTools, on every write path

Card `be447b3f`, discovered from the Code Review of `3c4e0df6`. Audited four paths that widen what a profile's bound agents can do; this record covers the two accepted into the reach/audit mechanism plus the two accepted OUT of it.

## What was decided — (c) extended into the mechanism

`role`/`restrictedTools` widen a profile's already-bound agents the same way an `AGENT_FORBIDDEN_PROFILE_KEYS` grant does, but neither CONFERS a capability — so neither joins that array, and both stay agent-writable exactly as `@decision 8c27ae8e` already ruled.

1. **`profileWideningsOf`** (`packages/shared/src/profileGrants.ts`) is a strict superset of `addedProfileGrants` — grant keys first (unchanged order), then `"role"`, then `"restrictedTools"`. `addedProfileGrants` is untouched; every grant-only caller (`roleChangeCapabilityCarryoverError`) keeps calling it directly.
2. `role`: ANY change is reportable, not only an "escalating" one — the computation does not judge direction, it reports like a grant addition and leaves judgment to the reader.
3. `restrictedTools`: INVERTED vs a boolean grant — true→false (removing the restriction) is the widening; false→true is a narrowing, never reported.
4. The **same** `profile_grant_reach` kind carries it — `addedKeys` grows past `AGENT_FORBIDDEN_PROFILE_KEYS`; a new `roleChange: {from, to}` field appears only when `"role"` is in `addedKeys`.
5. **Fires on every profile UPDATE/DELETE write path — this claim is now actually TRUE, not aspirational.** `mcp/setup.ts`'s and `mcp/platform.ts`'s own `profile_update` call `recordProfileGrantReach` (`source: "setup"` / `"platform"`). Deletion is a widening write path of its own (falling back to `resolveProfile`'s plain backstop widens exactly like an update when the deleted profile had `restrictedTools:true` or a non-null `role`) and has **three** write paths, not one — the platform `profile_delete` MCP tool, an agent manager's own `profile_delete` MCP tool, and the human REST `DELETE /api/profiles/:id` — round 2 shipped only the first and left the other two silently uncovered, which round 3's Code Review caught as the blocking Major. All three now route through ONE shared helper, `recordProfileDeleteGrantReach` (`grantReach.ts`), built on `PROFILE_DELETE_BACKSTOP_FIELDS` — so a fourth delete path literally cannot compute its own before/after pair and drift; it can only call the shared helper or skip the audit outright (the Code Review's own "ONE shared helper... so a fourth can't drift" framing). `source` grew a `"manager"` value for the second of the three. These (both `profile_update` MCP tools, and all three `profile_delete` paths) are exactly where this event is the ONLY signal a human gets on the two MCP surfaces that can't be interactively confirmed — each such tool description tells the calling agent to relay a present `grantReach` field; the REST route returns it for a human client to read directly. **Not every write path** — see "accepted OUT of scope" below for the one this card deliberately leaves uncovered.
6. The Profiles editor's confirm is extended too (`planGrantSave`/`GrantReachConfirm`) — role gets its own `roleChange` clause (`data-testid="grant-reach-role-change"`), since `grantKeyList`'s generic "you are granting X" sentence can't express a from/to value.
7. **The Setup Assistant's OWN `profile_update` response filters `grantReach.agents` to LIVE projects** (`setupVisibleGrantReach` in `grantReach.ts`) — this least-privilege surface's other reads (`list_all_projects`/`list_all_agents`) already exclude archived projects, so an unfiltered reach would leak an archived project's existence/agent name through a side channel its other tools don't expose. `agentCount` stays the TRUE total (archived-project agents included) and the durable event is filed BEFORE filtering, so the event and the Platform Lead's own unfiltered `profile_update`/`profile_delete` reads are unaffected — only the setup response's `agents[]` list is narrowed.
8. **`PROFILE_DELETE_BACKSTOP_FIELDS` is DERIVED from `resolveProfile({startupPrompt:null}, null)`, never hand-copied.** Round 2 restated `resolveProfile`'s no-profile backstop field-for-field as a standalone constant — a second source of truth with nothing to catch it drifting if `resolveProfile`'s own backstop ever changed. Round 3 replaced the hand-copy with a direct call, translating the two real shape differences (`allow`→`allowDelta`, backstop `harness:null`→`undefined`) in one place; the daemon test also asserts the two agree field-for-field, as a second line of defense for exactly the regression this round found no test would have caught.

## Do not

- **Do not add `role`/`restrictedTools` to `AGENT_FORBIDDEN_PROFILE_KEYS`.** That would reject them on every agent-facing writer, contradicting `@decision 8c27ae8e`'s standing ruling that both stay agent-writable. This card is a VISIBILITY layer on top of that ruling, never a reversal.
- **Do not touch the role enum/model**, or `LOCKED_PROFILE_ROLES`/`PROFILE_SPAWNABLE_ROLES`/`ROLE_CARRY_FORWARD_ONLY`. Project memory `roles-are-security-spine-not-toggles` rules out dissolving roles into toggles; a legibility fix goes ON TOP of the enum, never on its identifiers. This card audits existing role-change behavior — it never changes which changes are allowed.
- **Do not fold `profileWideningsOf` back into `addedProfileGrants`**, or change the latter's return type — `roleChangeCapabilityCarryoverError` and the web's own round-trip test rely on `addedProfileGrants`/`AGENT_FORBIDDEN_PROFILE_KEYS` staying an exact 1:1 correspondence.
- **Do not invent a sibling event kind.** `addedKeys` naming the two new keys fits `ProfileGrantReach`'s existing shape; only `role` needed the additive `roleChange` field.
- **Do not read the Setup/Platform tool-description note as a substitute for the event** — it is told to the agent because it's the only *interactive* signal on those surfaces; the event is what makes the fact durable regardless of whether any agent relays it.
- **Do not implement agent rebind here.** It's a genuinely different computation (see "Agent rebind" below), tracked on its own card `8b236b22` — folding it in would conflate two distinct hazards under one mechanism that only computes one of them correctly.
- **Do not let a `profile_delete` write path construct its own before/after pair instead of calling `recordProfileDeleteGrantReach`.** That is exactly the drift the shared helper exists to make structurally impossible — a hand-rolled `before: grantFieldsOf(existing), after: <restated backstop>` at a fourth call site is a silent regression back to round 2's gap, not a harmless refactor.
- **Do not hand-copy `resolveProfile`'s backstop into `PROFILE_DELETE_BACKSTOP_FIELDS` again.** It is DERIVED by calling `resolveProfile({startupPrompt:null}, null)` — see item 8 above. Restating it as a literal reintroduces the exact drift risk round 3 removed.

## (a)/(b) — accepted OUT of scope: no agent-reachable write path exists

Neither has an agent MCP tool that can reach it at all — the exact risk this mechanism exists for (an agent-driven change with no human in the loop) isn't present yet:

- **A Connection's host/secret.** No in-place edit route exists: `POST /api/connections` (`gateway/server.ts:2727-2743` → `connections/store.ts:134-149`) refuses on a name collision. The closest thing to a rotation is `provisionConnection`'s scoped rotation (`connections/store.ts:176-195`, rotate at `:186`), reachable ONLY from `POST /api/questions/:id/answer`'s credential branch (`gateway/server.ts:6187-6229`, call at `:6217`) — an explicitly NEVER-ECHO, human-only boundary (`:6199-6202`). Zero MCP tools touch `connections` (checked every file under `packages/daemon/src/mcp/`).
- **A capability-catalog definition's owner-typed `command`.** Also no in-place edit: `POST /api/capabilities` (`gateway/server.ts:2900-2908` → `capabilities/registry.ts:240-250`) refuses on a slug collision; changing one needs delete (`:2909-2911` → `registry.ts:253-259`) then recreate. Zero MCP tools touch `capability_defs`. `registry.ts`'s own module doc (`:1-11`) already frames the owner-typed `command` as "owner-approved as owner-typed-therefore-trusted, same trust model as `gateCommand`" — WHO-can-set was already decided; only reach-visibility is open, same posture as connections.

Should either surface ever grow an agent-facing write path, re-open this — the accept is conditioned on "no agent can reach this today", not on the widening being harmless.

## Agent rebind — accepted OUT of scope here, tracked on its own card

A `profile_update`/`profile_delete` widening reaches every agent ALREADY bound to the edited/deleted profile — the reach computation is keyed on the PROFILE changing. Rebinding a single agent onto a DIFFERENT, already-wider profile (`agent_update(profileId)` / `profile_assign`, on both the setup and platform surfaces) is a distinct hazard this card does not cover: the profile itself never changes, so `profileWideningsOf(before, after)` sees nothing to report — the widening is in which bound agents a STATIC profile's reach now includes, not in the profile's own fields.

Code Review of `8298bcdb` flagged this gap; it is boarded separately as card `8b236b22` ("audit an agent rebind that widens its profile reach") rather than folded in here — the per-agent computation it needs (one profile's existing trust, newly extended to one more agent) is a different shape from everything `profileWideningsOf`/`recordProfileGrantReach` compute in this card (one profile's trust changing, reaching every agent already bound to it).

## (d) — accepted, documented rather than "fixed"

`profile_grant_reach`'s `managerSessionId: ""` and missing `detail.projectId` (per `3c4e0df6`'s "Do not add to `DURABLE_AUDIT_EVENT_KINDS`") mean `db.ts`'s `eventsFilterConditions` (`COALESCE(s.project_id, t.project_id, json_extract(detail,'$.projectId'))`) resolves `projectId` to NULL for this kind — it can never match a `projectId`-filtered `events_search`; only the unscoped, platform-wide call surfaces it. Correct, not a bug: stamping a fake `projectId` would misrepresent a global fact as project-scoped, the opposite of `3c4e0df6`'s own ruling. Fixed by a one-line addition to `events_search`'s tool description (`mcp/platform.ts`), not a behavioral change.
