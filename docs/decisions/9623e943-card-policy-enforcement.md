# 9623e943 — card-policy enforcement at spawn and merge

Child 2 of the card-policies epic (8b6c750a). The schema, parser and selector landed earlier (78a9ae1c, d2bc231e); this record covers enforcement. Code: `orchestration/card-policy.ts` (pure evaluator), `sessions/service.ts` (`mergePolicyRefusal`, the spawn check, the batch drop), `gateway/server.ts` (waiver routes), `mcp/tasks.ts` (read-only `policy` view).

## What is enforced, and where

- `approved-request` at `worker_spawn` (tasked spawns only, after the held refusal, before any claim/worktree side effect). `approved-request` is met ONLY by a Request linked to the card of type `permission`, state `answered|consumed`, with `chosenOption === PERMISSION_ANSWERS[0]` (`"authorize"`). Its label is "owner-authorized permission Request".
- `code-review-report` and `investigate-checkpoint` at merge: `confirmWorkerMergeTracked` (before the lineage key, supersede and `attach`, so a refusal mints no op and is never cached), `confirmWorkerMerge` (backstop), and `mergeBatchTracked` (per candidate). All three call ONE function, `SessionService.mergePolicyRefusal`.
- Exempt: review spawns (taskless), recycle and boot-reconcile (they continue the SAME admitted card and never reach `spawnWorker`), and a card with a recorded `mergedSha` (PROVEN landed, so an idempotent re-confirm is never refused). The terminal COLUMN exempts nothing (a card can be dragged there). `worker_revive` is NOT exempt: it forks onto a follow-up card, which runs the full spawn-phase policy for THAT card, and a revived worker on a checkpoint card gets the checkpoint kickoff paragraph.
- A merge call that would ATTACH to an already-RUNNING op is never policy-refused (that op was admitted under the policy then in force); the policy is evaluated only when a call would mint a new op.
- A permission grant whose decided expiry (`decidedExpiresAt`) has lapsed does not count; "once" is not consumed by a spawn (the approval is per card).

## Rulings

- **Permission-only affirmative (LEAD ruling).** Only a `permission` Request has a structured yes/no. A `decision` Request's `chosenOption` is one of the asker's free-form options and an `input` Request's answer is free text, so neither can prove approval, and a "reject" option must not satisfy the requirement. The refusal names BOTH remedies: file a permission Request linked to the card, or have the owner record a waiver.
- **`evaluateCardPolicies` is the only reader of `cardPolicies` for enforcement.** It parses the RAW stored override with `parseCardPolicies`; `ok:false` means every policy is unmet (fail closed). `resolveConfig().orchestration.cardPolicies` silently degrades an invalid list to the default, so no enforcement site may read it (pinned by `card-policy-source-pins.mjs`). An unknown requirement kind rejects the whole list, which is stricter than the plan's per-requirement "unmet-unreadable" and still fails closed.
- **Fail closed on unreadable evidence**, but the refusal always names the waiver remedy, and the waiver is a plain DB write that does not depend on the failing read.
- **Code review evidence** = a session in this project with `reviewOfTaskId == card`, a `done` `worker_report` event on THAT session (the event's own `taskId` is null for a taskless reviewer, so the join goes through the session row), and `reviewBaseSha ==` the branch tip being landed. It proves a review HAPPENED on this tip, not that it passed. The reviewer's recycle lineage counts: `reviewOfTaskId` is carried forward to a recycled reviewer's successor (symmetric with `reviewBaseSha`), so the successor's `done` report satisfies the requirement. A branch that moved after the review is unmet (one consequence: a Loom union-merge advance of the branch also demands a new review; the waiver is the escape).
- **Investigate-checkpoint is detective, not preventive** (Loom cannot stop edits; worker plan mode is rejected). Evidence: a `blocked|progress` `worker_report` anywhere in the landing worker's `recycledFrom` lineage with `ts` before the worker's OWN first commit: the first commit on the branch's `--first-parent` line beyond the cut base (so main's commits brought in by a merge-forward never count), committer time (1s resolution, a same-second report is tolerated), read through `canonicalGit` (`firstBranchCommitTime`). An unreadable git read is unmet-unreadable. A branch with no commits is trivially met. **Named residual, no forgery defence:** an agent controls its own git dates and environment, and can amend or rebase its history, so this is a tripwire for honest workers, not a barrier.
- **merge_batch**: a policy-blocked candidate stays in `chosen` (like a held or review-moved one), so the f944d4e4 dedupe key is derived over the same candidate set with or without the policy and an evidence change cannot mint a second op. It is excluded from `batchable`, never solo-fallback-confirmed, and reported `started:false`.
- **Waivers** are per (card, policy, requirement kind), written ONLY by the human REST route `POST/DELETE /api/tasks/:id/policy-waivers` with an audit `card_policy_waived` event. There is no MCP tool.

## Human-answer requirement (review finding F1)

`approved-request` evidence also requires `answeredVia === "human"` (the `questions.answered_via` marker from card f7d70f75, stamped only by the human REST answer routes). `question_resolve`, `question_amend` and the companion `decision_resolve` write through `db.answerQuestion` without the stamp, so an agent can no longer approve its own spawn by resolving a Request from an owner chat turn. A row answered before the column existed carries NULL and does NOT count (fail closed): a pre-field approval must be re-asked or waived. This reuses the one existing discriminator; no second one was added. Pins: `card-policy-enforcement.mjs` S7, `card-policy-waiver-route.mjs` A1 (real REST answer), `card-policy-source-pins.mjs` P6 (only the gateway stamps it).

## Review round 2: landed proof, ssh holds, pinned tip

- **No card-level exemption.** The merge-phase check no longer exempts on the card's sticky `task.mergedSha` (or the terminal column). It exempts only when THIS worker's own branch is proven landed (`findLandedSquashCommit` with the gone-branch and worker-tip ledger facts, the ALREADY_MERGED proof), evaluated only after a requirement would otherwise block, failing closed on any doubt. A card that landed once and was moved back out of done gets a NEW worker whose branch has not landed, and that worker is held to the policy (solo and batch).
- **ssh holds are not card approvals.** `approved-request` evidence excludes a permission row whose `permissionAction` is an ssh_exec hold (`isSshApprovalAction`): an owner approving one ssh command must not satisfy a card's spawn policy.
- **Pinned-tip re-check.** Just before the squash, the merge-phase evidence is re-read against the tip the squash is pinned to. A code-review report counts there only if its base is that tip or the pinned tip is that base plus Loom's own union-merge of main (the same `verifyReviewedTipChain` walk the reviewed-tip check uses); any worker commit after the review breaks the chain. The checkpoint requirement is unaffected by a later commit (it is tied to the first commit). `merge_batch` applies the same pin in its per-candidate policy loop: each candidate is judged at the tip its reviewed-tip verdict read (`verifiedTip`, the sha assembly cherry-picks), not a fresh branch read. (An earlier version of this record called `batchHeadMoved` the backstop; that is wrong, it covers the batch worktree HEAD, not the candidate branches. The pin is what closes it.) Named residual: a candidate commit landing AFTER the batch policy loop but before assembly is not re-read by policy; assembly cherry-picks the pinned sha, so such a commit is simply not in the batch.

## Review round 4: sticky policy matching

`types`/`scopes` selectors match the card's CURRENT title, and an agent can rewrite a title, so a card could drop out of every policy at spawn and merge by being retitled (also innocently: we retitle to what shipped before a solo confirm). Matching is therefore the UNION of the live title match and a Loom-owned record of every policy that has ever matched the card (table `card_policy_matches`, PK (task, policy), CREATE TABLE only: no migrated column and no index of its own; `card-policy-waiver-migration.mjs` proves it on a pre-migration fixture DB).

- Recorded by the Db's own title chokepoints, so every write path is covered (agent tasks_update, human REST, ship-state): `insertTask` records the created title's matches; `updateTask` records the OLD title's matches BEFORE a different title applies (a title write can only add). The evaluator also records every policy that matched at an evaluation (spawn and every merge path).
- Enforced everywhere the evaluator runs (spawn, solo merge incl. the pre-squash recheck, `merge_batch`, the `tasks_get` policy view). `cardIds` selectors are unaffected.
- Nothing an agent can call removes a row. The human waiver remains the only escape and still clears a sticky-matched requirement. A recorded id whose policy no longer exists in the stored list is ignored (the evaluator iterates the CONFIGURED policies), so a policy the human deletes, or edits to a different id, stops applying; a policy edited in place under the same id keeps applying to previously matched cards, with its edited requirements.
- Not covered: a card retitled out of a selector BEFORE the policy was configured was never recorded, so it is never matched (nothing to be sticky about). A policy added later does not retroactively capture a card whose title no longer matches.
- A retitle while the stored `cardPolicies` list is unparseable records nothing (the Db recorder cannot read the list). The evaluator fails closed in the meantime (every tasked spawn and merge is refused), so the exposure opens only after the list is repaired, and reaching that state needs version skew or a downgrade.
- Sticky matches are project-scoped (card f330faee). Policy ids are per-project config, so the sticky table is now `card_policy_matches_v2` keyed (task_id, project_id, policy_id), and every read/write passes the project whose config is being evaluated. `relocateTask` leaves the source project's rows in place (a move back restores them) and, in its own transaction, records the destination's matches for the card's current title. Chosen over dropping rows on relocate because a drop cannot keep the original title-derived matches: A→B, retitle in B, B→A would shed A's policy. The legacy `card_policy_matches` table is read exactly once (a ONE-SHOT boot backfill guarded by the `app_meta` marker `card_policy_matches_v2_backfill_done`, checked first and stamped last in the same transaction as the copy, attributing each row to the card's current project; a re-run on every boot would re-derive rows against a card's NEW project after a later relocation and copy the source project's sticky ids onto the destination) and never written afterwards; it is kept only for downgrade. Named residual: a card relocated BEFORE this fix has its source-project rows attributed to its current project (the old table recorded no project), so that one-time over-enforcement persists until a human waiver clears it. Tests: `card-policy-sticky-project-scope.mjs`, `card-policy-waiver-migration.mjs`.
- Waivers are project-scoped too (card 0b165937). The same fail-open collision existed on the human-only waiver table: a waiver granted for A's "p1" cleared B's unrelated "p1" after a relocate. The waiver table is now `card_policy_waivers_v2` keyed (task_id, project_id, policy_id, requirement_kind); `listCardPolicyWaivers`/`deleteCardPolicyWaiver`/`upsertCardPolicyWaiver` all take the project, `dbPolicyEvidence` reads with the project being evaluated, and the human REST route writes and revokes under the card's current project (it stays human-only; no MCP path was added). Chosen as a new table, mirroring the sticky-match choice, because the legacy primary key cannot gain a column in place and the legacy table must stay intact for downgrade. `relocateTask` needs no waiver code: source-project waivers stay behind under the source key, so A→B→A restores them (symmetry with sticky matches) and B never sees them; a human re-waives under B. The legacy `card_policy_waivers` table is read once by a ONE-SHOT boot backfill (`app_meta` marker `card_policy_waivers_v2_backfill_done`, checked first and stamped last in the same transaction as the copy), attributing each row to the card's current project. Named residual (same as sticky matches): a card relocated BEFORE this fix has its source-project waiver attributed to its current project, so that one-time over-clearing persists until a human revokes it. Tests: `card-policy-waiver-project-scope.mjs`, `card-policy-waiver-route.mjs`, `card-policy-waiver-migration.mjs`.
- `workerBranchProvenLanded` is not keyed on the pinned tip: `findLandedSquashCommit` resolves the branch itself (trailer + re-task guard + ledger) and takes no tip parameter; threading one through that load-bearing primitive is out of this card's scope, and the exemption only matters once a requirement already blocks.

## Waiver audit project, downgrade residual, relocation semantics (card b4666737)

- **The audit event names its project.** Both the `waive` and `revoke` `card_policy_waived` event details carry `projectId` (the card's project at write time). Waivers are project-keyed, so without it the trail cannot say which project's "p1" a waive or revoke was for once the card has been relocated. Tests: `card-policy-waiver-route.mjs` (W2, W6).
- **Named residual: a downgrade can resurrect a revoked waiver (fails OPEN).** The v2 backfill copies the legacy `card_policy_waivers` table once and never touches it again, and the revoke route deletes only from `card_policy_waivers_v2`. A waiver granted before the v2 migration and revoked after it therefore still sits in the legacy table, and a daemon downgrade to a build that reads that table makes the requirement `waived` again. This is the opposite direction from the sticky-match residual (which over-enforces); no code change, because the legacy table is deliberately kept intact for downgrade. After any downgrade a human should re-check the waivers on cards they had revoked.
- **Relocation semantics are intended: a mid-flight relocate leaves the worker evaluated under its SOURCE project.** `relocateProjectTask` has no live-worker refusal. `mergePolicyRefusal` takes the project from `worker.projectId` (fixed at spawn) and passes it to `evaluateTaskPolicies`, which builds waiver and Request evidence with `project.id`. The merge phase therefore applies A's policies, A's waivers and A's sticky matches to a card that now lives in B, which is consistent (nothing from B leaks in, and nothing of A's is lost). A worker spawned after the relocate is evaluated under B. Checked by reading the code, not covered by a dedicated test.

## Do not

- Do not read `resolveConfig().orchestration.cardPolicies` at any enforcement site; use `evaluateCardPolicies` on the raw stored override.
- Do not drop the `answeredVia === "human"` requirement or add a second discriminator beside it.
- Do not make policy matching depend on the live title alone, and do not add any agent-callable way to remove a recorded sticky match.
- Do not exempt a worker from the merge policy on a card-level field (`mergedSha`, column); only its own branch being proven landed exempts it.
- Do not let an ssh_exec hold approval count as an `approved-request`.
- Do not widen the affirmative predicate to free text or to `decision`/`input` Requests.
- Do not add a second implementation of the merge check; the tracked path, the backstop and the batch drop share `mergePolicyRefusal`.
- Do not add an MCP tool that creates, changes or revokes a waiver.
- Do not read `reviewOfTaskId` from card/mutex/lane logic, and do not surface it in an agent-facing view.
