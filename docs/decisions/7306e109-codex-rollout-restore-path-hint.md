# 7306e109 — `restoreArchivedCodexRollout`'s `resolvedPathHint`: reuse, don't re-walk

## Do not

- Do not trust `resolvedPathHint` blindly — always verify it still exists on disk, that its filename actually names this conversation id, and that it sits under one of the two known roots (live sessions, or the archive, at exactly the `YYYY/MM/DD/<file>` depth for an archive-root hint). A stale, foreign, or misnamed value must fall through to the function's own full live-then-archive walk exactly as if no hint had been passed at all, never produce a wrong `restored`/`alreadyLive` result.
- Do not trust an archive-root hint just because it passes the checks above — always check whether a live copy already sits at the reconstructed destination first (card `7306e109` round 2 item 1). A stale archive hint (e.g. a prior EXDEV restore whose final `unlink` failed, leaving both copies in place) must report `alreadyLive` and leave the archive copy untouched, never overwrite or clobber the live file.
- Do not have `codex-rollout-archive.ts` import `codex-transcript.ts#resolveTranscriptFile` directly to get this "for free" — `codex-transcript.ts` already imports `codexRolloutArchiveRoot` from this file, so the reverse import would be circular. The hint exists specifically because that door is closed.

## Why this exists

`restoreArchivedCodexRollout` (card `5172fe3a`) used to unconditionally run its own `findRolloutByConversationId` walk against the live `sessions/` tree, and — if not found there — a second full walk against the (ever-growing) archive root, on **every** codex resume. For a resume whose id has no rollout anywhere (e.g. a session that was spawned but never actually ran a turn), both walks come up empty and the function pays the full cost of both trees on every single resume attempt, with the archive-tree cost growing unboundedly over a daemon's lifetime (card `b8124a1f`'s own archiver only ever adds to it).

`codex-transcript.ts#resolveTranscriptFile` already does the identical live-then-archive walk, with a module-level `resolvedPathCache` (keyed by conversation id) that makes a repeat lookup for the same id an O(1) hit. And `SessionService.resume()` (`sessions/service.ts`, ~line 3696) already calls that exact function — via `engineTranscriptExists(session.cwd, session.engineSessionId, session.harness)` — as its own resumability precondition, strictly BEFORE it ever reaches `PtyHost.spawn()` → `createCodexPty()`. So by the time `createCodexPty` is about to call `restoreArchivedCodexRollout`, the path for this exact conversation id has very likely already been resolved and cached moments earlier in the very same resume flow.

`createCodexPty` re-resolves via `resolveTranscriptFile` and passes the result into `restoreArchivedCodexRollout` as `resolvedPathHint`. **The actual win is narrower than "passing a hint is free": the call site unconditionally re-invokes `resolveTranscriptFile` itself, which is a real tree walk (live, then archive) whenever it isn't already a cache hit.** A hint is NOT cheaper than no hint in the case that matters most for cost — a conversation id with no rollout anywhere: `resolveTranscriptFile` pays its own full live-then-archive walk and returns `null`, then `restoreArchivedCodexRollout` (receiving `resolvedPathHint: null`) pays `findRolloutByConversationId` against *both* roots again on top of that — strictly MORE walking than calling `restoreArchivedCodexRollout` alone ever did, not fewer. The real gain is specifically the CACHE-HIT case this file's own header describes: `SessionService.resume()` already called `resolveTranscriptFile` moments earlier in the same resume flow (via `engineTranscriptExists`), so by the time `createCodexPty` re-calls it, `resolvedPathCache` very likely already holds this exact id — an O(1) hit, not a second walk — and it's *that* hit, not the hint mechanism in the abstract, that `restoreArchivedCodexRollout` gets to skip re-deriving.

`restoreArchivedCodexRollout` honors the hint only after re-verifying it: `fs.existsSync` first, then that its filename actually names this conversation id, then which of the two known roots (if either) it sits under — and, for an archive-root hint specifically, that the relative path is exactly `YYYY/MM/DD/<file>` deep (the shape the live destination is reconstructed from) and that no live copy already sits at that reconstructed destination. A hint that fails any of these checks is discarded and the function falls through to its own full walk. **An earlier version of this paragraph claimed such a stale hint "can never produce an incorrect `restored`/`alreadyLive` result" — that was false, and round 2 of card `7306e109` is the fix for exactly the gap that disproved it:** before the live-copy and filename/depth checks existed, a hint resolving under the archive root was trusted unconditionally — so a STALE archive hint (e.g. a prior EXDEV restore whose final `unlink` failed, leaving both copies in place, with `resolvedPathCache` still pointing at the archive path) would try to move the archive copy straight over an already-live file, clobbering or throwing instead of reporting `alreadyLive`. The current checks are what makes the "falls through to the full walk, same cost as no hint, never a wrong result" guarantee actually true.

This does not change `restoreArchivedCodexRollout`'s behavior for any caller that doesn't pass a hint (every existing unit test in `codex-rollout-archive.mjs` calls it with no `deps`, or with only `sessionsRoot`/`archiveRoot` overrides) — the full walk remains the correctness fallback, unconditionally.

## The CODEX_HOME-changed edge case (item 3, same card)

`restoreArchivedCodexRollout` resolves its destination's live-tree root from `codexSessionsRoot()`, which reads `realCodexHome()` (ultimately `process.env.CODEX_HOME || os.homedir()/.codex`) FRESH on every call — never cached at module load, deliberately (mirrors `codexSessionsRoot`'s own doc in `codex-transcript.ts`: a test that sets `CODEX_HOME` before calling gets genuine isolation). If `CODEX_HOME` were ever changed BETWEEN when a rollout was archived and when it's later restored, the destination would be rebuilt under the NEW `CODEX_HOME`'s `sessions/` tree, not the directory the file was originally archived out of.

In production this is not reachable: `codex-doctrine.ts#realCodexHome`'s own doc is explicit and load-bearing — codex spawns NEVER use a per-worker `CODEX_HOME` override (auth breaks under one), so every codex spawn on a given host resolves the exact same, unchanging real `~/.codex` for the daemon's entire lifetime. The only way to observe this edge case is a test harness (or a future change) that deliberately varies `CODEX_HOME` across the archive/restore boundary — a case that is not exercised by any production caller and is intentionally left unhandled rather than defended against with machinery nothing can trigger.
