# 6b8822d2 — The admission-time canonical-dirt preflights must run under the canonical repo's merge lock, or they race a sibling's in-flight squash

## Narrative

Observed by the lead, 2026-10-05 ~18:30Z: `merge_batch([b12f34d7 (e3fcd8ea), 4cc069d4 (69246a6e)])` ran with the gate interval not due, so both candidates took the per-branch solo fallback (`mergeGateOff`, reason "merge gate interval: not this landing's turn"). The 69246a6e fallback was refused with "canonical repo has STAGED, uncommitted changes that predate this merge" — and the staged paths it listed were EXACTLY e3fcd8ea's own diff. That squash landed moments later as commit `122af293`, and `git status` was clean immediately after. 69246a6e's own confirm had done nothing wrong; it had simply observed a sibling's legitimate work mid-flight and reported it as an unrelated, human-only problem.

### Root cause

`SessionService.confirmWorkerMerge` called `detectCanonicalStagedDirt` (the admission-time hoist from card `4b7ff996`'s CR follow-up) entirely UNLOCKED, long before the actual squash. `git merge --squash <branch>` stages the combined diff into the canonical index without committing; `mergeBranchLocked` (which performs the real squash + commit) runs INSIDE `withCanonicalIndexLock` — the per-repo FIFO mutex — but the admission-time probes did not. Between the squash call and the commit call, the canonical repo is genuinely, legitimately staged-but-uncommitted; a sibling branch's concurrent, unlocked probe landing in that window cannot tell that state apart from real human-authored residue.

This residual race was KNOWN and explicitly accepted when card `4b7ff996` hoisted the check to admission time — the surrounding comment named `mergeBranchLocked`'s own in-lock check as the "backstop," reasoning that the gate can run for minutes between the preflight and the squash. That reasoning covers a HUMAN (or an unrelated interrupted process) staging something new in that window — a real race the in-lock check genuinely catches, since by the time any caller's own `mergeBranchLocked` body runs it holds the exclusive lock and can see genuinely-settled state. It does NOT cover a CONCURRENT SIBLING MERGE: the in-lock check runs serialized inside the very same mutex a sibling's own squash holds, so it can only ever observe that sibling's work already cleanly committed (lock FIFO means the second caller's body never starts until the first's has finished) or not yet started — never mid-flight. The false refusal in this incident therefore could only ever happen at an UNLOCKED admission-time check; `mergeBranchLocked`'s in-lock check was never capable of catching this specific shape, accepted-risk framing notwithstanding.

### Why `merge_batch`'s interval/gate-off fallback triggers it

`mergeBatchTracked`'s `runFallback` iterates candidates in a `for…of` loop, `await`-ing `confirmWorkerMergeTracked` each time — looking sequential. But `PendingOpRegistry.attach()` (`orchestration/pending-ops.ts`) races the real `run()` against `SYNC_ATTACH_BUDGET_MS` (12s) and returns `{settled:false}` once that elapses while `run()` keeps executing in the background. A real merge-confirm (preflight → gate → squash) routinely exceeds 12s, so the loop advances to the next candidate while the prior one's real body is still running — `runFallback` genuinely launches multiple concurrent real confirms against the same repo, serialized only by each op's own `merge:<workerSessionId>` key (which differs per worker), never by repo. On the gate-interval-skip/gate-off path specifically, each candidate's own preflight-to-squash window collapses from minutes to near-zero (no gate runs at all), making two candidates' windows likely to overlap in wall-clock time.

The same exposure exists for two independent solo `worker_merge_confirm` calls on different workers sharing a repo (same `confirmWorkerMerge` code path, same unlocked preflights) — `merge_batch`'s fallback is simply today's most likely trigger because it deliberately fires multiple same-repo merges close together.

### The fix — ALL THREE admission-time probes, one shared lock acquisition

Round 1 of this card lock-wrapped only `detectCanonicalStagedDirt`. **Code Reviewer e001ee19 (round 2) found that premise incomplete**: `detectCanonicalDirtyOverlap` (unstaged-tracked overlap) and `detectCanonicalUntrackedOverlap` (untracked collision) are exposed to the identical race, not just the staged-dirt probe — see "Why the unstaged/untracked overlap siblings ARE exposed" below for the mechanism the round-1 draft of this record got wrong. All three now run inside **one single** `withCanonicalIndexLock(repoPath, …)` acquisition (never three separate ones — a second or third acquisition would itself queue behind, and briefly reopen the window for, whatever the first one just waited out):

```ts
({ stagedDirt, dirtyOverlap, untrackedOverlap } = await withCanonicalIndexLock(repoPath, async () => ({
  stagedDirt: await detectCanonicalStagedDirt(repoPath, …),
  dirtyOverlap: await detectCanonicalDirtyOverlap(repoPath, branch, …),
  untrackedOverlap: await detectCanonicalUntrackedOverlap(repoPath, branch, …),
})));
```

This forces all three probes to queue (FIFO) behind any currently in-flight squash on the same repo — by the time they acquire the lock, a concurrent sibling's squash has either not started or already committed, so the probes only ever see genuinely-clean or genuinely-stale human-authored state, never a sibling's transient mid-squash tree.

`withCanonicalIndexLock` is never held across a gate run — card `eda70da6` explicitly rejected that design ("Do not hold the lock across the gate run, or re-run the gate once the lock is held — both were considered and rejected"), and the gate itself (`gateSemaphore.runExclusive`) runs entirely between the unlocked admission preflights and the lock-wrapped `mergeBranch` call. So lock-wrapping the preflights adds, at most, a wait for whatever else currently holds the per-repo lock (another squash, or a `GitWriter` checkout/commit/createBranch) — never a wait across a multi-minute gate.

**The bound on that wait, stated precisely (Code Reviewer e001ee19, item 4): bounded PER HOLDER, SUMMED OVER THE FIFO QUEUE — there is no acquisition timeout.** `withCanonicalIndexLock` itself imposes no ceiling on how long a caller waits in queue; each individual holder's own mutating git calls are bounded via `withTimeout` + `killableCanonicalRaw` (card `24c0bdba`, a hung child kill-confirmed within its own `timeoutMs` + `killGraceMs`, defaulting to the same value — `git/bounded.ts`), so no ONE holder wedges the mutex forever (card `44c28799` fixed exactly that prior bug). But a caller queued behind N other holders waits the SUM of their individual bounds, not a flat per-call ceiling — under ordinary load N is 0 or 1 (sub-second), but the bound does not get smaller just because this probe is now also in the queue. The new admission-time lock acquisition is subject to this exact same queue-summed bound as every other `withCanonicalIndexLock` caller already is — no new bound mechanism was added, and none was needed, but "bounded" here means "no single holder wedges it forever," not "bounded by a fixed ceiling."

### `RepoQuarantinedError` at the combined probe site

`withCanonicalIndexLock` throws `RepoQuarantinedError` (not a sentinel value) when it finds the repo quarantined at acquisition time. **The combined probe call site catches this and returns the SAME `{merged:false, quarantined:true, gateRan:false, reason}` refusal shape `confirmWorkerMerge`'s own early backstop (checked before this call, unlocked) uses** — never `{staged:false}`/`{overlap:false}` (Code Reviewer e001ee19, item 3: falling through to those fail-safe defaults would let the real gate run burn a lane against a repo already known quarantined). This matters for the narrow but real case where a repo becomes quarantined in the GAP between that earlier unlocked check and this call (verified directly: `merge-confirm-admission-quarantine.mjs` quarantines the repo from inside `reviewedTipVerdict`, the real async step that runs in exactly that gap). The repo's quarantine state is additionally re-derived, authoritatively, inside the LATER squash's own `withCanonicalIndexLock` call (via that lock's own `guarded()` wrapper, `git/repo-lock.ts`) regardless of what this call site does — so even if this catch were removed, quarantine enforcement itself would not be skipped, only reported late and after a wasted gate run.

### Why the unstaged/untracked overlap siblings ARE exposed (round 1 of this record was wrong here)

**Round 1 claimed `git merge --squash` "stages cleanly into the index and never leaves unstaged/untracked content," so `detectCanonicalDirtyOverlap`/`detectCanonicalUntrackedOverlap` were not exposed to this race and were left unlocked. Code Reviewer e001ee19 (item 2) showed this premise is false**: git's internal `unpack_trees()` — the tree-merge machinery `--squash` uses — writes files into the WORKING TREE before the updated index is atomically renamed into place. Between those two steps, a concurrent `git status`/`git diff` in the canonical checkout can observe the squash's own worktree writes as **unstaged** modifications (`" M"`) against the still-old index, or as **untracked** (`"??"`) for a path the squash newly adds — exactly the two shapes `detectCanonicalDirtyOverlap`/`detectCanonicalUntrackedOverlap` test for. A sibling's in-flight squash is therefore just as capable of producing a false `canonical_dirty_overlap` refusal as it was of producing a false `canonical_staged_dirt` one. Both probes now share the SAME single lock acquisition as the staged-dirt probe (see "The fix" above) — not a separate one each, which would reopen the window between probes.

## Do not

- Do not revert any of the three probe calls back to a bare (unlocked) call — a sibling's real, in-flight squash is indistinguishable from genuine human residue/overlap to an unlocked read of ANY of the three; see the Narrative and the "ARE exposed" section above for the exact mechanism (including for the two that look, at a glance, like they only read already-landed state).
- Do not split the three probes back into separate `withCanonicalIndexLock` acquisitions "for clarity" — a second or third acquisition after the first releases reopens the exact race window for whichever probe runs later.
- Do not drop the `RepoQuarantinedError` catch, and do not revert it to `{staged:false}`/`{overlap:false}` — it must return the SAME `quarantined:true` shape the early backstop uses (see `merge-confirm-admission-quarantine.mjs`); the later squash's own lock call re-derives quarantine authoritatively regardless, so this catch is about not wasting a gate run, not about skipping enforcement.
- Do not state this card's bound as "bounded by the same kill-confirm timeouts every other lock holder relies on" without the FIFO qualifier — a caller queued behind N holders waits their SUM, not one holder's ceiling, and there is no acquisition timeout at all.
- Do not read the surrounding `confirmWorkerMerge` comment (~L18038 in the pre-round-2 line numbering, "this only fires when the canonical repo went dirty IN the race window between those preflights and this squash") as implying `mergeBranchLocked`'s in-lock check is a backstop for a CONCURRENT SIBLING merge — it never was; that in-lock check runs serialized inside the same lock a sibling's squash holds, so it can only observe a sibling's work already committed or not yet started, never mid-flight. It genuinely does backstop a human (or an unrelated interrupted process) staging something new in that window.

## Consequences

A gate-interval-skip (or gate-off) `merge_batch` fallback landing two-or-more candidates on the same repo in quick succession no longer risks one candidate's admission preflights falsely reporting the other's legitimate in-flight squash as unrelated staged/dirty/untracked residue requiring human intervention. The same protection applies to any two concurrent solo `worker_merge_confirm` calls against the same repo, and to a repo quarantined in the narrow gap between the early backstop and the combined probe lock. The added latency is the FIFO-queue-summed wait described above (ordinarily sub-second; no acquisition timeout) and is never paid across a gate run.
