# 7be85378 — CRASH-LOOPED gets a second, event-sourced derivation for the session archiveOnExit always archives first

## Do not

- Do not change `archiveOnExit`'s archival semantics to "fix" this — the gap is in the web's derivation, not in when a session gets archived. `SessionService.archiveOnExit` stays exactly as `6cd3ce9e` left it.
- Do not combine `session_recovery_abandoned` and `session_recovered` into ONE `orchestrationEventsByKinds` call. `listRecentEventsByKinds`'s shared 500-row cap is ordered across the combined kind set; `session_recovered` fires far more often than the rare, detector-fired `session_recovery_abandoned` (same "rare pair" framing as `43084723`'s boot-dialog kinds), so a combined query can evict a still-active abandoned row under real volume. Two separate queries, each with its own cap.
- Do not add a per-item `api.archivedSessionById`/`GET /api/archived-sessions/:id` fetch to confirm a session genuinely still exists before rendering its event-derived item. `5ced500b`'s own record already costed and rejected exactly this for the same reason: it is the one per-item request the whole attention design would contain. The residual (a permanently-DELETED session's abandoned event has no `session_recovered` counterpart and never will — `deleteSession`'s FK cascade does not touch `orchestration_events`) is accepted and covered by the dismiss affordance instead, not closed.
- Do not derive the event-sourced item without excluding every session id already present in the live `all` feed. A session that is CURRENTLY live/exited-but-unarchived is covered by the pre-existing `all.filter(isCrashLooped)` loop; without the exclusion the same episode renders twice.
- Do not treat `5ced500b`'s own claim — "`CRASH-LOOPED` is derived by iterating the live feed, so if the session were archived the item would not exist at all" — as having been wrong. It was correct and is why that card's defect (an item existing but resolving to the wrong project) never applied to this kind. This is a DIFFERENT defect: for the sessions `archiveOnExit` always archives (every worker; a manager/platform with zero live workers), the item never gets generated in the first place. The fix is a second derivation path for exactly the population the first one structurally excludes, not a correction to the first path.

## The defect

`CrashRecoveryWatcher.tick`'s give-up branch (`crash-recovery-watcher.ts`) stamps `[loom:crash-loop]` on a session's `lastError` only once `attempts >= maxAttempts`, with `processState === "exited"` required to reach that branch at all. Every exit in the loop that got it there already ran through `index.ts`'s `onExit` handler, which calls `SessionService.archiveOnExit` — unconditional for any role other than a manager/platform with live workers (`6cd3ce9e`'s own carve-out, which a worker never qualifies for). Nothing un-archives the row between that last exit and the give-up tick (only a *successful* `resume()` does, and the give-up branch deliberately never resumes). So by the time the crash-loop banner is written, the session is already archived — and `attention.ts`'s `isCrashLooped` is only ever evaluated against `all = api.allSessions().data`, which is `db.listAllSessions()`, `WHERE archived_at IS NULL`. The item structurally never gets built for this session. Confirmed by a hermetic repro driving the real `Db`/`CrashRecoveryWatcher` through four real crash/resume cycles, with a positive control proving `archivedAt` (not some fixture artifact) is the actual discriminator.

## The fix

`session_recovery_abandoned` is already a durable, role-agnostic event, filed independent of the session row's archival state — the same shape as `claude_boot_dialog_stuck`/`vault_index_lock_stale`/`codex_isolation_gap_disclosed`, each already given its own cross-session `orchestrationEventsByKinds` query specifically because a per-session-row or per-manager-liveness-gated read can lose the signal (`43084723`). `fleet.ts`'s `activeCrashLoopAbandonments` pairs it against `session_recovered` (latest-wins per session id, mirroring `activeVaultLockAlerts`'s stale/cleared fold) and excludes any session id already present in the live `all` feed (the dedupe). `attention.ts` feeds it from two SEPARATE kind-filtered queries (never one combined call — see "Do not" above) and builds a second CRASH-LOOPED item for whatever the pairing leaves active, carrying `projectId` straight from the event's own `detail`.

**No daemon call-site change was needed to get that `projectId` there.** The investigation that led to this card proposed adding `projectId: s.projectId` to `crash-recovery-watcher.ts`'s `fileEvent` call directly — but `session_recovery_abandoned` is already a `DURABLE_AUDIT_EVENT_KINDS` member (`db.ts`), and `appendEvent`'s own backstop (`9f7f2b50`) already stamps `detail.projectId` generically, at write time, for every event of a member kind whose caller didn't already set one. Verified directly: reverting a hand-added `fileEvent(s, "session_recovery_abandoned", { role: s.role, attempts, projectId: s.projectId })` back to the original `{ role: s.role, attempts }` and re-running `crash-recovery-watcher.mjs`'s test (4) still produced a stamped `projectId` matching the session's real project — the backstop alone was always sufficient. The explicit field was reverted out as redundant; only a pinning assertion on the existing behavior was kept.

### Clearing

- A later `session_recovered` for the same session id clears it (the pairing fold).
- A MANUAL human resume (the Archive tab's Restore, or the live-rail Resume button) routes through the exact same `SessionService.resume()` the watcher's own auto-resume calls — confirmed at `gateway/server.ts`'s `POST .../resume` route. The watcher's tick does not distinguish who resumed a session; on its next tick it sees `processState === "live"` and, after the stability window, files `session_recovered` and clears `lastError` regardless. So a manual resume clears the item too, bounded by the watcher's stability-window latency, not instantly.
- A `resumability: "dead"` session's Restore is the one exception: that path (`SessionService.restoreSession`) only clears `archived_at` with no resume attempt, and a dead session is excluded from the watcher's own candidate set entirely (`resumability === "dead"` short-circuits the tick), so it never files `session_recovered`. Its item instead starts resolving through the pre-existing `all`-derived loop the instant it's back on the live rail (its `lastError` and `processState` are unchanged) — the dedupe (above) hands it off cleanly, with no gap and no double-render.
- A permanently DELETED session's event has no clearing path at all (see "Do not" above) — covered by the dismiss affordance, the same fallback `codex_isolation_gap_disclosed` uses for its own no-clear-path case. The dismiss key is `${sessionId}:${event.ts}` (the abandoned event's own timestamp), so a later, separate crash-loop episode for the same session — a new `session_recovery_abandoned` with a later `ts` — mints a different key and re-surfaces even if the earlier episode was dismissed.

### projectId on old rows

A `session_recovery_abandoned` event filed before `9f7f2b50` shipped (the generic backstop this card relies on, not something new here) carries no `projectId` — that card's own record already declines to backfill such rows, deliberately. `fleet.ts`'s `resolveAttentionProjectId` still resolves those via its existing step 2 (the item's `sessionId`, looked up against whatever bounded live + archived pages the calling reader already polls) — the same fallback `5ced500b` built for exactly this "old row, no stated project id" shape.
