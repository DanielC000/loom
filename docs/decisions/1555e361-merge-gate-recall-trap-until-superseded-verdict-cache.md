# 1555e361 — the merge-gate re-call trap: an until-superseded verdict cache, identity-gated

## Narrative

The TTL'd `retained` dedupe (card 33172f01) only lasts `retainMs` (5s for merge, `MERGE_OP_RETAIN_MS`) — a caller polling for the outcome of a multi-minute gate run will, by nature, usually land its re-call after that window has closed, at which point the old dedupe found nothing and `attach()` re-invoked `run()` for real: a "safe poll" that silently became a genuine, unrequested second gate run, and — for a non-deterministic gate test — could launder a REJECTED branch into a merge with no decision anywhere in the loop. `opts.retainVerdictUntilSuperseded` closes that: for a `key` that opts in, every settle whose classified `outcome` is not one of `NEVER_CACHED_OUTCOMES` (`"cancelled"`, `"stale-base"`) also writes into a separate `untilSupersededVerdicts` map that carries NO expiry timer at all — a re-call finds it there regardless of how long it waited. It is superseded, not expired: the only way to clear it is for a genuinely fresh op under the same `key` to settle in turn, reachable only via `opts.bypassRetained` (today, `forceRemoveWorktree:true`), an explicit caller-chosen escalation, never a clock. The map is PROCESS-LOCAL, held only in the registry's own in-memory `Map` — it is NEVER written to the database and does NOT survive a daemon restart; a re-call whose gap spans a restart finds it EMPTY and mints a genuinely fresh op, exactly as before this card. It is deliberately decoupled from `retained`/`retainMs`: the two maps are written together at settle time but read by different consumers — `peek()` (worker_list/Board display) keeps consulting only the TTL'd `retained` map, while `attach()`'s own dedupe consults `untilSupersededVerdicts` first — so a settled merge can vanish from `worker_list`'s `pendingMerge` field after a few seconds (display, cosmetic) while a re-call minutes or hours later still safely returns the cached verdict instead of re-running the gate (safety, load-bearing). The safety property must never be allowed to depend on the display window's cadence.

**Identity (caught in the same card, before merge, first CR round):** "until superseded" alone is NOT enough for merge — a plain re-call after the worker pushed a genuine fix must NOT return the cached REJECTION for a commit that no longer exists ("my fix didn't work" read by the manager on work that changed underneath the cache). `opts.verdictIdentity` closes this: an opaque caller-supplied string identifying WHAT was validated (for merge: the worker branch's HEAD sha, resolved fresh on every call, BEFORE the dedupe decision) recorded alongside the verdict at settle time. A re-call's dedupe hit requires its OWN freshly-resolved identity to match the STORED one exactly (`undefined` matches only `undefined`). A MISMATCH is a genuine cache MISS, not merely "fall through to the TTL'd `retained` check instead" — that map was written at the same now-stale settle and would silently reproduce the identical wrong answer for its own few-second window, so a mismatch skips `retained` too and goes straight to a fresh mint.

**`identityOptional` (Round 2, caught by a regression in this same card's own test suite before merge):** strict identity comparison alone over-refuses. For merge specifically, a SUCCESSFUL confirm deletes the worker's branch as part of its own completion (`finalizeMerge`) — so a later re-call can never again resolve the SAME sha the cached verdict was validated against, even though nothing about the underlying answer changed. Without an escape hatch, that re-derives a fresh (though still safe) `ALREADY_MERGED` result on every poll instead of a pure cache hit, breaking a distinct, previously-tested invariant ("re-poll after settle returns the EXACT SAME opId"). `identityOptional` lets the CALLER declare, per call, "I know from context this registry can't see that identity cannot meaningfully differ here" — `confirmWorkerMergeTracked` sets it exactly when the worker's task has already reached its terminal lane (the SAME authoritative "already finished" signal `confirmWorkerMerge`'s own early-idempotency check already trusts), never merely because a git ref failed to resolve (usually TRANSIENT, must still fail closed to a fresh mint).

## Do not

- Do not let a merge poll re-run the gate after the TTL'd retention window closes — that's a genuine, unrequested second gate run, and for a non-deterministic gate test can launder a rejected branch into a merge with no decision in the loop.
- Do not serve an until-superseded cache hit whose freshly-resolved identity mismatches the identity stored at settle time — a mismatch is a MISS, and must skip the TTL'd `retained` fallback too (it was written at the same now-stale settle).
- Do not set `identityOptional` merely because a live worktree's git ref failed to resolve — that's usually transient and must still fail closed to a fresh mint. Only set it when the caller's own context makes identity divergence structurally impossible.
