# dccb6290 — the 32-specimen delta=+58 `fallback-unrecognized` population was a deployment lag, not a content bug

## Narrative

Card `dccb6290` was filed to discriminate between two readings of a measured population: 32 of 35 (later 36) `gen=1` `[prompt-mismatch-arm]` log lines showing `arm=fallback-unrecognized` at delta EXACTLY +58 (the fixed pasted-content-wrap framing overhead). Reading A (a worker's): a real same-length CONTENT divergence inside the wrap, invisible to every length-based signal — if true, ~94% of gen=1 kickoffs would carry an uncharacterised corruption. Reading B (the lead's): a CLASSIFICATION-LABEL gap, where a cleanly-recognized wrap still flows into the unrecognized bucket — benign, a labeling defect only.

Neither reading is correct. Cross-referencing the 32 specimens' own timestamps (`~/.loom/logs/daemon-output.log`, all between 2026-09-18T18:41:00Z and 2026-09-18T22:58:42Z) against `git log -S'isRecognizedPastedContentWrap'` (that symbol's SOLE introduction is commit `c9f373eb`, committed 2026-09-18T21:04:39Z) and the daemon's own `daemon_restart` tool-call history in the same log (restarts at 19:14:13Z, then not again until 2026-09-19T00:46:40Z) shows that **every one of the 32 specimens was generated by a running daemon process that predated `isRecognizedPastedContentWrap`'s existence entirely** — the fix that introduced pasted-content-wrap recognition was not deployed (no restart occurred) until hours after the last specimen in the window. `c9f373eb`'s own commit message states this directly: before it shipped, "[Loom's prompt-mismatch detector] fired [prompt-mismatch]/fallback-unrecognized on essentially every submission" that used the paste-wrap shape, regardless of content. That is Reading B's mechanism, but via total absence of wrap detection, not an exclusion-list gap in already-existing code — the literal code-reading in the card that produced Reading B was analyzing the CURRENT (post-fix) source to explain SEP-18 log lines generated by a different, older build.

Confirmation: zero delta-exact-58 gen=1 `fallback-unrecognized` specimens exist in the same log from the 2026-09-19T00:46:40Z restart (which deployed `c9f373eb`) through 2026-09-22T04:28Z — only 3 further gen=1 mismatch-arm lines occurred in that whole window, all matching the ALREADY-characterized `ff871b77` one-or-two-char-excess population (delta=59/60), not this one. A live content-substitution bug (Reading A) would be orthogonal to wrap-recognition and should have kept recurring after the fix; it did not.

`detectPastedContentWrapContentDivergence` (`packages/daemon/src/pty/host.ts`) ships anyway, as forward-looking instrumentation for the population this card asked to discriminate — a genuine future same-length substitution inside a recognized wrap — never as evidence one is currently happening.

## Do not

- Do not reason about a historical log specimen's classification using the CURRENT source tree without first checking whether the relevant code was actually deployed (a daemon restart) by the time that specimen was logged — a merged commit and a live running build are not the same thing, and `daemon_restart` events in `daemon-output.log` are how to check.
- Do not treat this shape's absence since 2026-09-19 as proof `detectPastedContentWrapContentDivergence` can never fire — it is real, additive instrumentation for a distinct (same-length substitution) population that simply has not been observed yet.
