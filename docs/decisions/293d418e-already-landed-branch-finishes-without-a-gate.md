# 293d418e — a content-proven already-landed branch finishes as ALREADY_MERGED without running the merge gate

## Narrative

A `merge_batch` that fast-forwards its candidates and then throws (finalize threw, a build_gate event write failed) leaves both branches on main with their tasks unfinalized. A same-ids re-call drops both at assembly ("cherry-pick produced an empty commit — already present") into the solo fallback `confirmWorkerMerge`, which used to run a FULL gate per branch and only then squash to nothing and finalize as `ALREADY_MERGED`: three gate runs for zero new code. `confirmWorkerMerge` already knew the answer before the gate (`preLanded`, the `findLandedSquashCommit` lookup that exists to skip the union-merge), and its own early ALREADY_MERGED finish only fired when the worktree was gone or the task terminal.

The fix: after every check that can refuse the confirm, and before any gate admission, a branch with `preLanded` truthy AND a clean, readable worktree finishes through `finishSoloAlreadyLanded` — the one helper the old early block now also uses (lookup → `tipAcrossLandedCheck` → `soloFinalizeTipGuard` → `finishAlreadyMerged`), which RE-runs the landed proof itself. The result carries `gateSkipped:"already-landed"` plus warning text, `merge_done` carries `gateSkipped` + `landedSha`, and nothing is written as a gate outcome.

**The proof (branch still present):** `findLandedSquashCommit` requires (a) a `Loom-Worker-Branch` trailer commit on main parsed from the final trailer block, (b) the re-task guard (merge-base(sha, branch) != sha — the branch was not re-cut onto its landed commit), and (c) `branchContentLandedInCommit` (@decision e076d2a2): every path the branch changed since its fork point is byte-identical between the landed commit and the branch tip; any git error fails CLOSED. That is CONTENT equivalence against main. It is deliberately not "the cherry-pick was empty" (that only says the batch tree already had the content, not that main does) and not the `Loom-Worker-PathSet` trailer (@decision 756a2cd8: a FILE-SET check only, and used solely when the branch is gone).

**Why a branch with an unlanded delta cannot skip — and the ONE residual:** a late commit that adds or edits any path in `mergeBase..branch` (a new path, or new content on a changed path) makes (c) non-empty, `preLanded` is null and the ordinary path runs unchanged (tests B1/B2). The residual: a late commit that REVERTS a changed path to its FORK-POINT content drops that path from `mergeBase..branch`, so (c) can be vacuously true and the skip finishes it (test E). That is not new — the old squash of that tree was empty too and finished ALREADY_MERGED through the same finalize pin — it is the documented residual of @decision cc9bce38: the branch is RETAINED when the landed commit carries a `Loom-Landed-Tip` trailer (a solo squash) but DELETED on a trailerless landing (a batch cherry-pick), in the old path and the new one alike. @decision 1555e361 guards against re-running a gate to launder a REJECTED branch into a merge; this path runs no gate and squashes nothing, so main cannot gain anything from it — finalize is cleanup only, and it is CAS-pinned to the landed tip (@decision cc9bce38), so a late commit RETAINS the branch instead of deleting it.

**Ordering — it lands AFTER:** ownership (`NotYourWorkerError`), the early idempotency block, the reviewed-tip refusal (@decision bbccf470's `reviewedTipVerdict`: a tip moved after review still refuses unless already landed), stranded-work, the canonical staged-dirt / dirty-overlap / untracked-overlap preflights, the HTML-entity title guard, the union-merge decision (skipped on `preLanded` anyway), and — new for this path — its OWN fresh worktree stamp (dirty or unreadable ⇒ fall through to the ordinary path and its `refuseWorktreeDirty`). **It BYPASSES:** the gate-timeout circuit breaker, self-check reuse, the inert-diff and emit-compare reductions, gate admission / repo guard, the pinned-gate-tip refusal, `mergeBranch` and its in-lock checks, the mainline-move tripwire and the merge-gate interval recording. Each of those guards a SQUASH or a gate verdict this path never produces.

**Intended behaviour change:** when main LATER modified a path the branch changed, the old path's squash CONFLICTED (`merged:false`); the skip compares against the LANDED commit rather than main's current tip, so it finishes `merged:true` — the branch's content did land, and a later unrelated edit on main does not un-land it. Pinned by test F.

**Interval mode:** unaffected. `recordMergeGateOutcome` runs only for `merge.ok && !merge.noop`; the old ALREADY_MERGED path was already a noop that never counted, and this one never reaches it. The reservation taken in `confirmWorkerMergeTracked` is released at settle either way, never consumed.

**Caching:** the result is a plain `merged:true, emptyKind:"ALREADY_MERGED"` — the same shape the existing early block returns and `confirmWorkerMergeTracked` already retains. It is terminal: the worker is retired and its task done, so replaying it for a later re-call is correct (and `identityOptional` already applies once the task is terminal). Nothing is added to the reviewed-tip or until-superseded-verdict machinery.

Test: `packages/daemon/test/batch-fallback-already-landed-skips-gate.mjs` (gate-call counter; A skip, B1/B2 late commits on a new / an already-changed path, C dirty worktree, D interval mode — zero gates + gateSkipped, counter untouched, E the revert-to-fork-point residual, F main-modified-path behaviour change). Measured RED before the change: 2 extra gate calls on the re-call; wiring-revert control (`if (false && preLanded)`) turns (A)/(D) RED again.

## Attribution: which commit is reported (card cd92e609)

`findLandedSquashCommit` returns the NEWEST `Loom-Worker-Branch` commit that passes its checks. When a later commit re-uses the branch name (a recycled or re-tasked branch) over an unrelated path, that newest commit also "holds" the branch's content, so it was published as `merge_done.landedSha` and in the `[loom:already-merged] … commit xxxxxxxx` text although it introduced none of it. The verdict was right (the finalize pin retains on doubt); only the named commit was wrong.

`findIntroducingSquashCommit` (git/worktrees.ts) fixes the NAMING only: given the lookup's sha it walks OLDER same-branch trailer commits (cap 16) applying the same per-commit checks (not an ancestor of the branch; `branchContentLandedInCommit` against that commit's own merge-base) and reports the oldest of the unbroken qualifying run. It returns its input on any error, a gone branch (a PathSet digest cannot separate two commits over the same paths), a branch with no changes of its own (a vacuous content match would qualify every older commit), or an unlisted sha.

Where it is used, and where deliberately NOT: `finishSoloAlreadyLanded` passes the result as `attributedSha` (only on the gate-skipped path, which is the only one that prints or stamps a sha) and `finishAlreadyMerged` / `finalizeMerge` use it for the announcement, the result warning and `merge_done.landedSha`. Everything else keeps the lookup's sha: the tip pin (`pinnedTipForLandedSquash` reads the trailer of the FOUND commit; pinning to an older commit's `Loom-Landed-Tip` could match a branch tip the newest commit's trailer would have retained — more permissive), the retain event's `landedSha`, `preLanded`'s union-skip, and the persisted `task.mergedSha` (read by `isCardDone`, `worker_revive`'s `commitSha`, the boot dangling-merge check, and overwritten by the drawer's lazy backfill from the newest-wins `getTaskMergedInfo` map). Boot-reconcile Pass A's mergedSha and `findLandedSquashCommitViaMap` are unchanged (still the newest).

## Do not

- Do not widen the trigger to "the batch cherry-pick was empty" — that proves the batch tree had the content, not that main does.
- Do not widen it to the file-set-only `Loom-Worker-PathSet` trailer (@decision 756a2cd8) — two different contents share a path set.
- Do not skip the dirty-worktree check or move this shortcut above the reviewed-tip / preflight refusals — finalize deletes the branch and worktree, so uncommitted or post-review work would be destroyed under `merged:true`.
- Do not record this finish as a gate outcome (`recordMergeGateOutcome`) or as a pass — it is `gateSkipped:"already-landed"`, never counted by the merge-gate interval.
- Do not fork a second copy of the lookup → tip-guard → `finishAlreadyMerged` sequence: call `finishSoloAlreadyLanded`.
- Do not use `findIntroducingSquashCommit` for gating, verification, pinning or the persisted `task.mergedSha`: it is attribution only, and a pin on an older commit would be more permissive than the lookup it decorates.
